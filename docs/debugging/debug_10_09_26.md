# Debug report — 10/09/26

Sessione: tuning clustering su `s2.2-vol` (SDC voxel-wise), ricalcando la sequenza applicata a
`s2.1-schaefer-200-tian-s2` il 01-09. Non una code review: due problemi trovati in sequenza
mentre si tentava di lanciare quel tuning, il primo bloccante, il secondo emerso mentre si
verificava cosa fosse già stato registrato dalle run di dim reduction del 07-09.

---

## §1 — Griglia di tuning di `agglomerative` rimasta sullo stato dell'ultima run

**Criticità: media** (bloccante ma rumoroso, nessun dato sbagliato prodotto).

Il primo lancio è fallito subito:

```
ERROR: [agglomerative] metric='dice' requires a strictly binary (0/1) matrix -
X has value(s) outside {0, 1}
```

`config/registry/params_clustering.json` è un registro condiviso da tutte le run di clustering, e
conserva i valori dell'**ultima** che l'ha toccato. L'ultima era quella del 03-09 sulla matrice
lesionale **grezza** (binaria, 5269 x 264274), dove `dice` è appropriato e dove la griglia era
stata ristretta a `linkage: [average, complete]`, `n_clusters: [2..6]` per contenere il costo su
264274 colonne. Su un embedding UMAP — continuo, 1570 x 2 — `dice` non è definito.

La validazione ha fatto esattamente il suo mestiere (`code_standards.md` §0): ha sollevato invece
di binarizzare implicitamente. Il problema non è il codice, è che il registro non porta traccia di
per quale tipo di input la sua griglia corrente sia valida.

Ripristinata la griglia del 01-09, recuperata dal campo `params` della riga corrispondente in
`results/sdc/clustering/tuning/agglomerative/runs_tuning.csv` (non ricostruita a memoria):
`n_clusters: [2,3,4,5,6,8,10]`, `linkage: [ward, average, complete, single]`,
`metric: [euclidean, cosine, manhattan]` — 70 combinazioni, coerenti con le 70 registrate dalla
run del 01-09.

**Lesson learned**: prima di "rilanciare lo stesso tuning di allora" su un registro condiviso,
confrontare la griglia corrente con quella registrata in `runs_tuning.csv` per la run che si vuole
ricalcare. Il registro è uno stato mutabile globale: "stessa pipeline, stesso config file" non
implica "stessi parametri", e il `params` di ogni riga di log è l'unica traccia di cosa fosse
davvero in griglia quel giorno.

## §2 — `append_run_log_entry` incolla due righe se il file non finisce con un a-capo

**Criticità: alta** (silenzioso, corrompe un log append-only, già avvenuto due volte).

Le run di tuning dim reduction del 07-09 su `s2.2-vol` (UMAP e t-SNE) risultavano **assenti** da
`results/sdc/dim_reduction/tuning/{umap,tsne}/runs_tuning.csv`, pur avendo la loro directory di
output regolarmente scritta. In realtà la riga c'era, ma fusa dentro la precedente:

```
notes: umap tuning atlante schaefer_200_tian_s2 s2.2-vol
                                                ^^^^^^^^ inizio della riga successiva
```

`csv.writer` emette il terminatore di riga **dopo** ogni riga, mai prima. Aprire in `"a"` e
scrivere presuppone quindi che il file finisca già con un a-capo. Se non ci finisce, la nuova riga
viene incollata all'ultima: una sola linea fisica con i campi di due righe, che `csv` rilegge come
un'unica riga sovradimensionata (i campi della seconda finiscono nel `restkey`). Niente solleva:
il controllo di coerenza dell'header introdotto in precedenza ispeziona solo la riga 1.

Scansione di tutti i 28 `runs*.csv` del repo:

| Stato | File |
| --- | --- |
| già corrotti | `results/sdc/dim_reduction/tuning/{umap,tsne}/runs_tuning.csv` |
| senza a-capo finale (corruzione alla prossima run) | `results/lesion/clustering/tuning/hdbscan/runs_tuning.csv`, `results/lesion/dim_reduction/production/{tsne,umap}/runs.csv`, `results/lesion/dim_reduction/tuning/tsne/runs_tuning.csv` |

**Fix del codice** (`src/utils/run_log.py`): prima di ogni append, se il file esiste e non è vuoto,
si legge l'ultimo byte e si aggiunge il terminatore mancante. L'invariante viene **ristabilita**
qui invece che data per acquisita, perché un file può perdere l'a-capo finale fuori da questo
modulo (una modifica a mano, un editor che lo rimuove, una run interrotta a metà scrittura).
Test di regressione: `tests/unit/test_run_log.py::test_append_to_file_missing_its_trailing_newline_does_not_glue_two_rows`
(fallisce sul codice vecchio, passa sul nuovo).

**Riparazione dei dati**: le due righe fuse sono state separate senza indovinare nulla — la cella
`notes` corrotta termina *esattamente* con il valore `session` della riga successiva (`s2.2-vol`),
quindi il punto di taglio è determinato, non stimato. Ai 4 file ancora integri è stato aggiunto
l'a-capo mancante. Nessuna riga persa: i 6 file sono ora tutti rileggibili con il conteggio di colonne dichiarato dal loro header.

**Lesson learned**: vedi `.claude/lessons_learned.md` #35.
