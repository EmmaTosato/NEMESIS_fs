# Debug report — 13/07/26

Sessione: fuzzing sistematico di `config/retrieval.json` e `config/file_patterns.json` — tipi sbagliati, valori vuoti, tutti i valori validi documentati, per ogni campo — su un fixture sintetico isolato (`/tmp`), eseguendo davvero la CLI (`python -m src.pipeline.retrieve_data`) come sottoprocesso e classificando ogni run: STOP pulito atteso, esecuzione riuscita attesa, o crash con traceback non catturato (l'obiettivo era proprio quest'ultima categoria). 89 casi generati, di cui 5 bug reali confermati (poi corretti) e nessun'altra sorpresa.

Organizzato per **categoria**, non per singolo bug — più bug qui sotto sono istanze dello stesso errore concettuale.

---

## 1. Operazione filesystem adiacente a un try/except esistente, ma fuori da esso

**Criticità: alta**

**Errore**: `_copy_one` aveva `destination.parent.mkdir(parents=True, exist_ok=True)` **subito prima** del blocco `try: shutil.copy2(...) except OSError:` — testualmente vicino, ma fuori. Un `output_root` il cui percorso collide con un file già esistente (es. un componente intermedio del path è un file, non una cartella) fa fallire `mkdir()` con `NotADirectoryError`/`FileExistsError`, mai catturato: l'intera run crashava con un traceback grezzo invece di loggare un "Failed" per quel file e continuare.

**Fix**: spostato `mkdir()` **dentro** il try/except, stesso trattamento di `shutil.copy2` (WARNING loggato, entry in `stats.failed`, run continua).

**Lezione**: due chiamate I/O consecutive che sembrano "fare la stessa cosa" (preparare+scrivere un file) vanno protette **insieme**, nello stesso blocco — la vicinanza testuale a un try/except non implica la copertura.

## 2. Validazione condizionale che salta il caso comune/di default

**Criticità: alta**

**Errore**: `_validate_group_filter` faceva discovery dei soggetti (`_discover_subjects`, che esercita `Dataset._subject_container` e quindi la validità dei template registrati) **solo se** `config.group_filter` era impostato. Con `group_filter: null` e `subjects: null` (il caso "recupera tutti", probabilmente il più comune), un template malformato in `file_patterns.json` (es. `{subject_id}` non presente come proprio segmento di path) non veniva mai controllato durante `_validate_upfront` — solo più tardi, **durante la copia vera**, fuori da qualsiasi try/except in `main()`. Con più dataset richiesti, i dataset precedenti nella lista potevano già avere file copiati prima che il crash fermasse tutto — violando esplicitamente la garanzia dichiarata nel docstring del modulo ("a bad request never leaves partial output behind").

**Fix**: nuova `_validate_subject_discovery`, chiamata **incondizionatamente** per ogni dataset in `_validate_upfront`, prima di qualunque copia.

**Lezione — stesso pattern già in `lessons_learned.md` §4** ("stesso input problematico, comportamento diverso a seconda del percorso di codice"): una validazione innescata solo da un ramo opzionale (qui: `group_filter` impostato) lascia scoperto esattamente il percorso più comune (nessun filtro). Vale la pena ricontrollare ogni volta che si aggiunge un ramo "if opzione X impostata: valida" — la domanda da farsi è sempre "cosa succede se X *non* è impostata?".

## 3. Valori JSON non validati per tipo prima di essere usati come chiave hashabile

**Criticità: alta**

**Errore**: `_parse_retrieve_item` controllava solo che le chiavi `object`/`space`/`modality` fossero *presenti* nel dict, mai che i loro *valori* fossero stringhe. Un config con `"space": ["mni"]` (lista invece di stringa) passava il parsing senza errori, e crashava più avanti con `TypeError: unhashable type: 'list'` — non dentro la validazione (dove ci si aspetterebbe un `ValueError` chiaro), ma dentro `_reject_duplicate_retrieve_items` (che mette la tripla in un `set`) o dentro `FilePatterns.has()` (che la usa come chiave di dict).

**Fix**: `_parse_retrieve_item` ora valida esplicitamente che ciascuno dei tre campi sia una stringa non vuota, prima di costruire `RetrieveItem`.

**Lezione**: quando un valore letto da JSON esterno finirà come chiave di un `dict`/elemento di un `set` più avanti nel flusso, il controllo di tipo va fatto **al punto di parsing**, non assunto — JSON permette liste/oggetti ovunque ci si aspetti una stringa, e l'errore che ne risulta (`TypeError: unhashable type`) non assomiglia per niente a un errore di dominio, è difficile da diagnosticare per chi legge solo il messaggio.

## 4. Duplicati non rilevati in una lista di input (nuova istanza)

**Criticità: media**

**Errore**: `datasets: ["UNIPD/WashU", "UNIPD/WashU"]` non veniva rigettato — `_build_datasets` costruisce un `dict` chiave=nome, quindi il duplicato collassava silenziosamente in una singola istanza `Dataset`, senza errore né segnale.

**Fix**: nuovo `_require_unique_str_list`, usato per `datasets` — rigetto esplicito con messaggio che elenca i duplicati, stesso pattern già usato per `retrieve` e per gli ID ripetuti in `subjects`.

**Lezione**: stessa categoria di `lessons_learned.md` §5 — ogni lista di input esterno che finisce per determinare "quante volte processo questa cosa" va controllata per duplicati esplicitamente, mai lasciata a un collasso implicito di una struttura dati (qui: le chiavi di un dict).

---

## 5. Orchestrazione CLI senza garanzia che *ogni* fase tocchi il filesystem sotto un confine di errore

**Criticità: media**

**Osservazione**: oltre al caso #1, anche `_log_path`/`_attach_file_handler` (setup del file di log) e `_write_report` (scrittura del report) giravano in `main()` **fuori** da qualunque try/except — un percorso di output/log non scrivibile (permessi, collisione con un file esistente) avrebbe crashato con traceback grezzo invece di un errore pulito, nonostante il resto di `main()` segua rigorosamente il contratto STOP/WARNING/ERROR documentato.

**Fix**: entrambe le fasi ora avvolte in `try/except OSError`, loggano un errore chiaro e ritornano `1` — nessuna riga di log su file (perché non ancora attaccata), ma il messaggio raggiunge comunque la console via lo `StreamHandler` di `basicConfig()`.

**Lezione**: quando un entry point CLI cresce nel tempo (nuove fasi aggiunte: verifica, poi report, poi log separato...), il "questo è protetto da un try/except" va riverificato per **ogni** fase aggiunta, non assunto per estensione dalle fasi precedenti — non è automatico.
