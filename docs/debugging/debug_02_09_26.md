## 1. `enrich_lesion_metadata.py::_join_variables` duplica colonne quando le variabili richieste sono già presenti nel metadata di input

**Criticità: alta** (scrive silenziosamente un `metadata.csv` con colonne duplicate — nessun
errore, nessun warning; `rc == 0`. Danno reale su `data/derived/lesion_matrix/21-07_s1.1/metadata.csv`
prima di essere notato via ispezione manuale del log di output)

**Errore**: la selezione finale delle colonne,
```python
return metadata_out[list(metadata.columns) + ordered_variable_columns]
```
assumeva che `metadata.columns` (le colonne già presenti nel file letto da disco) e
`ordered_variable_columns` (le variabili appena richieste in config) fossero sempre insiemi
disgiunti. Vero per ogni run storica di questo repo (ogni `write_in_place=true` passata aveva
sempre richiesto un sottoinsieme di variabili complementare a quello già presente — mai lo
stesso set due volte), falso per un refresh genuino (richiedere di nuovo esattamente le stesse
variabili per riallinearle a una fonte corretta). Con un nome ripetuto nella lista di selezione,
pandas produce due colonne con lo stesso nome nell'output.

Un secondo meccanismo, indipendente, colpiva specificamente `NIHSS`: `metadata_out` parte come
copia di `metadata` (che ha già `nihss` minuscolo da una run precedente), poi
`join_participant_variables` aggiunge una colonna **nuova e distinta** `NIHSS` (maiuscolo — il
nome così com'è in `variables`, non ancora rinominato), e solo dopo `.rename({"NIHSS": "nihss"})`
prova a portarla a `nihss` — ma quel nome è già occupato dalla vecchia colonna, quindi il rename
non sovrascrive, produce una seconda colonna `nihss`. Questo si verificava anche dopo il primo
fix (la deduplicazione della lista di selezione), perché la duplicazione qui nasce *prima*, dentro
`metadata_out` stesso.

**Causa**: nessuna run storica aveva mai ri-richiesto un set di variabili che si sovrapponesse a
quello già presente — il ramo non era mai stato esercitato, non per correttezza ma per assenza
di un caso reale che lo attivasse (stesso schema di `lessons_learned.md` #17).

**Diagnosi**: il primo run reale di refresh (`lesion_matrix/21-07_s1.1`, richiesta
`["age","sex","education","clinical_date","lesion_side","NIHSS"]` su un file che le aveva già
tutte) ha prodotto `rc == 0` con un log che elencava esplicitamente le colonne scritte:
`['subject_id', 'dataset', 'lesion_volume_voxels', 'lesion_side', 'nihss', 'nihss', 'age', 'sex',
'education', 'clinical_date', 'age', 'sex', 'education', 'clinical_date', 'lesion_side', 'nihss',
'nihss']` — 17 invece di 9. Notato leggendo l'output del comando, non da un test o un controllo
automatico.

**Fix**: due cambi in `_join_variables`:
1. `preserved_columns = [c for c in metadata.columns if c not in ordered_variable_columns]`,
   poi `metadata_out[preserved_columns + ordered_variable_columns]` — mai un nome ripetuto nella
   selezione.
2. Le colonne in via di refresh vengono tolte da `metadata` **prima** di passarlo a
   `join_participant_variables`/`join_lesion_side` (`base = metadata.drop(columns=[...])`), così
   il join/rename parte sempre da zero colonne con quel nome, indipendentemente da un rename
   mid-flight come quello di NIHSS.

**Recovery sul dato reale**: `data/derived/lesion_matrix/21-07_s1.1/metadata.csv` era già stato
scritto una volta col bug (17 colonne). Non recuperato con un dedup manuale sul file corrotto
(rischio di tenere per sbaglio la copia sbagliata) — invece: verificato che `lesion_volume_voxels`
fosse ancora corretto ricalcolandolo da `matrix.npy` (`X.sum(axis=1) == valore su disco`,
confermato), stripato il file alle sole 3 colonne sicuramente intatte (`subject_id`, `dataset`,
`lesion_volume_voxels`), poi ri-arricchito da zero con `enrich_lesion_metadata.py` già corretto —
verificato idempotente su un secondo rilancio identico, e i valori confrontati contro
`assets/metadata/*_participants_lesions.tsv` (0 mismatch).

**Lezione**: nuova voce, `.claude/lessons_learned.md` #34.
