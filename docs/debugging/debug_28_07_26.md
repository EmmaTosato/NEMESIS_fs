## 1. `append_run_log_entry`: refactor incompleto del contratto log_dir/filename lascia 5 call site e 2 file di test sullo schema pre-refactor

**Criticità: alta** (30 test falliti su tutta la suite prima del fix; in produzione, ogni run reale di `build_lesion_matrix.py`, `compute_sdc.py`, `mask_fc.py`, `build_fc_matrix.py`, `clustering.py` avrebbe creato una **directory** chiamata `runs.csv` invece del file di log atteso, con lo storico run scritto in un percorso annidato mai letto da nessuno — silenzioso, nessun errore, nessun warning)

**Errore**: la sessione 2026-07-27 (3) (`.claude/stato_progetto.md`) ha rifattorizzato `append_run_log_entry` (`src/utils/run_log.py`) cambiando il suo contratto: prima riceveva il path *esatto* del CSV da scrivere; dopo, riceve una *directory* (`log_dir`) e decide da sé il filename (`runs.csv` per `run_type="production"`, `runs_tuning.csv` per `"tuning"`). Il refactor ha aggiornato correttamente solo i 2 chiamanti in `dim_reduction.py`/`dim_reduction_clustering.py` (gli unici citati nel changelog di quella sessione). Cinque punti sono rimasti sul vecchio contratto, passando ancora un path che include già `"runs.csv"`:
- `build_lesion_matrix.py:126`
- `compute_sdc.py:204`
- `mask_fc.py:125`
- `build_fc_matrix.py:125`
- `clustering.py::_runs_csv_path` (usata da entrambi i call site del file)

Risultato concreto: `append_run_log_entry` appende `"runs.csv"` una seconda volta al path ricevuto (già terminante in `"runs.csv"`), poi fa `runs_csv_path.parent.mkdir(parents=True, exist_ok=True)` — che crea, come effetto collaterale, una **directory** chiamata `runs.csv` esattamente dove ci si aspettava un file, con il CSV vero scritto un livello sotto (`.../runs.csv/runs.csv`), mai letto da nessun consumer. In parallelo, `tests/unit/test_run_log.py` testava ancora lo schema di *prima* del refactor (colonne `run_id`/`run_type`, mai più scritte — sostituite da `session`/`id` e dalla scelta del filename): 5 test falliti direttamente contro l'implementazione attuale, non contro un bug dei chiamanti.

**Causa**: pattern già noto — `.claude/lessons_learned.md` #12 ("rename/refactor fixed at the most obvious call site, not grepped across every consumer repo-wide"). Il refactor di `run_log.py` è stato verificato solo sui 2 chiamanti toccati nella stessa sessione, mai grep'ato sull'intero repo (`grep -rn "append_run_log_entry("`) né sulla suite di test del modulo stesso.

**Fix**:
1. `build_lesion_matrix.py`, `compute_sdc.py`, `mask_fc.py`, `build_fc_matrix.py`: `config.output_root / "runs.csv"` → `config.output_root` (passa la directory, non più il path completo).
2. `clustering.py::_runs_csv_path` → rinominata `_run_log_dir`, ritorna `config.output_root / method` (senza `"runs.csv"`) — nome vecchio ormai fuorviante (non ritornava più un path a un csv nemmeno prima del fix, a rigore).
3. `tests/unit/test_run_log.py` riscritto sullo schema attuale (`session`/`id`, `runs.csv` vs `runs_tuning.csv` come file separati, non una colonna `run_type`) — aggiunto anche `test_production_and_tuning_write_separate_files`, mai scritto prima, che verifica direttamente il comportamento centrale del refactor del 27/07 (mai coperto a livello unitario).
4. 6 asserzioni stale in 4 file di integration test (`test_build_lesion_matrix_pipeline.py`, `test_clustering_pipeline.py` ×2, `test_dim_reduction_pipeline.py` ×2, `test_dim_reduction_clustering_pipeline.py` ×2) aggiornate allo schema attuale: `"production" in runs_csv` → verifica assenza di `runs_tuning.csv`; lettura di `runs.csv` per una run di tuning → corretta in `runs_tuning.csv`; chiave `run_id`/`run_type` → `session`/rimossa.

**Lezione**: pattern esistente, nessuna voce nuova — appesa a `.claude/lessons_learned.md` #12 ("Seen in").

**Test**: suite completa rilanciata dopo il fix: **405 passed, 12 skipped, 0 failed** (`pytest tests/ -q`), da 30 failed prima del fix (confermato preesistenti via `git stash`).
