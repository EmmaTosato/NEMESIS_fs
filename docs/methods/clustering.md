# Clustering — what these methods actually do

Plain-language reference for the methods wired into `src/analysis/clustering.py` (`config/registry/params_clustering.json`). Not a general ML textbook chapter — just enough to read a config's hyperparameters and know what they're actually controlling. For dimensionality reduction, see `docs/methods/dimensionality_reduction.md`.

## The problem it solves

Clustering groups subjects based on similarity, without knowing the "right" answer in advance (unsupervised) — the hypothesis being that clusters correspond to distinct lesion/disconnection topographies. Most methods here (KMeans, Agglomerative, GaussianMixture, SpectralClustering) require a fixed number of groups decided upfront; DBSCAN is the exception — it discovers the group count from the data's density structure instead. It runs either on a dimensionality-reduction embedding (`dim_reduction_clustering.py`) or directly on a feature matrix (`clustering.py`) — see `docs/guides/analysis.md` for when each script applies.

## Choosing hyperparameters: `clustering.py`'s fine-tuning mode

Unlike dimensionality reduction, clustering has no ground truth to score a choice of `n_clusters`/`eps` against — every metric below is an *internal* validation index computed straight from `(X, cluster_labels)`, meaningful only within one method's own swept grid, never compared across methods. `clustering.py --config ...` with `"fine_tuning": true` (same convention as `dim_reduction.py`, see `docs/guides/clustering.md`) sweeps every value in that method's `tuning_grid` (`config/registry/params_clustering.json`) and scores each combination with:

- **Silhouette score** — how much closer each point is to its own cluster than to the nearest other one. Range `[-1, 1]`, higher is better.
- **Calinski-Harabasz** — ratio of between-cluster to within-cluster variance. Higher is better, but grows somewhat mechanically with cluster count, so read it alongside the other two, not alone.
- **Davies-Bouldin** — average similarity to the nearest other cluster. Lower is better.

These 3 are generic across all 5 methods (`src/analysis/clustering_tuning.py`'s `compute_clustering_metrics`) — for DBSCAN specifically, noise (`-1`) is excluded before computing them, and `noise_fraction` is reported alongside as its own column. Some methods also get one extra, method-specific column in the same swept table (KMeans' `inertia` — the elbow criterion; GMM's `bic`/`aic` — likelihood-based, unlike the other two which are purely geometric), and 3 methods get a standalone diagnostic plot independent of the swept grid (not a function of which value ends up chosen): Agglomerative's dendrogram, Spectral's eigengap plot, DBSCAN's k-distance plot — see each method's own section below. No automatic selection anywhere — a human reads `tuning_results.csv`/the plots and writes the chosen value into `params_clustering.json`'s `"params"` by hand, same philosophy as `dim_reduction.py`.

## Consensus/stability clustering: RSC and Monti (`src/analysis/consensus_clustering.py`)

Silhouette/Calinski-Harabasz/Davies-Bouldin are all computed from a *single* run per candidate `k` — none of them say anything about how much the result depends on chance. Two literature methods add that as two more optional columns in the same fine-tuning sweep, restricted to `kmeans`/`gmm`/`spectral` (`CONSENSUS_ELIGIBLE_METHODS`) since `params_clustering.json` already sweeps exactly `n_clusters`/`n_components` for these three, and — unlike Agglomerative/DBSCAN — all three have genuine internal stochasticity to exploit (centroid/mixture-component init, or Spectral's own internal KMeans pass) without needing to touch the data at all. They answer two different questions:

- **RSC** ("Repeated Spectral Clustering", Tshimanga et al. 2025, cited by Zanola et al. 2026 in `papers/`) — *"how stable is the assignment to random init, on the exact same data?"* No resampling: the same method runs `n_repeats` times on the full dataset, varying only the random seed. Across those runs, a co-occurrence matrix records how often each pair of subjects lands in the same cluster. The paper's own selection criterion carries over unchanged: for a given candidate `k`, look at the gap between the `k`-th and `(k-1)`-th (1-indexed) sorted eigenvalues of that co-occurrence matrix's normalized Laplacian — the bigger that specific gap, the more that `k` is supported by repeated runs, not just one lucky init. Reported as the `rsc_eigengap` column (higher = more stable).
- **Monti et al. 2003** — *"how stable is the assignment to who's in the sample?"* Each of the `n_repeats` runs clusters a random subsample (`subsample_fraction`) of subjects rather than everyone; the consensus matrix entry for a pair is co-clustered/co-sampled, i.e. conditioned on both actually being drawn together. One deliberate deviation from the literal 2003 formula: instead of the paper's own area-under-the-consensus-CDF statistic (later shown by Șenbabaoğlu et al. 2014 to be biased toward favoring larger `k`), this uses their standard fix, the **Proportion of Ambiguous Clustering (PAC)** — the fraction of consensus values falling in an ambiguous middle band (default `(0.1, 0.9)`; a value near 0 or 1 is unambiguous evidence either way, near 0.5 isn't). Reported as `monti_stability = 1 - PAC` (higher = more stable, same direction as `rsc_eigengap`).

Both are opt-in per method: absent from `params_clustering.json` by default (`load_consensus_config` returns `None`, zero behavior change to any existing sweep), enabled by adding a `"consensus"` block — see `docs/guides/clustering.md` for the exact JSON shape. When present, `tuning_results.csv`/`tuning_plot.png` gain the corresponding column(s) exactly like the generic 3 metrics, and `config.md` additionally states each method's own literature-defined "suggested k" (`consensus_suggestion_lines` — RSC's argmax eigengap, Monti's argmax `monti_stability`) as plain informational text, never applied anywhere automatically — the "no automatic selection" philosophy above is unchanged.

## KMeans (`kmeans_cluster`, `"kmeans"`)

Partitions subjects into `n_clusters` groups by iteratively placing a centroid per cluster and assigning each subject to its nearest centroid, then re-computing centroids, until stable.

- **Must decide `n_clusters` upfront** — KMeans doesn't discover the number of clusters, it enforces exactly the number given. Choosing it is a separate step: inspect a t-SNE/UMAP plot first, or run `clustering.py`'s fine-tuning mode (see above) — its `inertia` column is the elbow criterion (look for where adding another cluster stops meaningfully lowering it), alongside the generic silhouette/Calinski-Harabasz/Davies-Bouldin.
- **Assumes roughly spherical, similar-sized clusters** in whatever space it's run on. This is exactly why `dim_reduction_clustering.py` clusters the *embedding* rather than the raw voxel/parcel matrix by default in this pipeline's typical use — clustering directly on hundreds of thousands of raw voxel columns is both computationally wasteful and geometrically unreliable for KMeans (`clustering.py`, the no-reduction script, exists for when that's still the deliberate choice, e.g. clustering directly on a small parcellated matrix).
- **Sensitive to feature scale**: features with a larger numeric range dominate the distance calculation. Not a concern for `fraction_lesioned`-parcellated features (all already in `[0, 1]`) or for a PCA/UMAP/t-SNE embedding (already on a comparable scale) — would matter if clustering directly on raw voxel counts of very different magnitudes.
- **Stochastic centroid initialization**: set `random_state` for reproducibility; `n_init` controls how many random initializations are tried before keeping the best (higher = more robust to bad initial placement, slower).

## AgglomerativeClustering (`agglomerative_cluster`, `"agglomerative"`)

Hierarchical, bottom-up: starts with every subject as its own cluster and repeatedly merges the two closest clusters until `n_clusters` remain (or, alternatively via `distance_threshold`, until the closest pair is farther apart than a cutoff - not used by default here).

- **Must decide `n_clusters` upfront**, same as KMeans — `clustering.py`'s fine-tuning mode writes a `dendrogram.png` alongside the generic metric sweep specifically for this method (`src/analysis/clustering_tuning.compute_dendrogram_linkage`, refit with the full tree exposed, independent of any one `n_clusters` cut): read off a sensible cut by eye from where merge distances jump, then cross-check against the silhouette/Calinski-Harabasz/Davies-Bouldin curves for that same candidate.
- **`linkage`** controls how "distance between two clusters" is defined when merging: `"ward"` (default here) minimizes the increase in within-cluster variance, tends towards similarly-sized, roughly spherical clusters (closest in spirit to KMeans); `"average"`/`"complete"`/`"single"` are less shape-constrained but more sensitive to outliers (`"single"` especially, prone to "chaining" distinct groups together through a few intermediate points).
- **Deterministic** given the data and `linkage` — no `random_state`.
- Unlike KMeans, produces a full merge hierarchy internally (a dendrogram) - production mode still only surfaces the final `n_clusters` cut, but fine-tuning mode's `dendrogram.png` now exposes the full hierarchy for inspection before picking one.

## GaussianMixture (`gmm_cluster`, `"gmm"`)

Soft/probabilistic clustering: models the data as a mixture of `n_components` Gaussian distributions and assigns each subject to the component with the highest posterior probability (`fit_predict` hardens the soft assignment into a single label, same output shape as the other methods here).

- **Must decide `n_components` upfront** (GaussianMixture's own name for what the other methods here call `n_clusters` — same role) — `clustering.py`'s fine-tuning mode adds `bic`/`aic` columns to the sweep for this method specifically: unlike the generic geometric indices, these are likelihood-based and penalize model complexity, giving GMM a criterion the other methods don't have (lower is better for both).
- **Allows elliptical, differently-sized clusters** (each component has its own covariance), unlike KMeans' implicit assumption of similarly-sized spherical clusters — a real advantage if lesion/disconnection topographies are expected to differ in spread, not just location.
- **Stochastic initialization**: set `random_state` for reproducibility.
- Being probabilistic, the underlying model also exposes per-subject class probabilities (`predict_proba`) — not used by this pipeline today (only the hardened label is kept), but worth knowing about if soft cluster membership becomes useful later.

## DBSCAN (`dbscan_cluster`, `"dbscan"`)

Density-based: groups points that are densely packed together (at least `min_samples` points within `eps` distance of each other), and explicitly labels points that don't belong to any dense region as **noise**, with label `-1` — not an error, a legitimate "this subject didn't fit any cluster" outcome.

- **Does not take `n_clusters`** — the number of clusters is discovered from the density structure, not fixed upfront.
- **`eps`/`min_samples` are not universal defaults** — unlike `n_clusters` (whose "right" value is a modeling choice regardless of data scale), `eps` is a literal distance threshold in whatever feature space is being clustered on, so it must be re-tuned per feature space (raw voxels vs. a parcellated matrix vs. a UMAP/PCA embedding all have wildly different natural distance scales). The `eps: 0.5, min_samples: 5` registered in `config/registry/params_clustering.json` is a starting point to override, not a validated default. `clustering.py`'s fine-tuning mode writes a `k_distance_plot.png` for this method specifically (`src/analysis/clustering_tuning.compute_k_distance`, sorted distance to each point's `min_samples`-th nearest neighbor) — the standard way to read off a reasonable `eps` by eye, at the curve's steepest rise ("knee"); the swept `eps` grid's `noise_fraction`/silhouette columns (noise excluded) then confirm whether that reading actually produces a sensible partition.
- **`-1` (noise) is reported separately, not silently counted as a cluster**: `clustering.py`/`dim_reduction_clustering.py`'s "Clusters found: N" line excludes label `-1` from `N` and adds a "(+ M noise points, label -1)" note when present — counting noise as a genuine cluster would silently overstate how many groups were actually found.
- Well-suited to finding irregularly-shaped clusters and outliers KMeans/GMM would force into some cluster regardless; poorly suited when clusters have meaningfully different densities (a single global `eps` can't separate a dense cluster and a sparse one at the same time).

## SpectralClustering (`spectral_cluster`, `"spectral"`)

Graph-based: builds a similarity graph between subjects (here, `affinity="nearest_neighbors"` — an edge between a subject and its nearest neighbors, not a full pairwise similarity matrix) and clusters via the eigenvectors of that graph's Laplacian, then a final KMeans pass on the resulting low-dimensional embedding.

- **Must decide `n_clusters` upfront**, same as KMeans/Agglomerative — `clustering.py`'s fine-tuning mode writes an `eigengap_plot.png` for this method specifically (`src/analysis/clustering_tuning.compute_eigengap`, the smallest eigenvalues of the affinity graph's normalized Laplacian, computed once from the same `affinity`/`n_neighbors` params spectral clustering itself would use): the eigengap heuristic reads the suggested `n_clusters` off the biggest jump between consecutive eigenvalues — a criterion this method actually has theoretical grounding for, unlike the generic geometric indices applied to the other methods.
- **Finds non-convex clusters KMeans can't** — because it works on graph connectivity rather than raw Euclidean distance, two crescent-shaped or otherwise non-spherical groups that KMeans would slice incorrectly can come out correctly separated.
- **`affinity`** controls how the similarity graph is built — `"nearest_neighbors"` (used here) scales better and avoids assuming a single global distance scale, unlike `"rbf"` (a dense Gaussian-kernel similarity matrix, sensitive to its `gamma` bandwidth parameter and expensive on large subject counts).
- **Stochastic** (the final KMeans pass): set `random_state` for reproducibility.
- **Computationally heavier than KMeans/Agglomerative** — building and decomposing the similarity graph doesn't scale as well to NEMESIS's larger subject counts (thousands); more practical on the smaller, already-clustered-once subsets (e.g. Task 3's n~500 fMRI cohort) than on the full lesion cohort.
