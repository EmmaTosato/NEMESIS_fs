## `src/analysis/reduction.py` / `clustering.py` — modeling strategies

Plain `dict[str, Callable]` registries (`REDUCTION_METHODS`, `CLUSTERING_METHODS`), not classes/ABCs — same "explicit registry over hardcoded dispatch" precedent as `config/registry/file_patterns.json`. Each entry is a pure `(X, params) -> array` function: `params` is unpacked with `**params` straight into the underlying `sklearn`/`umap` estimator's constructor, no in-code defaults for any hyperparameter (`code_standards.md` §5) — those live only in `config/registry/params_reduction.json`/`params_clustering.json` (`src/analysis/params.py`). Invalid/unexpected keys in `params` surface as whatever error `sklearn`/`umap` itself raises for a bad constructor argument — not re-validated here, since re-implementing each estimator's accepted-parameter surface would just duplicate their own API.

- `reduction.py`: `umap_embed`, `tsne_embed`, `pca_embed`, `pca_varimax_embed`, `pacmap_embed`.
- `clustering.py`: `kmeans_cluster`, `agglomerative_cluster`, `gmm_cluster`, `dbscan_cluster`, `spectral_cluster`.

`pca_varimax_embed` is the one exception to the "blind `**params` unpack" rule above: it wraps two distinct estimators (`sklearn.decomposition.PCA`, then `factor_analyzer.Rotator(method="varimax")`, per Thiebaut de Schotten et al. 2020's methodology - `docs/methods/dimensionality_reduction.md`), so it reads `n_components`/`rotation_max_iter` from `params` explicitly and raises `ValueError` if either is missing, or if `n_components < 2` (varimax rotates *between* components - nothing to rotate with one). Component scores are computed via `np.linalg.lstsq` (regressing each centered subject row onto the rotated loadings) - the paper's "multiple regression" step, not a re-projection through the rotated loadings directly.

## `src/analysis/params.py` — per-method hyperparameters

`load_method_params(params_file, method) -> dict` reads `config/registry/params_reduction.json`/`params_clustering.json`'s `{method: {"params": {...}}}` shape and returns the raw `params` dict for one method. Validates the file exists, its top-level shape is a JSON object (`lessons_learned.md` #7), `method` has an entry, and that entry's `"params"` value is itself a JSON object — raises `ValueError` naming what's wrong and, for an unknown method, the list of methods actually registered in the file. Does **not** validate individual hyperparameter keys/values — that's `sklearn`/`umap`'s own job when `reduction.py`/`clustering.py` unpacks the returned dict into an estimator constructor.

Two more loaders, sharing the same private `_load_method_entry` helper (refactored out of `load_method_params` when these were added): `load_tuning_grid(params_file, method) -> dict[str, list]` reads an optional `"tuning_grid"` key (`{hyperparam: [values to sweep]}`) — raises `ValueError` if the method has none registered (fine-tuning not configured for it, e.g. any clustering method in `params_reduction.json`'s sense - see `clustering_tuning.py` below for those), or if any swept value list is empty. `load_trustworthiness_n_neighbors(params_file, method) -> int` reads an optional `"trustworthiness_n_neighbors"` key (umap/tsne/pacmap - see `tuning.py`'s `METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS`) — the `n_neighbors` passed to `sklearn.manifold.trustworthiness` when scoring a fine-tuning sweep, a *different* setting from the `n_neighbors` hyperparameter being swept in `tuning_grid`, kept as its own named field specifically so the two aren't confused.

## `src/analysis/model_config.py` — modeling config parsing

3 loaders, one per modeling pipeline script: `load_dim_reduction_config`, `load_clustering_config`, `load_dim_reduction_clustering_config` → `DimReductionConfig`/`ClusteringConfig`/`DimReductionClusteringConfig` (all `frozen=True`). 5 fields are identical across all three (`project`, `input_path`, `output_root`, `session_name`, `overwrite`) and are parsed once by a shared `_load_shared_fields` helper — the method-specific fields (`reduction_method`/`clustering_methods`, and their `params_file`(s)) are parsed per-loader.

`reduction_method` (single string) is validated against `REDUCTION_METHODS` via `_validate_method`, same fail-fast-at-the-config-boundary principle as `build_config.py`'s `resample_interpolation` check, and the reason this module was built *after* `reduction.py`/`clustering.py` rather than in the handoff's original listing order. `clustering_methods` on `ClusteringConfig`/`DimReductionClusteringConfig` is **always a list** (`tuple[str, ...]` once parsed), never a bare string, even for one method - `_require_str_list` validates it's a non-empty list of non-empty strings with no duplicate entries (`lessons_learned.md` #5 - an undetected duplicate would silently re-run the same method twice in the loop below), then `_require_method_list` validates each element against `CLUSTERING_METHODS` the same way `_validate_method` does for a single value. `reduction_method` deliberately stayed single-valued when this was added - a run reduces the input once, then clusters that one embedding with however many clustering methods are requested.

**`run_notes: str | None`** (optional, `_optional_str`) is on all 3 configs here (and on `BuildMatrixConfig` in `build_config.py`) — a free-text note the human writes explaining *why* a run's config differs methodologically from a previous one, propagated into that method's `runs.csv` entry (see `run_log.py` below). **`fine_tuning: bool`** (required, `_require_bool`) is on all 3 configs - but on `DimReductionClusteringConfig` it only ever governs the *clustering* half: the reduction step there always runs once at its already-chosen production params (`reduction_params_file`'s `"params"`, never `"tuning_grid"`) - re-sweeping the reduction itself is `dim_reduction.py`'s job alone. See `dim_reduction_clustering.py`'s own two-modes section below for what its `fine_tuning=true` actually does.

**`regress_out_volume: bool`** (required, `_require_bool`) is on `DimReductionConfig`/`DimReductionClusteringConfig` only (not `ClusteringConfig` - clustering never computes an embedding itself, nothing to regress there) - production-mode-only, ignored when `fine_tuning=true` (a tuning sweep is diagnostic, never saved as a production artifact). See `src/analysis/covariates.py` below for what it does and why it can't be a silent default.

## `src/analysis/tuning.py` — manual fine-tuning for umap/tsne/pca/pca_varimax/pacmap

No automatic parameter selection anywhere in this module - it only produces a comparison table; a human reads it (or the accompanying plot) and writes the chosen parameters into `params_reduction.json`'s `"params"` by hand. t-SNE's `early_exaggeration`/`learning_rate`/`max_iter` are excluded on purpose (fixed from Thiebaut de Schotten et al. 2020, `docs/methods/dimensionality_reduction.md`) - only `perplexity` is swept, added on request since the paper's own supplementary material sweeps it too. Every clustering method is excluded here too - fine-tuning for those lives in `clustering_tuning.py` below, not this module.

`TUNING_METRIC_NAMES = {"umap": "trustworthiness", "tsne": "trustworthiness", "pca": "cumulative_explained_variance", "pca_varimax": "cumulative_explained_variance", "pacmap": "trustworthiness"}` - the quality metric is genuinely different per *family* of method (decided with the user), not per individual method - `pca_varimax` reuses PCA's criterion (varimax is an orthogonal rotation, doesn't change total variance explained) and `tsne`/`pacmap` reuse UMAP's (trustworthiness is a generic neighbor-preservation metric, not UMAP-specific):
- `evaluate_umap(X, params, trustworthiness_n_neighbors)` / `evaluate_tsne(X, params, trustworthiness_n_neighbors)` / `evaluate_pacmap(X, params, trustworthiness_n_neighbors)` embed then score with `sklearn.manifold.trustworthiness` - how well local neighborhoods survive the projection. `evaluate_umap`/`evaluate_tsne` both read `params["metric"]`: for `"jaccard"`/`"dice"` (see `src/analysis/distances.py::binary_pairwise_distance` below), both the embedding *and* the `trustworthiness` call are given the same precomputed distance matrix (`metric="precomputed"` on both) instead of raw `X` - scoring a binary-metric embedding against `trustworthiness`'s own euclidean default would judge it by a notion of "originally close" it was never built to preserve. `evaluate_tsne` additionally forces `init="random"` whenever `metric="precomputed"` - `sklearn.manifold.TSNE`'s own default `init="pca"` can't run on a distance matrix. `evaluate_pacmap` has no such branch - its `tuning_grid` never sweeps `metric`.
- `evaluate_pca(X, params)` / `evaluate_pca_varimax(X, params)` fit `sklearn.decomposition.PCA` directly (not via `pca_embed`/`pca_varimax_embed`, which only return the transformed array) specifically to read `.explained_variance_ratio_.sum()` off the fitted estimator - PCA's own natural criterion, and the exact one the paper uses to choose a component count.

`_EVALUATORS: dict[str, Callable]` dispatches by method name (Strategy registry, same precedent as `REDUCTION_METHODS`/`CLUSTERING_METHODS`) rather than an `if/elif` chain - the original 2-branch `if/elif` (umap/pca) was refactored into this registry specifically when adding `pca_varimax`/`pacmap`, since a 2-branch `if/elif` growing to 4 branches is exactly the pattern `lessons_learned.md` #1 warns about. `METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS = {"umap", "tsne", "pacmap"}` is consulted both here and by `dim_reduction.py` (to decide whether to load `trustworthiness_n_neighbors` from config at all) - a single shared source of truth for "which methods need this extra setting", not duplicated/hardcoded in both places.

`run_tuning_sweep(method, X, base_params, tuning_grid, trustworthiness_n_neighbors) -> pd.DataFrame` takes the Cartesian product of `tuning_grid`'s value lists (`itertools.product`), evaluates each combination via `_EVALUATORS[method]` (swept keys override `base_params`; un-swept keys like `random_state` stay fixed), and returns one row per combination: swept parameter values + the metric column. Raises `ValueError` for any method not in `TUNING_METRIC_NAMES` (registry-driven, not an implicit fallback).

## `src/analysis/distances.py` — fast pairwise distances for binary feature data

`binary_pairwise_distance(X, metric) -> np.ndarray` computes a full `(n_samples, n_samples)` Jaccard or Dice distance matrix for a binary `(n_samples, n_features)` array (voxel-wise lesion masks: `metric` must be `"jaccard"` or `"dice"` - `SUPPORTED_BINARY_METRICS` - `ValueError` otherwise, and `ValueError` if any row is all-zero (union/sum would be 0, both metrics undefined for an empty sample).

Exists because `scipy.spatial.distance.pdist`'s boolean metrics compute one pair at a time - measured at ~19 minutes extrapolated for 1150 subjects × 254865 voxel features. Binary overlap between every pair at once is instead a single matrix multiplication (`X @ X.T` counts shared "on" features per pair, via BLAS) - Jaccard/Dice distance follow from that intersection count plus each row's own sum, in seconds instead of minutes. Casts to `float64` before the multiply regardless of `X`'s own dtype (usually `uint8`) - intersection counts can exceed a narrow integer type's range and silently wrap (`lessons_learned.md` #13).

Used by `tuning.py::evaluate_umap`/`evaluate_tsne` (above) whenever the swept `metric` is `"jaccard"`/`"dice"` - not used anywhere in `reduction.py` itself, only in the fine-tuning evaluators (production `dim_reduction.py` calls `REDUCTION_METHODS[method](X, params)` directly, passing `metric` straight through as a string to `umap-learn`/sklearn, which handle jaccard/dice natively on raw `X` without needing this precomputed shortcut - `binary_pairwise_distance` exists purely as the *fine-tuning* sweep's performance fix, not a production dependency). `metric` is an explicit key in both `umap`/`tsne`'s `"params"` in `params_reduction.json` (rather than left absent, silently falling back to the library's own default) specifically so `covariates.py`'s incompatibility check below has something concrete to read - production `umap` runs with `metric="jaccard"` as of session s1.1's 26-07 tuning round, `tsne` still with `metric="euclidean"` (its own tuning round hasn't concluded which value to adopt).

## `src/analysis/covariates.py` — post-reduction volume regression

`regress_out_covariate(embedding, covariate) -> np.ndarray`: removes the linear effect of a covariate from each embedding column via `np.linalg.lstsq` OLS residuals. Deliberately operates on the already-computed 2D embedding, not the raw voxel matrix - regressing a scalar covariate off a binary 0/1 matrix column-by-column would produce non-binary residuals (destroying the structure `distances.py`'s Jaccard/Dice machinery depends on) and is statistically unstable on the many voxel columns with very low lesion prevalence. Raises `ValueError` on an embedding/covariate row-count mismatch, and on a zero-variance covariate (nothing to regress out - not a case that can be silently no-op'd per `code_standards.md` §0).

`check_volume_regression_compatible(regress_out_volume, reduction_params) -> None`: raises `ValueError` if `regress_out_volume=True` together with `reduction_params.get("metric")` in `{"jaccard", "dice"}` - those metrics already normalize distances by each subject's own lesion size (see `docs/methods/dimensionality_reduction.md`), so regressing volume out a second time on top would remove real topographic signal, not a confound. A method/params with no `"metric"` key at all (`pca`, `pacmap`, `tsne` today) is unaffected - `regress_out_volume` is free either way. Deliberately **not** a silent override (`regress_out_volume` forced to `False` when the metric is incompatible) - `code_standards.md` §0 treats that as exactly the kind of fallback that hides a real conflict from the caller; this raises instead, at config-boundary time, before either pipeline computes anything.

Both `dim_reduction.py::_run_production` and `dim_reduction_clustering.py::main()` call `check_volume_regression_compatible` right after `load_method_params` resolves `params`/`reduction_params` (that's the only place `metric` is known - it lives in `params_reduction.json`, a file separate from the pipeline's own config, so the check can't run any earlier), then `regress_out_covariate(embedding, X.sum(axis=1))` right after computing the embedding, when `config.regress_out_volume` is `True`. `X.sum(axis=1)` (lesion volume in voxels, not ml) is deliberately not converted to ml first - a scalar rescaling of the covariate doesn't change OLS residuals, so skipping the conversion avoids needing the reference image's voxel size (not otherwise available at this point in either pipeline) for no behavioral difference. Both call sites duplicate this 2-3 line snippet rather than sharing a helper - same per-CLI-duplication convention as `_write_standalone_diagnostic` in `dim_reduction_clustering.py`/`clustering.py` (the two pipelines are deliberately decoupled CLIs, `dim_reduction_clustering.py` does not import from `dim_reduction.py`).

## `src/analysis/clustering_tuning.py` — manual fine-tuning for kmeans/agglomerative/gmm/dbscan/spectral

Same "no automatic selection" philosophy as `tuning.py`, but clustering has no ground truth to score against - every generic metric is an *internal* validation index computed straight from `(X, cluster_labels)`, meaningful only within one method's own swept grid, never compared across methods.

`compute_clustering_metrics(X, labels) -> dict[str, float]` returns `{"silhouette", "calinski_harabasz", "davies_bouldin", "noise_fraction"}` for every method uniformly - `sklearn.metrics.silhouette_score`/`calinski_harabasz_score`/`davies_bouldin_score` excluding any DBSCAN-style noise (`label == -1`) first (undefined for a "cluster" that isn't one), with `noise_fraction` always reported so the exclusion is visible rather than silent. A degenerate combination (fewer than 2 non-noise clusters, or every non-noise point its own cluster) can't have the 3 metrics computed at all - caught (the same condition `sklearn` itself would raise on) and recorded as `NaN` with a logged warning rather than aborting the whole sweep, since a bad hyperparameter combination is expected information in a tuning sweep, not a bug (distinct from `lessons_learned.md`'s silent-fallback pattern: this is one documented, intentional strategy for a legitimate domain case, not a caught-and-hidden error).

`compute_silhouette_samples(X, labels) -> tuple[np.ndarray, np.ndarray]` is the per-sample counterpart used for `plotting.plot_silhouette_analysis` (production time, not the sweep above): same noise-exclusion convention as `compute_clustering_metrics`, but returns `(non_noise_labels, sample_silhouette_values)` from `sklearn.metrics.silhouette_samples` instead of one aggregate number - their mean equals `compute_clustering_metrics`'s `"silhouette"` exactly. Unlike `compute_clustering_metrics`'s NaN-and-warn on a degenerate combination (built for an unattended sweep over many combinations), this **raises** `ValueError` - it runs once for the single already-chosen production result, so the caller (`clustering.py`/`dim_reduction_clustering.py`'s `_run_one_method`) decides whether to skip the plot, catching that specific exception and logging a warning rather than failing the whole run.

`run_clustering_tuning_sweep(method, X, base_params, tuning_grid, consensus_config=None) -> pd.DataFrame` mirrors `tuning.py`'s sweep shape (Cartesian product, swept keys override `base_params`), but two methods get an extra scalar column beyond the 3 generic ones, computed by refitting the actual estimator instead of going through `CLUSTERING_METHODS[method]` (which only returns labels): `_kmeans_with_extra_metrics` keeps `KMeans.inertia_` (the elbow criterion), `_gmm_with_extra_metrics` keeps `GaussianMixture.bic(X)`/`.aic(X)` (likelihood-based, unlike the other 3 which are purely geometric) - `_EXTRA_METRICS_EVALUATORS` dispatches by method name, absent for the other 3 (agglomerative/dbscan/spectral get only the 3 generic columns from their swept grid). `METHOD_METRIC_COLUMNS: dict[str, list[str]]` is the single source of truth `clustering.py` reads to know which columns a given method's sweep will produce (and therefore which to plot) - `noise_fraction` is only listed for `"dbscan"` even though `compute_clustering_metrics` always returns it, since it's mechanically 0.0 for every other method (never noise-producing) and plotting a flat line adds nothing.

Three methods also get a standalone diagnostic, independent of which value in the swept grid ends up chosen (`STANDALONE_DIAGNOSTIC_METHODS = {"agglomerative", "spectral", "dbscan"}`, computed once from `base_params`, not per swept combination):
- `compute_dendrogram_linkage(X, params) -> np.ndarray` refits `AgglomerativeClustering` with `n_clusters=None, distance_threshold=0, compute_distances=True` (forces the full merge tree down to singleton leaves, ignoring any `n_clusters`/`distance_threshold` already in `params`), then converts `children_`/`distances_` into the scipy linkage-matrix format `plotting.plot_dendrogram` expects (the standard sklearn-docs recipe for bridging the two).
- `compute_eigengap(X, params, max_k=20) -> np.ndarray` builds the same affinity graph `spectral_cluster` would (`"nearest_neighbors"` via `sklearn.neighbors.kneighbors_graph` symmetrized, or `"rbf"` via `sklearn.metrics.pairwise.rbf_kernel` - `ValueError` for any other `affinity`), computes the normalized graph Laplacian (`scipy.sparse.csgraph.laplacian`) and its smallest `max_k` eigenvalues (`scipy.linalg.eigh`, `subset_by_index`) - the eigengap heuristic (`plotting.plot_eigengap`) reads a suggested `n_clusters` off the biggest gap between consecutive values, a criterion with actual theoretical grounding for spectral clustering specifically (a Laplacian's near-zero-eigenvalue multiplicity approximates the count of well-separated graph components), unlike the generic geometric indices applied to the other methods.
- `compute_k_distance(X, min_samples) -> np.ndarray` - sorted distance from each point to its `min_samples`-th nearest neighbor (self included in the count, matching DBSCAN's own definition) - the standard k-distance plot for reading off a reasonable `eps` by eye (`plotting.plot_k_distance`), at the curve's steepest rise.

`clustering.py`'s `_write_standalone_diagnostic` dispatches to whichever of the 3 applies via an explicit `if/elif` (not a registry - each branch needs a different `base_params` key: `min_samples` for dbscan, nothing extra for the other two) and raises `ValueError` for `min_samples` missing from `base_params` rather than defaulting it silently.

`consensus_suggestion_lines(results, method) -> list[str]` reads `rsc_eigengap`/`monti_stability` columns (if present in `results`) and returns the "RSC suggests .../Monti suggests ..." lines described below - empty list when neither column is present. Pure text formatting, shared between `clustering.py`/`dim_reduction_clustering.py`'s `_write_tuning_output`, since it doesn't close over either script's own config type (unlike `_write_standalone_diagnostic`, deliberately duplicated per script). Written to its own `consensus_suggestions.md` (only when the list is non-empty), a sibling of `tuning_results.csv`/`config.md` in the tuning output dir - deliberately **not** appended into `config.md` itself: that file is a static snapshot of how the run was launched (config JSON, swept params, combinations evaluated), and a computed suggestion doesn't belong mixed into a historical launch record.

## `src/analysis/consensus_clustering.py` — consensus/stability clustering (RSC + Monti)

Two literature methods scoring how *stable* a candidate `k` is (as opposed to how *good* it looks on a single run, all silhouette/Calinski-Harabasz/Davies-Bouldin can say) - restricted to `CONSENSUS_ELIGIBLE_METHODS = {"kmeans", "gmm", "spectral"}` (`K_PARAM_NAME` maps each to its own "how many clusters" parameter name: `n_clusters` for kmeans/spectral, `n_components` for gmm), since these are the only 3 with genuine internal stochasticity to exploit without touching the data itself - a repeat of `agglomerative`/`dbscan` with a different seed reproduces the identical partition (deterministic given the same input), so a "co-occurrence matrix" for them would be degenerate (all 0s/1s, no information).

- `run_rsc_repeats(method, X, params, n_repeats, base_seed=0) -> np.ndarray`: RSC (Tshimanga et al. 2025, cited by Zanola et al. 2026 - `papers/Zanola et al - 2026 - ...`) - `n_repeats` runs of `CLUSTERING_METHODS[method]` on the full, unmodified `X`, only `random_state` varying (`base_seed + i`). Returns the `(n_samples, n_samples)` co-occurrence matrix (fraction of runs where each pair shared a cluster).
- `run_monti_repeats(method, X, params, n_repeats, subsample_fraction, base_seed=0) -> np.ndarray`: Monti et al. 2003 - `n_repeats` runs, each on an `np.random.default_rng`-drawn subsample (without replacement, size `round(subsample_fraction * n_samples)`) of subjects. Returns the `(n_samples, n_samples)` consensus matrix (co-clustered / co-sampled per pair, conditioned on both having been drawn together) - raises `ValueError` if any pair was never jointly sampled across all `n_repeats` draws (too few repeats/too small a fraction for this `n_samples` - an explicit failure, never a silent `NaN`/`0`).
- `compute_rsc_eigengap(cooccurrence_matrix, k) -> float`: gap between the `k`-th and `(k-1)`-th (1-indexed) sorted eigenvalues of the co-occurrence matrix's normalized Laplacian (`scipy.sparse.csgraph.laplacian(..., normed=True)` + `scipy.linalg.eigh`, same machinery as `clustering_tuning.compute_eigengap` but applied to `C` itself as the affinity, and reading the specific position-`k` gap rather than the biggest gap anywhere - matches the paper's own selection criterion, compared across the different `C_k` built per candidate `k`).
- `compute_monti_stability(consensus_matrix, ambiguous_band=(0.1, 0.9)) -> float`: `1 - PAC` (Proportion of Ambiguous Clustering - fraction of the consensus matrix's upper-triangle entries falling inside `ambiguous_band`). Deliberate deviation from Monti et al. 2003's own area-under-CDF statistic, per Șenbabaoğlu et al. 2014's finding that it's biased toward larger `k` - PAC is the standard fix (e.g. `ConsensusClusterPlus`), not an invention here.

Wired into `clustering_tuning.run_clustering_tuning_sweep` via an optional `consensus_config` parameter (`None` by default - zero behavior change to any pre-existing call): `{"rsc": {"n_repeats": int}, "monti": {"n_repeats": int, "subsample_fraction": float}}`, either/both keys, adding `"rsc_eigengap"`/`"monti_stability"` columns per swept row (`k` read straight off that row's own already-built `combo_params[K_PARAM_NAME[method]]`, since it's exactly what `tuning_grid` swept to produce it). `CONSENSUS_METRIC_COLUMNS = ("rsc_eigengap", "monti_stability")` in `clustering_tuning.py` is a fixed constant (not merged into the static `METHOD_METRIC_COLUMNS`, since it's opt-in/conditional) - both pipelines extend their own `metric_cols` with `[c for c in CONSENSUS_METRIC_COLUMNS if c in results.columns]` before plotting, so the subplot grid only ever includes columns that actually got computed. Loaded via `params.py::load_consensus_config(params_file, method) -> dict | None` (absent `"consensus"` key -> `None`, a legitimate "not requested" case; present for a method outside `CONSENSUS_ELIGIBLE_METHODS`, or malformed, raises `ValueError` - an impossible config must fail loudly, never be silently ignored, per `code_standards.md` §0). Not registered in the checked-in `config/registry/params_clustering.json` by default - fully opt-in, see `docs/guides/clustering.md` for the JSON block to add.

## `src/utils/run_log.py` — per-method `runs.csv`, and hand-written `SESSIONS.md`

Two separate concerns, deliberately not one file:

- **`runs.csv`** (machine-written, `run_log.py`): "every run that ever wrote into this method folder, and how did it differ." `append_run_log_entry(runs_csv_path, run_id, now, run_type, params_summary, output_dir, run_notes, extra_columns=None)` appends one row (`run_id, timestamp, run_type, params, output, notes`, plus any `extra_columns` prepended as leading columns) to `runs_csv_path` (creating it with a header if absent) - **never overwritten**, unlike a run's own `config.md`/report which describe only that one run. `params`/`notes` are free text (JSON-dumped params, the human's `run_notes`); a real CSV rather than markdown so it's queryable with pandas once a project accumulates many runs. `run_type` is `"production"` or `"tuning"`, both landing in the *same* file chronologically - the point is seeing "s2 used the parameters this same file's `tune1` sweep found best" in one place, not two separate histories to cross-reference. Not atomic (a log, not a primary artifact - same tier as `summaries/`/`logs/`, see `docs/dev/design_patterns.md`). `run_log.py` has no notion of session *meaning* - it never reads or writes session descriptions, only appends rows keyed by `run_id`. `extra_columns` exists solely for `dim_reduction_clustering.py` (every other caller passes none, keeping their files' schema exactly `FIELDNAMES`) - every call writing to the same `runs_csv_path` must pass the same `extra_columns` keys, since the header is fixed on the first write.

  Called once per clustering method actually run (`clustering.py`/`dim_reduction_clustering.py` call it once per iteration of their `clustering_methods` loop, not once per whole CLI invocation) after writing that method's report - `runs_csv_path` sits one directory above the dated `session_name` subfolders: `<output_root>/<method>/runs.csv` (`dim_reduction.py`, `clustering.py`), or directly `<output_root>/runs.csv` for `build_lesion_matrix.py`/`compute_sdc.py` (no method axis there). `dim_reduction_clustering.py` is the one exception: it has *two* axes (reduction, clustering) but only nests output folders two levels deep (`<output_root>/<reduction_method>/<clustering_method>/<session>/`) and shares one `<output_root>/<reduction_method>/runs.csv` across every clustering method run against that reduction, distinguishing rows via the `reduction_method`/`clustering_method` `extra_columns` rather than splitting into one file per `(reduction, clustering)` combination - a single reduction's methods are naturally compared together, so one shared, queryable history serves that better than N near-duplicate files.

- **`SESSIONS.md`** (hand-written, never touched by code): what a `session_name`'s session number (e.g. `s1.1`) actually *means* - datasets, modality, what changed - one entry per session, written by a human, not generated. Canonical copy lives at `data/SESSIONS.md` (a session spans the whole data→results chain, not just matrix building, so it isn't nested under any one pipeline's output folder); `results/SESSIONS.md` is a symlink to it, so it's visible from either side without duplication. `data/SESSIONS.md` is the one path under `data/` explicitly un-ignored in `.gitignore` (`!data/SESSIONS.md`) - everything else under `data/` stays local-only (raw/derived neuroimaging data), but this file is small, hand-curated project knowledge and is meant to be versioned/shared like any other doc.

## `src/pipeline/build_lesion_matrix.py` — CLI entry point

`python -m src.pipeline.build_lesion_matrix --config config/pipelines/build_lesion_matrix.json`. Same shape as `retrieve_data.py` (`main(argv) -> int`, staged `try`/`except` per phase, `summaries/build_lesion_matrix/<project>/` + `logs/build_lesion_matrix/<project>/` written every run) but simpler control flow: `build_lesion_matrix()` either succeeds for every requested subject or raises - there's no per-subject error accumulation to report, unlike `retrieve_data.py`'s copy phase.

Phases, each with its own `try`/`except` (`lessons_learned.md` #9 - a later-added phase isn't automatically covered by an earlier phase's error boundary): load config → attach log file handler → `build_lesion_matrix()` → `artifacts.save_matrix()` (output dir = `output_root/<dd-mm>_<session_name>`) → optional QC-volume writing (only if `parcellate and save_parcellated_volumes`) → write report.

**QC-volume writing is intentionally not atomic**, unlike `save_matrix`: `_write_parcellated_volumes` reloads the reference image (`features.lesion.load_reference_image`, added alongside this script since `build_lesion_matrix()` itself doesn't return it) and the resampled atlas (`load_and_resample_atlas`, called a second time - cheap, the atlas is small), then writes one `.nii.gz` per subject directly into `output_dir/parcellated_volumes/`. A failure partway through leaves some but not all subjects' volumes on disk; this is accepted because the run's actual output (the matrix artifact) is already saved successfully by that point - a `return 1` still signals the incomplete QC step to the caller/SLURM job without discarding the real output.

**Found while testing this script**: `artifacts.save_matrix`'s original `extra_arrays` validation (added in `src/utils/artifacts.py` during that step) wrongly assumed every extra array is subject-row-aligned with `X`. `non_constant_mask` is feature-aligned (length = pre-drop feature count), not subject-aligned - the check was removed; `save_matrix` now makes no assumption about `extra_arrays`' shape relationship to `X`, since that meaning is caller-specific (documented in `artifacts.py`).

`attach_file_handler(log_path)` - the same "console + file, remove any stale FileHandler from a previous `main()` call in-process" logic every pipeline script needs. Extracted once `build_lesion_matrix.py` plus the 3 modeling scripts below would otherwise have carried 4 near-identical copies (past the "revisit at the 4th consumer" threshold already applied to `_require_*`). **Deliberately not** used by `retrieve_data.py`, which keeps its own pre-existing copy - that script is stable/in production and wasn't touched.

## `src/analysis/plotting.py` — minimal cluster visualization

`compose_run_title(output_dir, project) -> str`: builds every plot title (matplotlib `ax.set_title`/`fig.suptitle`, plotly `title`) from the run's own `output_dir` path instead of ad hoc per-script string concatenation - drops a leading `"results"` path segment and joins the rest with `" › "`, e.g. `results/lesion/dim_reduction/umap/21-07_s1_d01` -> `"clinical_connectome — lesion › dim_reduction › umap › 21-07_s1_d01"`. Motivation: `config.project` alone (always `"clinical_connectome"` today) never distinguished modality/session/tag, so two different runs of the same method used to get identical titles - `output_dir` already encodes modality/pipeline/method/session/tag (`<dd-mm>_<session_name>[_<tag>]`, tag from `params_reduction.json`/`params_clustering.json`'s `tag_param`/`tag_prefix`, see `src/analysis/params.py`), and it's the exact same `Path` every pipeline script already builds for `save_matrix`/logging - so the title can't drift out of sync with where the file actually lives, and needs no update if `results/` gets nested deeper later (e.g. the `results/<modality>/{dim_reduction,clustering,dim_reduction_clustering}/` layout). All 3 modeling CLIs (`dim_reduction.py`, `dim_reduction_clustering.py`, `clustering.py`) call it for every plot title, including `plot_clusters_comparison`'s `suptitle` (passed `comparison_dir`, not a per-method `output_dir`) and `dim_reduction.py`'s fine-tuning `tuning_plot.png` (passed the tuning `output_dir`, which includes the `tuning/` path segment for free). `scripts/replot_dim_reduction.py` does **not** use it - it has no `project` config value to hand (works directly off an existing run's `matrix.npy`/`metadata.csv`, no config load), and keeps its own simpler `"{run_dir.name} (replot)"` title.

`plot_clusters_2d(X_2d, cluster_labels, output_path, xlabel, ylabel, title)`: one function, a 2D scatter of `X_2d`'s first two columns colored by `cluster_labels`, saved to `output_path`. Added on request specifically for the two clustering pipeline scripts below, ahead of the handoff note's original "plotting explicitly deferred" scope - a first visual sanity check of cluster separation, nothing richer (per-dataset coloring, >2D, interactivity) yet. Raises `ValueError` if `X_2d` has fewer than 2 columns rather than producing a degenerate/empty plot.

`plot_silhouette_analysis(sample_labels, sample_silhouette_values, X_2d, display_labels, output_path, xlabel, ylabel, title)`: the classic sklearn-style two-panel per-sample silhouette diagnostic, added on request as the production-time breakdown of the single aggregate number `compute_clustering_metrics`/`clustering_tuning.py` reports during fine-tuning - a mean can hide one bad cluster averaged out by good ones. Left panel: one filled horizontal band per cluster (`ax.fill_betweenx`), each member's own coefficient sorted ascending within its band, colored via the same `_palette_for_labels` as the scatter, plus a dashed line at the mean (equals `compute_clustering_metrics`'s `"silhouette"` exactly). Right panel: the same 2D scatter as `plot_clusters_2d`. Takes two separate label arrays deliberately: `sample_labels`/`sample_silhouette_values` come from `clustering_tuning.compute_silhouette_samples` (noise already excluded there - undefined for a "cluster" that isn't one, so no band is drawn for it), while `display_labels` is the **full** vector including noise, so the scatter panel still shows where those points physically sit (grayed out). Raises `ValueError` on the same `< 2` columns case as `plot_clusters_2d`. Called by both `clustering.py`/`dim_reduction_clustering.py`'s `_run_one_method`, right after `plot_clusters_interactive`, wrapped in `try/except ValueError` (unlike `plot_clusters_interactive`'s no-try/except convention just above) since `compute_silhouette_samples` can legitimately raise on a degenerate production result (e.g. a single cluster) - logged as a warning, doesn't fail the run, matching the same "warn and skip, don't crash" precedent as the `X_2d.shape[1] < 2` branch right above it.

`plot_embedding_interactive(X_2d, metadata, output_path, xlabel, ylabel, title, color_column="dataset")`: un-defers per-dataset coloring and interactivity for `dim_reduction.py`'s production embedding plot. Needs `metadata` (not just `X_2d`) because the point is per-subject identity: a self-contained `plotly` HTML, colored by `metadata[color_column]`, every `metadata` column shown on hover (`subject_id`/`dataset`) - the static `embedding_plot.png` only ever shows anonymous dots, this is how a specific outlier point gets traced back to a subject. Raises `ValueError` on the same `< 2` columns case as the other plot functions, plus a metadata/`X_2d` row-count mismatch and a missing `color_column`. `dim_reduction.py`'s `_run_production` writes it alongside `embedding_plot.png` as `embedding_plot_interactive.html` (same best-effort `try/except Exception` + `logging.warning` as the static plot - a plot failure doesn't invalidate the already-saved embedding artifact); `scripts/replot_dim_reduction.py` regenerates both from an existing run's `matrix.npy`/`metadata.csv` without recomputing the embedding.

`plot_clusters_interactive(X_2d, metadata, output_path, xlabel, ylabel, title, cluster_column="cluster_label", dataset_column="dataset")`: same idea for `dim_reduction_clustering.py`/`clustering.py`, but with a dropdown to switch the point coloring between `cluster_column` and `dataset_column` in one file, instead of writing two - answers "does this cluster boundary track a site effect, or genuine structure?" without opening a second file. Implementation: two full `px.scatter` trace sets (one colored by `cluster_column` cast to `str` for discrete colors, one by `dataset_column`) merged into a single `go.Figure`, toggled via each trace's `visible` flag from an `updatemenus` dropdown - `plotly` drops a trace's legend entry automatically when `visible=False`, so the legend always matches whichever coloring is active, no manual legend bookkeeping. Raises on the same `< 2` columns / row-count-mismatch cases as `plot_embedding_interactive`, plus a missing `cluster_column` or `dataset_column`. Both `dim_reduction_clustering.py`'s `_run_one_method` and `clustering.py`'s `_run_one_method` call it right after `plot_clusters_2d`, writing `cluster_plot_interactive.html` alongside `cluster_plot.png` - **not** wrapped in `try/except` here (unlike `dim_reduction.py`'s plot calls), matching this file's own pre-existing convention where a plot failure is not treated as non-fatal; `scripts/replot_dim_reduction.py` regenerates both for an existing run too.

`plot_clusters_comparison(X_2d, labels_by_method, output_path, xlabel, ylabel, suptitle)`: same idea as `plot_clusters_2d` but a grid of subplots (`ncols = min(3, len(labels_by_method))`, `nrows` = ceil of the rest), one per method, same `X_2d` for all of them, colored by that method's own labels - added when `clustering.py`/`dim_reduction_clustering.py` gained support for multiple `clustering_methods` in one run. X/Y limits are computed once from `X_2d` and applied to every subplot, so no single method's cluster spread looks artificially wider/narrower just from independent auto-scaling. Same `ValueError`-if-fewer-than-2-columns guard as `plot_clusters_2d`, plus one for an empty `labels_by_method`.

`plot_clusters_comparison_interactive(X_2d, labels_by_method, metadata, output_path, xlabel, ylabel, title)`: the interactive sibling of `plot_clusters_comparison`, built the same way `plot_clusters_interactive` is - one full `px.scatter` trace set per method (not per cluster/dataset pair), all but the first hidden, toggled via an `updatemenus` dropdown with one button per method. Same 2D layout and points for every option, only the coloring (and hover, via `metadata`) changes - lets you eyeball whether two methods agree on a cluster boundary without opening N separate `cluster_plot_interactive.html` files. Same `ValueError` guards as `plot_clusters_comparison` (`< 2` columns, empty `labels_by_method`) plus the metadata row-count check shared with `plot_clusters_interactive`.

Two more, for fine-tuning sweeps (`tuning.py` above): `plot_tuning_curve(df, param_col, metric_col, output_path, title)` - a line plot, for a 1-parameter `tuning_grid` (PCA's `n_components`). `plot_tuning_heatmap(df, param_x, param_y, metric_col, output_path, title)` - a 2D heatmap via `df.pivot`, for a 2-parameter grid (UMAP's `n_neighbors` x `min_dist`). `dim_reduction.py` picks curve vs. heatmap by `len(tuning_grid)` (1 vs. 2); a grid with more than 2 swept parameters logs a warning and skips the plot rather than guessing a visualization - `tuning_results.csv` is still written either way, so no data is lost, just the convenience plot.

5 more, for `clustering.py`'s fine-tuning mode (`clustering_tuning.py` above): `plot_clustering_tuning_metrics(df, param_col, metric_cols, output_path, title)` - one line-plot subplot per metric in `metric_cols`, all sharing `param_col` on the x-axis; unlike `plot_tuning_curve` (always exactly one metric), silhouette/Calinski-Harabasz/Davies-Bouldin/method-specific extras live on incomparable scales, so overlaying them on one shared axis would mislead - each gets its own subplot instead. `plot_clustering_tuning_heatmaps(df, param_x, param_y, metric_cols, output_path, title)` is the 2-parameter analogue (one heatmap subplot per metric instead of one line-plot subplot) - added when `params_clustering.json`'s grids grew a second dimension per method (`agglomerative.linkage`, `gmm.covariance_type`, `dbscan.min_samples`, `spectral.n_neighbors`, alongside each method's already-swept `n_clusters`/`n_components`/`eps`); both `clustering.py`/`dim_reduction_clustering.py`'s `_write_tuning_output` pick curve vs. heatmap vs. "no plot, just a warning" by `len(swept_params)` (1/2/more), mirroring `dim_reduction.py`'s own `plot_tuning_curve`/`plot_tuning_heatmap` choice above - `tuning_results.csv` always has every combination regardless of whether a plot could be drawn for it. The 3 standalone-diagnostic plots each wrap a scipy/numpy computation from `clustering_tuning.py` with no logic of their own: `plot_dendrogram(linkage_matrix, output_path, title, truncate_last_p=30)` (`scipy.cluster.hierarchy.dendrogram`, `truncate_mode="lastp"` since a full tree over hundreds/thousands of subjects is unreadable), `plot_eigengap(eigenvalues, output_path, title)` (marks the single biggest gap between consecutive eigenvalues via `np.argmax(np.diff(eigenvalues))`, raises `ValueError` on fewer than 2 eigenvalues), `plot_k_distance(distances, output_path, title)` (the sorted curve as-is, no computation - reading the "knee" is left entirely to the human).

## `src/pipeline/dim_reduction.py` / `dim_reduction_clustering.py` / `clustering.py` — the 3 modeling CLIs

Same shape as `build_lesion_matrix.py` (`main(argv) -> int`, staged `try`/`except`, `reports/<script>/<project>/` + `logs/<script>/<project>/`), reading an existing matrix artifact via `artifacts.load_matrix(input_path)` rather than building one. Output dir layout adds a method-name segment: `<output_root>/<method>/<dd-mm>_<session_name>/` (`dim_reduction.py`, `clustering.py`), `<output_root>/<reduction_method>/<method>/<dd-mm>_<session_name>/` (`dim_reduction_clustering.py`, nested two levels deep - mirrors `dim_reduction.py`'s own `<output_root>/<method>/` layout one level up, rather than the flat `<reduction>-<method>` folder name used before this was reorganized).

**`clustering.py`/`dim_reduction_clustering.py` run every method in `clustering_methods` in a loop, not just one**: a private `_run_one_method(config, method, ...)` helper does the full per-method flow (params → cluster → `save_matrix` → `cluster_plot.png` → `runs.csv`) and returns the `cluster_labels` it actually saved (or `None` on failure, which stops the whole run - no partial-failure tolerance, consistent with the rest of this pipeline's fail-fast error handling). `main()` collects `{method: cluster_labels}` across the loop and reuses those exact arrays for the comparison plot below - never re-runs a method a second time just to get labels for the plot (would be wasteful, and for a method without a fixed `random_state` could silently produce labels inconsistent with what was actually saved to `matrix.npy`/`metadata.csv`).

**No `summaries/` report for these 3 modeling CLIs** (`dim_reduction.py`/`clustering.py`/`dim_reduction_clustering.py`) - removed on request: it duplicated the same config JSON/summary lines already written to each run's own `config.md` (production: via `save_matrix`'s readme; fine-tuning: `_write_tuning_output`'s `config.md`), just in a second, flat location (`summaries/<pipeline>/<project>/`). `runs.csv` already gives the flat, cross-run chronological view that duplication was half-providing. `REPORT_FILENAME_PREFIX` survives in each script purely as the log filename prefix (`logs/<pipeline>/<project>/<prefix>__<timestamp>.log`) - unrelated to the removed report. `build_lesion_matrix.py`/`mask_fc.py`/`build_fc_matrix.py`/`compute_sdc.py`/`retrieve_data.py` keep their own `summaries/` reports unchanged - out of scope for this removal.

**Comparison plot**: after the loop (guarded by the same `>= 2` columns check as the per-method `cluster_plot.png`, not by `len(clustering_methods)` - it's written even for a single method, as a degenerate one-subplot grid, so the output shape doesn't depend on how many methods were requested), `plotting.plot_clusters_comparison` writes `cluster_comparison.png` to `<output_root>/comparison/<dd-mm>_<session_name>/` (`clustering.py`) or `<output_root>/<reduction_method>/comparison/<reduction_method>_<dd-mm>_<session_name>/` (`dim_reduction_clustering.py` - reduction name repeated before the tag here specifically, since the comparison folder is the one place where scanning individual folder names out of context is common) - a grid of subplots (one per method, `ncols = min(3, n)`), same 2D data (raw first-2-features for `clustering.py`, embedding first-2-components for `dim_reduction_clustering.py`), shared x/y axis limits across every subplot so the comparison is visually honest. `plotting.plot_clusters_comparison_interactive` writes a companion `cluster_comparison_interactive.html` alongside it - same dropdown-per-trace-set mechanism as `plot_clusters_interactive`, but one option per clustering method instead of a fixed cluster/dataset pair. A minimal `config.md` lists the methods compared and each one's individual output dir. Same tier as `summaries/`/`logs/` - not atomic, no `manifest.json`, a secondary/derived artifact built from labels the per-method runs already wrote, not a source of truth of its own.

**Where cluster labels live, and what `matrix.npy` means when there's no reduction** (decided during implementation, not fully specified in the handoff note): both clustering-involving scripts append `cluster_label` as a new column on the loaded `metadata.csv` - never a separate `cluster_labels.npy` file - so every artifact this pipeline produces stays loadable through the same `load_matrix(input_dir) -> (X, metadata, extra_arrays)` contract, no special case for "this one has labels in a different place." Consistently, `matrix.npy` always holds *the feature space clustering actually ran on*: the embedding for `dim_reduction_clustering.py`, the unchanged input `X` for `clustering.py` (which re-saves it into the new artifact dir - accepted storage duplication in exchange for one uniform contract instead of a one-off shape for the no-reduction case).

`dim_reduction_clustering.py` clusters the **embedding**, not the raw input matrix (`CLUSTERING_METHODS[method](embedding, params)`) - matches the handoff's stated flow ("reduction dispatch → clustering dispatch on the embedding").

Both clustering scripts write `cluster_plot.png` via `plotting.plot_clusters_2d` after a successful `save_matrix`, once per method in `clustering_methods` - `dim_reduction_clustering.py` plots the embedding's first 2 components, `clustering.py` plots the raw matrix's first 2 features (explicitly labeled "raw" in the axis titles, since with no reduction those 2 axes are an arbitrary, not-necessarily-meaningful projection). If fewer than 2 columns are available (e.g. a 1-component reduction), the plot step is skipped with a `logging.warning` rather than failing the run - the matrix/labels are still the real output, the plot is a convenience. Right after, both scripts also write `silhouette_plot.png` via `plotting.plot_silhouette_analysis`, fed by `clustering_tuning.compute_silhouette_samples` on the *same* space used to fit the clustering (`dim_reduction_clustering.py`'s `embedding`, `clustering.py`'s full `X` - not just its first 2 display columns, unlike `cluster_plot.png`, so it stays a reliable diagnostic even when the raw-feature scatter isn't a meaningful projection). Skipped the same way on a degenerate result (`ValueError` from `compute_silhouette_samples`, caught and logged as a warning).

Both clustering scripts' `_clusters_found_line` helper excludes DBSCAN/OPTICS-style noise label `-1` from the "Clusters found: N" count and reports it separately ("+ M noise points, label -1") whenever present - counting `-1` as a genuine cluster would silently overstate the result (a real caught case, not a hypothetical: `np.unique(cluster_labels)` alone doesn't know `-1` is special). Generic over any method that happens to produce `-1`, not special-cased on the string `"dbscan"`.

### `dim_reduction.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

`main()` loads the matrix once, then branches into `_run_production` or `_run_fine_tuning` based on `config.fine_tuning` - two functions, not one function with a large internal `if`, since their output shapes are fundamentally different (a matrix artifact vs. a comparison table) and sharing more than the initial `load_matrix` call would just be forced coupling.

- **Production** (`fine_tuning=false`, unchanged from before this round): `load_method_params` → `REDUCTION_METHODS[method]` → `save_matrix` at `<output_root>/<method>/<dd-mm>_<session_name>/`.
- **Fine-tuning** (`fine_tuning=true`): `load_method_params` + `load_tuning_grid` (+ `load_trustworthiness_n_neighbors` iff `method in METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS`, i.e. umap/tsne/pacmap) → `tuning.run_tuning_sweep` → written to a **separate branch** of the output tree, `<output_root>/<method>/tuning/<dd-mm>_<session_name>/{tuning_results.csv, tuning_plot.png, config.md}` - deliberately not `save_matrix`/not the same directory shape as a production run, so a sweep can never be mistaken for, or silently collide with, a real embedding artifact. No `manifest.json` here (unlike every other artifact in this pipeline) - a tuning table isn't meant to be read back via `artifacts.load_matrix`, so there's nothing that needs the completeness marker that function relies on.

Both modes call `append_run_log_entry` (`run_log.py`) after writing their output, tagged `"production"`/`"tuning"` respectively, into the *same* `<output_root>/<method>/runs.csv` - see `run_log.py` above for why that's one shared chronological file rather than two.

### `clustering.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

Same `main()` branch-on-`config.fine_tuning` shape as `dim_reduction.py` above, but `clustering.py` already loops over multiple `clustering_methods` in production mode, so its fine-tuning mode loops too (`_run_fine_tuning` iterates `config.clustering_methods`, calling `_run_one_method_tuning` once per method - same fail-fast "stop on first method's failure" behavior as the production loop's `_run_one_method`, no partial-run tolerance either mode).

- **Production** (`fine_tuning=false`, unchanged): as described above (`load_method_params` → `CLUSTERING_METHODS[method]` → `save_matrix`).
- **Fine-tuning** (`fine_tuning=true`), per method: `load_method_params` + `load_tuning_grid` → `clustering_tuning.run_clustering_tuning_sweep` → `<output_root>/<method>/tuning/<dd-mm>_<session_name>/{tuning_results.csv, tuning_plot.png, config.md}` (same deliberately-separate-branch shape as `dim_reduction.py`'s tuning output, same reasoning: a sweep table is never mistaken for a production artifact, no `manifest.json`). `_write_tuning_output` additionally calls `_write_standalone_diagnostic` when `method in STANDALONE_DIAGNOSTIC_METHODS` (agglomerative/spectral/dbscan), writing that method's own extra diagnostic plot into the same tuning output directory.

Same shared `<output_root>/<method>/runs.csv` convention as `dim_reduction.py` - `_runs_csv_path(config, method)` is reused unchanged between `_run_one_method` (production) and `_run_one_method_tuning` (fine-tuning), tagged `"production"`/`"tuning"` respectively.

### `dim_reduction_clustering.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep, clustering only)

Added after `clustering.py`'s own fine-tuning mode, on request - the one-shot alternative to `dim_reduction.py --fine_tuning=false` (save the embedding) then separately `clustering.py --fine_tuning=true` pointed at it: useful when you only want to tune clustering hyperparameters against a specific reduction without needing that embedding written to disk as its own artifact first. The reduction step itself is **never** swept here in either mode - `REDUCTION_METHODS[config.reduction_method](X, reduction_params)` runs exactly once in `main()`, before the `config.fine_tuning` branch, always at `reduction_params_file`'s `"params"` (not `"tuning_grid"`); re-tuning the reduction is `dim_reduction.py`'s job alone, kept a strictly separate concern.

- **Production** (`fine_tuning=false`, unchanged): as described above - clusters the one embedding with every method in `clustering_methods`, writes the comparison plot.
- **Fine-tuning** (`fine_tuning=true`), per method against that same one embedding: `load_method_params` + `load_tuning_grid` (both from `clustering_params_file`) → `clustering_tuning.run_clustering_tuning_sweep` → `<output_root>/<reduction_method>/<method>/tuning/<dd-mm>_<session_name>/{tuning_results.csv, tuning_plot.png, config.md}` + a standalone diagnostic plot for agglomerative/spectral/dbscan - same shape and same `_write_tuning_output`/`_write_standalone_diagnostic` logic as `clustering.py`'s own fine-tuning mode (duplicated, not shared, per this codebase's established per-CLI convention - see `clustering_tuning.py` above), just nested one level deeper under `reduction_method` and reading `embedding` instead of raw `X`. **No comparison plot** in this mode, even with multiple `clustering_methods` requested - a sweep's rows aren't a single set of cluster labels, there's nothing to compare side by side the way `plot_clusters_comparison` expects. Same shared `<output_root>/<reduction_method>/runs.csv` as production, tagged `"tuning"`, same `reduction_method`/`clustering_method` `extra_columns`.

**The intended workflow** (confirmed with the user, kept manual by design - no automatic parameter selection, and no plan to add one for any of the 4 fine-tunable methods; cross-validation for a future regression/classification task on top of clustering is a separate, not-yet-designed concern): run with `fine_tuning: true` → open `tuning_results.csv`/`tuning_plot.png` → pick parameters by eye → write them into `params_reduction.json`'s `"params"` for that method → set `fine_tuning: false`, pick a new `session_name`, optionally fill in `run_notes` explaining the change → re-run for the real embedding.

`DimReductionClusteringConfig` uses two explicitly named fields, `reduction_params_file` and `clustering_params_file`, rather than the two-element positional list (`"params_file": [...]`) shown in the original handoff note — decided during implementation: a positional list makes the mapping from list index to method implicit, the same category of fragility as `lessons_learned.md` #1 (though in practice `params.py`'s own per-method validation would catch a swapped pair too, since a reduction-method key wouldn't be found in a clustering params file). Named fields cost nothing extra and remove the ambiguity outright.

## `src/features/lesion.py` — lesion feature matrix

`build_lesion_matrix(data_root, datasets, reference_template_path, lesion_glob, binarize_threshold, resample_interpolation, parcellate, group_filter, atlas_path=None, parcel_aggregation=None) -> (X, metadata, non_constant_mask, parcel_ids, excluded_by_group)`

**`group_filter`** restricts subject discovery to specific naming-derived groups (`src.retrieval.dataset.group_of` - ST/HC/PD/GM), via the shared `src/features/subject_discovery.py::discover_files_by_subject` also used by `src/features/functional.py`. `None` means no restriction. Subjects excluded this way are returned separately as `excluded_by_group`, never conflated with a genuine missing-file gap - see `debug_27_07_26.md` and `docs/guides/matrix_building.md`.

Migrated from `notebooks/lesion_analysis.ipynb` (voxel-wise path, cells 4-8): same algorithm, restructured into typed, independently testable functions. The notebook is left as-is as the exploratory reference — this module is the version pipeline code actually calls.

**`reference_template_path` is an explicit, caller-supplied file, not derived from `datasets`** — changed from the original "pick the first lesion file of `reference_dataset` (sorted)" behavior, on request: that implicit choice silently tied the common voxel grid to whatever resolution one arbitrary subject's file happened to have, with no guarantee it matched a canonical space (e.g. MNI152 2mm) rather than just *a* space with the same name. `load_reference_image(reference_template_path) -> nib.Nifti1Image` now does exactly one thing - load that file, raising `FileNotFoundError` with a clear message if it's missing - and is also the function `build_lesion_matrix.py`'s `_write_parcellated_volumes` calls directly for QC reconstruction, without re-running subject discovery. The old `reference_dataset` field/param and its "must be one of `datasets`" validation are gone entirely, not deprecated-in-place.

Two output shapes for `X`, chosen by `parcellate`:

- **`parcellate=False`** (voxel-wise, the notebook's original behaviour): each subject is a flattened binarized lesion volume, resampled onto `reference_template_path`'s grid when its native resolution differs. `parcel_ids` is `None` — voxel-wise has no parcel identity to report.
- **`parcellate=True`**: each subject is the **proportion of damage per atlas region** — the same characterisation Thiebaut de Schotten et al. 2020 (`papers/Thiebaut de Schotten et al - 2020 - Brain disconnections link structural connectivity with function and behaviour/`) use ahead of their varimax-rotated PCA (MMP + 12 manually-defined subcortical regions, 372 ROIs total). `atlas_path` is caller-supplied — any volumetric, discrete-label NIfTI atlas works, not just MMP; swapping atlases is a config change (`atlas_path` + a distinct `session_name`), no code change.

Both paths end with `_drop_constant_features`: columns (voxels or parcels) that are identical across every subject carry no information for downstream PCA/UMAP/clustering and are dropped. `non_constant_mask` records which columns survived (against the pre-drop feature count) so the mask can be reapplied to related data (e.g. re-running with a different subject selection) — `parcel_ids` is filtered to the same surviving columns, so it always lines up 1:1 with `X`'s columns when `parcellate=True`.

### Parcel aggregation is a registry, not hardcoded

```python
PARCEL_AGGREGATIONS: dict[str, Callable[[np.ndarray], np.ndarray]] = {
    "fraction_lesioned": lambda voxel_block: voxel_block.mean(axis=1),
}
```

Each entry reduces a `(n_subjects, n_voxels_in_parcel)` block to `(n_subjects,)`. Only `"fraction_lesioned"` exists today because binary lesion masks only support one meaningful reduction (proportion of damage) — kept as an explicit registry (same "registry over hardcoded dispatch" precedent as `config/registry/file_patterns.json` and `REDUCTION_METHODS`/`CLUSTERING_METHODS`, planned) because SDC/FC data is continuous and will need other reductions (e.g. mean/sum of connectivity weights) on the same parcellation machinery — not a speculative abstraction for lesion masks alone.

### Atlas resampling always uses nearest-neighbor interpolation

`load_and_resample_atlas(atlas_path, reference_img)` forces `interpolation="nearest"` regardless of the lesion masks' own `resample_interpolation` config value. A label atlas holds discrete parcel ids, not continuous intensities — any other interpolation would invent label values that match no real parcel. This is the one place in the module where an interpolation choice is *not* a config value, deliberately: it isn't a real degree of freedom, unlike the lesion masks' own interpolation.

### `reconstruct_parcel_volume` — QC only, not part of the matrix-building path

`reconstruct_parcel_volume(parcel_values, atlas_labels, parcel_ids) -> np.ndarray` paints one subject's per-parcel value vector back onto the atlas voxel grid, for visual inspection (e.g. in `fsleyes`) of what a parcellated feature actually looks like spatially. It is pure numpy — no file I/O — and is not called by `build_lesion_matrix`. It backs the `save_parcellated_volumes` config flag on `build_lesion_matrix.py` (`_write_parcellated_volumes`, see that section below): when set, the pipeline script calls `load_and_resample_atlas` again (cheap — the atlas is small) and writes one `.nii.gz` per subject via `nibabel`, using the reference image's affine.

### Validation

`parcellate=True` requires both `atlas_path` and `parcel_aggregation`; `parcellate=False` forbids both — validated in `build_lesion_matrix` itself (`_validate_parcellation_args`), not left to config-layer callers, since the function can be invoked directly (tests, notebooks) as well as through `src/pipeline/build_lesion_matrix.py`.

## `src/analysis/build_config.py` — `build_lesion_matrix.json` parsing

`load_build_matrix_config(path) -> BuildMatrixConfig`, same shape and style as `src/retrieval/config.py`'s `load_config`: hand-written `_require_*`/`_optional_*` helpers (own copy, not shared with `src/retrieval/config.py` — each is a handful of lines, premature to abstract per the handoff note's explicit deferral), every field validated upfront so a malformed config is rejected before any file is touched.

Two upfront value-domain checks, beyond type checking, both deliberate (config validation is a system boundary — `code_standards.md` §0):

- **`binarize_threshold`** must be in `[0.0, 1.0]`. Lesion mask values after resampling are nominally binary/interpolated-to-[0,1]; a threshold outside that range produces a *silently degenerate* result (every voxel above or below threshold for every subject) that only surfaces much later, as an empty/collapsed feature matrix after `_drop_constant_features` — far from where the bad config value was set.
- **`resample_interpolation`** must be one of `{"linear", "nearest", "continuous"}` — the exact set `nilearn.image.resample_to_img` accepts. Without this check, a typo here (e.g. `"neareast"`) only surfaces when `resample_to_img` is actually called on a subject whose native resolution differs from the reference grid — potentially after a long run has already processed hundreds of subjects with matching resolution.

`parcellate`/`atlas_path`/`parcel_aggregation`/`save_parcellated_volumes` are cross-validated the same way as `build_lesion_matrix` itself (`_validate_parcellation_fields` mirrors `_validate_parcellation_args`) — kept as two separate checks (config layer + function layer) deliberately, since `build_lesion_matrix` can be called directly without going through this config loader (see "Validation" above). `parcel_aggregation`, when given, is checked against `src.features.lesion.PARCEL_AGGREGATIONS` directly (`analysis` importing from `features` is a downward, architecture-compliant dependency).

## `src/features/functional.py` — FC lesion masking (implemented, two decoupled pipelines)

**Goal**: for each WashU subject, mark as missing (`NaN`) the rows/columns of FC-matrix nodes (parcels) whose territory substantially overlaps the subject's lesion — same operation Siegel et al. 2016 (`papers/Siegel et al - 2016 .../markdown/_full.md`) and Griffis et al. 2019 (`papers/Griffis et al - 2019 .../markdown/_full.md`) apply on this same WashU cohort. FC input: `data/clinical_connectome/derivatives/UNIPD/WashU/features/<subject>/func/*_FC-pearson_atlas-<combo>.csv`, node×node Pearson matrices for 12 atlas combos (`Yan{100,200,300,400}TianS{1,2,3}Buckner7N`), space `MNI152NLin6Asym`.

**Atlas source**: `Atlases/fmriprep/atlas-<combo>/` on the EBRAIN server (`/data/corbetta/Clinical_connectome/Atlases/fmriprep/`) — already BIDS-Derivatives-formatted (`*_dseg.tsv` label lookup + `*_space-MNI152NLin6Asym_dseg.nii.gz` native 1mm + `*_res-2_dseg.nii.gz` 2mm), generated by XCP-D/AtlasPack conventions. Verified against the real WashU FC CSVs: node order and count in `_dseg.tsv` match the CSV header/index exactly for at least one combo (`Yan200TianS2Buckner7N`, 239 nodes) — the `_res-2` (2mm) volume is used directly since it matches WashU's lesion mask resolution, no atlas resampling needed for this dataset. The 12 combos (tsv + res-2 nii.gz only, ~2MB total) are committed at `assets/atlases/fmriprep/atlas-<combo>/`, same precedent as the other reference atlases already under `assets/atlases/`.

**Methodology decided (no custom parcellation function)**: rather than a hand-written voxel-loop (as `_parcellate_matrix` above does for lesion masks), parcel coverage is computed by reusing `nilearn.maskers.NiftiLabelsMasker` with the same two-masker pattern XCP-D itself uses for its own `min_coverage` BOLD-coverage thresholding (`xcp_d/interfaces/connectivity.py`, class `NiftiParcellate`): one masker with no `mask_img` (total voxel count per parcel), one with `mask_img=healthy_img` (voxel count restricted to non-lesioned voxels) — the ratio is `parcel_coverage`. A parcel is "compromised" when `parcel_coverage < min_coverage` (default 0.5, matching both XCP-D's own default and the field-standard overlap threshold for stroke lesion studies — Lesion Quantification Toolkit, Griffis et al. 2021). Compromised nodes' rows/columns are matched by **node name** (from the atlas's own `_dseg.tsv`), never by column position.

**NaN, not zero, at the masking step — imputation deferred to a separate later step**: literature review across this exact WashU/Corbetta lineage shows the field converged on marking compromised entries as missing (`NaN`), not on zeroing them directly. Griffis et al. 2019's own methods text is explicit about *why* zero shows up downstream anyway: *"Because the PLSC approach cannot accommodate missing values, functional connectivity between parcels that had been excluded ... was set to 0"* — i.e. `NaN` is the correct/honest representation of "not computable", and a concrete fill value is substituted only immediately before a method (PLSC/PCA/UMAP) that cannot itself accept missing values. Neither `sklearn`'s `PCA` nor `umap-learn` (the implementations already registered in `REDUCTION_METHODS`) tolerate `NaN` natively, so this project follows the same two-stage split: `src/features/functional.py` marks compromised entries `NaN` and stops there; a separate, explicitly-configurable imputation step (planned: `NAN_IMPUTATION_STRATEGIES` registry, default `"zero"`, same registry-over-hardcoded-dispatch precedent as `PARCEL_AGGREGATIONS`/`REDUCTION_METHODS`) runs only immediately before `dim_reduction.py`, logging how many values it filled in — never hidden inside a masker/reduction call.

**Two non-obvious bugs found and fixed while validating this against real WashU data** (both would have silently corrupted results if shipped as-is):

1. **Silent `uint8` overflow in the voxel-counting trick**: computing "voxels per parcel" via `NiftiLabelsMasker(strategy="sum")` on an all-ones counting image requires that image to have a wide-enough integer dtype. With `uint8`, the sum wraps at 256 (e.g. a 695-voxel parcel reports 183 = `695 mod 256`) — silently, no error, no warning. Fixed by using `int32` for the counting image.
2. **A fully-lesioned parcel disappears from the masked masker's output instead of reading 0**: `NiftiLabelsMasker(mask_img=healthy_img)` drops any label with zero surviving voxels entirely (`labels_` shorter than the unmasked masker's), rather than returning a 0 count for it — naively dividing the two makers' outputs by position would either crash (shape mismatch) or silently misalign every later label. Fixed by indexing both maskers' results by their own `labels_` (never by position) and treating an absent label as `coverage = 0.0` explicitly.

**Two pipelines, deliberately decoupled — including at the config level** (own dataclass/loader each in `src/analysis/build_config.py`, own CLI script, own `jobs/run_*.sh`, own output tree, own `runs.csv`):

1. **`src/pipeline/mask_fc.py`** (`config/pipelines/mask_fc.json` → `MaskFcConfig`/`load_mask_fc_config`) — the only pipeline that ever touches a lesion mask or an atlas. For each `atlas_combo` in the config's `atlas_combos` list (processed sequentially, one `mask_dataset_fc()` call per combo): discovers subjects with both a lesion mask and an FC file for that combo (`discover_subject_files`, built on the shared `src/features/subject_discovery.py::discover_files_by_subject` also used by `src/features/lesion.py` — a subject with FC but no lesion mask is a known, legitimate per-subject gap, logged as a `WARNING` and skipped, never a hard stop for the whole run, per `docs/guides/datasets.md`'s "sulla maggior parte" coverage note; a subject excluded by the config's `group_filter` — e.g. a WashU healthy control, which structurally never has a lesion mask — is reported separately as `excluded_by_group`, never conflated with the missing-lesion case, see `docs/guides/fc_matrix_building.md`), resamples each subject's lesion onto the atlas grid, computes parcel coverage (`compute_parcel_coverage`, the `nilearn.maskers.NiftiLabelsMasker` double-masker pattern below), `NaN`-masks the FC matrix by node name, and **writes the masked matrix to disk as-is** — `data/derived/features/masked_fc/<combo>/<subject>_masked_fc.csv`, a human-inspectable intermediate artifact, independent of how it's later vectorized. Also writes a per-combo `mask_summary.csv` (subject_id, n_compromised_nodes) - the raw material for the not-yet-run "find the exclusion threshold empirically" notebook analysis.
2. **`src/pipeline/build_fc_matrix.py`** (`config/pipelines/build_fc_matrix.json` → `BuildFcMatrixConfig`/`load_build_fc_matrix_config`) — reads *only* the already-masked CSVs `mask_fc.py` wrote (`masked_fc_root/<combo>/*.csv`); no lesion mask, no atlas, no raw FC data touched here, by design. For each `atlas_combo`: vectorizes each subject's masked matrix to its upper triangle (excluding the diagonal — the matrix is symmetric with a non-informative diagonal of 1.0), asserts every subject's edge labels match exactly before stacking (`stack_fc_vectors`, never assumed), drops constant edges (`drop_constant_edges` below), and writes the result via the existing `src/utils/artifacts.save_matrix`/`load_matrix` pair (same atomic-write artifact format already used by `build_lesion_matrix.py`: `matrix.npy`/`metadata.csv`/`config.md`/`manifest.json`, plus an `edge_names.npy` extra array) to `data/derived/features/fc_matrix/<combo>/<date>_<session_name>/`. The matrix still has `NaN` in it (compromised edges) — imputation to a concrete fill value is deliberately out of scope here, see below.

**`drop_constant_edges`** (in `src/features/functional.py`): an edge with **any** `NaN` is never evaluated for constancy — kept unconditionally (an open design point, not yet decided: the per-subject/per-edge exclusion threshold below). Among fully-observed edges only, one with an identical value across every subject is dropped. Unlike the binary lesion-matrix case (`_drop_constant_features` above, where constant all-zero columns are common and unremarkable), an exactly-identical *continuous* FC value across every subject is not expected — `build_fc_matrix.py` logs any drop at `WARNING` (with the edge name and shared value, worth a human look) and logs `INFO` when none are found (a routine, expected outcome, still explicitly confirmed rather than silently skipped).
