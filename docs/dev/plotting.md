# Embedding/cluster visualization — technical reference

Audience: developers/agents working on `src/analysis/plotting.py`, `embedding_coloring.py`, `embedding_plots.py`, and the metadata-enrichment functions in `src/features/clinical.py` that feed the coloring layer.

This file covers how a computed embedding/clustering result gets turned into PNG/HTML output. For the models that produce the arrays being plotted, and the 2 CLIs that call into this layer, see `docs/dev/models.md`. For the config fields that select which plots get made (`color_by`, `viz_n_components`), see `docs/dev/config.md`.

> `src/pipeline/dim_reduction_clustering.py` was retired 14-08-26 - see `docs/dev/clustering_migration_plan.md`. Every reference to it below has been updated; its own `color_by`/embedding-coloring integration was not carried over to `clustering.py`, which today only ever produces cluster-colored plots (`plot_clusters_2d`/`plot_clusters_comparison*`), never dataset/volume/side-colored ones.

## `src/analysis/plotting.py` — minimal cluster visualization

`_CATEGORICAL_PALETTE` (10 hex tones - pink/azzurro/green/orange/purple/gold/teal/red-brown hue families) is CVD-safe on every **adjacent** pairwise combination (not all-pairs), verified with the `dataviz` skill's `scripts/validate_palette.js` (OKLab/Machado-CVD math and thresholds). `_palette_for_labels`/`_palette_for_categories` cycle through it past 10 clusters/categories (an inherent limit of a validated set, not a bug). `_NOISE_COLOR` (fixed neutral gray) is kept out of that cycle so it never impersonates a real cluster/category - used for HDBSCAN/OPTICS noise (label `-1`) and any categorical `missing_label`.

**Extended from 5 to 10 colors, 01-09-26** - HDBSCAN production runs on the s1.1 cohort routinely found 8-20 real clusters (excl. noise) at reasonable `min_cluster_size`/`min_samples`, cycling the original 5-color set 2-4x and making `cluster_plot.png` hard to read. The original 5 were validated **all-pairs** (worst ΔE 8.6/18.3, both clear of the 8.0/15.0 gates) - a stronger, scatter-appropriate guarantee, since two clusters can sit next to each other anywhere on the plot, not just adjacent in a legend. The dataviz skill's own guidance is that an all-pairs-safe categorical caps at ~3-4 slots for a scatter/bubble/small-multiples chart regardless of palette size (the documented skill-default 8-color palette itself only clears all-pairs on its first 3 slots) - so no palette size actually solves 8-20 distinguishable clusters in one scatter; the real fix for that would be small multiples (one panel per cluster) or folding minor clusters into "Other". Chose the 10-color, adjacent-only expansion as a deliberate best-effort middle ground instead (user decision) - better than 5, not a rigorous fix for >10 clusters, which still cycles.

`compose_run_title(output_dir, project) -> str`: builds every plot title (matplotlib `ax.set_title`/`fig.suptitle`, plotly `title`) from the run's own `output_dir` path instead of ad hoc per-script string concatenation - drops a leading `"results"` path segment and joins the rest with `" › "`, e.g. `results/lesion/dim_reduction/umap/21-07_s1_d01` -> `"clinical_connectome — lesion › dim_reduction › umap › 21-07_s1_d01"`. Motivation: `config.project` alone (always `"clinical_connectome"` today) never distinguished modality/session/tag, so two different runs of the same method used to get identical titles - `output_dir` already encodes modality/pipeline/method/session/tag (`<dd-mm>_<session_name>[_<tag>]`, tag built from `params_reduction.json`/`params_clustering.json`'s `tag_param`/`tag_prefix` - parallel lists, one prefixed value per declared hyperparameter - see `src/analysis/params.py`, `docs/dev/config.md`), and it's the exact same `Path` every pipeline script already builds for `save_matrix`/logging - so the title can't drift out of sync with where the file actually lives, and needs no update if `results/` gets nested deeper later (e.g. the `results/<modality>/{dim_reduction,clustering}/` layout). Used today only for `dim_reduction.py`'s own fine-tuning `tuning_plot.png` title (`_write_tuning_output`, `docs/dev/models.md`) - every other consumer has since moved to a shorter, `_modality_title`-based composer below (`compose_cluster_plot_title`/`compose_embedding_plot_title`/`compose_clustering_tuning_title`/`compose_comparison_title`), none of which repeat `output_dir`'s full path inside the title text. **`clustering.py` used `compose_run_title` for its own production scatter/comparison/tuning titles too until 31-08-26** - despite `compose_cluster_plot_title` already existing (and this doc already documenting it) as the intended production-title composer, it had only ever been wired into `scripts/replot_dim_reduction.py`, never back into `clustering.py` itself (found during a naming-consistency audit after the `tag-params-multi-key` refactor). Fixed by wiring `compose_cluster_plot_title` into `clustering.py`'s production `cluster_plot.png`/`silhouette_plot.png`, the new `compose_clustering_tuning_title` (below) into every tuning-mode plot, and `compose_comparison_title` (previously only used for `plot_clusters_comparison`'s `suptitle`) into `cluster_comparison_interactive.html`'s title too - `compose_run_title` is now `dim_reduction.py`-only.

`compose_cluster_plot_title(output_dir, reduction_method, clustering_method) -> str`: `"<Modality> - <ReductionMethod> - <ClusteringMethod>"` (e.g. `"Lesions - Umap - Kmeans"`), each segment `str.capitalize()`d. `compose_embedding_plot_title(output_dir, reduction_method, color_by=None) -> str` is the analogous title for `dim_reduction.py`'s own embedding scatters (no clustering method to name): `"Lesions - Umap"` for the single-color `embedding_plot_unico.png`, `"Lesions - Umap - Dataset"`/`"- Volume"`/`"- Side"` for the colored variants below. Both need no `project` config value (unlike `compose_run_title`) - `scripts/replot_dim_reduction.py` uses them too, deriving `reduction_method`/`clustering_method` from the run directory's own path segments instead of a config load.

`compose_clustering_tuning_title(output_dir, method) -> str` (31-08-26): `"<Modality> - Clustering Tuning - <Method>"` (e.g. `"Lesions - Clustering Tuning - Agglomerative"`, `"Sdcs - Clustering Tuning - Spectral"`) - the title for every plot `clustering.py`'s fine-tuning mode writes (`tuning_plot.png`, `dendrogram_metric=*.png`/`eigengap_affinity=*.png`/`interclass_distance_matrix.png`/`stability_plot.png`/`consensus_matrix_heatmap.png`/`n_repeats_convergence.png` - all built from the one `title` `_write_tuning_output`/`_run_one_method_tuning` compute once). Replaces `compose_run_title` there (which dumped `output_dir`'s full path, e.g. `"clinical_connectome — lesion › clustering › tuning › agglomerative › umap › 27-08_s1.1_dice_n10"` - a tuning run's own directory/`config.md` already carry `reduction_method`/`session_name`, no need to repeat them inside every plot title too). The per-metric/per-affinity diagnostics append their own suffix on top (`f"{title} (metric={metric})"`/`f"{title} (affinity={affinity})"`), same convention as before.

`plot_clusters_2d(X_2d, cluster_labels, output_path, xlabel, ylabel, title, point_sizes=None)`: one function, a 2D scatter of `X_2d`'s first two columns colored by `cluster_labels`, saved to `output_path` - validated categorical palette (`_palette_for_labels`), legend anchored outside the axes, axis limits padded beyond the data's own min/max, bold/padded title. Raises `ValueError` if `X_2d` has fewer than 2 columns rather than producing a degenerate/empty plot. `plot_embedding_2d(X_2d, output_path, xlabel, ylabel, title)` is the single-color sibling for `dim_reduction.py`'s base `embedding_plot_unico.png` - same figure size/axis padding/bold-padded-title conventions, just no legend/palette (nothing to group by). `plot_embedding_categorical(X_2d, categories, output_path, xlabel, ylabel, title, legend_title, missing_label="unknown")` extends that same visual treatment to an arbitrary string category per point (`dataset`, `lesion_side`) via `_palette_for_categories` - a string-keyed sibling of `_palette_for_labels` where `missing_label` always gets the same neutral gray already reserved for cluster noise (`-1`), so a structurally-missing value (e.g. a dataset with no `lesion_side` column) never impersonates a real category. `plot_embedding_continuous(X_2d, values, output_path, xlabel, ylabel, title, colorbar_label)` is the continuous-quantity sibling (`lesion_volume_voxels`) - a `viridis` colormap + colorbar instead of a legend, same figure/axis conventions otherwise.

**`_MARKER_SIZE`/`_MARKER_ALPHA`/`_declutter_points` now shared across all 6 static scatter functions (01-09-26)** - `plot_clusters_2d`/`plot_clusters_comparison`/`plot_silhouette_analysis` originally kept their own opaque `_MARKER_SIZE=18`, no declutter, deliberately out of scope when the embedding functions got their fix (26-08-26, below) - "same density problem is plausible there too at this scale, revisit if it's hit in practice." Hit in practice on HDBSCAN production plots (`cluster_plot.png`, 1150-5269 subjects, `min_cluster_size`/`min_samples` chosen deliberately loose enough to have too many small clusters to read once overplotted) - fixed by applying the exact same recipe: `_MARKER_SIZE` lowered `18`→`6` (matches `_EMBEDDING_MARKER_SIZE`, kept as a separate constant since it also derives `_POINT_SIZE_FLOOR`/`_POINT_SIZE_SCALE` for HDBSCAN's `point_sizes`), `_MARKER_ALPHA=0.9` added, `_declutter_points` called once before scattering in all 3 functions. `plot_clusters_comparison` declutters `X_2d` once outside its per-method loop (same coordinates feed every subplot, only labels/colors vary) - dosed against one subplot's own figsize (`_COMPARISON_SUBPLOT_WIDTH`/`_COMPARISON_SUBPLOT_HEIGHT`), not the full multi-subplot canvas; same for `plot_silhouette_analysis`'s scatter panel (`_SILHOUETTE_SUBPLOT_WIDTH`, not the 2-panel-wide figure). `plot_clusters_2d`'s `point_sizes` branch (HDBSCAN membership-confidence sizing) doses the declutter against the base `_MARKER_SIZE` even though rendered sizes vary per point - same "not a precise spacing guarantee" tradeoff already documented for exact-duplicate pairs below, not worth a per-point-size-aware declutter.

`plot_embedding_2d`/`plot_embedding_categorical`/`plot_embedding_continuous` use their own `_EMBEDDING_MARKER_SIZE=6`/`_EMBEDDING_MARKER_ALPHA=0.9` (26-08-26, same values as `_MARKER_SIZE`/`_MARKER_ALPHA` above by construction, kept as separate constants since the two families were fixed in separate sessions) - `dim_reduction.py`'s production embedding plots run at ~5000+ subjects (the full lesion cohort, `26-08_s1.2`), where an opaque `_MARKER_SIZE=18` marker overlapped into one indistinguishable blob (validated visually, candidate configs compared side by side on the real cohort before choosing this one). Alpha was tried much lower first (0.35) with no declutter, but with `_declutter_points` below doing the actual overlap-removal, only a light transparency touch (0.9) is needed on top - a heavier one made single-run plots look washed out without adding legibility once points aren't literally stacked any more.

**`_declutter_points(X_2d, xlim, ylim, figsize, marker_size) -> np.ndarray` (26-08-26 session, on request; reused by the 3 cluster-plot functions above since 01-09-26)**: called right before scattering, to push points that would literally overlap on screen apart - a second, complementary fix to the alpha/size change above, addressing "can we space points out instead of just making them transparent". Distance is computed in **screen pixels** (`figsize`/`_EMBEDDING_DPI`/`xlim`/`ylim` convert data units to pixels first), not raw data units - a first attempt at this used a percentile of the raw nearest-neighbor-distance distribution as the threshold and had **zero visible effect**, because the real problem is screen-space overplotting (thousands of points rendered into a ~1000-pixel-wide static PNG), not literal duplicate data coordinates; a "typical" data-space distance has no defined relationship to how many screen pixels a marker occupies. The dose is capped at `_DECLUTTER_MARKER_DIAMETERS=1.0` marker diameter deliberately, not more: visually compared at 1/2/3 diameters on the real cohort, zoomed into the densest core - 1 diameter stops literal marker-on-marker occlusion while leaving genuinely tight sub-clusters (e.g. one dataset's subjects sitting very close together in the embedding) visually intact; 2-3 diameters started dissolving those sub-clusters into the surrounding cloud, which would misrepresent how close those subjects actually are in UMAP space. **This is the one place in this file that moves a point's plotted position away from its real embedding coordinate** - unlike every other function here, which only changes how a point is rendered (color, size, alpha), never where. Runs `_DECLUTTER_ITERATIONS=3` passes (resolving one crowded pair can create a new one with a third point) of "push each still-crowded point away from its current nearest neighbor by the shortfall, scaled by `_DECLUTTER_STRENGTH=0.8`"; an exact-duplicate pair (0 pixel distance, no defined "away from" direction) is pushed apart in a random direction each (`_DECLUTTER_RANDOM_STATE=0`), which can end up separating the pair by up to ~2 marker diameters in the worst case (both kicked in opposite random directions) rather than exactly 1 - acceptable since exact duplicates are rare and the goal is "not fully overlapping," not a precise spacing guarantee. A single point (nothing can overlap with fewer than 2) is a documented no-op, not an error. `_EMBEDDING_DPI=150` must stay equal to the `dpi=` these 3 functions actually `savefig()` at, otherwise the declutter is dosed against a marker footprint that isn't the one actually rendered.

All three stay 2D-only - no static 3D counterpart exists anywhere in this module (an interactive, rotatable view is the only sane rendering of a 3D scatter - see `src.analysis.embedding_app`/`src.pipeline.embedding_app`, `docs/guides/embedding_app.md`, not a static file). Same reasoning applies to `plot_embedding_grid_blocks` below - and, since 26-08-26, more strictly than "stays 2D": a >2-component tuning combination gets **no** `embeddings_grid_*.png` cell at all any more, not even a refit-to-2D one (`dim_reduction.py::_build_grid_blocks` drops such a cell outright instead of calling `embedding_for_viz` on it - see `docs/dev/models.md`). `scripts/plot_tuning_embedding_3d.py` (26-08-26) is the one place a 3-component *tuning* combination actually gets rendered, in 3D, reusing `src.analysis.embedding_app.build_embedding_figure` (a pure function, no production-run concept baked in) directly on one `embeddings.npz` entry - see that script's own module docstring for why it's a separate small tool rather than an extension of either `embedding_app` (deliberately production-only, see that module's docstring) or `generate_understanding_umap_report` (deliberately a 2D grid across the whole sweep, not a single combo in 3D) - and why it's a manual, on-request tool rather than something either pipeline generates automatically for every leaf/color mode.

`plot_silhouette_analysis(sample_labels, sample_silhouette_values, X_2d, display_labels, output_path, xlabel, ylabel, title)`: the classic sklearn-style two-panel per-sample silhouette diagnostic, added on request as the production-time breakdown of the single aggregate number `compute_clustering_metrics`/`clustering_tuning.py` reports during fine-tuning (`docs/dev/models.md`) - a mean can hide one bad cluster averaged out by good ones. Left panel: one filled horizontal band per cluster (`ax.fill_betweenx`), each member's own coefficient sorted ascending within its band, colored via the same `_palette_for_labels` as the scatter, plus a dashed line at the mean (equals `compute_clustering_metrics`'s `"silhouette"` exactly). Right panel: the same 2D scatter as `plot_clusters_2d`. Takes two separate label arrays deliberately: `sample_labels`/`sample_silhouette_values` come from `clustering_tuning.compute_silhouette_samples` (noise already excluded there - undefined for a "cluster" that isn't one, so no band is drawn for it), while `display_labels` is the **full** vector including noise, so the scatter panel still shows where those points physically sit (grayed out). Raises `ValueError` on the same `< 2` columns case as `plot_clusters_2d`. Called by `clustering.py`'s `_run_one_method`, right after `plot_clusters_2d`, wrapped in `try/except ValueError` since `compute_silhouette_samples` can legitimately raise on a degenerate production result (e.g. a single cluster) - logged as a warning, doesn't fail the run, matching the same "warn and skip, don't crash" precedent as the `X_2d.shape[1] < 2` branch right above it.

**`plot_embedding_interactive` was removed 2026-08-14** (production embedding's per-run interactive HTML, `embedding_plot_interactive.html`, with a dropdown to switch coloring) - superseded by `src.pipeline.embedding_app` (a live Dash app, `docs/guides/embedding_app.md`), which reads any already-written production run directly and covers every color mode with no static file to keep in sync per run, plus real 2D/3D toggling (the interactive HTML was the only rendering a 3-component embedding ever got in this codebase; that's now the embedding_app's job too). `write_embedding_plots` (below) no longer writes it; a 3-component `embedding` now makes that function a no-op (still validates `zlabel` is given, still raises on other column counts, just renders nothing - all rendering for that case moved to the live app).

**`plot_clusters_interactive` was removed 2026-08-27** (production clustering's per-run interactive HTML, `cluster_plot_interactive.html`, colored by `cluster_label` only) - same rationale as `plot_embedding_interactive` above: superseded by `src.pipeline.embedding_app`, which already covers single-run interactive browsing (including cluster-colored production runs) with no static file to keep in sync per run. `clustering.py`'s `_run_one_method` no longer calls it, and `scripts/replot_dim_reduction.py` no longer regenerates it - both now only write `cluster_plot.png`. `plot_clusters_comparison_interactive` (below) is unaffected - it shows multiple clustering methods side by side simultaneously, a capability the Dash app doesn't have (one run at a time).

**`dim_reduction.py`'s `metadata.csv` is no longer "carried over unchanged"** (2026-08 session): production mode adds 3 columns before `save_matrix`, via `src/features/clinical.py::enrich_metadata_with_lesion_info(metadata, X) -> pd.DataFrame` - `lesion_volume_voxels` (`X.sum(axis=1)`, only valid for a strictly binary `X` - raises `ValueError` otherwise, 2026-08 literature-validation review, since a parcellated `fraction_lesioned` matrix would silently produce a value that's neither a voxel count nor proportional to lesion volume in ml), `lesion_side` (`join_lesion_side`, below), and `nihss` (`join_nihss`, below). Called unconditionally in production mode (not gated by `color_by`, so `metadata.csv` always has the same 5-6 columns regardless of what a given run chose to plot) but **not** in fine-tuning mode - fine-tuning writes no `metadata.csv` at all (only `tuning_results.csv`/plots), so an unresolvable subject's `lesion_side`/`nihss` there would abort a sweep for a column it never uses. All 3 columns are persisted (not just computed at plot time) specifically so `scripts/replot_dim_reduction.py` can regenerate `dim_reduction.py`'s plots from `matrix.npy`/`metadata.csv` alone (only when the saved embedding has exactly 2 components, see above), without ever reloading the original (potentially huge) feature matrix or rejoining `assets/metadata`. A run predating this change has none of these 3 columns - `scripts/replot_dim_reduction.py` raises `ValueError` rather than guessing at a fallback, telling the user to rerun `dim_reduction.py` instead. `clustering.py` never calls this function itself (14-08-26 - see `docs/dev/clustering_migration_plan.md`) - when `input_path` is an embedding `dim_reduction.py` already produced, these 3 columns simply pass through unchanged in `metadata.csv`, inherited rather than recomputed.

`src/features/clinical.py::join_lesion_side(metadata) -> pd.Series`: for each unique `metadata["dataset"]` value, loads `METADATA_ROOT/f"{dataset.replace('/', '_')}_participants_lesions.tsv"` (`METADATA_ROOT = Path("assets/metadata")`, a fixed repo asset root, same class of module constant as `dim_reduction.py`'s `LOGS_ROOT` - monkeypatchable in tests, not a config field) via the existing `load_participants`. Three cases: the file doesn't exist at all - `FileNotFoundError` propagates (an unresolvable dataset name is a real configuration problem, never silently papered over); the file exists but has no `lesion_side` column at all (real case: PASPORT, which has `lesion_volume_ml` instead) - every subject in that dataset gets `"unknown"`, logged once at `WARNING` (a known structural per-dataset gap, not an error); the column exists but one subject's value is missing/blank (`"n/a"`, reusing `_normalize_missing`) - that subject alone gets `"unknown"`. Raises `ValueError` if a subject in `metadata` has no matching row in its dataset's participants.tsv at all (a real matrix/metadata mismatch, not a legitimate "missing" case).

`src/features/clinical.py::join_nihss(metadata) -> pd.Series`: same per-dataset join as `join_lesion_side`, for the baseline NIHSS severity score - but continuous, so a missing value is `np.nan`, never a string sentinel (no categorical "unknown" bucket makes sense for a number). Same three cases as `join_lesion_side`, with NaN instead of `"unknown"`: dataset-wide missing `NIHSS` column (real case: PASPORT, which only has `NIHSS_at_presentation`/`NIHSS_24H`/`NIHSS_3m`, deliberately **not** treated as equivalent to a baseline `NIHSS` - a clinical-equivalence assumption this function has no basis to make on its own) logs one `WARNING` and marks every subject in that dataset NaN; a per-row missing/blank cell is NaN too; a subject entirely absent from its dataset's participants.tsv raises `ValueError` (data mismatch); a non-missing, non-numeric cell raises `ValueError` too (data corruption, never silently coerced).

`plot_clusters_comparison(X_2d, labels_by_method, output_path, xlabel, ylabel, suptitle)`: same idea as `plot_clusters_2d` but a grid of subplots (`ncols = min(3, len(labels_by_method))`, `nrows` = ceil of the rest), one per method, same `X_2d` for all of them, colored by that method's own labels - added when `clustering.py` gained support for multiple `clustering_methods` in one run. X/Y limits are computed once from `X_2d` and applied to every subplot, so no single method's cluster spread looks artificially wider/narrower just from independent auto-scaling. Same `ValueError`-if-fewer-than-2-columns guard as `plot_clusters_2d`, plus one for an empty `labels_by_method`.

`plot_clusters_comparison_interactive(X_2d, labels_by_method, metadata, output_path, xlabel, ylabel, title)`: the interactive sibling of `plot_clusters_comparison` - one full `px.scatter` trace set per method (not per cluster/dataset pair), all but the first hidden, toggled via an `updatemenus` dropdown with one button per method. Same 2D layout and points for every option, only the coloring (and hover, via `metadata`) changes - lets you eyeball whether two methods agree on a cluster boundary without opening N separate per-method HTML files. Same `ValueError` guards as `plot_clusters_comparison` (`< 2` columns, empty `labels_by_method`) plus a metadata row-count check.

One more, for fine-tuning sweeps (`tuning.py`, `docs/dev/models.md`): `plot_tuning_curve(df, param_col, metric_col, output_path, title)` - a line plot, for a 1-parameter `tuning_grid` with no `nested_params` declared (PCA's `n_components`, PaCMAP's `n_neighbors`). `dim_reduction.py` only uses it for that undeclared-1-parameter case; with no `nested_params` and 2+ swept parameters it still gets no plot at all - a WARNING is logged, `tuning_results.csv` is still written either way. When `nested_params` **is** declared (umap/tsne, 2026-08 session), this function isn't used at all - `plot_embedding_grid_blocks` below takes over instead, one call per leaf subfolder. `plot_clustering_tuning_heatmaps` below is a distinct function (clustering-tuning, not dim-reduction-tuning) and unaffected by any of this.

4 more, for `clustering.py`'s fine-tuning mode (`clustering_tuning.py`, `docs/dev/models.md`): `plot_clustering_tuning_metrics(df, param_col, metric_cols, output_path, title)` - one line-plot subplot per metric in `metric_cols`, all sharing `param_col` on the x-axis; unlike `plot_tuning_curve` (always exactly one metric), silhouette/Calinski-Harabasz/Davies-Bouldin/method-specific extras live on incomparable scales, so overlaying them on one shared axis would mislead - each gets its own subplot instead. `plot_clustering_tuning_heatmaps(df, param_x, param_y, metric_cols, output_path, title)` is the 2-parameter analogue (one heatmap subplot per metric instead of one line-plot subplot) - added when `params_clustering.json`'s grids briefly grew a second dimension per method, reverted since (each method's `tuning_grid` sweeps exactly one parameter today: `n_clusters`/`n_components`/`min_cluster_size`), so this function stays in code unused by the current registry, wired back in the moment a grid grows a second dimension again; `clustering.py`'s own `_write_tuning_output` picks curve vs. heatmap vs. "no plot, just a warning" by `len(swept_params)` (1/2/more), mirroring `dim_reduction.py`'s own `plot_tuning_curve`/`plot_tuning_heatmap` choice above - `tuning_results.csv` always has every combination regardless of whether a plot could be drawn for it. The 2 standalone-diagnostic plots each wrap a scipy/numpy computation from `clustering_tuning.py` with no logic of their own, laid out as a subplot grid rather than one file per value (28-08-26 fix, `docs/dev/models.md`, same "one file per outer value, one subplot per inner value" shape as `plot_interclass_distance_matrix` above): `plot_dendrograms_grid(linkage_matrices_by_linkage, output_path, title, truncate_last_p=30)` (`scipy.cluster.hierarchy.dendrogram` per subplot, `truncate_mode="lastp"` since a full tree over hundreds/thousands of subjects is unreadable), `plot_eigengaps_grid(eigenvalues_by_label, output_path, title)` (marks each subplot's single biggest gap between consecutive eigenvalues via `np.argmax(np.diff(eigenvalues))`, raises `ValueError` on an empty dict or fewer than 2 eigenvalues in any entry). HDBSCAN (which replaced DBSCAN) has no standalone diagnostic - `plot_k_distance` was removed along with `compute_k_distance` when DBSCAN was replaced, since HDBSCAN has no single `eps` to read off a plot by eye.

**Subplot spacing, all 3 side-by-side grids (31-08-26)**: `plot_interclass_distance_matrix`'s `wspace` raised `0.5` -> `1.1` (plus `pad=0.04` on each subplot's own colorbar) after visually finding real dataset-name labels (`"UKLFR/stroke_UKLFR"`) overlapping the previous subplot's colorbar - each subplot draws its own y-tick labels (not shared with its neighbor's), so the gap has to fit one subplot's colorbar *and* the next subplot's label text, not just the two axes. `plot_dendrograms_grid`/`plot_eigengaps_grid` had no explicit `wspace` at all (matplotlib's default ~0.2, tight but not overlapping for their shorter labels) - given an explicit `wspace=0.35` for the same "always a deliberate value here, never the default" convention.

## `src/analysis/embedding_coloring.py` / `embedding_plots.py` — pluggable embedding coloring (2026-08 session)

Replaces `dim_reduction.py`'s old hardcoded `for color_by, column in (("Dataset", "dataset"), ("Side", "lesion_side")):` + a separate copy-pasted Volume block (~45 lines) with a small registry plus a shared writer, so adding a new coloring mode is one dict entry, not a new hand-written block - and the same writer is reused by both `dim_reduction.py`'s production and fine-tuning (`nested_params`) output.

`embedding_coloring.py`: `COLOR_MODES: dict[str, ColorMode]` - `ColorMode(kind, column, label, log_scale=False)`, `kind` is `"categorical"` (legend, `plot_embedding_categorical`) or `"continuous"` (colorbar, `plot_embedding_continuous`), `column` is the exact `metadata.csv` column this mode reads (`"dataset"` → `dataset`, `"side"` → `lesion_side`, `"volume"` → `lesion_volume_voxels`, `"nihss"` → `nihss`). `color_values(metadata, mode_name)` is the one place every consumer (`embedding_plots.py`, `embedding_app.py`) actually reads a mode's values - straight from that column, raising `ValueError` if `metadata` doesn't have it yet (e.g. `"volume"` before `build_lesion_matrix.py` ran, `"side"`/`"nihss"` before `enrich_lesion_metadata.py` did). `resolve_color_mode(name) -> ColorMode` raises `ValueError` (with the known-modes list) for an unregistered name, rather than a raw `KeyError`. "Single color" (`_unico`) is not a registry entry - it's the always-generated base case, never listed in a `color_by` config.

**Collapsed 2026-08-17** from two independently-maintained mechanisms (fixing a doc/code mismatch that had crept in here: this paragraph used to describe a `compute(metadata, X) -> np.ndarray` callable that no longer exists in the code): a live `compute` callable that recomputed a value for the production/tuning writers, and a separate `PERSISTED_COLUMN_BY_MODE` mapping used only by `embedding_app`'s read-only explorer. The two were meant to agree but had no way to be checked against each other - `"volume"`'s live `compute` did `X.sum(axis=1)` with zero guard against a parcellated (continuous, non-binary) `X`, silently producing a meaningless number, while the persisted `lesion_volume_voxels` column right there in the same `metadata.csv` was already correct. Every mode now reads its own column straight from metadata, never recomputed from `X` or rejoined from `participants.tsv` live - `X` is no longer needed by any color mode at all, since dataset/side/volume/nihss/cluster are all per-subject facts already resolved once upstream (`build_lesion_matrix.py`, `enrich_lesion_metadata.py`).

**`log_scale` (2026-08 session, per-mode flag, continuous only)**: `"volume"` is the only mode with `log_scale=True` today. Found by inspecting a real `embeddings_grid_volume.png`: lesion volume is heavily right-skewed (1 to ~40000 voxels on the real 1150-subject cohort) - on a linear color scale, a handful of large-lesion outliers stretch the range so far that almost every other point renders the same dark color, no usable gradient. `"nihss"` stays linear (`log_scale=False`, the default) - deliberately, on request, so the two modes keep the *same* palette (`viridis`, both) and are told apart by their color's actual spread/shape rather than by a second hue family. `resolve_color_mode(...).log_scale` is threaded through by both `write_embedding_plots`/`write_embedding_grid` (below) into `plot_embedding_continuous`/`plot_embedding_grid_blocks`'s own `log_scale` param - a `matplotlib.colors.LogNorm` fit to the non-missing values instead of the default linear normalization. Raises `ValueError` if any non-missing value is `<= 0` (LogNorm can't represent it, and matplotlib's own silent behavior - masking it out, i.e. treating it as "missing" - would misrepresent a genuine zero-volume subject as if its value were unresolvable, the same bucket as a genuinely missing `NIHSS`). `src.analysis.embedding_app`'s own figure builder threads `log_scale` through too (see `docs/guides/embedding_app.md`) - unlike the removed `plot_embedding_interactive`, which stayed linear regardless of it (plotly express has no direct `LogNorm`-equivalent color axis; `embedding_app` gets around this by log-transforming the values itself and relabeling the colorbar ticks back to real units, same fix applied to the notebook prototype first).

`plot_embedding_continuous`'s NaN handling (relevant since `"nihss"` is the first `COLOR_MODES` entry that can legitimately produce `NaN` values - `"volume"` never does): a `NaN` point is drawn in the same fixed neutral gray as the categorical plots' missing/noise bucket (`_NOISE_COLOR`), underneath the colored points, with a small "missing" legend entry - not left to matplotlib's own default (a fully transparent, invisible marker with no visual sign anything is missing). The colorbar's range is fit to the non-`NaN` values only, so a handful of missing subjects never compresses the color scale for everyone else. `plot_embedding_grid_blocks`'s continuous branch got the exact same NaN treatment in the same session, as a bug fix rather than new functionality - it had never NaN-checked `color_values` at all (unlike `plot_embedding_continuous`), so a missing subject there would have hit matplotlib's default invisible-transparent-point behavior with no legend entry, latent until `"nihss"` became the first continuous mode that could actually reach a tuning grid with real gaps.

**Bug fix, same session**: `plot_embedding_grid_blocks`'s continuous branch never called `fig.colorbar(...)` at all before this session - the figure had no legend/colorbar whatsoever for a continuous coloring (found by inspecting a real `embeddings_grid_volume.png`, a pre-existing gap unrelated to `nihss`/`log_scale`, just surfaced by using the plot for the first time). Fixed by capturing the first cell's `scatter` return value (`continuous_mappable`) and every cell's `Axes` (`data_axes`), then `fig.colorbar(continuous_mappable, ax=data_axes, label=legend_title, shrink=0.6)` once after the main loop - same "take it from the first cell only" convention already used for the categorical branch's shared legend.

`embedding_plots.py` has two writers, both wrapping every color-mode's static PNG in its own `try/except Exception` + `logging.warning` (same convention `dim_reduction.py`'s old hardcoded block already used - one bad coloring, e.g. a dataset with no resolvable `participants.tsv` for `lesion_side`, must not abort the whole run):
- `write_embedding_plots(embedding, metadata, X, color_by, output_dir, xlabel, ylabel, title_fn, zlabel=None, file_prefix="embedding_plot")`: the single-embedding case (production). `embedding` must have exactly 2 or 3 columns (raises otherwise) - with 3, this is a no-op (see the `plot_embedding_interactive` removal note above: no static rendering exists for a 3-component embedding in this module, only the live `embedding_app`). Writes `<file_prefix>_<name>.png` per mode in `color_by` that computed successfully (each independently try/except'd).
- `write_embedding_grid(blocks, metadata, X, color_by, output_dir, xlabel, ylabel, title_fn, file_prefix="embeddings_grid")`: the tuning-leaf case. `blocks: list[tuple[str, list[tuple[str, np.ndarray]]]]` (block title + `[(cell title, embedding), ...]`) is built by the *caller* (`dim_reduction.py`'s `_build_grid_blocks`, `docs/dev/models.md`) - this function only decides which color to render each block set in, calling `plotting.plot_embedding_grid_blocks` once per color (always for `_unico`, plus once per `color_by` entry).

`plotting.plot_embedding_grid_blocks(blocks, output_path, xlabel, ylabel, suptitle, color_values=None, color_kind=None, legend_title=None)`: one row of small scatter subplots per block (real embeddings, not a numeric curve - the point is seeing how the point cloud's *shape* changes with a swept parameter, not just how one score moves), a dedicated label row above each block's scatter row, and a blank spacer row between blocks (a `matplotlib.gridspec` layout, not just subplot padding) - real whitespace, so multiple blocks in one figure read as visually distinct sections. All cells share one x/y axis range (padded beyond every embedding's combined min/max) and one legend/colorbar (taken from the first cell only - every cell is a fit of the same subjects, so per-cell legends would be redundant).
