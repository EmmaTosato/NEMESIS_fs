# Embedding/cluster visualization — technical reference

Audience: developers/agents working on `src/analysis/plotting.py`, `embedding_coloring.py`, `embedding_plots.py`, and the subject registry (`src/utils/participants.py`) that feeds the coloring layer.

This file covers how a computed embedding/clustering result gets turned into PNG/HTML output. For the models that produce the arrays being plotted, and the 2 CLIs that call into this layer, see `docs/dev/models.md`. For the config fields that select which plots get made (`color_by`, `viz_n_components`), see `docs/dev/config.md`.

> `src/pipeline/dim_reduction_clustering.py` no longer exists (see `.claude/history/project_changelog.md`). Every reference to it below has been updated; its own `color_by`/embedding-coloring integration was not carried over to `clustering.py`, which today only ever produces cluster-colored plots (`plot_clusters_2d`), never dataset/volume/side-colored ones.

## `src/analysis/plotting.py` — minimal cluster visualization

`_CATEGORICAL_PALETTE` (10 hex tones - pink/azzurro/green/orange/purple/gold/teal/red-brown hue families) is CVD-safe on every **adjacent** pairwise combination (not all-pairs), verified with the `dataviz` skill's `scripts/validate_palette.js` (OKLab/Machado-CVD math and thresholds). `_palette_for_labels`/`_palette_for_categories` cycle through it past 10 clusters/categories (an inherent limit of a validated set, not a bug). `_NOISE_COLOR` (fixed neutral gray) is kept out of that cycle so it never impersonates a real cluster/category - used for HDBSCAN/OPTICS noise (label `-1`) and any categorical `missing_label`.

**Why 10 colors, validated adjacent-only**: HDBSCAN production runs on the s1.1-vol cohort routinely find 8-20 real clusters (excl. noise) at reasonable `min_cluster_size`/`min_samples`, which a 5-color set would cycle 2-4x, making `cluster_plot.png` hard to read. A 5-color set can be validated **all-pairs** (worst ΔE 8.6/18.3, both clear of the 8.0/15.0 gates) - a stronger, scatter-appropriate guarantee, since two clusters can sit next to each other anywhere on the plot, not just adjacent in a legend. The dataviz skill's own guidance is that an all-pairs-safe categorical caps at ~3-4 slots for a scatter/bubble/small-multiples chart regardless of palette size (the documented skill-default 8-color palette itself only clears all-pairs on its first 3 slots) - so no palette size actually solves 8-20 distinguishable clusters in one scatter; the real fix for that would be small multiples (one panel per cluster) or folding minor clusters into "Other". The 10-color, adjacent-only set is a deliberate best-effort middle ground instead (user decision) - better than 5, not a rigorous fix for >10 clusters, which still cycles.

`compose_run_title(output_dir, project) -> str`: builds every plot title (matplotlib `ax.set_title`/`fig.suptitle`, plotly `title`) from the run's own `output_dir` path instead of ad hoc per-script string concatenation - drops a leading `"results"` path segment and joins the rest with `" › "`, e.g. `results/lesion/dim_reduction/umap/21-07_s1_d01` -> `"clinical_connectome — lesion › dim_reduction › umap › 21-07_s1_d01"`. Motivation: `config.project` alone (always `"clinical_connectome"` today) never distinguished modality/session/tag, so two different runs of the same method would get identical titles - `output_dir` already encodes modality/pipeline/method/session/tag (`<dd-mm>_<session_name>[_<tag>]`, tag built from `params_reduction.json`/`params_clustering.json`'s `tag_param`/`tag_prefix` - parallel lists, one prefixed value per declared hyperparameter - see `src/analysis/params.py`, `docs/dev/config.md`), and it's the exact same `Path` every pipeline script already builds for `save_matrix`/logging - so the title can't drift out of sync with where the file actually lives, and needs no update if `results/` gets nested deeper later (e.g. the `results/<modality>/{dim_reduction,clustering}/` layout). Used only for `dim_reduction.py`'s own fine-tuning `tuning_plot.png` title (`_write_tuning_output`, `docs/dev/models.md`) - every other consumer uses a shorter, `_modality_title`-based composer below (`compose_cluster_plot_title`/`compose_embedding_plot_title`/`compose_clustering_tuning_title`), none of which repeat `output_dir`'s full path inside the title text. `clustering.py` uses `compose_cluster_plot_title` for its production `cluster_plot.png`/`silhouette_plot.png` and `compose_clustering_tuning_title` (below) for every tuning-mode plot, so `compose_run_title` is `dim_reduction.py`-only.

`compose_cluster_plot_title(output_dir, reduction_method, clustering_method) -> str`: `"<Modality> - <ReductionMethod> - <ClusteringMethod>"` (e.g. `"Lesions - Umap - Kmeans"`), each segment `str.capitalize()`d, except the acronym `ADP` (`_clustering_method_title`); the modality is `Lesions`, `SDC` for `sdc` (`_modality_title`). `compose_embedding_plot_title(output_dir, reduction_method, color_by=None) -> str` is the analogous title for `dim_reduction.py`'s own embedding scatters (no clustering method to name): `"Lesions - Umap"` for the single-color `embedding_plot_unico.png`, `"Lesions - Umap - Dataset"`/`"- Lesion volume"`/`"- Lesion side"` for the colored variants below (`dim_reduction.py` passes the mode's `label` capitalized; `replot_dim_reduction.py` passes it as is). Both need no `project` config value (unlike `compose_run_title`) - `src/pipeline/replot_dim_reduction.py` uses them too, deriving `reduction_method`/`clustering_method` from the run directory's own path segments instead of a config load.

`compose_clustering_tuning_title(output_dir, method) -> str`: `"<Modality> - Clustering Tuning - <Method>"` (e.g. `"Lesions - Clustering Tuning - Agglomerative"`, `"SDC - Clustering Tuning - Spectral"`) - the title for every plot `clustering.py`'s fine-tuning mode writes (`tuning_plot.png`, `dendrogram_metric=*.png`/`eigengap_affinity=*.png`/`interclass_distance_matrix.png`/`stability_plot.png` - all built from the one `title` `_write_tuning_output`/`_run_one_method_tuning` compute once). Unlike `compose_run_title` (which dumps `output_dir`'s full path, e.g. `"clinical_connectome — lesion › clustering › tuning › agglomerative › umap › 31-08_s1.1-vol_dice_n10"`), it does not repeat the path: a tuning run's own directory/`config.md` already carry `reduction_method`/`session_name`. The per-metric/per-affinity diagnostics append their own suffix on top (`f"{title} (metric={metric})"`/`f"{title} (affinity={affinity})"`), same convention.

`plot_clusters_2d(X_2d, cluster_labels, output_path, xlabel, ylabel, title, point_sizes=None)`: one function, a 2D scatter of `X_2d`'s first two columns colored by `cluster_labels`, saved to `output_path` - validated categorical palette (`_palette_for_labels`), legend anchored outside the axes, axis limits padded beyond the data's own min/max, bold/padded title. Raises `ValueError` if `X_2d` has fewer than 2 columns rather than producing a degenerate/empty plot. `plot_embedding_2d(X_2d, output_path, xlabel, ylabel, title)` is the single-color sibling for `dim_reduction.py`'s base `embedding_plot_unico.png` - same figure size/axis padding/bold-padded-title conventions, just no legend/palette (nothing to group by). `plot_embedding_categorical(X_2d, categories, output_path, xlabel, ylabel, title, legend_title, missing_label="unknown", category_order=None)` extends that same visual treatment to an arbitrary string category per point (`dataset`, `lesion_side`) via `_palette_for_categories` - a string-keyed sibling of `_palette_for_labels` where `missing_label` always gets the same neutral gray already reserved for cluster noise (`-1`), so a structurally-missing value (e.g. a dataset with no `lesion_side` column) never impersonates a real category. `plot_embedding_continuous(X_2d, values, output_path, xlabel, ylabel, title, colorbar_label, log_scale=False)` is the continuous-quantity sibling (`lesion_volume_voxels`, NIHSS, disconnection) - a `viridis` colormap + colorbar instead of a legend, same figure/axis conventions otherwise.

**`_MARKER_SIZE`/`_MARKER_ALPHA`/`_declutter_points` are shared across every static scatter function**: `plot_clusters_2d`/`plot_silhouette_analysis` use the same recipe as the embedding functions below, because HDBSCAN production plots (`cluster_plot.png`, 1150-5269 subjects, `min_cluster_size`/`min_samples` chosen deliberately loose enough to have many small clusters) are unreadable once overplotted: `_MARKER_SIZE=6` (matches `_EMBEDDING_MARKER_SIZE`, kept as a separate constant since it also derives `_POINT_SIZE_FLOOR`/`_POINT_SIZE_SCALE` for HDBSCAN's `point_sizes`), `_MARKER_ALPHA=0.9`, `_declutter_points` called once before scattering. `plot_silhouette_analysis`'s scatter panel declutters against its own subplot size (`_SILHOUETTE_SUBPLOT_WIDTH`, not the 2-panel-wide figure). `plot_clusters_2d`'s `point_sizes` branch (HDBSCAN membership-confidence sizing) doses the declutter against the base `_MARKER_SIZE` even though rendered sizes vary per point - same "not a precise spacing guarantee" tradeoff already documented for exact-duplicate pairs below, not worth a per-point-size-aware declutter.

`plot_embedding_2d`/`plot_embedding_categorical`/`plot_embedding_continuous` use their own `_EMBEDDING_MARKER_SIZE=6`/`_EMBEDDING_MARKER_ALPHA=0.9` (same values as `_MARKER_SIZE`/`_MARKER_ALPHA` above by construction, kept as separate constants) - `dim_reduction.py`'s production embedding plots run at ~5000+ subjects (the full lesion cohort, `26-08_s1.2-vol`), where opaque, larger markers overlap into one indistinguishable blob (the values were chosen by comparing candidate configs side by side on the real cohort). Alpha was tried much lower first (0.35) with no declutter, but with `_declutter_points` below doing the actual overlap-removal, only a light transparency touch (0.9) is needed on top - a heavier one made single-run plots look washed out without adding legibility once points aren't literally stacked any more.

**`_declutter_points(X_2d, xlim, ylim, figsize, marker_size) -> np.ndarray` (also used by `plot_clusters_2d`/`plot_silhouette_analysis`)**: called right before scattering, to push points that would literally overlap on screen apart - a second, complementary fix to the alpha/size change above, addressing "can we space points out instead of just making them transparent". Distance is computed in **screen pixels** (`figsize`/`_EMBEDDING_DPI`/`xlim`/`ylim` convert data units to pixels first), not raw data units - a first attempt at this used a percentile of the raw nearest-neighbor-distance distribution as the threshold and had **zero visible effect**, because the real problem is screen-space overplotting (thousands of points rendered into a ~1000-pixel-wide static PNG), not literal duplicate data coordinates; a "typical" data-space distance has no defined relationship to how many screen pixels a marker occupies. The dose is capped at `_DECLUTTER_MARKER_DIAMETERS=1.0` marker diameter deliberately, not more: visually compared at 1/2/3 diameters on the real cohort, zoomed into the densest core - 1 diameter stops literal marker-on-marker occlusion while leaving genuinely tight sub-clusters (e.g. one dataset's subjects sitting very close together in the embedding) visually intact; 2-3 diameters started dissolving those sub-clusters into the surrounding cloud, which would misrepresent how close those subjects actually are in UMAP space. **This is the one place in this file that moves a point's plotted position away from its real embedding coordinate** - unlike every other function here, which only changes how a point is rendered (color, size, alpha), never where. Runs `_DECLUTTER_ITERATIONS=3` passes (resolving one crowded pair can create a new one with a third point) of "push each still-crowded point away from its current nearest neighbor by the shortfall, scaled by `_DECLUTTER_STRENGTH=0.8`"; an exact-duplicate pair (0 pixel distance, no defined "away from" direction) is pushed apart in a random direction each (`_DECLUTTER_RANDOM_STATE=0`), which can end up separating the pair by up to ~2 marker diameters in the worst case (both kicked in opposite random directions) rather than exactly 1 - acceptable since exact duplicates are rare and the goal is "not fully overlapping," not a precise spacing guarantee. A single point (nothing can overlap with fewer than 2) is a documented no-op, not an error. `_EMBEDDING_DPI=150` must stay equal to the `dpi=` these 3 functions actually `savefig()` at, otherwise the declutter is dosed against a marker footprint that isn't the one actually rendered.

All three stay 2D-only - no static 3D counterpart exists anywhere in this module (an interactive, rotatable view is the only sane rendering of a 3D scatter - see `src.analysis.embedding_app`/`src.pipeline.embedding_app`, `docs/guides/embedding_app.md`, not a static file). Same reasoning applies to `plot_embedding_grid_blocks` below - and, more strictly than "stays 2D": a >2-component tuning combination gets **no** `embeddings_grid_*.png` cell at all, not even a refit-to-2D one (`dim_reduction.py::_build_grid_blocks` drops such a cell outright instead of calling `embedding_for_viz` on it - see `docs/dev/models.md`). `src/pipeline/plot_tuning_embedding_3d.py` is the one place a 3-component *tuning* combination actually gets rendered, in 3D, reusing `src.analysis.embedding_app.build_embedding_figure` (a pure function, no production-run concept baked in) directly on one `embeddings.npz` entry - see that script's own module docstring for why it's a separate small tool rather than an extension of either `embedding_app` (deliberately production-only, see that module's docstring) or `generate_understanding_umap_report` (deliberately a 2D grid across the whole sweep, not a single combo in 3D) - and why it's a manual, on-request tool rather than something either pipeline generates automatically for every leaf/color mode.

`plot_silhouette_analysis(sample_labels, sample_silhouette_values, X_2d, display_labels, output_path, xlabel, ylabel, title)`: the classic sklearn-style two-panel per-sample silhouette diagnostic, added on request as the production-time breakdown of the single aggregate number `compute_clustering_metrics`/`clustering_tuning.py` reports during fine-tuning (`docs/dev/models.md`) - a mean can hide one bad cluster averaged out by good ones. Left panel: one filled horizontal band per cluster (`ax.fill_betweenx`), each member's own coefficient sorted ascending within its band, colored via the same `_palette_for_labels` as the scatter, plus a dashed line at the mean (equals `compute_clustering_metrics`'s `"silhouette"` exactly). Right panel: the same 2D scatter as `plot_clusters_2d`. Takes two separate label arrays deliberately: `sample_labels`/`sample_silhouette_values` come from `clustering_tuning.compute_silhouette_samples` (noise already excluded there - undefined for a "cluster" that isn't one, so no band is drawn for it), while `display_labels` is the **full** vector including noise, so the scatter panel still shows where those points physically sit (grayed out). Raises `ValueError` on the same `< 2` columns case as `plot_clusters_2d`. Called by `clustering.py`'s `_run_one_method`, right after `plot_clusters_2d`, wrapped in `try/except ValueError` since `compute_silhouette_samples` can legitimately raise on a degenerate production result (e.g. a single cluster) - logged as a warning, doesn't fail the run, matching the same "warn and skip, don't crash" precedent as the `X_2d.shape[1] < 2` branch right above it.

**No per-run interactive embedding HTML**: the interactive view of a production embedding (with switchable coloring) is `src.pipeline.embedding_app` (a live Dash app, `docs/guides/embedding_app.md`), which reads any already-written production run directly and covers every color mode with no static file to keep in sync per run, plus real 2D/3D toggling (a 3-component embedding is rendered only there). `write_embedding_plots` (below) writes only static PNGs; a 3-component `embedding` makes it a no-op (still validates `zlabel` is given, still raises on other column counts, just renders nothing).

**No per-run interactive cluster HTML**: single-run interactive browsing (including cluster-colored production runs) is covered by `src.pipeline.embedding_app`, with no static file to keep in sync per run. `clustering.py`'s `_run_one_method` and `src/pipeline/replot_dim_reduction.py` write only `cluster_plot.png`.

**`dim_reduction.py` does not enrich `metadata.csv` itself.** A run's `metadata.csv` carries only what belongs to that run: `subject_id`, `dataset`, and `lesion_volume_voxels` (written once by `build_lesion_matrix.py`, `src/features/lesion.py`, valid only for a strictly binary `X` - it raises otherwise, since a parcellated `fraction_lesioned` matrix would silently produce a value that is neither a voxel count nor proportional to lesion volume in ml). The clinical per-subject fields (`lesion_side`, `NIHSS`) are **not** copied into it: they live once in the subject registry, `assets/metadata/participants.csv`, and are resolved there at plot time (see `color_values` below). A run therefore gets those colours whether or not any enrichment step was ever applied to it, including runs produced before the registry existed. `src/pipeline/replot_dim_reduction.py` still regenerates plots from `matrix.npy`/`metadata.csv` alone (only when the saved embedding has exactly 2 components, see above), without reloading the original feature matrix.

`lesion_side` and `NIHSS` are resolved from the subject registry (`assets/metadata/participants.csv`, via `src/utils/participants.py::load_participants_registry`), not from any per-run column. Written there once by `src/pipeline/enrich_metadata.py`; see `docs/dev/metadata.md` for how each value gets in and which datasets structurally lack which variable. On read, `color_values` turns an empty `lesion_side` cell into the `"unknown"` bucket and an empty `NIHSS` cell into `NaN` - a categorical mode's values are sorted as plain strings downstream, so a NaN there would raise `TypeError`, while a numeric quantity has no legitimate categorical "unknown" to plot into. A subject in the run with no registry row at all is treated the same way (missing value plus a warning), not as an error: for a colour, "absent from the registry" and "blank cell" are the same fact, and raising would make a whole run unplottable over a handful of subjects.


There is no cross-method comparison plot (no `plot_clusters_comparison*`, no `compose_comparison_title`): `clustering.py` produces no cross-method comparison artifact at all, not even for a single-method run (`docs/dev/models.md`, `docs/guides/clustering.md`). Comparing methods means opening each method's own `cluster_plot.png`, or `embedding_app.py` one run at a time.

One more, for fine-tuning sweeps (`tuning.py`, `docs/dev/models.md`): `plot_tuning_curve(df, param_col, metric_col, output_path, title)` - a line plot, for a 1-parameter `tuning_grid` with no `nested_params` declared (PCA's `n_components`, PaCMAP's `n_neighbors`). `dim_reduction.py` only uses it for that undeclared-1-parameter case; with no `nested_params` and 2+ swept parameters it still gets no plot at all - a WARNING is logged, `tuning_results.csv` is still written either way. When `nested_params` **is** declared (umap/tsne), `plot_tuning_curve` isn't used at all - `plot_embedding_grid_blocks` below takes over instead, one call per leaf subfolder. The clustering-tuning plots below are distinct functions, unaffected by any of this.

More, for `clustering.py`'s fine-tuning mode (`clustering_tuning.py`, `docs/dev/models.md`). `_write_tuning_output` chooses the main plot per method and number of swept parameters:

- `plot_clustering_tuning_metrics(df, param_col, metric_cols, output_path, title, log_x=False)`: one line-plot subplot per metric in `metric_cols`, all sharing `param_col` on the x-axis (`log_x` for `adp`'s `Z`, swept over orders of magnitude); unlike `plot_tuning_curve` (always exactly one metric), silhouette/Calinski-Harabasz/Davies-Bouldin/method-specific extras live on incomparable scales, so overlaying them on one shared axis would mislead. Used for exactly 1 swept parameter (kmeans).
- `plot_clustering_tuning_heatmaps(df, param_x, param_y, metric_cols, output_path, title)`: the 2-parameter analogue, one heatmap subplot per metric. Used for exactly 2 swept parameters (gmm, hdbscan) and, for `hdbscan_soft`, once per `cluster_selection_method` value (`tuning_plot_cluster_selection_method=<value>.png`, `min_cluster_size` x `min_samples` inside).
- `plot_grouped_tuning_metrics(df, x_param, group_param, metric_cols, output_path, title, log_x=False)`: one subplot per metric, `x_param` on the x-axis, one line per value of `group_param`. Used for `adp` swept over `metric` and `Z` (one line per metric, `Z` on a log x-axis: a heatmap of 2 metrics x 18 `Z` would be unreadable).
- `plot_spectral_tuning(df, param_col, metric_cols, output_path, title)`: spectral with an `affinity` axis - builds one label per `(affinity, n_neighbors/gamma)` and delegates to `plot_grouped_tuning_metrics`.
- Any other number of swept parameters (e.g. agglomerative's `n_clusters` x `linkage` x `metric`): no metric plot, a WARNING is logged; `tuning_results.csv` always has every combination.

`plot_stability_analysis(df, target_param, nuisance_param, metric_col, output_path, title)` and `plot_interclass_distance_matrix(results_by_metric, output_path, title)` are the kmeans/gmm stability diagnostic (one panel per target value, mean ± std of the metric against `n_init`, one line per init) and the agglomerative interclass distance matrix (one heatmap per metric, `docs/dev/models.md`). The 2 standalone-diagnostic plots each wrap a scipy/numpy computation from `clustering_tuning.py` with no logic of their own, laid out as a subplot grid rather than one file per value (same "one file per outer value, one subplot per inner value" shape as `plot_interclass_distance_matrix`): `plot_dendrograms_grid(linkage_matrices_by_linkage, output_path, title, truncate_last_p=30)` (`scipy.cluster.hierarchy.dendrogram` per subplot, `truncate_mode="lastp"` since a full tree over hundreds/thousands of subjects is unreadable), `plot_eigengaps_grid(eigenvalues_by_label, output_path, title)` (marks each subplot's single biggest gap between consecutive eigenvalues via `np.argmax(np.diff(eigenvalues))`, raises `ValueError` on an empty dict or fewer than 2 eigenvalues in any entry). HDBSCAN has no standalone diagnostic (no k-distance plot): it has no single `eps` to read off a plot by eye.

`compose_tuning_leaf_title(output_dir, reduction_method, leaf) -> str` titles one nested-tuning leaf's `embeddings_grid_*.png`: `"<Modality> - <ReductionMethod> - <Metric> - <N> Components"`, only the keys present in `leaf` (t-SNE's leaf has no `n_components`).

**Subplot spacing, all 3 side-by-side grids**: `plot_interclass_distance_matrix` uses `wspace=1.1` (plus `pad=0.04` on each subplot's own colorbar) because real dataset-name labels (`"UKLFR/stroke_UKLFR"`) overlap the previous subplot's colorbar at smaller values - each subplot draws its own y-tick labels (not shared with its neighbor's), so the gap has to fit one subplot's colorbar *and* the next subplot's label text, not just the two axes. `plot_dendrograms_grid`/`plot_eigengaps_grid` use an explicit `wspace=0.35` (matplotlib's default ~0.2 is tight for them) - the same "always a deliberate value here, never the default" convention.

## Naming dei file di plot

Ogni file di plot vive dentro la directory della sua run, che porta già metodo, sessione e iperparametri (`03-09_s1.2-vol_m_euclidean_n2_k5`). Il **nome del file identifica quindi solo cosa mostra**, non la run: non va ripetuto lì ciò che il path dice già.

Tre forme, in ordine di specificità. Un plot nuovo deve rientrare in una di queste.

| Forma | Quando | Esempi |
| :--- | :--- | :--- |
| `<cosa>.png` | c'è un solo file di quel tipo per run | `cluster_plot.png`, `silhouette_plot.png`, `tuning_plot.png`, `stability_plot.png`, `interclass_distance_matrix.png` |
| `<cosa>_<variante>.png` | un file per variante di una dimensione **chiusa e nota** (i color mode di `COLOR_MODES`) | `embedding_plot_side.png`, `embeddings_grid_nihss.png` |
| `<cosa>_<parametro>=<valore>.png` | un file per valore di un iperparametro **spazzato dalla run** | `dendrogram_metric=cosine.png`, `eigengap_affinity=rbf.png` |

Note sulle scelte, per non rimetterle in discussione ogni volta:

- **`=` nel nome è deliberato**, non una svista. Segnala che il segmento è una coppia parametro/valore proveniente dalla griglia di tuning, e non un pezzo fisso del nome: `dendrogram_metric=cosine` si legge senza ambiguità, `dendrogram_cosine` no. Sono nati così quando dendrogramma ed eigengap sono passati da un file unico a uno per valore dell'asse spazzato (`.claude/lessons_learned.md` #31).
- **Singolare vs plurale è informativo**: `embedding_plot_*` è un singolo embedding (produzione), `embeddings_grid_*` è una griglia di embedding (tuning). Non sono due nomi per la stessa cosa.
- **Il suffisso non è uniforme** (`_plot` oppure niente) e resta così: ogni nome è già inequivocabile dentro la sua directory, e uniformarlo significherebbe rinominare artefatti referenziati da decine di file tra doc, test e risultati già prodotti — costo reale, guadagno nullo. La regola per i nomi **nuovi** è: usare `_plot` solo quando il nome da solo non direbbe che è un'immagine (`cluster` → `cluster_plot`), ometterlo quando lo dice già (`dendrogram`).

## `src/analysis/embedding_coloring.py` / `embedding_plots.py` — pluggable embedding coloring

A small registry plus a shared writer, so adding a new coloring mode is one dict entry, not a new hand-written block - and the same writer is used by both `dim_reduction.py`'s production and fine-tuning (`nested_params`) output.

`embedding_coloring.py`: `COLOR_MODES: dict[str, ColorMode]` - `ColorMode(kind, column, label, description, registry_column=None, log_scale=False, restricted_to_modality=None, categories=None)`, `kind` is `"categorical"` (legend, `plot_embedding_categorical`) or `"continuous"` (colorbar, `plot_embedding_continuous`), `column` is the `metadata.csv` column of the run for that mode, `registry_column` the `assets/metadata/participants.csv` column holding the same fact for the subject, `description` the Italian sentence the app shows above the plot. The registered modes are `dataset`, `side` (`lesion_side`), `location` (`location_dominant_2mm`, closed vocabulary), `volume`, `disconnection_load` and `disconnection_mean` (these two `restricted_to_modality="sdc"`), `nihss` and `cluster_label`; `volume`, `disconnection_load` and `disconnection_mean` are "grid modes" (`2mm`/`1mm` column, `grid_column`, `available_grids`). `color_values(metadata, mode_name)` is the one place every consumer (`embedding_plots.py`, `embedding_app.py`) actually reads a mode's values. Resolution order: a mode declaring a `registry_column` is read from `assets/metadata/participants.csv` by `subject_id` (the registry wins over any copy of that column in the run's own `metadata.csv`, which can be stale and, for volume, is counted on whatever grid that run's matrix used); a mode without one (`dataset`, `cluster_label`) is read from the run's `metadata.csv`. A mode resolvable from neither raises `ValueError` (a registry column not yet populated by `enrich_metadata.py`, or `cluster_label` on a `dim_reduction.py` run). Missing registry values - an empty cell, or a subject with no registry row at all (logged once as a warning) - become the explicit `"unknown"` bucket for categorical modes (their values get sorted as plain strings downstream, so a NaN would raise `TypeError`) and `NaN` for continuous ones. `resolve_color_mode(name) -> ColorMode` raises `ValueError` (with the known-modes list) for an unregistered name, rather than a raw `KeyError`. "Single color" (`_unico`) is not a registry entry - it's the always-generated base case, never listed in a `color_by` config.

**One persisted source per mode**: a color mode has no `compute` callable and no separate persisted-column mapping. Two parallel mechanisms (a live recomputation for the writers, a persisted column for `embedding_app`) could not be checked against each other, and a recomputation like `X.sum(axis=1)` for `"volume"` has no guard against a parcellated (continuous, non-binary) `X`, silently producing a meaningless number, while the persisted `lesion_volume_voxels` column in the same `metadata.csv` is already correct. Every mode reads its own value from a persisted place, never recomputed from `X` - `X` is not needed by any color mode at all, since dataset/side/volume/nihss/cluster are all facts already resolved once upstream (`build_lesion_matrix.py` for the run-level ones, `src/pipeline/enrich_metadata.py` for the subject-level clinical ones).

**Closed vocabularies (`ColorMode.categories`, categorical only)**: a mode whose values are a fixed list (`location`: the seven lesion-location categories) declares it, and every renderer then colours a label by its position in that list, not by its position among the labels a given plot contains - `_palette_for_categories(..., category_order=...)` in `plotting.py`, the one palette function, shared by `plot_embedding_categorical`, `plot_embedding_grid_blocks` and `embedding_app.build_embedding_figure`. Without it a rare label missing from a run (a small cohort with no `cortex_white_boundary`) would shift the colour of every label after it, so the same category would change colour from run to run. `_ordered_categories` gives the legend order (list order, `"unknown"` last, always the neutral grey); a value outside the list raises in `color_values` and in both helpers rather than being drawn in whichever colour is left. Modes without `categories` (`dataset`, `side`) stay open: sorted, coloured by position among the present labels. `embedding_coloring.py` repeats the lesion-location list instead of importing it (it stays free of the imaging stack); `tests/unit/test_embedding_coloring.py` pins the two copies together.

**`plot_hdbscan_grid(grid, output_path, suptitle)`**: one scatter subplot per cell of a list-of-rows grid (`None` = empty cell), each cell `(title, embedding_2d, cluster_labels)`. The embedding drawn need not be the space the clusters were found in (`src/analysis/tuning_evaluations.py` passes the 2D twin of a higher-dimensional fit). Noise keeps `_NOISE_COLOR`, clusters the validated palette; colors are per subplot because HDBSCAN numbers clusters arbitrarily. Constrained layout with fixed padding keeps title, subplot titles and axes apart whatever the number of title lines; each cell autoscales to its own embedding.

**`log_scale` (per-mode flag, continuous only)**: `"volume"` is the only mode with `log_scale=True` today. Lesion volume is heavily right-skewed (1 to ~40000 voxels on the real 1150-subject cohort) - on a linear color scale, a handful of large-lesion outliers stretch the range so far that almost every other point renders the same dark color, no usable gradient. `"nihss"` stays linear (`log_scale=False`, the default) - deliberately, so the two modes keep the *same* palette (`viridis`, both) and are told apart by their color's actual spread/shape rather than by a second hue family. `resolve_color_mode(...).log_scale` is threaded through by both `write_embedding_plots`/`write_embedding_grid` (below) into `plot_embedding_continuous`/`plot_embedding_grid_blocks`'s own `log_scale` param - a `matplotlib.colors.LogNorm` fit to the non-missing values instead of the default linear normalization. Raises `ValueError` if any non-missing value is `<= 0` (LogNorm can't represent it, and matplotlib's own silent behavior - masking it out, i.e. treating it as "missing" - would misrepresent a genuine zero-volume subject as if its value were unresolvable, the same bucket as a genuinely missing `NIHSS`). `src.analysis.embedding_app`'s own figure builder threads `log_scale` through too (see `docs/guides/embedding_app.md`): plotly express has no direct `LogNorm`-equivalent color axis, so `embedding_app` log-transforms the values itself and relabels the colorbar ticks back to real units.

`plot_embedding_continuous`'s NaN handling (relevant to every registry-resolved continuous mode, e.g. `"nihss"`, whose gaps are dataset-wide): a `NaN` point is drawn in the same fixed neutral gray as the categorical plots' missing/noise bucket (`_NOISE_COLOR`), underneath the colored points, with a small "missing" legend entry - not left to matplotlib's own default (a fully transparent, invisible marker with no visual sign anything is missing). The colorbar's range is fit to the non-`NaN` values only, so a handful of missing subjects never compresses the color scale for everyone else. `plot_embedding_grid_blocks`'s continuous branch applies the exact same NaN treatment, so a missing subject in a tuning grid never falls back to matplotlib's default invisible-transparent-point behavior with no legend entry.

**Colorbar of `plot_embedding_grid_blocks`'s continuous branch**: the first cell's `scatter` return value (`continuous_mappable`) and every cell's `Axes` (`data_axes`) are captured, then `fig.colorbar(continuous_mappable, ax=data_axes, label=legend_title, shrink=0.6)` is called once after the main loop - same "take it from the first cell only" convention already used for the categorical branch's shared legend.

`embedding_plots.py` has two writers, both wrapping every color-mode's static PNG in its own `try/except Exception` + `logging.warning` (one bad coloring, e.g. a dataset with no resolvable `participants.tsv` for `lesion_side`, must not abort the whole run):
- `write_embedding_plots(embedding, metadata, color_by, output_dir, xlabel, ylabel, title_fn, zlabel=None, file_prefix="embedding_plot")`: the single-embedding case (production). `embedding` must have exactly 2 or 3 columns (raises otherwise) - with 3, this is a no-op (see the note on interactive views above: no static rendering exists for a 3-component embedding in this module, only the live `embedding_app`). Writes `<file_prefix>_<name>.png` per mode in `color_by` that computed successfully (each independently try/except'd).
- `write_embedding_grid(blocks, metadata, color_by, output_dir, xlabel, ylabel, title_fn, file_prefix="embeddings_grid")`: the tuning-leaf case. `blocks: list[tuple[str, list[tuple[str, np.ndarray]]]]` (block title + `[(cell title, embedding), ...]`) is built by the *caller* (`dim_reduction.py`'s `_build_grid_blocks`, `docs/dev/models.md`) - this function only decides which color to render each block set in, calling `plotting.plot_embedding_grid_blocks` once per color (always for `_unico`, plus once per `color_by` entry).

`plotting.plot_embedding_grid_blocks(blocks, output_path, xlabel, ylabel, suptitle, color_values=None, color_kind=None, legend_title=None, log_scale=False, category_order=None)`: one row of small scatter subplots per block (real embeddings, not a numeric curve - the point is seeing how the point cloud's *shape* changes with a swept parameter, not just how one score moves), a dedicated label row above each block's scatter row, and a blank spacer row between blocks (a `matplotlib.gridspec` layout, not just subplot padding) - real whitespace, so multiple blocks in one figure read as visually distinct sections. All cells share one x/y axis range (padded beyond every embedding's combined min/max) and one legend/colorbar (taken from the first cell only - every cell is a fit of the same subjects, so per-cell legends would be redundant).

## `src/analysis/component_map_plots.py`

`build_reproducibility_figure(reproducibility, selected) -> go.Figure` draws the bar chart of the "Mappe delle componenti" panel of the Embedding Explorer (`docs/guides/embedding_app.md`, numbers in `docs/dev/covariance_pca.md`): one bar per component with the correlation across voxels between its two maps from two random halves of the subjects, the `selected` component (1-based) darker, a dashed line at `PAPER_REPRODUCIBILITY` (0.813, the mean reported by Thiebaut de Schotten et al. 2020, from halves of 666 subjects; the halves here are larger, so it is a reference and not a target). It is a plotly figure, not matplotlib. Raises `ValueError` for an empty `reproducibility` or a `selected` outside `1..n`.

## Figure dei notebook di lettura di un tuning

Le figure di `dendrogram_embedding_explorer` (`notebooks/post-results_analysis/`) sono disegnate nel notebook con matplotlib e nilearn, non da `plotting.py`, e non usano `_CATEGORICAL_PALETTE`. Convenzioni (uso dei notebook: `docs/guides/evaluate_clustering_tuning.md`):

**`dendrogram_embedding_explorer`, prima figura (albero + embedding), una per k**

- **Un colore per cluster, uguale nei due pannelli.** L'embedding ha esattamente k colori e le foglie dell'albero hanno il colore del cluster a cui appartengono. La palette è un elenco fisso di 20 tinte: le prime 10 sono quelle di `tab10` di matplotlib, le più distinguibili; le altre servono solo oltre k = 10. Per questo `LAST_P` (le foglie dell'albero, quindi i colori) non supera 20.
- **Il colore del cluster grande si segue da un k al successivo.** Quando un cluster si divide, il pezzo più grande tiene il suo colore e il più piccolo ne prende uno nuovo.
- **Nomi per foglie.** Le foglie sono numerate da sinistra a destra (`L1`, `L2`, ...) con il numero di soggetti sull'asse x, e un cluster si chiama con le foglie che contiene (`L5–L6`). Le foglie restano le stesse a ogni k, mentre le etichette numeriche del clustering (0, 1, 2...) cambiano: il nome per foglie è l'unico che si segue da una figura alla successiva.
- **Legenda e nomi nell'embedding.** La legenda ha una voce per cluster (nome e numero di soggetti) e segna "nuovo" i due nati dall'ultima divisione; nell'embedding il nome di ogni cluster è scritto sulla mediana dei suoi punti, in grassetto per i due nuovi.
- **Linea del taglio.** Rossa tratteggiata, a metà tra l'altezza dell'ultima fusione tenuta e quella della prima scartata.

**`dendrogram_embedding_explorer`, seconda figura (mappa anatomica)**: sfondo nero, una riga per ciascuno dei due figli, tre sezioni dal rosso al giallo con colorbar; la scala è propria di ogni mappa (calcolo in `docs/dev/anatomical_maps.md`).
