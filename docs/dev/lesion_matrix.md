# Lesion feature matrix — technical reference

Audience: developers/agents working on `src/features/lesion.py`, `src/analysis/build_config.py` (the `build_lesion_matrix.json`-parsing half), and `src/pipeline/build_lesion_matrix.py`.

This file covers turning retrieved lesion masks into a feature matrix ready for dimensionality reduction. For the models that consume that matrix, see `docs/dev/models.md`. For the equivalent FC pipeline, see `docs/dev/fc_matrix.md`. For "how do I run this", see `docs/guides/matrix_building.md`. For **which** interpolation to resample masks with and why (and which cohorts are actually resampled), see `knowledge/neuroimaging/lesion_resampling.md`.

**Found while writing the real configs**: `lesion_glob` in every doc/config up to this point (inherited from `notebooks/lesion_analysis.ipynb`/the handoff note) was `"*/lesion/mni/*_label-lesion_mask.nii.gz"` - checked against real retrieved data in `data/clinical_connectome/` and found wrong: the actual local layout (from `src/retrieval/output_layout.py`, post-BIDS-refactor) is `<subject>/lesion/manual_masks/anat/<subject>_space-MNI152NLin6Asym_label-lesion_mask.nii.gz`. Fixed to `"*/lesion/manual_masks/anat/*_label-lesion_mask.nii.gz"` in the real `config/pipelines/build_lesion_matrix.json` - confirmed against all 4 datasets in scope at the time (`find` count of subject dirs vs. matching lesion files: WashU 202/202, PASPORT 83/83, PSP 168/168, UKLFR 697/697, all equal).

**Parcellation removed (25/08/26)**: an earlier version of this module also supported an atlas-parcellated output shape (`parcellate: true` - each subject's feature vector was the proportion of damage per atlas region, the characterisation Thiebaut de Schotten et al. 2020 use ahead of their varimax-rotated PCA), built via `src/pipeline/build_combined_atlas.py`/`src/atlases/` (a Glasser MMP + Harvard-Oxford subcortical combined atlas). Both were removed as a project decision - the parcellation-then-varimax-PCA replication this fed is no longer pursued through this pipeline (see `management/notes/TODO.md`). Voxel-wise is now the only output shape `build_lesion_matrix()` produces.

## `src/features/lesion.py` — lesion feature matrix

`build_lesion_matrix(data_root, datasets, reference_template_path, lesion_glob, binarize_threshold, resample_interpolation, group_filter, min_lesion_volume_voxels, max_out_of_brain_fraction, brain_mask_path) -> (X, metadata, non_constant_mask, excluded_by_group, excluded_by_min_volume, excluded_by_out_of_brain)`

**`group_filter`** restricts subject discovery to specific naming-derived groups (`src.retrieval.dataset.group_of` - ST/HC/PD/GM), via the shared `src/features/subject_discovery.py::discover_files_by_subject` also used by `src/features/functional.py` (`docs/dev/fc_matrix.md`). `None` means no restriction. Subjects excluded this way are returned separately as `excluded_by_group`, never conflated with a genuine missing-file gap - see `debug_27_07_26.md` and `docs/guides/matrix_building.md`.

### Lesion-quality thresholds (`min_lesion_volume_voxels`, `max_out_of_brain_fraction`)

Two independent, optional subject-admission filters, applied after discovery/`group_filter` but before `_drop_constant_features` (`_filter_by_lesion_quality`, called from `build_lesion_matrix`) - each `None` disables the corresponding check entirely (no default threshold is ever applied silently):

- **`min_lesion_volume_voxels`**: a subject is kept iff `lesion_volume_voxels >= min_lesion_volume_voxels`. Uses *this run's own* `lesion_volume_voxels` (already computed by `_voxelwise_matrix_with_volume` from the run's own resampled/binarized voxel data), not `assets/metadata/participants.csv`'s column of the same name - that registry value may come from a different run's grid/`binarize_threshold` and would be self-inconsistent to filter against here.
- **`max_out_of_brain_fraction`**: a subject is kept iff `out_of_brain_fraction <= max_out_of_brain_fraction`, where `out_of_brain_fraction` is the fraction of that subject's own (resampled, binarized) lesion voxels falling outside `brain_mask_path` (same reference grid as `reference_template_path`; a checked-in MNI152 brain mask ships under `assets/templates/tpl-MNI152NLin6Asym_res-{1,2}_desc-brain_mask.nii.gz`, matching the two `_T1w` reference templates already used for `reference_template_path`). Conceptually the same check `scripts/lesion_fix.py` performs (that script *corrects* a mask by zeroing the offending voxels; this one only measures the fraction, to decide admission). A subject with 0 lesion voxels (a legitimate per-subject case, see `_voxelwise_matrix_with_volume`) gets `out_of_brain_fraction = 0.0` by explicit convention (vacuously true), never `NaN` - always safe to threshold. `metadata` gains an `out_of_brain_fraction` column only when this threshold is active (computing it costs one extra brain-mask load/resample, skipped entirely when unused).
- **`brain_mask_path`** is read from the config whenever present, independent of `max_out_of_brain_fraction` (`src/analysis/build_config.py`) - **required** only when `max_out_of_brain_fraction` is set (config-load raises otherwise), but stays available even when it's `None`. Deliberately *not* the same "forced to `None` outside its own branch" convention as `SdcMatrixConfig`'s representation-specific fields: `scripts/check_lesion_quality.py` reads this same field to compute `out_of_brain_fraction` for every subject regardless of whether `build_lesion_matrix.py`'s own filter is active - that script is exactly how a real `max_out_of_brain_fraction` value gets picked in the first place, so forcing the field to `None` here would make it unreachable until after the threshold decision it's meant to inform (found the hard way: the field is `None` in production, since `max_out_of_brain_fraction` starts `null` by design - the first real run of `check_lesion_quality.py` failed until this was fixed).
- Both thresholds are computed on the full pre-constant-drop voxel grid (`X_voxelwise`), since `out_of_brain_fraction` needs each column at its real spatial position - `_drop_constant_features` runs strictly after filtering, on the *final* admitted subject set, so which columns end up constant reflects who actually survived, not the pre-filter population.
- Excluded subjects are returned as `excluded_by_min_volume`/`excluded_by_out_of_brain` (each empty when its threshold is `None`) - never conflated with `excluded_by_group`, and persisted to `config.md`/the report exactly like it (`src/pipeline/build_lesion_matrix.py`'s `_summary_lines`).
- If every subject is filtered out by these thresholds, `build_lesion_matrix` raises `ValueError` rather than proceeding with an empty matrix.
- **Not implemented for `build_sdc_matrix.py`** (project decision, 28-09-26): both metrics are lesion-mask-derived, and `src/features/sdc.py` deliberately never loads a raw lesion mask (see `docs/dev/sdc_matrix.md`, "Why participants.tsv, not manual_masks/ on disk") - adding these checks there would mean either reintroducing that already-fixed risk (globbing `manual_masks/` directly) or precomputing the metrics into the registry first, neither of which is currently in scope.
- **Immutable once built**: these thresholds only take effect for a run that hasn't happened yet - an already-built `data/derived/lesion_matrix/<session>/` is never filtered in place (would corrupt the reproducibility of every downstream analysis that already read it). Forgetting to set a threshold before a run means deleting that run's output directory and its `runs.csv` row, then rebuilding - not patching the existing matrix/metadata.csv.

### `compute_lesion_volumes` / `compute_lesion_quality_metrics` — the same core, two thin public wrappers

Both share `_voxelwise_matrix_with_volume` (discovery/resampling/binarization, same as `build_lesion_matrix`) so their numbers are directly comparable to what `min_lesion_volume_voxels`/`max_out_of_brain_fraction` would filter on - no admission applied, every subject discovered under `data_root`/`datasets` (after `group_filter`) is reported:

- **`compute_lesion_volumes(data_root, datasets, reference_template_path, lesion_glob, binarize_threshold, resample_interpolation, group_filter) -> (metadata, excluded_by_group)`** - `lesion_volume_voxels` only, no `brain_mask_path` needed (cheaper: skips the brain-mask load/resample entirely). The single computation `src/pipeline/enrich_metadata.py` relies on for `assets/metadata/participants.csv`'s `lesion_volume_voxels` column (via `config.lesion_volume_config`, a `build_lesion_matrix.json`-shaped config) - see `docs/dev/metadata.md`.
- **`compute_lesion_quality_metrics(data_root, datasets, reference_template_path, lesion_glob, binarize_threshold, resample_interpolation, group_filter, brain_mask_path) -> (metadata, excluded_by_group)`** - `out_of_brain_fraction` only (no `lesion_volume_voxels` - computed internally as a byproduct of discovery, but dropped before returning: `assets/metadata/participants.csv` is the one place to get volume, never a second copy here). `out_of_brain_fraction` is always present, unlike `build_lesion_matrix`'s conditional column.

Two consumers reuse `compute_lesion_quality_metrics`, both meant to avoid re-paying the expensive per-subject nibabel load + resample (minutes over the full ~5700-subject cohort) on every invocation - each caches the result to a CSV and only recomputes when told to:

- **`scripts/check_lesion_quality.py`** - CLI entry point, `python scripts/check_lesion_quality.py --config config/pipelines/build_lesion_matrix.json` (reuses that same config file - `load_build_matrix_config`, `data_root`/`datasets`/`reference_template_path`/`lesion_glob`/`binarize_threshold`/`resample_interpolation`/`group_filter`/`brain_mask_path` - rather than a second, drift-prone config shape). Writes `assets/metadata/lesion_quality_metrics.csv` (`subject_id`, `dataset`, `out_of_brain_fraction` - no volume column, see above; default path, overridable via `--output-path`) atomically (temp file + `os.replace`, same convention as `scripts/populate_metadata.py::write_table`). `--overwrite` forces a recompute; without it, an existing output file makes the run exit immediately (`0`, informational log only) - safe to invoke repeatedly (e.g. before every notebook session) without cost. Also writes a `summaries/check_lesion_quality/`/`logs/check_lesion_quality/` report/log pair, same shape as every other pipeline entry point.
- **`notebooks/exploration/dataset_exploration.ipynb`**'s "Lesione fuori dal brain" section - same load-or-compute-and-cache pattern against the same CSV path, driven by a notebook-local `OVERWRITE_LESION_QUALITY` toggle. Previously used its own copy-pasted logic against `nilearn.datasets.load_mni152_brain_mask()` (an internet-fetched generic MNI mask); now imports `compute_lesion_quality_metrics` directly and uses the same `assets/templates/tpl-MNI152NLin6Asym_res-*_desc-brain_mask.nii.gz` resolution as `config/pipelines/build_lesion_matrix.json`'s `reference_template_path`/`brain_mask_path` (both hardcoded to the same `res-` suffix as the notebook, kept in sync by hand when that config changes), so the notebook's numbers and the production pipeline's numbers are computed by the identical, tested code path. For volume, this section joins against `participants_lesion["lesion_volume_voxels"]` (already loaded from `participants.csv` earlier in the notebook, for the "Volume della lesione" subsection) rather than recomputing it.

`assets/metadata/lesion_quality_metrics.csv` is a diagnostic cache, not a registry column - `assets/metadata/participants.csv` is the single place for `lesion_volume_voxels` (found 28-09-26: keeping a second, independently computed copy here had already drifted from it by up to 38x for some subjects, before this was fixed - see `.claude/history/methods_changelog.md` and `docs/dev/metadata.md`).

Migrated from `notebooks/lesion_analysis.ipynb` (voxel-wise path, cells 4-8): same algorithm, restructured into typed, independently testable functions. The notebook is left as-is as the exploratory reference — this module is the version pipeline code actually calls.

**`reference_template_path` is an explicit, caller-supplied file, not derived from `datasets`** — changed from the original "pick the first lesion file of `reference_dataset` (sorted)" behavior, on request: that implicit choice silently tied the common voxel grid to whatever resolution one arbitrary subject's file happened to have, with no guarantee it matched a canonical space (e.g. MNI152 2mm) rather than just *a* space with the same name. `load_reference_image(reference_template_path) -> nib.Nifti1Image` now does exactly one thing - load that file, raising `FileNotFoundError` with a clear message if it's missing.

**Resolved 23-09-26**: production's `reference_template_path` (`config/pipelines/build_lesion_matrix.json`, likewise `build_sdc_matrix.json` for the voxelwise SDC representation) now points at a real, versioned MNI152NLin6Asym template under `assets/templates/` (`tpl-MNI152NLin6Asym_res-1_T1w.nii.gz`/`_res-2_T1w.nii.gz`, from TemplateFlow, verified shape/affine against project data), not a specific patient's lesion mask. `load_reference_image`/`resample_to_img` only ever read shape+affine, never pixel content, so a T1w structural image works identically to a binary mask as the grid reference - no code change needed, only the config path. Both resolutions are shipped; which one a pipeline uses is a plain config edit (`reference_template_path` pointing at the `_res-1_`/`_res-2_` file), not a code change.

The fragility this replaces: the previous reference, `sub-STUNIPD0001`'s own lesion mask under gitignored `data/`, silently changed grid (2mm → 1mm) on 23-09-26 when that subject's file was replaced during an unrelated dataset refresh - exactly the risk this section used to flag as open. Existing, already-built lesion matrices are unaffected (their voxel grid was fixed at build time); only new runs pick up whichever template the config now names.

Each subject is a flattened binarized lesion volume, resampled onto `reference_template_path`'s grid when its native resolution differs. `_drop_constant_features` then drops columns (voxels) that are identical across every subject - they carry no information for downstream PCA/UMAP/clustering. `non_constant_mask` records which columns survived (against the pre-drop feature count) so the mask can be reapplied to related data (e.g. re-running with a different subject selection).

`_discover_lesion_files(data_root, datasets, lesion_glob, group_filter)` derives the subject-folder glob from `lesion_glob` itself (the last bare `"*"` path segment) rather than assuming subject folders are `dataset_root`'s immediate children (true only under the older subject-first retrieval layout, see `docs/dev/retrieval.md`) - works for either local layout without hardcoding one. Raises `FileNotFoundError` if the subject-folder glob itself finds nothing (an unreachable dataset - wrong path/name in config, or never retrieved) before `group_filter` narrows the list, since `Path.glob` on a missing directory returns `[]` with no exception and a typo'd dataset name would otherwise silently contribute 0 subjects rather than fail loudly. `group_of()` validates every discovered subject-dir name unconditionally, not only when `group_filter` is set (`lessons_learned.md` #4/#28) - skipping that check for the common "this dataset doesn't mix groups" case let a malformed folder name through silently instead of raising.

`load_reference_image(reference_template_path)` requires an explicit, caller-supplied file rather than deriving one implicitly (e.g. "the first lesion file found") - see above for the known, still-open gap in what that file currently points to in production.

### Validation

`binarize_threshold`/`resample_interpolation` are cross-validated at the config layer (`src/analysis/build_config.py`) before `build_lesion_matrix()` is ever called - see below.

## `src/analysis/build_config.py` — `build_lesion_matrix.json` parsing

`load_build_matrix_config(path) -> BuildMatrixConfig`, same shape and style as `src/retrieval/config.py`'s `load_config`: hand-written `_require_*`/`_optional_*` helpers (own copy, not shared with `src/retrieval/config.py` — each is a handful of lines, premature to abstract per the handoff note's explicit deferral), every field validated upfront so a malformed config is rejected before any file is touched.

Two upfront value-domain checks, beyond type checking, both deliberate (config validation is a system boundary — `code_standards.md` §0):

- **`binarize_threshold`** must be in `[0.0, 1.0]`. Lesion mask values after resampling are nominally binary/interpolated-to-[0,1]; a threshold outside that range produces a *silently degenerate* result (every voxel above or below threshold for every subject) that only surfaces much later, as an empty/collapsed feature matrix after `_drop_constant_features` — far from where the bad config value was set.
- **`resample_interpolation`** must be one of `{"linear", "nearest", "continuous"}` — the exact set `nilearn.image.resample_to_img` accepts. This is the validation rationale only — the *domain* rationale for picking `"nearest"` (discrete/binary data) over `"linear"`/`"continuous"` (continuous fields), and its interaction with `binarize_threshold` (a no-op under `"nearest"`), is in `knowledge/neuroimaging/lesion_resampling.md`. Without this check, a typo here (e.g. `"neareast"`) only surfaces when `resample_to_img` is actually called on a subject whose native resolution differs from the reference grid — potentially after a long run has already processed hundreds of subjects with matching resolution.
- **`min_lesion_volume_voxels`** (optional, `None`/absent = disabled) must be a non-negative integer. **`max_out_of_brain_fraction`** (optional, same default) must be in `[0.0, 1.0]`, same range rationale as `binarize_threshold`. **`brain_mask_path`** is required (a non-empty string) exactly when `max_out_of_brain_fraction` is set - but unlike `SdcMatrixConfig`'s representation-specific fields, it stays *readable* (not forced to `None`) even when unused by `build_lesion_matrix.py` itself, since `scripts/check_lesion_quality.py` reads it independently of that threshold (see `compute_lesion_quality_metrics` above).

`load_build_matrix_config` also parses `MaskFcConfig`/`BuildFcMatrixConfig` for the FC pipeline (`docs/dev/fc_matrix.md`) - same module, same style, different config shape.

## `src/pipeline/build_lesion_matrix.py` — CLI entry point

`python -m src.pipeline.build_lesion_matrix --config config/pipelines/build_lesion_matrix.json`. Same shape as `retrieve_data.py` (`main(argv) -> int`, staged `try`/`except` per phase, `summaries/build_lesion_matrix/<project>/` + `logs/build_lesion_matrix/<project>/` written every run) but simpler control flow: `build_lesion_matrix()` either succeeds for every requested subject or raises - there's no per-subject error accumulation to report, unlike `retrieve_data.py`'s copy phase.

Phases, each with its own `try`/`except` (`lessons_learned.md` #9 - a later-added phase isn't automatically covered by an earlier phase's error boundary): load config → attach log file handler (`src/utils/logging_setup.py`, `docs/dev/config.md`) → `build_lesion_matrix()` → `artifacts.save_matrix()` (output dir = `output_root/<dd-mm>_<session_name>`) → write report.

**Found while testing this script**: `artifacts.save_matrix`'s original `extra_arrays` validation (added in `src/utils/artifacts.py` during that step) wrongly assumed every extra array is subject-row-aligned with `X`. `non_constant_mask` is feature-aligned (length = pre-drop feature count), not subject-aligned - the check was removed; `save_matrix` now makes no assumption about `extra_arrays`' shape relationship to `X`, since that meaning is caller-specific (documented in `artifacts.py`).
