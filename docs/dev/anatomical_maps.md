# Anatomical maps — technical reference

Audience: developers/agents working on `src/analysis/anatomical_maps.py` and the two anatomy panels it feeds in `src/analysis/embedding_app.py` (single-subject lesion viewer, per-cluster overlap map). For how these panels look/behave from a user's point of view, see `docs/guides/embedding_app.md` ("Anatomia lesionale", "Overlap map per cluster"). For the feature matrix these maps ultimately visualize provenance of, see `docs/dev/lesion_matrix.md`.

Both functions here were promoted (01-09-26) from the exploratory prototype in `notebooks/post-results_analysis/embedding_to_anatomy_mapping.ipynb` §2 — same algorithm, given type hints/tests, no behavior change.

## `resolve_lesion_paths(subject_ids, dataset_by_subject, data_root, lesion_glob) -> dict[str, Path]`

Resolves each requested `subject_id` to its real lesion mask file **on disk, under today's retrieval layout** — never from a run's own historical `config.md` (a run's recorded layout can be stale relative to the current `data/` tree, see the notebook's "Configurazione" cell). One `discover_files_by_subject` call per distinct dataset among `subject_ids` (`src/features/subject_discovery.py`, the same helper `build_lesion_matrix.py`/`build_fc_matrix.py` use) — cheap, globs once per dataset rather than once per subject.

Raises `ValueError` naming every subject that couldn't be resolved (absent from `dataset_by_subject`, or not found on disk under `data_root`/`lesion_glob`) — never returns a map silently smaller than requested (`code_standards.md` §0). This is the single point where "subject not retrieved locally" (a partial retrieval sample) becomes a clear, named error instead of a downstream `KeyError`/empty plot.

## `build_overlap_map(lesion_paths, reference_img, binarize_threshold, resample_interpolation) -> (count_img, percentage_img)`

Voxel-wise across every mask in `lesion_paths`, on `reference_img`'s grid: `count_img`'s value at each voxel is how many of the given subjects had a lesion there; `percentage_img` is that count divided by `len(lesion_paths)`, ×100. Both are `nib.Nifti1Image`s sharing `reference_img`'s affine.

Same resample/binarize contract as `src/features/lesion.py::_load_and_binarize_lesion` (kept as a separate private helper, `_load_and_binarize`, here — that one returns a raveled feature vector, not a volume) — so the map faithfully represents what the feature matrix (and any embedding built from it) actually saw, not an independently-chosen display threshold. Raises `ValueError` on an empty `lesion_paths` — there is no meaningful overlap map over zero subjects.

**Perf**: per-subject load+resample runs on a `ThreadPoolExecutor` (01-09-26) — measured ~40ms/subject, 15.7s of a 16.7s cluster-overlap-map build on a real 408-subject cluster, i.e. it dominates everything else in the app. `nib.load`/`nilearn.image.resample_to_img` are I/O- and SciPy-C-level-bound, releasing the GIL for the bulk of their work, so this is a real wall-clock win, not concurrency theater. Same failure semantics as a plain sequential loop: the first subject that raises (corrupt/missing file) aborts the whole map (`ThreadPoolExecutor.map` propagates it) — no per-subject isolation here, since `resolve_lesion_paths` already surfaces "which subject is missing" explicitly, before any loading is attempted, and a load failure past that point (a corrupt file, not a missing one) is rare enough not to warrant its own isolation layer yet.

## Consumers in `src/analysis/embedding_app.py`

Two independent anatomy panels sit below the embedding scatter, both driven by a single `LesionViewerConfig` (built once at app startup from `build_lesion_matrix.json` via `src/analysis/build_config.py::load_build_matrix_config` — never re-parsed by hand) bundling `data_root`/`lesion_glob`/`reference_img`/`binarize_threshold`/`resample_interpolation`:

- **Single-subject lesion viewer** (`_build_subject_lesion_view`/`lesion_viewer_content_for`): visible under every run, regardless of method. Clicking an embedding point resolves that one subject via `resolve_lesion_paths` and shows its real lesion mask directly (`nilearn.plotting.view_img` on the mask file itself, `threshold=lesion_cfg.binarize_threshold` — the same binarization the source matrix used, not a separately-chosen display value), `cmap="autumn"`, no colorbar (a binary 0/1 mask has no gradient to show).
- **Per-cluster overlap map** (`_build_cluster_overlap_view`/`overlap_map_content_for`): visible only for a `clustering.py` production run (i.e. `metadata.csv` has a `cluster_label` column) — hidden entirely for a `dim_reduction.py` run. Selecting a cluster from the dropdown selects every subject with that `cluster_label`, resolves their masks, and calls `build_overlap_map`; the app displays `percentage_img` (not `count_img`) via `nilearn.plotting.view_img`, `cmap="hot"`, `threshold=1e-6` (a near-zero epsilon, not `lesion_cfg.binarize_threshold` — that threshold already binarized each *individual* subject's mask before counting; the display threshold here only needs to hide true-zero voxels, so any voxel with real overlap, however small, is shown), colorbar **on** (unlike the subject viewer — percentage overlap is a genuinely continuous, informative value, not a flat 0/1).

Both panels share the same never-raises-into-the-callback contract: `lesion_viewer_content_for`/`overlap_map_content_for` catch `ValueError` (unresolvable subject/cluster, missing file) and render an `html.P` status message in the panel instead of crashing the click/dropdown callback — a single bad subject or an empty/unresolvable cluster must not take down the whole app.

**Cluster-overlap cache** (`build_app`'s `cluster_view_cache`, 01-09-26 perf fix): a plain closure-scoped `dict[(run.key, cluster_label), (StatMapView, int)]`, process-lifetime, **not** a module-level global (`code_standards.md` §1). Exists specifically because the cluster-overlap panel is the one place in this app where a fresh rebuild is expensive (the ~40ms/subject cost above, multiplied by however many subjects are in the cluster) — every other panel in `build_app` (the embedding scatter, the single-subject viewer) is deliberately left uncached, since at this cohort size (~1150+ subjects, small `matrix.npy`, one small NIfTI) a fresh rebuild is already fast enough that caching would add complexity for no measurable benefit. A failed build (`ValueError`) is never cached, so a transient/fixable problem (e.g. a not-yet-retrieved subject) can be retried on the next click rather than sticking as a cached failure for the app's lifetime.

## What the map means, read together with `docs/guides/embedding_app.md`

`percentage_img` answers, per voxel: *what fraction of this cluster's subjects had a lesion there*. A voxel that stays "hot" (close to 100%) across most of the cluster indicates the cluster is anatomically coherent in that region — a genuine spatial signature, not just a co-location in embedding space. A cluster with no hot voxels anywhere (percentages spread thin) is a looser, more heterogeneous grouping anatomically, even if it looked well-separated in the 2D/3D scatter. This reading is not itself written down anywhere else in the repo — it follows directly from the mechanism above, not from a separate documented claim.
