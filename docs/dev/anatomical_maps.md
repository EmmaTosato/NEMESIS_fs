# Anatomical maps — technical reference

Audience: developers/agents working on `src/analysis/anatomical_maps.py` and the five anatomy panels it feeds in `src/analysis/embedding_app.py` (single-subject lesion viewer, per-cluster lesion overlap map, single-subject SDC disconnectome viewer, per-cluster disconnection mean map, per-cluster representative-subject viewer). For how these panels look/behave from a user's point of view, see `docs/guides/embedding_app.md` ("Anatomia lesionale", "Overlap map per cluster", "Disconnessione (SDC)", "Frequency map disconnessione per cluster", "Soggetto rappresentativo del cluster"). For the feature matrices these maps ultimately visualize provenance of, see `docs/dev/lesion_matrix.md`/`docs/dev/sdc_matrix.md`.

`resolve_lesion_paths`/`build_overlap_map` were promoted from the exploratory prototype in `notebooks/post-results_analysis/embedding_to_anatomy_mapping.ipynb` §2 — same algorithm, given type hints/tests, no behavior change. `build_mean_map` (29-09-26) is the continuous-data counterpart, for the SDC extension of the same notebook.

## `resolve_lesion_paths(subject_ids, dataset_by_subject, data_root, glob_pattern) -> dict[str, Path]`

Resolves each requested `subject_id` to its real file **on disk, under today's retrieval layout** — never from a run's own historical `config.md` (a run's recorded layout can be stale relative to the current `data/` tree, see the notebook's "Configurazione" cell). One `discover_files_by_subject` call per distinct dataset among `subject_ids` (`src/features/subject_discovery.py`, the same helper `build_lesion_matrix.py`/`build_fc_matrix.py` use) — cheap, globs once per dataset rather than once per subject.

Despite the name, `glob_pattern` is generic — the same function resolves a lesion mask (`LesionViewerConfig.lesion_glob`, `*/manual_masks/*/anat/*_label-lesion_mask.nii.gz`) or an SDC disconnectome map (`SdcViewerConfig.disconnectome_glob`, `src.analysis.embedding_app.SDC_DISCONNECTOME_GLOB` — the same fixed pattern `src.features.sdc.build_sdc_voxelwise_matrix` uses with `object_="disconnectome"`), whichever the caller passes.

Raises `ValueError` naming every subject that couldn't be resolved (absent from `dataset_by_subject`, or not found on disk under `data_root`/`glob_pattern`) — never returns a map silently smaller than requested (`code_standards.md` §0). This is the single point where "subject not retrieved locally" (a partial retrieval sample) becomes a clear, named error instead of a downstream `KeyError`/empty plot. Used where a partial result is never legitimate — the two single-subject panels below have no meaningful "show it anyway, minus the one subject that failed" mode.

## `resolve_available_lesion_paths(subject_ids, dataset_by_subject, data_root, glob_pattern) -> (dict[str, Path], list[str])`

Same resolution as `resolve_lesion_paths` (shares its core via the private `_resolve_lesion_paths_partial`), for a caller that CAN legitimately proceed with fewer subjects than requested instead of needing every one of them - the two per-cluster aggregate panels below (29-09-26, on request). Returns `(resolved, missing)` and never raises over an individual unresolvable subject - logs a `WARNING` naming every excluded one instead (`code_standards.md` §6), so the gap is visible in the server log even if a caller forgets to surface `missing` in its own UI.

Still raises `ValueError` if a `subject_id` has no entry in `dataset_by_subject` at all (a caller bug, distinct from "not found on disk" and never silently folded into `missing`), and if **every** requested subject is unresolvable (an aggregate map built from zero subjects is not a legitimate partial result, just an empty one dressed up as a warning).

**Why this gap is real, not hypothetical**: a lesion-mask swap on 23-09-26 (`.claude/history/data_changelog.md`) replaced UKLFR/WashU's raw files with a fresh copy that didn't 1:1 cover every previously-retrieved subject - 24 UKLFR subjects and 7 WashU subjects lost their local file entirely, while still being registered in any `lesion_matrix`/`clustering.py` production run's `metadata.csv` built before that date. Any cluster containing one of those subjects would otherwise fail this panel entirely over a single missing file - `resolve_available_lesion_paths` lets the map still render over whichever cluster members ARE resolvable, with the gap surfaced rather than hidden.

## `build_overlap_map(lesion_paths, reference_img, binarize_threshold, resample_interpolation) -> (count_img, percentage_img)`

Voxel-wise across every **binary** mask in `lesion_paths`, on `reference_img`'s grid: `count_img`'s value at each voxel is how many of the given subjects had a lesion there; `percentage_img` is that count divided by `len(lesion_paths)`, ×100. Both are `nib.Nifti1Image`s sharing `reference_img`'s affine.

Same resample/binarize contract as `src/features/lesion.py::_load_and_binarize_lesion` (kept as a separate private helper, `_load_and_binarize`, here — that one returns a raveled feature vector, not a volume) — so the map faithfully represents what the feature matrix (and any embedding built from it) actually saw, not an independently-chosen display threshold. Raises `ValueError` on an empty `lesion_paths` — there is no meaningful overlap map over zero subjects.

**Worked example**: a cluster of 6 subjects, one voxel `v`. 2 of the 6 masks are lesioned at `v` (binarized `True`) after resampling onto `reference_img`'s grid, 4 are not. `counts[v] = 2` (the voxelwise sum of the six 0/1 values), `percentage[v] = 100 * 2 / 6 ≈ 33.3` — i.e. "33.3% of this cluster's subjects are lesioned at `v`". This is done independently per voxel across the whole grid, so `percentage_img` is exactly the voxelwise mean of the binarized masks, expressed as 0–100 instead of 0–1.

## `build_mean_map(image_paths, reference_img, resample_interpolation) -> mean_img`

The **continuous**-data counterpart of `build_overlap_map`, for a value that is never binarized — today only SDC's own `disconnectome-map.nii.gz`, a `[0, 1]` per-voxel disconnection probability (`src/features/sdc.py`'s module docstring). No `binarize_threshold`/`count_img`: there is no "how many subjects crossed a threshold" concept for a continuous value, only the voxelwise sample mean itself, returned as one `nib.Nifti1Image`. Raises `ValueError` on an empty `image_paths`.

Both `build_overlap_map` and `build_mean_map` share `_GridResampler.load` (resample-only, no thresholding — `build_overlap_map` thresholds its result) and the same per-call `ThreadPoolExecutor` perf/failure shape:

**Perf**: per-subject load+resample runs on a `ThreadPoolExecutor` — measured ~40ms/subject, 15.7s of a 16.7s cluster-overlap-map build on a real 408-subject cluster, i.e. it dominates everything else in the app. Con maschere a 1mm e template a 2mm (la situazione attuale) `resample_to_img` per soggetto costa ~200ms + ~110ms di `get_fdata`: `_GridResampler` calcola quindi **una volta per griglia sorgente** (shape + affine) la corrispondenza voxel→voxel facendo passare un volume di indici dallo stesso `resample_to_img(interpolation="nearest")` (identica per costruzione, voxel fuori campo inclusi) e la applica a ogni soggetto come semplice indexing sul dtype nativo (~49ms/soggetto in totale). Il risultato è bit-identico al percorso per-soggetto (testato su maschere reali e sintetiche); ogni interpolazione diversa da `nearest` mescola davvero i valori e mantiene `resample_to_img` per soggetto. `nib.load`/`nilearn.image.resample_to_img` are I/O- and SciPy-C-level-bound, releasing the GIL for the bulk of their work, so this is a real wall-clock win, not concurrency theater. Same failure semantics as a plain sequential loop: the first subject that raises (corrupt/missing file) aborts the whole map (`ThreadPoolExecutor.map` propagates it) — no per-subject isolation here, since `resolve_lesion_paths` already surfaces "which subject is missing" explicitly, before any loading is attempted, and a load failure past that point (a corrupt file, not a missing one) is rare enough not to warrant its own isolation layer yet.

## Consumers in `src/analysis/embedding_app.py`

Five anatomy panels sit below the embedding scatter, in two families driven by two independent config dataclasses — `LesionViewerConfig` (from `build_lesion_matrix.json` via `src/analysis/build_config.py::load_build_matrix_config`) and `SdcViewerConfig` (from `build_sdc_matrix.json` via `load_build_sdc_matrix_config`, requiring `representation="voxelwise"` — the only representation with a raw `disconnectome-map.nii.gz` to visualize, `src.pipeline.embedding_app.main` fails fast otherwise). The two configs are never cross-reused (each loads its own `reference_img`/`resample_interpolation` — `build_sdc_matrix.json`'s own `reference_template_path` is a different grid from `build_lesion_matrix.json`'s, confirmed by reading both rather than assumed identical):

- **Single-subject lesion viewer** (`_build_subject_lesion_view`/`lesion_viewer_content_for`), panel "Anatomia lesionale": visible under every run, regardless of modality/method (every SDC-admitted subject also has a lesion mask, see `docs/dev/sdc_matrix.md`'s admission criterion). Clicking an embedding point resolves that one subject via `resolve_lesion_paths` and shows its real lesion mask directly (`nilearn.plotting.view_img` on the mask file itself, `threshold=lesion_cfg.binarize_threshold` — the same binarization the source matrix used), `cmap="autumn"`, no colorbar (a binary 0/1 mask has no gradient to show). `magma` was tried and reverted the same day (29-09-26) — its top color for a binary mask is a near-white pale yellow, illegible against the white background on real data; see `_build_subject_lesion_view`'s own docstring for the other colormaps compared before settling back on `autumn`. Also offers a "Salva PNG (glass brain)" download (`_download_lesion_glass_png`) — see "Static PNG export" below.
- **Per-cluster lesion overlap map** (`_build_cluster_overlap_view`/`overlap_map_content_for`), panel "Overlap map per cluster": visible only for a `clustering.py` production run (`metadata.csv` has `cluster_label`). Resolves the cluster's subjects via `resolve_available_lesion_paths` (29-09-26, was `resolve_lesion_paths`) - a cluster member unresolvable on disk is excluded from the map, not a reason to fail the whole panel, with an amber warning line naming who was excluded (`_missing_subjects_warning`, `_anatomy_viewer`'s own `warning` param). `n_subjects` in the heading counts only the resolved subjects the map was actually built from. Calls `build_overlap_map`, displays `percentage_img` via `view_img`, `cmap="hot"`, `threshold=1e-6`, colorbar on.
- **Single-subject SDC disconnectome viewer** (`_build_subject_disconnectome_view`/`disconnectome_viewer_content_for`, 29-09-26), panel "Disconnessione (SDC)": visible only for a `modality="sdc"` run (panel `style` toggled by `_update_disconnectome_panel_visibility`, gated on `run.modality`) — a "lesion" modality run's subjects have no `disconnectome-map.nii.gz` to resolve. Resolves the subject's disconnectome map via `resolve_lesion_paths`/`SdcViewerConfig.disconnectome_glob` and shows it directly, `cmap=_DISCONNECTOME_CMAP` (`"magma"`), `threshold=_DISCONNECTOME_DISPLAY_THRESHOLD` (0.02, never a binarize threshold — continuous, never binarized), colorbar **on** (unlike the lesion viewer). Also offers a "Salva PNG (glass brain)" download (`_download_disconnectome_glass_png`) at a different, higher threshold — see "Static PNG export" below.
- **Per-cluster disconnection mean map** (`_build_cluster_disconnection_view`/`disconnection_map_content_for`, 29-09-26), panel "Frequency map disconnessione per cluster": visible only when **both** `modality="sdc"` **and** `pipeline="clustering"` (`_update_disconnection_map_panel_visibility` checks both). Reuses the *same* `cluster-picker` dropdown as the lesion overlap panel — one clustering run has exactly one set of clusters regardless of which map family is being viewed, so a second dropdown would only duplicate its options. Same `resolve_available_lesion_paths` skip-and-warn behavior as the lesion overlap panel above. Calls `build_mean_map`, displays the resulting `mean_img` via `view_img`, `cmap=_DISCONNECTOME_CMAP`, `threshold=_DISCONNECTOME_DISPLAY_THRESHOLD`, colorbar on.
- **Per-cluster representative-subject viewer** (`representative_subject_content_for`, 29-09-26), panel "Soggetto rappresentativo del cluster": visible only for a `pipeline="clustering"` run (any modality), positioned after the two per-cluster map panels above - style toggled by the *same* `_update_cluster_picker` callback that already gates `cluster-map-panel` (one extra `Output`, identical `run.pipeline != "clustering"` condition). Reuses the shared `cluster-picker` dropdown too, whose own widget lives inside `cluster-map-panel` - Dash resolves a callback's `Input`/`State` by component id regardless of where in the tree that id lives, so this panel's own callback (`_update_representative_subject`) reads the same value `disconnection-map-panel` already does. For the selected cluster, resolves the real subject closest to that cluster's centroid in the embedding space (`cluster_centroids_with_nearest_subject`, see below) and shows that subject's own lesion or SDC disconnectome view - dispatched by `run.modality` (`"lesion"` → `_build_subject_lesion_view`, anything else → `_build_subject_disconnectome_view`), the same dispatch logic notebooks/post-results_analysis/clustering_evaluation.ipynb's `plot_representative_map` does by parsing `input_path` instead (this app already has `modality` as a first-class `ProductionRun` field). Offers "Salva HTML"/"Salva PNG" like the two single-subject panels, not the glass-brain download.

## `cluster_centroids_with_nearest_subject(embedding, metadata) -> pd.DataFrame`

Promoted 29-09-26 from the same notebook's `cluster_centroids`/`nearest_subject_to_centroid` (same algorithm, adapted to read `embedding`/`metadata` directly instead of the notebook's own `extended_runs` dict) - per `cluster_label`, the centroid (mean of that cluster's own embedding coordinates) and the real `subject_id` closest to it (Euclidean distance) in that **same reduced embedding space** (the plotted `dim0`/`dim1`[/`dim2`] coordinates), not the original pre-reduction feature matrix - a centroid is a mean point, never a real subject, so "closest real subject" is always an approximation of it, not the point itself. Two consumers: `_add_cluster_centroids_trace` (the black circled-centroid overlay on the main embedding scatter, `graph_content_for`) and `representative_subject_content_for` (which real subject's anatomy the panel above shows) - both read the exact same computation, never two independently-derived answers.

Raises `ValueError` if `metadata` has no `cluster_label` column (only a `clustering.py` run has one) or if `embedding`/`metadata` have mismatched row counts (would otherwise silently misalign a point to the wrong `subject_id`).

**Centroid overlay** (`_add_cluster_centroids_trace`, called from `graph_content_for` right after `build_embedding_figure`): a black-outlined, transparent-fill circle at each cluster's centroid plus its `cluster_label` as text, added as one extra Plotly trace (`go.Scatter`/`go.Scatter3d` matching the run's own 2D/3D-ness) on top of the existing point traces - an overlay on the live interactive scatter (29-09-26, on request), not a separate static matplotlib plot like the notebook's own `plot_embedding_with_centroids`. A no-op (mutates nothing) for a `dim_reduction.py` run, which has no `cluster_label` to group by.

`_DISCONNECTOME_DISPLAY_THRESHOLD` (29-09-26, was the near-zero epsilon `threshold=1e-6` for both panels above) — at `1e-6`, near-zero disconnection-probability noise rendered in the colormap's own near-black floor color as ugly black speckle scattered across the brain — most visible, and explicitly flagged by the user ("troppo nero"), on the per-cluster mean map. Confirmed clean at 0.02 against a real 975-subject cluster mean and a real single-subject map (`tmp/anatomy_rendering/110_cluster_disconnection_*`, `120_disconnectome_single_*`, gitignored, local-only) — lower thresholds trade cleanliness for less of the diffuse signal around the main tract; 0.05/0.1 were also compared and are cleaner still but visibly thinner. `_DISCONNECTOME_CMAP` itself was briefly `"nipy_spectral"` the same day (to match Thiebaut de Schotten et al. 2020's own Fig. 1 colormap, `knowledge/nemesis/Thiebaut de Schotten et al - 2020...`) before being reverted to `"magma"` ("non mi piace la palette arcobaleno") - see `_DISCONNECTOME_CMAP`'s own code comment for the full reasoning, including why the threshold fix is a distinct problem from the glass-brain download's own threshold below (that one is specific to summing along the full volume depth).

All five share the same never-raises-into-the-callback contract: each `*_content_for` function catches `ValueError` (unresolvable subject/cluster, missing file) and renders an `html.P` status message in its panel instead of crashing the click/dropdown callback. `representative_subject_content_for`'s own callback (`_update_representative_subject`) additionally catches `UndisplayableRunError` around its own `load_run` call (needed there, unlike the other panels, because it reads the run's embedding coordinates, not just its metadata) - `load_run` isn't itself wrapped by any `*_content_for` function, so each caller is responsible for its own boundary, same lesson as `code_standards.md`/`lessons_learned.md` #9.

**Stale-selection fix (01-09-26, extended 29-09-26)**: `embedding-graph.clickData` is a client-side prop that does **not** reset just because `run-picker` switches to a different run (Dash/React patches the same-id `dcc.Graph` node in place rather than remounting it) — a naive "Salva HTML"/"Salva PNG" callback reading `State("embedding-graph", "clickData")` directly would silently offer a download for the *previous* run's clicked subject even after the visible panel had already reset to its placeholder. Both single-subject panels fix this the same way: their own `dcc.Store` (`lesion-viewer-subject` / `disconnectome-viewer-subject`) is the single source of truth for "which subject is actually shown right now", set atomically with the panel's `children` by the same callback, reset to `None` on a run change or an irrelevant modality — the Save buttons read *this* Store via `State`, never `clickData` directly.

**Cluster-view caches** (`build_app`'s `cluster_view_cache` / `disconnection_view_cache`): two plain closure-scoped `dict[(run.key, cluster_label), (StatMapView, int, nib.Nifti1Image)]`, process-lifetime, **not** module-level globals (`code_standards.md` §1) — kept as two separate dicts rather than one shared namespace, since a clustering run's own `run.key` doesn't encode which of the two map families (lesion overlap vs. disconnection mean) produced a given entry. Exist specifically because the two per-cluster panels are the one place in this app where a fresh rebuild is expensive (the ~40ms/subject cost above, multiplied by however many subjects are in the cluster) — every other panel (the embedding scatter, both single-subject viewers) is deliberately left uncached, since at this cohort size a fresh rebuild is already fast enough that caching would add complexity for no measurable benefit. A failed build (`ValueError`) is never cached, so a transient/fixable problem can be retried on the next click. The image itself (`percentage_img` / `mean_img`) is carried alongside the view so "Salva PNG" reuses it instead of paying the per-subject cost a second time.

## Static PNG export (`_static_png_bytes`, `_static_glass_brain_png_bytes`)

All five anatomy panels offer "Salva PNG" next to "Salva HTML" — a non-interactive counterpart rendered via `nilearn.plotting.plot_stat_map` rather than `view_img`'s own HTML (which has no static-image export). Same `threshold`/`cmap`/`colorbar` per panel as its interactive `view_img` call, so the two downloads always agree on what they show. One divergence: `plot_stat_map`'s own `bg_img` default is already an MNI152 template object, not `view_img`'s `"MNI152"` string shortcut — passing that string to `plot_stat_map` raises `ValueError: File not found: 'MNI152'`, so `_static_png_bytes` omits `bg_img` entirely and relies on the default. The lesion/disconnectome single-subject downloads resolve the subject's file path directly (`resolve_lesion_paths`) rather than building the interactive view first; the two cluster-map downloads reuse their own cache's image instead of recomputing it; the representative-subject panel's download (`_download_representative_png`) first re-derives the representative `subject_id` via `cluster_centroids_with_nearest_subject`, then resolves and renders its file directly, same as the single-subject downloads - no cache, since it's the same one-subject cost as those, not the per-cluster per-subject cost the two cluster-map caches exist for.

The two single-subject panels (lesion, SDC disconnectome) additionally offer a "Salva PNG (glass brain)" download (`_static_glass_brain_png_bytes`, `_download_lesion_glass_png`/`_download_disconnectome_glass_png`, 29-09-26) — a single transparent-brain silhouette (`nilearn.plotting.plot_glass_brain`, `display_mode="lyrz"`) instead of 3 flat ortho slices. Not offered on the two per-cluster panels (not requested). Colormap/threshold diverge from the panel's own ortho view, deliberately:

- **Lesion**: `cmap="autumn"`, same as the ortho view above (both settled on `autumn` the same day, see that view's own docstring) — a binary mask has no gradient to show, autumn's solid bright yellow reads clearly on both projections. `threshold=lesion_cfg.binarize_threshold`, same as the ortho download — a binary mask has no near-zero noise to hide.
- **SDC disconnectome**: `cmap="magma"`, same colormap as the ortho view above. `threshold=_DISCONNECTOME_GLASS_BRAIN_THRESHOLD` (0.1) and `alpha=_DISCONNECTOME_GLASS_BRAIN_ALPHA` (0.9), not `_DISCONNECTOME_DISPLAY_THRESHOLD` — a `plot_glass_brain` projection sums along the full depth of the volume, so the ortho views' own 0.02 (already enough to clean up a flat slice) still isn't high enough here: every near-zero background voxel becomes visible as thin dark streaks across the whole silhouette. Confirmed on real subject data across several threshold values (`tmp/anatomy_rendering/90_disconnectome_glass_lyrz_magma_alpha90_thr*.png`, gitignored, local-only) — 0.1 hides the streaking without cutting into the real signal.

A cortical-surface projection (`plot_img_on_surf`/`view_img_on_surf`) was evaluated for both data types and **rejected** for this cohort, not adopted for either panel: a 12-subject sample of real lesion masks showed 5/12 with zero suprathreshold surface vertices at all, and the same check on a real subject's disconnectome map found 766 suprathreshold surface vertices against 112,410 suprathreshold voxels in the full volume (>99% signal loss) — both lesion and disconnectome signal live mostly subcortical/deep white matter, essentially invisible on a cortical-surface projection.

## What the maps mean, read together with `docs/guides/embedding_app.md`

`percentage_img` (lesion overlap) answers, per voxel: *what fraction of this cluster's subjects had a lesion there*. A voxel that stays "hot" (close to 100%) across most of the cluster indicates the cluster is anatomically coherent in that region — a genuine spatial signature, not just a co-location in embedding space. A cluster with no hot voxels anywhere (percentages spread thin) is a looser, more heterogeneous grouping anatomically, even if it looked well-separated in the 2D/3D scatter.

`mean_img` (disconnection mean map) answers the structural-disconnection analogue: *on average, how disconnected is this voxel across the cluster's subjects*. Since the underlying value is already a per-subject probability (not a binary mask), this is a genuine average of continuous quantities, not a %-of-subjects-crossing-a-threshold count — a cluster whose mean map stays close to 1.0 along a specific tract/region indicates a shared structural-disconnection signature, independent of whether the subjects' own lesions overlap anatomically (two different lesion sites can produce the same downstream disconnection pattern — the entire premise behind studying SDC separately from lesion topography, see the project's own core hypothesis in `README.md`).
