## `src/analysis/reduction.py` / `clustering.py` — modeling strategies

Plain `dict[str, Callable]` registries (`REDUCTION_METHODS`, `CLUSTERING_METHODS`), not classes/ABCs — same "explicit registry over hardcoded dispatch" precedent as `config/registry/file_patterns.json`. Each entry is a pure `(X, params) -> array` function: `params` is unpacked with `**params` straight into the underlying `sklearn`/`umap` estimator's constructor, no in-code defaults for any hyperparameter (`code_standards.md` §5) — those live only in `config/registry/params_reduction.json`/`params_clustering.json` (`src/analysis/params.py`, see `docs/dev/config.md`). Invalid/unexpected keys in `params` surface as whatever error `sklearn`/`umap` itself raises for a bad constructor argument — not re-validated here, since re-implementing each estimator's accepted-parameter surface would just duplicate their own API.

- `reduction.py`: `umap_embed`, `tsne_embed`, `pca_embed`, `pca_varimax_embed`, `pacmap_embed`.
- `clustering.py`: `kmeans_cluster`, `agglomerative_cluster`, `gmm_cluster`, `hdbscan_cluster`, `spectral_cluster`, `evidence_accumulation_cluster` (see `consensus_clustering.py` section below for what makes `evidence_accumulation_cluster` different from the blind-`**params`-unpack rule the other 5 follow).

`pca_varimax_embed` is the one exception to the "blind `**params` unpack" rule above: it wraps two distinct estimators (`sklearn.decomposition.PCA`, then `factor_analyzer.Rotator(method="varimax")`, per Thiebaut de Schotten et al. 2020's methodology - `knowledge/dim_reduction_clustering/dim_reduction_literature_survey.md`), so it reads `n_components`/`rotation_max_iter` from `params` explicitly and raises `ValueError` if either is missing, or if `n_components < 2` (varimax rotates *between* components - nothing to rotate with one). Component scores are computed via `np.linalg.lstsq` (regressing each centered subject row onto the rotated loadings) - the paper's "multiple regression" step, not a re-projection through the rotated loadings directly. Loadings passed to `Rotator` are `PCA.components_.T * sqrt(explained_variance_)` (factor loadings), never the raw `components_` (unit-norm eigenvectors) - bug found and fixed 2026-08 during a literature-validation review, before this method ever had a `params_reduction.json` entry (no production run affected): unscaled eigenvectors make varimax weight every component equally regardless of how much variance it explains, and - since `PCA.components_` is orthonormal and varimax is an orthogonal rotation - silently degenerate the subsequent `lstsq` "multiple regression" step into a plain projection (`rotated_loadings.T @ rotated_loadings == I` only under the bug). Regression test: `tests/unit/test_reduction.py::test_pca_varimax_embed_rotates_scaled_loadings_not_raw_eigenvectors`.

`embed(reduction_method, X, params, distance_cache=None) -> np.ndarray` (2026-08, literature-validation review; widened 25-08-26, `docs/debugging/debug_25_08_26.md`): the single call site every `REDUCTION_METHODS[reduction_method]` invocation now goes through, both in production (`dim_reduction.py`) and in `embedding_for_viz` below - `clustering.py` never calls it (see `docs/dev/clustering_migration_plan.md` §2). When `params["metric"]` is one of `distances.py::PRECOMPUTABLE_METRICS` (`"jaccard"`/`"dice"`/`"euclidean"`), `X` is replaced by its precomputed `distances.py::precomputed_distance` matrix and `metric` switched to `"precomputed"` - the exact same path `tuning.py`'s `evaluate_umap`/`evaluate_tsne` already use for their fine-tuning sweeps (built there first, as a speed optimization, then ported to the single-run production path). Two independent reasons this matters, not just one: (1) *exactness* - umap-learn only computes an *exact* k-NN graph itself for datasets under 4096 samples (`n_index_samples < 4096` in `UMAP.fit()`, sets `self._small_data = True` - `umap/umap_.py` in the umap-learn source) - above that it silently switches to the approximate NNDescent/pynndescent search, an undocumented, version-dependent threshold; routing every call through `embed` removes that dependency entirely, regardless of cohort size (relevant now that the real cohort, `25-08_s1.2`, is at 5269 subjects - past the threshold). (2) *speed*, for `"euclidean"` specifically - umap-learn/sklearn's own per-fit neighbor search on a high-dimensional raw matrix (264274 voxels) is itself the bottleneck, not the distance computation: measured directly on `25-08_s1.2`, `sklearn.metrics.pairwise.euclidean_distances` computes the *entire* 5269x5269 distance matrix in 88s, while a single uncached umap fit at `metric="euclidean"` took 17-35 *minutes* for one `n_neighbors`/`min_dist` combination alone. Also forces `init="random"` for `reduction_method="tsne"` when precomputing (sklearn's own default `init="pca"` can't run on a distance matrix). `distance_cache`, when passed, lets a caller compute the main embedding and a viz refit at the same metric without recomputing the precomputed matrix twice - `dim_reduction.py` builds one shared cache per run. `pca`/`pca_varimax`/`pacmap` are unaffected by any of this - their `params_reduction.json` entries never carry a `"metric"` key, so `params.get("metric")` is `None` and the whole branch is a no-op for them.

`embedding_for_viz(reduction_method, X, reduction_params, embedding, viz_n_components, distance_cache=None) -> np.ndarray` (2026-08 session): returns an embedding with exactly `viz_n_components` columns, for plotting only - reuses `embedding` unmodified (`is` identity, zero extra cost) when it already has that many columns, otherwise refits via `embed` above (so a jaccard/dice/euclidean refit gets the same precomputed-distance treatment, sharing `distance_cache` with the main fit rather than recomputing it a second time) from scratch on the same raw `X` with only `n_components` overridden. Exists because `embedding[:, :viz_n_components]` is not a valid substitute for umap/tsne/pacmap: their output dimensions have no importance ordering (unlike PCA's variance-ranked components, where a second fit at fewer components is mathematically equivalent to slicing - the same rule covers every `REDUCTION_METHODS` entry without a per-method branch), so a slice can make real cluster structure look artificially merged or split. The refit shares the original fit's neighbor graph (depends only on `metric`/`n_neighbors`, not `n_components`) since every other param is held identical. One caller: `dim_reduction.py::_run_production` (own `viz_n_components`, 2 or 3). `clustering.py` has no raw `X`/reduction params to refit from by design (it only ever receives an already-built matrix, see `docs/dev/clustering_migration_plan.md` §2) - its own, unrelated mechanism for the same underlying problem is `_resolve_viz_embedding` (plan §3), a companion embedding read from a config-supplied path, never a refit.

Only `umap`/`tsne` actually get this refit (`_REFITTABLE_FOR_VIZ`, deliberately narrow, 2026-08-17) - every other `REDUCTION_METHODS` entry raises instead: `pca_varimax` is excluded because varimax rotates *jointly* across every retained component, so a refit at a different `K` solves a different optimization problem, not "the same K rotated factors, fewer of them" - a 2D refit would show factors with no relationship to the production run's own interpretable ones (the whole point of the Thiebaut de Schotten et al. 2020 methodology this reproduces is that each rotated factor has a specific anatomical meaning). `pca` is excluded even though a refit *would* be mathematically equivalent to slicing (greedy variance ordering means the top components don't change when more are requested) - kept out anyway rather than silently reintroduced, since no real config has ever needed a mismatched `viz_n_components` for `pca` and this function should not guess at intent. `pacmap` is excluded despite being neighbor-graph-based like umap/tsne, where the same reasoning would in principle apply - excluded explicitly on request rather than inferred, since getting this wrong would silently change a real production method's behavior.

## `src/analysis/tuning.py` — manual fine-tuning for umap/tsne/pca/pca_varimax/pacmap

No automatic parameter selection anywhere in this module - it only produces a comparison table; a human reads it (or the accompanying plot) and writes the chosen parameters into `params_reduction.json`'s `"params"` by hand. t-SNE's `early_exaggeration`/`learning_rate`/`max_iter` are excluded on purpose (fixed from Thiebaut de Schotten et al. 2020, `knowledge/dim_reduction_clustering/dim_reduction_tuning_guide.md`) - only `perplexity` is swept, added on request since the paper's own supplementary material sweeps it too. Every clustering method is excluded here too - fine-tuning for those lives in `clustering_tuning.py` below, not this module.

`TUNING_METRIC_NAMES = {"umap": "trustworthiness", "tsne": "trustworthiness", "pca": "cumulative_explained_variance", "pca_varimax": "cumulative_explained_variance", "pacmap": "trustworthiness"}` - the quality metric is genuinely different per *family* of method (decided with the user), not per individual method - `pca_varimax` reuses PCA's criterion (varimax is an orthogonal rotation, doesn't change total variance explained) and `tsne`/`pacmap` reuse UMAP's (trustworthiness is a generic neighbor-preservation metric, not UMAP-specific):
- `evaluate_umap(X, params, trustworthiness_n_neighbors)` / `evaluate_tsne(X, params, trustworthiness_n_neighbors)` / `evaluate_pacmap(X, params, trustworthiness_n_neighbors)` embed then score with `sklearn.manifold.trustworthiness` - how well local neighborhoods survive the projection. `evaluate_umap`/`evaluate_tsne` both read `params["metric"]`: for any `distances.py::PRECOMPUTABLE_METRICS` value (`"jaccard"`/`"dice"`/`"euclidean"` - widened from jaccard/dice-only 25-08-26, `docs/debugging/debug_25_08_26.md`), both the embedding *and* the `trustworthiness` call are given the same `distances.py::precomputed_distance` matrix (`metric="precomputed"` on both) instead of raw `X` - scoring a precomputed-metric embedding against `trustworthiness`'s own euclidean-on-raw-`X` default would judge it by a notion of "originally close" it was never built to preserve. For `"euclidean"` specifically this is also a large speed win at this project's scale, not just an exactness/scoring-consistency guarantee - see `embed`'s entry above for the measured numbers, same underlying mechanism. `evaluate_tsne` additionally forces `init="random"` whenever `metric="precomputed"` - `sklearn.manifold.TSNE`'s own default `init="pca"` can't run on a distance matrix. `evaluate_pacmap` has no such branch - its `tuning_grid` never sweeps `metric`. Caveat: the euclidean speedup magnitude was only independently measured for `evaluate_umap` (see `embed`'s entry above); `evaluate_tsne` was widened the same way on request, same already-validated mechanism, but without its own live timing run - don't assume the same 88s-vs-17-35min order of magnitude for t-SNE until it's actually measured on a real sweep.
- `evaluate_pca(X, params)` / `evaluate_pca_varimax(X, params)` fit `sklearn.decomposition.PCA` directly (not via `pca_embed`/`pca_varimax_embed`, which only return the transformed array) specifically to read `.explained_variance_ratio_.sum()` off the fitted estimator - PCA's own natural criterion, and the exact one the paper uses to choose a component count.

`_EVALUATORS: dict[str, Callable]` dispatches by method name (Strategy registry, same precedent as `REDUCTION_METHODS`/`CLUSTERING_METHODS`) rather than an `if/elif` chain - the original 2-branch `if/elif` (umap/pca) was refactored into this registry specifically when adding `pca_varimax`/`pacmap`, since a 2-branch `if/elif` growing to 4 branches is exactly the pattern `lessons_learned.md` #1 warns about. `METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS = {"umap", "tsne", "pacmap"}` is consulted both here and by `dim_reduction.py` (to decide whether to load `trustworthiness_n_neighbors` from config at all) - a single shared source of truth for "which methods need this extra setting", not duplicated/hardcoded in both places.

`run_tuning_sweep(method, X, base_params, tuning_grid, trustworthiness_n_neighbors) -> tuple[pd.DataFrame, dict[tuple, np.ndarray]]` takes the Cartesian product of `tuning_grid`'s value lists (`itertools.product`), evaluates each combination via `_EVALUATORS[method]` (swept keys override `base_params`; un-swept keys like `random_state` stay fixed). Returns `(results, embeddings_by_combo)`: `results` is unchanged from before 2026-08 (one row per combination, swept values + metric column, still the only thing written to `tuning_results.csv`); `embeddings_by_combo` (added 2026-08, in-memory only, never serialized) keys each combination's actual embedding by its exact `combo` tuple (`tuning_grid.keys()` order) - so a caller that needs to *see* an embedding, not just its score (`dim_reduction.py`'s `embeddings_grid` plot), doesn't have to refit it. Raises `ValueError` for any method not in `TUNING_METRIC_NAMES` (registry-driven, not an implicit fallback).

## `src/analysis/distances.py` — fast precomputed pairwise distances for umap/tsne

`SUPPORTED_BINARY_METRICS = {"jaccard", "dice"}` and `PRECOMPUTABLE_METRICS = SUPPORTED_BINARY_METRICS | {"euclidean"}` (widened 25-08-26, `docs/debugging/debug_25_08_26.md`) - the two sets stay distinct on purpose: `SUPPORTED_BINARY_METRICS` is exactly the metrics with a domain restriction (`require_binary_matrix` below applies only to these), `PRECOMPUTABLE_METRICS` is every metric this module can turn into a cached precomputed distance matrix at all, the set `tuning.py`/`reduction.py` actually check against before taking the precomputed-distance path.

`binary_pairwise_distance(X, metric) -> np.ndarray` computes a full `(n_samples, n_samples)` Jaccard or Dice distance matrix for a binary `(n_samples, n_features)` array (voxel-wise lesion masks): `metric` must be in `SUPPORTED_BINARY_METRICS` - `ValueError` otherwise, and `ValueError` if any row is all-zero (union/sum would be 0, both metrics undefined for an empty sample). Exists because `scipy.spatial.distance.pdist`'s boolean metrics compute one pair at a time - measured at ~19 minutes extrapolated for 1150 subjects × 254865 voxel features. Binary overlap between every pair at once is instead a single matrix multiplication (`X @ X.T` counts shared "on" features per pair, via BLAS) - Jaccard/Dice distance follow from that intersection count plus each row's own sum, in seconds instead of minutes. Casts to `float64` before the multiply regardless of `X`'s own dtype (usually `uint8`) - intersection counts can exceed a narrow integer type's range and silently wrap (`lessons_learned.md` #13).

`euclidean_pairwise_distance(X) -> np.ndarray` (25-08-26) wraps `sklearn.metrics.pairwise.euclidean_distances(X.astype(np.float64))` - no binary/domain restriction, any real-valued matrix is valid. Exists for a *different* reason than `binary_pairwise_distance` above: umap-learn/sklearn don't have a slow *distance computation* for euclidean (that part is cheap, the same Gram-matrix/BLAS trick as the binary case) - what's slow is their own per-fit *neighbor search*, repeated from scratch on every call in a sweep with no way to cache it internally. Measured directly on the real `25-08_s1.2` lesion matrix (5269 subjects × 264274 voxels): the entire 5269×5269 distance matrix computes in 88s, while a single uncached umap fit at `metric="euclidean"` took 17-35 *minutes* for one `n_neighbors`/`min_dist` combination. Precomputing once and reusing (`distance_cache` in `tuning.py`/`reduction.py`) turns that per-call cost into a one-time cost, exactly the same shape of fix `binary_pairwise_distance` already was for jaccard/dice, just for a different root cause.

`precomputed_distance(X, metric) -> np.ndarray` (25-08-26) dispatches to `binary_pairwise_distance` or `euclidean_pairwise_distance` by metric name - the single entry point `tuning.py`/`reduction.py` call once `metric` is known to be in `PRECOMPUTABLE_METRICS`. Raises `ValueError` for any metric outside that set.

`require_binary_matrix(X, metric) -> None` (2026-08, literature-validation review): raises `ValueError` if `X` has any value outside `{0, 1}` - jaccard/dice's set-overlap definition (and the `X @ X.T` intersection-count trick above) is meaningless once a "1" can mean "partial membership". Nothing upstream guarantees this: `dim_reduction.py` reads any `matrix.npy` artifact regardless of which pipeline wrote it - `build_lesion_matrix.py` always produces a strictly binary voxel-wise matrix, but `build_fc_matrix.py` (and any future atlas-based/continuous feature source) does not. Called by `binary_pairwise_distance` itself, and directly by `dim_reduction.py`'s production path (before `reduction.py::embed`, so a bad matrix fails fast with a clean error before any output directory is even created) and by `embed` itself (defense-in-depth for any other caller, e.g. a viz refit). Deliberately *not* extended to `euclidean_pairwise_distance` - euclidean has no `{0,1}` domain restriction, any real-valued matrix is a valid input.

Used by `tuning.py::evaluate_umap`/`evaluate_tsne` (above) and by `reduction.py::embed` (also above) - every `REDUCTION_METHODS` call site (production and fine-tuning alike, both umap and tsne) now routes any `PRECOMPUTABLE_METRICS` value through this same precomputed-distance path. `metric` is an explicit key in both `umap`/`tsne`'s `"params"` in `params_reduction.json` (rather than left absent, silently falling back to the library's own default) - production `umap` and `tsne` both currently run with `metric="euclidean"` (checked 18-08-26 against the registry directly; `umap` briefly ran with `metric="jaccard"` after session s1.1's 26-07 tuning round, but the registry was since reset to `"euclidean"` without this doc being updated to match - `AUDIT_FINDINGS.md` #33) - meaning the euclidean-specific speed fix isn't a hypothetical, it directly speeds up the actual production config on file today.

## `src/analysis/clustering_tuning.py` — manual fine-tuning for kmeans/agglomerative/gmm/hdbscan/spectral

Same "no automatic selection" philosophy as `tuning.py`, but clustering has no ground truth to score against - every generic metric is an *internal* validation index computed straight from `(X, cluster_labels)`, meaningful only within one method's own swept grid, never compared across methods.

`compute_clustering_metrics(X, labels, combo_params=None) -> dict[str, float]` returns `{"silhouette", "calinski_harabasz", "davies_bouldin", "noise_fraction"}` for every method uniformly - `sklearn.metrics.silhouette_score`/`calinski_harabasz_score`/`davies_bouldin_score` excluding any HDBSCAN-style noise (`label == -1`) first (undefined for a "cluster" that isn't one), with `noise_fraction` always reported so the exclusion is visible rather than silent. A degenerate combination (fewer than 2 non-noise clusters, or every non-noise point its own cluster) can't have the 3 metrics computed at all - caught (the same condition `sklearn` itself would raise on) and recorded as `NaN` with a logged warning rather than aborting the whole sweep, since a bad hyperparameter combination is expected information in a tuning sweep, not a bug (distinct from `lessons_learned.md`'s silent-fallback pattern: this is one documented, intentional strategy for a legitimate domain case, not a caught-and-hidden error).

`combo_params` (optional, only `run_clustering_tuning_sweep` below always passes it): when given, `_require_euclidean_compatible` raises `ValueError` upfront if it names a distance/affinity the 3 geometric indices' Euclidean assumption doesn't hold for (`AUDIT_FINDINGS.md` HIGH #13) - silhouette/Calinski-Harabasz/Davies-Bouldin all default to Euclidean distance internally, correct only as long as the clustering method itself also treated `X` as a plain Euclidean feature space. `_EUCLIDEAN_SAFE_AFFINITY = {None, "nearest_neighbors", "rbf"}` (spectral's `affinity`) and `_EUCLIDEAN_SAFE_METRIC = {None, "euclidean"}` (agglomerative's `metric`) are an explicit allow-list (`lessons_learned.md` #20, over a free-form guess) of every value known to still mean "X is a plain Euclidean feature matrix" - anything else, most importantly `affinity="precomputed"` (X is itself a distance/affinity matrix under an arbitrary metric, e.g. Jaccard/Dice) or a non-Euclidean `metric`, makes X's own coordinates meaningless to a Euclidean index, so the function refuses outright rather than silently scoring the wrong geometry. Dormant today - no production/tuning config sets either value (`AUDIT_FINDINGS.md` #13).

`compute_silhouette_samples(X, labels) -> tuple[np.ndarray, np.ndarray]` is the per-sample counterpart used for `plotting.plot_silhouette_analysis` (production time, not the sweep above, see `docs/dev/plotting.md`): same noise-exclusion convention as `compute_clustering_metrics`, but returns `(non_noise_labels, sample_silhouette_values)` from `sklearn.metrics.silhouette_samples` instead of one aggregate number - their mean equals `compute_clustering_metrics`'s `"silhouette"` exactly. Unlike `compute_clustering_metrics`'s NaN-and-warn on a degenerate combination (built for an unattended sweep over many combinations), this **raises** `ValueError` - it runs once for the single already-chosen production result, so the caller (`clustering.py`'s `_run_one_method`) decides whether to skip the plot, catching that specific exception and logging a warning rather than failing the whole run.

`dunn_index(X, labels) -> float` (2026-08, `project-clustering-tuning-evaluation-tables` memory): Dunn Index (Dunn 1974) - ratio of the smallest inter-cluster distance to the largest intra-cluster diameter, higher is better (opposite direction from Davies-Bouldin). Never implemented in this repo before this addition, no sklearn/scipy built-in exists - a from-scratch implementation on `sklearn.metrics.pairwise_distances` (Euclidean by default, same assumption as `compute_clustering_metrics`, not metric-aware). Same noise-exclusion convention as `compute_clustering_metrics`/`compute_silhouette_samples`; raises `ValueError` for fewer than 2 non-noise clusters, or when every non-noise cluster is a singleton (every intra-cluster diameter is `0.0`, which would make the ratio a division by zero). Consumed by `notebooks/post-results_analysis/clustering_evaluation.ipynb` (`docs/guides/evaluation.md`), not wired into `run_clustering_tuning_sweep`'s own per-combination columns (DBCV was explicitly rejected for the same table - see the hdbscan section below - Dunn wasn't rejected, but adding it to the production/tuning sweep itself was out of scope for this addition).

`run_clustering_tuning_sweep(method, X, base_params, tuning_grid, consensus_config=None) -> (pd.DataFrame, dict[tuple, np.ndarray])` mirrors `tuning.py`'s sweep shape (Cartesian product, swept keys override `base_params`; the returned dict keys each combination's already-computed cluster-label array by its `combo` tuple, same role as `tuning.py`'s `embeddings_by_combo` - see `save_tuning_clusterings` below), but two methods get an extra scalar column beyond the 3 generic ones, computed by refitting the actual estimator instead of going through `CLUSTERING_METHODS[method]` (which only returns labels): `_kmeans_with_extra_metrics` keeps `KMeans.inertia_` (the elbow criterion), `_gmm_with_extra_metrics` keeps `GaussianMixture.bic(X)`/`.aic(X)` (likelihood-based, unlike the other 3 which are purely geometric) - `_EXTRA_METRICS_EVALUATORS` dispatches by method name, absent for the other 3 (agglomerative/hdbscan/spectral get only the 3 generic columns from their swept grid). `METHOD_METRIC_COLUMNS: dict[str, list[str]]` is the single source of truth `clustering.py` reads to know which columns a given method's sweep will produce (and therefore which to plot) - `noise_fraction` is only listed for `"hdbscan"` even though `compute_clustering_metrics` always returns it, since it's mechanically 0.0 for every other method (never noise-producing) and plotting a flat line adds nothing.

**GMM's `covariance_type` (project-clustering-tuning-redesign memory, 26-08-26)**: unlike agglomerative's `linkage`×`metric` (some pairings invalid) or kmeans's `k`×`init` (deliberately never a joint grid), `n_components` × `covariance_type` is a legitimate **joint** sweep with zero code change to `run_clustering_tuning_sweep` - `covariance_type` is just another key in `tuning_grid`, reaching `GaussianMixture(**params)` through the exact same `_gmm_with_extra_metrics` path every other swept key already does. AIC/BIC (already computed, see above) are the statistically correct tool to compare `covariance_type` values (they penalize by the number of free parameters, which is exactly what differs between e.g. `"full"` and `"spherical"`) - this is the standard GMM model-selection technique (Fraley & Raftery 1998/2002; sklearn's own `plot_gmm_selection.html` worked example grids the same two keys), not a compromise. `config/registry/params_clustering.json`'s checked-in `"gmm".tuning_grid` sweeps both.

Two methods also get a standalone diagnostic, independent of which value in the swept grid ends up chosen (`STANDALONE_DIAGNOSTIC_METHODS = {"agglomerative", "spectral"}`). **Fixed 28-08-26**: both used to be computed once from `base_params` alone, silently never reflecting the *other* swept axis relevant to that diagnostic (`metric` for the dendrogram, `affinity`/its hyperparameter for the eigengap) - documented as a known limitation for the dendrogram in `clustering_tuning_guide.md` before being fixed here; the eigengap had the identical gap, found only while fixing the first one. Both diagnostics now group by that axis (one file per value) with a subplot per value of the other, mirroring `compute_interclass_distance_matrix`'s existing per-metric grouping below:
- `compute_dendrogram_linkage(X, params) -> np.ndarray` refits `AgglomerativeClustering` with `n_clusters=None, distance_threshold=0, compute_distances=True` (forces the full merge tree down to singleton leaves, ignoring any `n_clusters`/`distance_threshold` already in `params`), then converts `children_`/`distances_` into the scipy linkage-matrix format `plotting.plot_dendrograms_grid` (`docs/dev/plotting.md`) expects (the standard sklearn-docs recipe for bridging the two). `clustering.py::_write_agglomerative_diagnostics` calls it once per `(metric, linkage)` combination - every swept `metric` value (or `base_params`/default `"euclidean"` alone when `metric` isn't swept) × every swept `linkage` value valid for that metric (`is_invalid_ward_metric_combo` skips `ward`+non-euclidean, same rule the sweep itself applies) - and writes one `dendrogram_metric=<metric>.png` per metric, with one subplot per valid linkage inside (`plot_dendrograms_grid`).
- `compute_eigengap(X, params, max_k=20) -> np.ndarray` builds the same affinity graph `spectral_cluster` would (`"nearest_neighbors"` via `sklearn.neighbors.kneighbors_graph` symmetrized, or `"rbf"` via `sklearn.metrics.pairwise.rbf_kernel` - `ValueError` for any other `affinity`), computes the normalized graph Laplacian (`scipy.sparse.csgraph.laplacian`) and its smallest `max_k` eigenvalues (`scipy.linalg.eigh`, `subset_by_index`) - the eigengap heuristic (`plotting.plot_eigengaps_grid`, `docs/dev/plotting.md`) reads a suggested `n_clusters` off the biggest gap between consecutive values, a criterion with actual theoretical grounding for spectral clustering specifically (a Laplacian's near-zero-eigenvalue multiplicity approximates the count of well-separated graph components), unlike the generic geometric indices applied to the other methods. `clustering.py::_write_spectral_diagnostics` calls it once per `(affinity, hyperparameter)` combination - every swept `affinity` value (or `base_params`/default `"rbf"` alone when `affinity` isn't swept) × every swept value of that affinity's own hyperparameter (`SPECTRAL_AFFINITY_HYPERPARAM`: `n_neighbors` for `nearest_neighbors`, `gamma` for `rbf`) - and writes one `eigengap_affinity=<affinity>.png` per affinity, with one subplot per hyperparameter value inside.

HDBSCAN (which replaced DBSCAN) gets no standalone diagnostic: DBSCAN had one (`compute_k_distance`, a sorted distance-to-`min_samples`-th-neighbor plot for reading off a reasonable `eps` by eye) because it needs a single global distance threshold; HDBSCAN has no such threshold to read off a plot - `min_cluster_size` is judged directly from the swept `noise_fraction`/silhouette columns instead, so `compute_k_distance`/`plotting.plot_k_distance` were removed rather than kept unused.

### HDBSCAN — `min_samples` joint sweep + probabilities_-sized production scatter

Per the `project-clustering-tuning-redesign` design record (26-08-26 - checked against sklearn's own official HDBSCAN example, `plot_hdbscan.html`, sklearn 1.9.0, the same `sklearn.cluster.HDBSCAN` this repo already uses, not the standalone `hdbscan` package): DBCV/condensation-tree diagnostics were considered and explicitly dropped - even sklearn's own canonical example uses neither, only a scatter with marker size scaled by `probabilities_` plus visual/ground-truth inspection, so a new dependency (the standalone `hdbscan` package, `environment.yml` change) wasn't judged worth it for something the most authoritative source doesn't consider necessary.

`min_samples` was added to `tuning_grid` alongside `min_cluster_size` (`config/registry/params_clustering.json`'s checked-in `"hdbscan"` entry) - deterministic like agglomerative (no `random_state`), so both axes are swept **jointly in one run** (the user's explicit constraint: no repeated/sequential tuning runs), reusing `plotting.plot_clustering_tuning_heatmaps` as-is - the same 2-swept-param heatmap mechanism already built for agglomerative's `n_clusters`×`linkage` - zero new plotting code for the tuning side. `run_clustering_tuning_sweep` itself needed no change either: HDBSCAN's `combo_params` never carries `"affinity"`/`"metric"`, so `compute_clustering_metrics`'s existing euclidean guard always passes through.

The one genuinely new piece: `hdbscan_labels_and_probabilities(X, params) -> (labels_, probabilities_)` (`clustering_tuning.py`) fits `HDBSCAN` directly and returns both arrays - `CLUSTERING_METHODS["hdbscan"]` (`hdbscan_cluster`) stays labels-only, the uniform contract every generic caller (the sweep, `run_rsc_repeats`, ...) relies on, so `probabilities_` (per-point membership confidence, always `0` for noise) is only reachable this way. `clustering.py::_run_one_method`'s production path calls it specifically for `method == "hdbscan"` (every other method still goes through `CLUSTERING_METHODS[method]`), feeding the result into `plotting.plot_clusters_2d`'s new optional `point_sizes` parameter - `None` (every other method, and every prior call site) is byte-for-byte the original fixed-`_MARKER_SIZE` behavior; when given, each marker's area scales with its own value, floored at `_POINT_SIZE_FLOOR` so a 0-probability noise point stays visible instead of collapsing to nothing. `sns.scatterplot`'s own legend-building breaks on an array-like `s=` (it reuses the array verbatim as a single legend marker size) - the `point_sizes`-given branch builds the categorical legend by hand via `plt.Line2D` instead of `sns.scatterplot`, matplotlib's own `ax.scatter` has no such issue.

`clustering.py`'s `_write_standalone_diagnostic` dispatches to whichever of the 2 applies via an explicit `if/elif` (not a registry - kept as an explicit dispatch for symmetry with when a third branch existed) and raises `ValueError` for any method outside `STANDALONE_DIAGNOSTIC_METHODS` rather than silently no-oping.

### Agglomerative's metric-aware sweep — `n_clusters` x `linkage` x `metric`

Per the `project-clustering-tuning-redesign` design record (26-08-26): unlike every other `CLUSTERING_METHODS` entry, agglomerative is deterministic given `(X, linkage, metric)` (no `random_state`) - sweeping `linkage`/`metric` directly alongside `n_clusters` is methodologically fine, no stability pre-check needed. But the grid is deliberately **not a full cube**: sklearn's own `AgglomerativeClustering` `metric` docstring - *"If linkage is 'ward', only 'euclidean' and 'l2' are accepted"* - makes `linkage="ward"` + a non-euclidean `metric` an invalid combination. `is_invalid_ward_metric_combo(combo_params) -> bool` (`clustering_tuning.py` - public since 28-08-26, also reused by `clustering.py::_write_agglomerative_diagnostics` to skip the same invalid pairing when building per-metric dendrograms) flags exactly that; `run_clustering_tuning_sweep`'s main loop skips a flagged combination with a logged warning (never lets sklearn's own `ValueError` crash the sweep, never silently drops it either).

For every surviving combination, `run_clustering_tuning_sweep` routes agglomerative through a dedicated branch instead of the generic `compute_clustering_metrics`/`_require_euclidean_compatible` guard (which would blanket-abort the whole sweep the moment `metric` isn't euclidean-safe - too coarse for a method whose whole point here is exploring non-euclidean metrics):
- `_agglomerative_fit_metric_aware(X, params) -> (labels, metric)` fits `AgglomerativeClustering` with `metric` honored directly for every native sklearn string (`euclidean`/`cosine`/`manhattan`/...); `jaccard`/`dice` (`distances.py::SUPPORTED_BINARY_METRICS`, no native sklearn string) are precomputed first via `distances.py::precomputed_distance` and fit with `metric="precomputed"` (lesson #29 - reuses the same precompute machinery already built for umap/t-SNE, no new plumbing).
- `compute_clustering_metrics_metric_aware(X, labels, metric) -> dict[str, float]` always keeps silhouette (`sklearn.metrics.silhouette_score` accepts any metric string or `"precomputed"` - lesson #15, thread the same metric used for clustering into scoring), but Calinski-Harabasz/Davies-Bouldin are mathematically euclidean-only (centroid-based, no `metric` parameter exists for them at all) - `NaN` for any other metric, not aborted. Same degenerate-combination NaN-and-warn convention as `compute_clustering_metrics`; `noise_fraction` is always `0.0` (agglomerative never produces the HDBSCAN-style `-1` label).

**Interclass distance matrix diagnostic** (new, modeled on sklearn's `plot_agglomerative_clustering_metrics.html` "interclass distance matrix" panel): independent of any clustering fit - a metric-selection pre-check, and the substitute diagnostic for combinations where Calinski-Harabasz/Davies-Bouldin were skipped above. `compute_interclass_distance_matrix(X, proxy_labels, metric) -> (groups, matrix)` computes the average pairwise distance within (diagonal) vs. between (off-diagonal) groups of a weak ground-truth `proxy_labels` grouping (`clustering.py::_write_agglomerative_diagnostics` uses each subject's `"dataset"` metadata column as that proxy - vascular territory/lesion side are noted as other candidates in the design record, not yet wired since no such column exists in `metadata` today; skipped with a logged warning, not a sweep failure, when `metadata` has no `"dataset"` column at all). A group with fewer than 2 members has an undefined within-group spread, recorded as `NaN` (not `0.0`, which would misrepresent "no data" as "identical"). `plotting.plot_interclass_distance_matrix(results_by_metric, output_path, title)` (`docs/dev/plotting.md`) lays out one heatmap subplot per metric in `results_by_metric` - computed once per swept `metric` value (or the `base_params`/default `"euclidean"` alone when `metric` isn't swept), written to `interclass_distance_matrix.png` alongside the per-metric dendrogram file(s) above.

`config/registry/params_clustering.json`'s checked-in `"agglomerative".tuning_grid` now sweeps all 3 axes (`n_clusters` x `linkage` x `metric`, `metric` candidates `euclidean`/`cosine`/`manhattan`/`dice` per the design record) - with 3 swept keys, `_write_tuning_output`'s generic 1-or-2-param `tuning_plot.png` is skipped (logged warning, existing behavior, unchanged code path) in favor of the two diagnostics above, which are the actually-informative outputs for this method's redesign.

`consensus_suggestion_lines(results, method) -> list[str]` reads `rsc_eigengap`/`monti_stability` columns (if present in `results`) and returns the "RSC suggests .../Monti suggests ..." lines described below - empty list when neither column is present. Pure text formatting, called from `clustering.py`'s `_write_tuning_output`. Written to its own `consensus_suggestions.md` (only when the list is non-empty), a sibling of `tuning_results.csv`/`config.md` in the tuning output dir - deliberately **not** appended into `config.md` itself: that file is a static snapshot of how the run was launched (config JSON, swept params, combinations evaluated), and a computed suggestion doesn't belong mixed into a historical launch record.

### Stability analysis (kmeans/gmm) — init/n_init validation before trusting the sweep

Per the `project-clustering-tuning-redesign` design record (26-08-26): `k`/`n_components` is the real target hyperparameter for kmeans/gmm, but both methods converge to a local optimum of their own objective (inertia for k-means, log-likelihood for GMM's EM) depending on random init - a plain sweep over `k`/`n_components` alone never validates that its own `init`/`n_init` choice is actually stable. `k` and `init` are deliberately **not** swept as a joint 2D grid (a heatmap was explicitly rejected) - instead, `init`/`n_init` is validated once, separately, at a handful of representative target values, *before* trusting the plain sweep's per-target scores.

`STABILITY_ELIGIBLE_METHODS = {"kmeans", "gmm"}` (`clustering_tuning.py`) - the only 2 `CLUSTERING_METHODS` with this genuine random-init instability; agglomerative/hdbscan are deterministic given the data, spectral's own k-means-inherited instability is instead removed at the source (`assign_labels="cluster_qr"`, see the spectral section below), so none of the 3 need this diagnostic. `STABILITY_TARGET_PARAM`/`STABILITY_NUISANCE_PARAM`/`STABILITY_METRIC_NAME` map each eligible method to its own hyperparameter names/scored metric (kmeans: `n_clusters`/`init`/`inertia`; gmm: `n_components`/`init_params`/`bic`) - one generic sweep function serves both, only these 3 lookups differ per method.

`representative_values(values: list[int]) -> list[int]`: min/median/max of a swept list, deduplicated and sorted (e.g. `[2,3,4,5,6,8,10] -> [2,6,10]`) - instability generally grows with the target value, so validating at a single point of `tuning_grid` doesn't generalize across its whole range. Raises `ValueError` on an empty list.

`compute_stability_sweep(method, X, target_values, nuisance_values, n_init_range, n_repeats) -> pd.DataFrame`: for each `(target, nuisance, n_init)` combination, repeats a fit `n_repeats` times varying only `random_state`, recording the method's own metric - long-form, one row per `(target, nuisance, n_init, repeat)`, aggregated (mean ± std per `n_init`) only at plot time. `target_values` is typically `representative_values(tuning_grid[STABILITY_TARGET_PARAM[method]])`, not the full swept range - the caller (`clustering.py::_write_stability_output`) decides that; this function only runs the grid it's given. Raises `ValueError` for a method outside `STABILITY_ELIGIBLE_METHODS`.

`plotting.plot_stability_analysis(df, target_param, nuisance_param, metric_col, output_path, title)` (`docs/dev/plotting.md`): one panel per unique `target_param` value, errorbar mean ± std(`metric_col`) vs `n_init`, one line per `nuisance_param` value - modeled on sklearn's `plot_kmeans_stability_low_dim_dense.html`, faceted across the representative target values instead of a single one.

Config: `params.py::load_stability_config(params_file, method) -> dict | None` loads the optional `"stability"` block (`{"nuisance_values": [...], "n_init_range": [...], "n_repeats": int}` - `docs/dev/config.md`) - absent means "not requested" (`None`), present for a method outside `STABILITY_ELIGIBLE_METHODS` or malformed raises `ValueError`. The representative target values are deliberately **not** part of this block - they're always derived from the method's own `tuning_grid`, never declared separately (a second source of truth for the same values would drift). Wired into `clustering.py::_run_one_method_tuning`: when a `"stability"` block is present, `_write_stability_output` runs after the plain sweep completes, writing `stability_results.csv`/`stability_plot.png` into the same tuning output directory - a failure here (bad `tuning_grid`/sklearn `ValueError`) fails the whole method's tuning run, same fail-fast philosophy as every other tuning step.

### Spectral — `assign_labels="cluster_qr"` + `affinity`×(`n_neighbors`/`gamma`) sweep

Per the `project-clustering-tuning-redesign` design record (26-08-26/27-08-26): `compute_eigengap` (above) was judged "already covered" at design time - same shape as kmeans's inertia elbow/GMM's AIC-BIC. Its *plotting* wasn't left unchanged though: `plotting.plot_eigengaps_grid` (28-08-26 fix, above) now groups by `affinity` with a subplot per hyperparameter value, the same gap found for the dendrogram.

**Hidden instability found and removed at the source**: `SpectralClustering`'s `assign_labels` parameter (the final label-assignment step on the Laplacian eigenvectors) defaults to `"kmeans"` in sklearn - our config never overrode it, so `spectral` silently inherited k-means's own seed-sensitivity (sklearn's own `random_state` docstring: *"used for [...] the K-Means initialization"* when `assign_labels='kmeans'`). Resolved **without** a stability analysis (unlike kmeans/gmm, which needed one because `init`/`n_init` are their only options): sklearn's own `assign_labels` docstring recommends an alternative - *"The cluster_qr method directly extract[s] clusters from eigenvectors in spectral clustering. In contrast to k-means and discretization, cluster_qr has no tuning parameters and runs no iterations, yet may outperform k-means and discretization in terms of both quality and speed."* `config/registry/params_clustering.json`'s checked-in `"spectral"` and `"evidence_accumulation"` (`base_method="spectral"`) entries now fix `"assign_labels": "cluster_qr"` explicitly in `"params"` - deterministic, no seed variance to validate, no new run needed.

**`affinity`×its own hyperparameter** - same asymmetric-grid shape as agglomerative's `linkage`×`metric`, but the risk here is wasted compute, not an invalid sklearn combination (sklearn silently ignores whichever of `n_neighbors`/`gamma` doesn't apply to the chosen `affinity`, it doesn't raise): `run_spectral_affinity_aware_sweep(X, base_params, tuning_grid, consensus_config=None) -> (pd.DataFrame, dict[tuple, np.ndarray])` (`clustering_tuning.py`) requires `"affinity"` to be a `tuning_grid` key, and runs `run_clustering_tuning_sweep` once per swept `affinity` value (`SPECTRAL_AFFINITY_HYPERPARAM = {"nearest_neighbors": "n_neighbors", "rbf": "gamma"}` picks each sub-sweep's own extra hyperparameter), concatenating the results with an explicit `"affinity"` column - `"n_neighbors"`/`"gamma"` end up `NaN` on the rows of the affinity they don't apply to (an artifact of `pd.concat`, not a degenerate combination). `clustering.py::_run_one_method_tuning` dispatches to it only when `"affinity"` is actually a swept key; the plain `n_clusters`-only sweep (no `"affinity"` swept, e.g. any pre-existing config) is entirely unaffected, still goes through `run_clustering_tuning_sweep` directly.

`plotting.plot_spectral_tuning(df, param_col, metric_cols, output_path, title)` renders the result: one subplot per metric, one line per `(affinity, hyperparameter)` combination (label built from whichever of `n_neighbors`/`gamma` is actually set for that row) - `clustering.py::_write_tuning_output` calls it instead of the generic 1-or-2-swept-param dispatch specifically when `method == "spectral" and "affinity" in tuning_grid`, writing to the same `tuning_plot.png` filename every other method uses (`param_col` is whichever other `tuning_grid` key isn't `affinity`/`n_neighbors`/`gamma` - typically `n_clusters`; a shape with more than 1 such key logs a warning and skips the plot, same fallback spirit as the generic dispatch's `>2`-param case).

**Known limitation, by design, not a gap**: `config.save_tuning_clusterings` is rejected upfront (clear `ValueError`-shaped `logging.error` + `return False`, not a silent misalignment) when combined with a swept `"affinity"` - `run_spectral_affinity_aware_sweep`'s `labels_by_combo` keys are `(affinity, *sub_combo)`, where `sub_combo`'s own key order varies per affinity sub-sweep (each restricted to only its own hyperparameter), so it never lines up with the full `tuning_grid.keys()` order `_write_tuning_clusterings`/`_combo_key` assume for every other method's sweep.

**Considered and rejected as out of scope**: `SpectralBiclustering` (clusters rows AND columns of a matrix simultaneously, meant for checkerboard-structured data like genomics/images) is a genuinely different algorithm, not a tuning variant of `SpectralClustering` - would be a 7th `CLUSTERING_METHODS` entry if ever pursued, not part of this redesign.

## `src/analysis/consensus_clustering.py` — consensus/stability clustering (RSC + Monti)

Two literature methods scoring how *stable* a candidate `k` is (as opposed to how *good* it looks on a single run, all silhouette/Calinski-Harabasz/Davies-Bouldin can say) - restricted to `CONSENSUS_ELIGIBLE_METHODS = {"kmeans", "gmm", "spectral"}` (`K_PARAM_NAME` maps each to its own "how many clusters" parameter name: `n_clusters` for kmeans/spectral, `n_components` for gmm), since these are the only 3 with genuine internal stochasticity to exploit without touching the data itself - a repeat of `agglomerative`/`hdbscan` with a different seed reproduces the identical partition (deterministic given the same input), so a "co-occurrence matrix" for them would be degenerate (all 0s/1s, no information).

- `run_rsc_repeats(method, X, params, n_repeats, base_seed=0) -> np.ndarray`: RSC (Tshimanga et al. 2025, cited by Zanola et al. 2026 - `knowledge/Zanola et al - 2026 - ...`) - `n_repeats` runs of `CLUSTERING_METHODS[method]` on the full, unmodified `X`, only `random_state` varying (`base_seed + i`). Returns the `(n_samples, n_samples)` co-occurrence matrix (fraction of runs where each pair shared a cluster).
- `run_monti_repeats(method, X, params, n_repeats, subsample_fraction, base_seed=0) -> np.ndarray`: Monti et al. 2003 - `n_repeats` runs, each on an `np.random.default_rng`-drawn subsample (without replacement, size `round(subsample_fraction * n_samples)`) of subjects. Returns the `(n_samples, n_samples)` consensus matrix (co-clustered / co-sampled per pair, conditioned on both having been drawn together) - raises `ValueError` if any pair was never jointly sampled across all `n_repeats` draws (too few repeats/too small a fraction for this `n_samples` - an explicit failure, never a silent `NaN`/`0`).
- `compute_rsc_eigengap(cooccurrence_matrix, k) -> float`: gap between the `(k+1)`-th and `k`-th (1-indexed) sorted eigenvalues of the co-occurrence matrix's normalized Laplacian (`AUDIT_FINDINGS.md` #58 - wording fixed to match what the code actually computes) (`scipy.sparse.csgraph.laplacian(..., normed=True)` + `scipy.linalg.eigh`, same machinery as `clustering_tuning.compute_eigengap` but applied to `C` itself as the affinity, and reading the specific position-`k` gap rather than the biggest gap anywhere - matches the paper's own selection criterion, compared across the different `C_k` built per candidate `k`).
- `compute_monti_stability(consensus_matrix, ambiguous_band=(0.1, 0.9)) -> float`: `1 - PAC` (Proportion of Ambiguous Clustering - fraction of the consensus matrix's upper-triangle entries falling inside `ambiguous_band`). Deliberate deviation from Monti et al. 2003's own area-under-CDF statistic, per Șenbabaoğlu et al. 2014's finding that it's biased toward larger `k` - PAC is the standard fix (e.g. `ConsensusClusterPlus`), not an invention here.

`subsampling_stability_index(method, X, params, subsample_fraction, base_seed=0) -> float` (2026-08, `project-clustering-tuning-evaluation-tables` memory): a lighter sibling of `run_monti_repeats` above - a single full-vs-one-subsample comparison (Adjusted Rand Index between a fit on all of `X` and the same `method`/`params` refit on one random `subsample_fraction` subsample, without replacement), not an `n_repeats` co-occurrence ensemble. Deliberately **not** restricted to `CONSENSUS_ELIGIBLE_METHODS`: unlike `run_rsc_repeats`/`run_monti_repeats` (meaningless for a deterministic method - repeating it gives an identical result every time), a single full-vs-subsample comparison is meaningful for any `CLUSTERING_METHODS` entry, deterministic or not (e.g. `agglomerative`). Raises `ValueError` for an unregistered `method`, an out-of-range `subsample_fraction`, or a subsample smaller than 2 points. Reuses only `CLUSTERING_METHODS` and the same `rng.choice` draw-without-replacement shape as `run_monti_repeats` - not its co-occurrence-matrix machinery, a different output shape for a different question. Consumed by `notebooks/post-results_analysis/clustering_evaluation.ipynb` (`docs/guides/evaluation.md`), not wired into any production/tuning config.

Wired into `clustering_tuning.run_clustering_tuning_sweep` via an optional `consensus_config` parameter (`None` by default - zero behavior change to any pre-existing call): `{"rsc": {"n_repeats": int}, "monti": {"n_repeats": int, "subsample_fraction": float}}`, either/both keys, adding `"rsc_eigengap"`/`"monti_stability"` columns per swept row (`k` read straight off that row's own already-built `combo_params[K_PARAM_NAME[method]]`, since it's exactly what `tuning_grid` swept to produce it). `CONSENSUS_METRIC_COLUMNS = ("rsc_eigengap", "monti_stability")` in `clustering_tuning.py` is a fixed constant (not merged into the static `METHOD_METRIC_COLUMNS`, since it's opt-in/conditional) - both pipelines extend their own `metric_cols` with `[c for c in CONSENSUS_METRIC_COLUMNS if c in results.columns]` before plotting, so the subplot grid only ever includes columns that actually got computed. Loaded via `params.py::load_consensus_config(params_file, method) -> dict | None` (`docs/dev/config.md`) (absent `"consensus"` key -> `None`, a legitimate "not requested" case; present for a method outside `CONSENSUS_ELIGIBLE_METHODS`, or malformed, raises `ValueError` - an impossible config must fail loudly, never be silently ignored, per `code_standards.md` §0). Not registered in the checked-in `config/registry/params_clustering.json` by default - fully opt-in, see `docs/guides/clustering.md` for the JSON block to add.

### `assign_clusters_from_cooccurrence` + `CLUSTERING_METHODS["evidence_accumulation"]` (2026-08) - Evidence Accumulation Clustering as a production method, not just a diagnostic

Everything above (`run_rsc_repeats`/`compute_rsc_eigengap`) only ever scores *how stable* an already-chosen `k` is for some other method's sweep - it never produced cluster labels of its own. `assign_clusters_from_cooccurrence(co_occurrence_matrix, threshold) -> np.ndarray` closes that gap: Fred & Jain's own "Merge" step (2002, ICPR, "Data clustering using evidence accumulation" - `knowledge/sota/Fred et al - 2002 - Data clustering using evidence accumulation.md` - the exact paper Zanola cites) - implemented as **single-link** hierarchical clustering (`scipy.cluster.hierarchy.linkage`, `method="single"`) on `1 - co_occurrence_matrix` as a distance, cut at the paper's own fixed similarity **threshold** `t` (`fcluster(..., criterion="distance", t=1.0 - threshold)` - merging pairs with `co_assoc(i,j) > t` is exactly merging pairs with `distance(i,j) < 1 - t`), matching the paper's "cutting weak links at a threshold of t... equivalent to cutting the dendrogram produced by the single link (SL) method... at threshold t" exactly - **no deviation** (`AUDIT_FINDINGS.md` #14, fixed 26-08-26: this paragraph previously described the opposite, a fixed-`n_clusters`/`criterion="maxclust"` cut that was never actually implemented - the code and its own docstring were already correct, only this paragraph was wrong). Method-agnostic: doesn't care whether `co_occurrence_matrix` came from repeated kmeans, gmm, or spectral. The number of final clusters is *not* chosen in advance - it emerges from how many connected components survive the threshold cut, per the paper's own recommended default `t = 0.5` ("patterns... co-located in a cluster at least 50% of the times"). Zanola et al. 2026's RSC ("the final cluster assignment is based on the co-occurrence matrix C") doesn't specify which cut criterion it uses either (deferred to Tshimanga et al. 2025, not available in `knowledge/`) - only Fred & Jain's own threshold-based variant is implemented here. Returns 0-indexed labels (`fcluster` is 1-indexed; every `CLUSTERING_METHODS` function returns 0-indexed).

`clustering.py::evidence_accumulation_cluster(X, params) -> np.ndarray`, registered as `CLUSTERING_METHODS["evidence_accumulation"]`: reads `params["base_method"]` (required, must be in `CONSENSUS_ELIGIBLE_METHODS = {"kmeans", "gmm", "spectral"}`), repeats it `params["n_repeats"]` times via `run_rsc_repeats(base_method, X, params, n_repeats, base_seed)`, then calls `assign_clusters_from_cooccurrence` on the resulting co-occurrence matrix - `base_method="spectral"` reproduces Zanola et al. 2026's RSC exactly; `"kmeans"`/`"gmm"` are equally valid, since Fred & Jain's algorithm never fixes the base clusterer (deliberately *not* a separate branded `"rsc"` method - that would have hardcoded a choice the underlying algorithm doesn't make). `params` needs `base_method`'s own hyperparameters (e.g. for `"spectral"`: `n_clusters`, `affinity`, `n_neighbors`/`gamma`) plus `n_repeats` (required) and `base_seed` (optional, default 0); the "how many clusters" key is read via `K_PARAM_NAME[base_method]` (`n_clusters` for kmeans/spectral, `n_components` for gmm) and used only for the **Split** phase (each of the `n_repeats` runs) - the **Merge**-phase cut is a deliberately separate knob, `params["threshold"]` (the paper's `t`), forwarded straight to `assign_clusters_from_cooccurrence` (fixed alongside `AUDIT_FINDINGS.md` #14 above; this sentence previously implied the Split-phase key was reused for the final cut too, which the code never did). A fixed `random_state` is rejected with `ValueError` rather than silently accepted or overridden - each of the `n_repeats` runs must get its own seed (`base_seed + i`), a single shared one would make every repeat identical (degenerate all-0/1 co-occurrence). Config entry: `config/registry/params_clustering.json`'s `"evidence_accumulation"` (`tag_param`/`tag_prefix` same shape as `"kmeans"`, since the tag is about `n_clusters`; default `base_method` there is `"spectral"`, matching Zanola's own choice, but any `CONSENSUS_ELIGIBLE_METHODS` value works).

Since `run_rsc_repeats`/`assign_clusters_from_cooccurrence` live in `consensus_clustering.py`, which already imports `CLUSTERING_METHODS` from `clustering.py` (for the generic diagnostics above), `evidence_accumulation_cluster` imports them back with a **local import inside the function body**, not at module top - a module-level import in that direction would be circular (`clustering.py` → `consensus_clustering.py` → `clustering.py`, the second module partially initialized). Deliberate, commented in place, not an accident.

To choose `n_clusters` for a production `"evidence_accumulation"` run: sweep `n_clusters` fine-tuning the same `base_method` directly (e.g. `"spectral"`, not `"evidence_accumulation"`) with `consensus_config={"rsc": {"n_repeats": ...}}` - that sweep's `rsc_eigengap` column and `consensus_suggestions.md` already implement exactly Zanola's own model-selection criterion (max spectral gap on the co-occurrence matrix, compared across candidate `k`) when `base_method="spectral"`. `"evidence_accumulation"` itself is excluded from `CONSENSUS_ELIGIBLE_METHODS` on purpose (unchanged by this addition) - it already aggregates over `n_repeats` internally, so wrapping it in an outer reseed/resample diagnostic doesn't add information, and would immediately hit the `random_state` rejection above if attempted.

### evidence_accumulation's tuning redesign — `threshold`×Split-`k` sweep + convergence check + consensus matrix heatmap

Per the `project-clustering-tuning-redesign` design record (26-08-26/27-08-26, last of the 6 `CLUSTERING_METHODS` addressed): unlike kmeans/gmm/spectral, evidence_accumulation needs no *external* stability check - the `n_repeats` runs *are* the algorithm's own built-in answer to base-method instability, that's the whole point of "accumulating evidence" across repeats. The redesign here validates two of the paper's own loosely-specified assumptions instead.

**Clarification reached in discussion, settling a real user question** ("does `consensus_config`'s RSC/Monti diagnostic make sense in production for every method, like a kind of tuning?"): `run_rsc_repeats`/`run_monti_repeats` back two genuinely different *uses* of the same math - **Mode A** is the existing `consensus_config` block wired into kmeans/gmm/spectral's own tuning sweep (`rsc_eigengap`/`monti_stability` columns above): a `k`-*selection* diagnostic, repeating a fit at each candidate `k` to score how stable each candidate is. **Mode B** is `evidence_accumulation` itself: no `k` is ever chosen in advance - it repeats a base method at an *abundant* Split-phase `k` (larger than the true expected count) and derives final labels directly from the co-occurrence matrix, the cluster count *emerges* from the data. The user explicitly wants Mode B, not Mode A ("non voglio selezionare il k, voglio usarlo come nel paper") - **Mode A's `consensus_config` diagnostic stays exactly as it is**, not extended, not moved to production (an earlier idea in the same discussion to do so is retracted - it was still framed around "certifying a chosen k", not this method's actual goal).

**(1) `threshold`×Split-phase `K_PARAM_NAME[base_method]` joint sweep**: unswept before this redesign (`threshold` was the only swept key; the Split-phase `k`, e.g. `n_clusters` for `base_method="spectral"`/`"kmeans"`, sat fixed in `base_params`). Needs **zero code change** to `run_clustering_tuning_sweep` - a bigger `tuning_grid` just means more entries in the sweep's existing per-split-param co-occurrence cache (`AUDIT_FINDINGS.md` #35, `_evidence_accumulation_labels`'s `cooccurrence_cache`, already efficient), not a new caching mechanism. What *is* new: `clustering.py::_write_tuning_output` writes `tuning_plot.png` via `plotting.plot_grouped_tuning_metrics(results, "threshold", split_k_param, metric_cols, ...)` - one line per Split-phase `k` value, `x=threshold` - instead of the generic 2-swept-param heatmap, whenever `method == "evidence_accumulation" and "threshold" in tuning_grid and len(swept_params) == 2` (a plain `threshold`-only sweep, 1 swept param, is entirely unaffected - unchanged line-plot dispatch). Lets a human read whether the Merge-phase result is sensitive to "how much larger than expected" the Split decomposition was, per the paper's own loosely-specified assumption.

**(2) `n_repeats` convergence check** (new): does the co-occurrence matrix actually stabilize as `n_repeats` grows, or is `base_params`' own default (`50`) arbitrary? `consensus_clustering.compute_evidence_accumulation_convergence(base_method, X, split_params, checkpoints, base_seed=0) -> pd.DataFrame` builds the co-occurrence matrix **incrementally**, one `base_method` fit at a time, scoring `compute_monti_stability`'s PAC-style stability at each requested checkpoint (`{"n_repeats", "stability_score"}` rows) - never refit from scratch per checkpoint, standard practice for ensemble/consensus methods. `clustering.py::_default_convergence_checkpoints(n_repeats)` picks 5 evenly-spaced checkpoints (10/25/50/75/100% of `base_params`' own `n_repeats`, floored at 1, deduplicated) with no separate config field needed. Plotted via the already-existing `plotting.plot_tuning_curve` (same `(param_col, metric_col)` shape it already supports, no new plotting code) into `n_repeats_convergence.csv`/`.png`.

**(3) Consensus matrix heatmap** (new, Monti et al. 2003's own headline visualization, already cited by name in `consensus_clustering.py`'s module docstring): `plotting.plot_consensus_matrix_heatmap(co_occurrence, labels, output_path, title)` plots the co-occurrence matrix with subjects reordered by their final cluster assignment (`np.argsort(labels)`) - block-diagonal = confident/clean clusters at that threshold, fuzzy = an ambiguous cut. Computed at `base_params`' own `n_repeats`/`threshold` (via `run_rsc_repeats`/`assign_clusters_from_cooccurrence`, reused as-is, no new consensus machinery).

All 3 are wired as a new standalone diagnostic (`clustering.py::_write_evidence_accumulation_diagnostics`, dispatched from `_write_standalone_diagnostic` like agglomerative's/spectral's) - `STANDALONE_DIAGNOSTIC_METHODS` now includes `"evidence_accumulation"` (3 methods, not 2). `config/registry/params_clustering.json`'s checked-in `"evidence_accumulation".tuning_grid` now sweeps both `threshold` and `n_clusters` (the Split phase); `"assign_labels": "cluster_qr"` was also added to its `"params"` (same fix as spectral's own entry, since `base_method="spectral"` here inherits the identical hidden instability).

**Known open question, not yet resolved (AUDIT_FINDINGS.md #37)**: `config/registry/params_clustering.json`'s `"evidence_accumulation".params` has `n_clusters=6` for the **Split** phase (the per-repeat decomposition size, `K_PARAM_NAME[base_method]`) - per Fred & Jain 2002 this should be *larger* than the true expected final cluster count (many small, compact clusters to combine), not the final count itself. `6` is also the exact default used for `"kmeans"`/`"gmm"`'s own *final* `n_clusters`/`n_components` two entries above in the same file - with a Split budget this low, no repeat can ever produce more than 6 micro-clusters, so the Merge phase (`threshold`) can only ever *coarsen* that ceiling, never resolve finer structure than it. Left unchanged deliberately in the 18-08-26 audit-triage session (a scientific parameter choice, not a code defect) - raising it is a decision for whoever runs the next `evidence_accumulation` production/tuning round, not something to change silently here.

## `src/pipeline/dim_reduction.py` / `clustering.py` — the 2 modeling CLIs

Same shape as `build_lesion_matrix.py` (`docs/dev/lesion_matrix.md`: `main(argv) -> int`, staged `try`/`except`, `reports/<script>/<project>/` + `logs/<script>/<project>/`), reading an existing matrix artifact via `artifacts.load_matrix(input_path)` rather than building one.

**Output tree: `production/` vs `tuning/`** (2026-08 session, both CLIs): the very first segment under `output_root` is always `production` or `tuning` - never mixed, never both writing into the same subtree - so a tuning sweep and a production artifact can never collide on disk and a directory listing immediately says which kind of run produced it. Before this session, `tuning/` sat *inside* each method's own folder (`<output_root>/<method>/tuning/...`); it's now a top-level sibling of `production/`, each with its own method-name segment underneath: `<output_root>/production/<method>/<dd-mm>_<session_name>/` and `<output_root>/tuning/<method>/<dd-mm>_<session_name>/`. `comparison/` (`clustering.py` only) is a production-only artifact, so it only ever exists under the `production/` branch. `runs.csv` lives inside the `production/` branch next to the method folders it logs, `runs_tuning.csv` inside `tuning/` - see `src/utils/run_log.py` below for the exact per-CLI paths.

**`clustering.py` runs every method in `clustering_methods` in a loop, not just one**: a private `_run_one_method(config, method, ...)` helper does the full per-method flow (params → cluster → `save_matrix` → `cluster_plot.png` → `runs.csv`) and returns the `cluster_labels` it actually saved (or `None` on failure, which stops the whole run - no partial-failure tolerance, consistent with the rest of this pipeline's fail-fast error handling). `main()` collects `{method: cluster_labels}` across the loop and reuses those exact arrays for the comparison plot below - never re-runs a method a second time just to get labels for the plot (would be wasteful, and for a method without a fixed `random_state` could silently produce labels inconsistent with what was actually saved to `matrix.npy`/`metadata.csv`).

**No `summaries/` report for these 2 modeling CLIs** (`dim_reduction.py`/`clustering.py`) - removed on request: it duplicated the same config JSON/summary lines already written to each run's own `config.md` (production: via `save_matrix`'s readme; fine-tuning: `_write_tuning_output`'s `config.md`), just in a second, flat location (`summaries/<pipeline>/<project>/`). `runs.csv` already gives the flat, cross-run chronological view that duplication was half-providing (see `docs/dev/config.md`). Each script keeps a `LOG_FILENAME_PREFIX` (`"dim_reduction"`/`"clustering"`, renamed 27-08-26 from `REPORT_FILENAME_PREFIX`/`"..._summary"` once it stopped naming anything but the log file) purely as the log filename prefix (`logs/<pipeline>/<project>/<prefix>__<timestamp>.log`) - unrelated to the removed report. `build_lesion_matrix.py`/`mask_fc.py`/`build_fc_matrix.py`/`compute_sdc.py`/`retrieve_data.py` keep their own `summaries/` reports unchanged - out of scope for this removal.

**Comparison plot**: after the loop (guarded by whether a viz embedding could be resolved at all - see `_resolve_viz_embedding` below, not by `len(clustering_methods)` - it's written even for a single method, as a degenerate one-subplot grid, so the output shape doesn't depend on how many methods were requested), `plotting.plot_clusters_comparison` (`docs/dev/plotting.md`) writes `cluster_comparison.png` to `<output_root>/production/comparison/<dd-mm>_<session_name>/` - a grid of subplots (one per method, `ncols = min(3, n)`), same viz data for all of them, shared x/y axis limits across every subplot so the comparison is visually honest. A minimal `config.md` lists the methods compared and each one's individual output dir. Same tier as `summaries/`/`logs/` - not atomic, no `manifest.json`, a secondary/derived artifact built from labels the per-method runs already wrote, not a source of truth of its own.

**Where cluster labels live, and what `matrix.npy` means**: `clustering.py` appends `cluster_label` as a new column on the loaded `metadata.csv` - never a separate `cluster_labels.npy` file - so every artifact this pipeline produces stays loadable through the same `load_matrix(input_dir) -> (X, metadata, extra_arrays)` contract, no special case for "this one has labels in a different place." `matrix.npy` always holds *the feature space clustering actually ran on* - whatever `input_path` pointed at (an already-computed embedding or a raw matrix, see `reduced_data` below), re-saved unchanged into the new artifact dir (accepted storage duplication in exchange for one uniform contract).

**`reduced_data` + `viz_embedding_path` - how `clustering.py` decides what it can plot** (14-08-26 session, extended 26-08-26; see `docs/dev/clustering_migration_plan.md` for the full rationale): `clustering.py` never calls `embed()`/`embedding_for_viz()` itself - `config.reduced_data` (required bool) states whether `input_path` is an already-computed embedding or a raw feature matrix; loading (`load_matrix`) is identical either way, but `reduced_data` is no longer purely declarative (see below). What branches on `X`'s actual shape is `_resolve_viz_embedding(X, metadata, viz_embedding_path, input_path, reduced_data)`, called once in `main()` before the per-method loop: reuses `X` unmodified when it already has 2 or 3 columns; otherwise reads a companion 2D/3D embedding from `config.viz_embedding_path` (optional - a separate artifact, e.g. produced via `dim_reduction.py` with the same `random_state`/`n_neighbors`/`metric` and only `n_components` different), validated to cover the exact same subjects in the exact same order (`ValueError` otherwise); returns `None` (never a slice of `X`, `lessons_learned.md` #16) when neither applies. `None` propagates through the whole run: every scatter plot (`cluster_plot.png`/`silhouette_plot.png`/`cluster_comparison.png`) is skipped with a warning, while the matrix/cluster-label artifact itself is still written normally - a missing viz is a display limitation, not a pipeline failure.

**Companion-embedding cross-check** (26-08-26, found in discussion: the two structural checks above - shape, subject order - don't guarantee `viz_embedding_path` is actually a *twin* of `X`'s own embedding, only that it's plottable and covers the right subjects; a companion built with a different reduction method or different hyperparameters passes both checks while producing a geometrically unrelated layout - real cluster labels plotted onto a misleading picture, with no error to notice it by). When `reduced_data` is `True` (`input_path` is itself a `dim_reduction.py` production run, so it has something comparable to check), `_resolve_viz_embedding` additionally calls `_require_matching_reduction_run(input_path, viz_embedding_path)`, which raises `ValueError` unless: (1) both runs' reduction method matches (`src.utils.artifacts.read_dim_reduction_method`, read from each run's own `config.md` title line - not derived from either path's directory structure, since neither is guaranteed to sit under a `<production>/<method>/` convention the way `embedding_app.py`'s `discover_production_runs` can rely on); (2) every resolved param except `n_components` is identical between the two runs (`src.utils.artifacts.read_run_params`, each run's own `"Params used: {...}"` line - generic dict comparison, symmetric, no per-method special-casing). Skipped entirely when `reduced_data` is `False` - `input_path` is then a raw feature matrix from a different pipeline (e.g. `build_lesion_matrix.py`), whose `config.md` has no reduction method/params to compare against in the first place. `read_run_params` is also the extraction target for `embedding_app.py`'s own `run_params` (thin wrapper now, `src/utils/artifacts.py` is the single source of truth for both).

Right after a successful `save_matrix`, `clustering.py` writes `cluster_plot.png` via `plotting.plot_clusters_2d` on the resolved viz embedding (once per method in `clustering_methods`), then `silhouette_plot.png` via `plotting.plot_silhouette_analysis` - fed by `clustering_tuning.compute_silhouette_samples` on the *real* `X` (never the viz embedding), so the silhouette diagnostic stays reliable even when the display scatter isn't the same space the clustering actually ran in. Skipped the same way on a degenerate result (`ValueError` from `compute_silhouette_samples`, caught and logged as a warning) - independent of whether a viz embedding was available at all.

`clustering.py`'s `_clusters_found_line` helper excludes HDBSCAN/OPTICS-style noise label `-1` from the "Clusters found: N" count and reports it separately ("+ M noise points, label -1") whenever present - counting `-1` as a genuine cluster would silently overstate the result (a real caught case, not a hypothetical: `np.unique(cluster_labels)` alone doesn't know `-1` is special). Generic over any method that happens to produce `-1`, not special-cased on the string `"hdbscan"`.

### `dim_reduction.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

`main()` loads the matrix once, then branches into `_run_production` or `_run_fine_tuning` based on `config.fine_tuning` - two functions, not one function with a large internal `if`, since their output shapes are fundamentally different (a matrix artifact vs. a comparison table) and sharing more than the initial `load_matrix` call would just be forced coupling.

- **Production** (`fine_tuning=false`): `load_method_params` → `reduction.py::embed` (routes jaccard/dice through the precomputed-distance path, see the `embed`/`distances.py` sections above) → `embedding_for_viz` (builds `viz_embedding`, reused as-is if `params["n_components"] == config.viz_n_components`) → `save_matrix` at `<output_root>/<method>/<dd-mm>_<session_name>/` (the real, possibly-higher-dimensional embedding) → `embedding_plots.write_embedding_plots(viz_embedding, ...)` for the plots (`config.color_by`, `docs/dev/plotting.md`).
- **Fine-tuning** (`fine_tuning=true`): `load_method_params` + `load_tuning_grid` + `load_nested_params` (+ `load_trustworthiness_n_neighbors` iff `method in METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS`, i.e. umap/tsne/pacmap; all from `params.py`, `docs/dev/config.md`) → `tuning.run_tuning_sweep` → written to a **separate branch** of the output tree, `<output_root>/tuning/<method>/<dd-mm>_<session_name>/` (2026-08 session: `tuning/` is a top-level sibling of `production/`, not nested inside `<method>/` as it was before - see "Output tree: `production/` vs `tuning/`" below) - deliberately not `save_matrix`/not the same directory shape as a production run, so a sweep can never be mistaken for, or silently collide with, a real embedding artifact. No `manifest.json` here (unlike every other artifact in this pipeline) - a tuning table isn't meant to be read back via `artifacts.load_matrix`, so there's nothing that needs the completeness marker that function relies on.

  When `config.save_tuning_embeddings` is `True` (opt-in, off by default - a later 2026-08 addition), `_write_tuning_output` also serializes every combination `run_tuning_sweep` actually computed (the full evaluated grid, not just the ones drawn in `embeddings_grid_*.png`) into one `embeddings.npz` at the top of that tuning run's output dir - `np.savez(output_dir / "embeddings.npz", **{key: array for key, array in embeddings_by_combo.items()})`, keyed by a self-describing `"k1=v1,k2=v2,..."` string built from `tuning_grid.keys()`'s own order for that run (`_combo_key`) - the same names/values each row of that same run's `tuning_results.csv` already carries (`str(bool)` is `"True"`/`"False"`, matching pandas' own CSV serialization), so a caller rebuilds the exact key from any row without a separate index file. Exists so a downstream tool (Fase C's PAIR-style interactive replot, `knowledge/dim_reduction_clustering/dim_reduction_tuning_guide.md`) can read back a saved combination's embedding and just plot it, with no refit.

  Same flag also writes a `metadata.csv` alongside it (one per run, not per leaf - every combination in a sweep shares the same subjects/row order): unlike `embeddings_grid_*.png`'s color modes, which compute `side`/`nihss`/`volume` live from `metadata`/`X` at plot time (`src/analysis/embedding_coloring.py` - `join_lesion_side`/`join_nihss` hit the `participants.tsv` registry on the spot, `volume` is `X.sum(axis=1)`), a saved `embeddings.npz` needs a *self-contained* metadata to be useful later without reloading `X` or re-hitting that registry. `_run_fine_tuning` therefore calls `enrich_metadata_with_lesion_info(metadata, X)` (the same call `_run_production` always makes) right before `_write_tuning_output`, but **only** when `config.save_tuning_embeddings` is `True` - every other tuning run (the default) keeps `metadata` exactly as loaded, unchanged behavior and no registry-lookup cost paid for nothing. Propagates `enrich_metadata_with_lesion_info`'s own `FileNotFoundError`/`ValueError` (an unresolvable dataset/subject) the same way `_run_production` does.

  Without `nested_params` declared: `{tuning_results.csv, tuning_plot.png (1 param only), config.md}` - unchanged since before the 2026-08 session. With `nested_params` declared (umap/tsne): `_write_nested_tuning_leaves` groups `results` by `nested_params` via `results.groupby(nested_params, sort=False)` - grouping the **actual result rows**, not the Cartesian product of every config-declared value, writing one subfolder per real combination (`<param>=<value>/...`, nested in `nested_params`'s declared order) with its own filtered `tuning_results.csv` always, plus `embeddings_grid_<color>.png` unless every cell this leaf could show turns out to need `n_components != _TUNING_GRID_N_COMPONENTS` (2).

  **26-08-26, on request: no cell is ever refit any more** - `_build_grid_blocks` (for each free/grid parameter, one cell per value it can take, every *other* free parameter held at `base_params`' own value - raises `ValueError` if that exact combination was never computed) looks up each cell's already-computed embedding from `embeddings_by_combo` and, if its own `n_components` isn't exactly `_TUNING_GRID_N_COMPONENTS`, **drops that cell** (logged, never rendered) instead of calling `embedding_for_viz` to refit it to 2D - a block left with zero surviving cells is omitted from the returned blocks list entirely, and a leaf whose every block ends up empty gets no `embeddings_grid` output written at all. Two ways a cell/leaf can end up dropped: (1) `"n_components"` is itself one of `nested_params` (fixed for the whole leaf) and isn't 2 - checked upfront in `_write_nested_tuning_leaves` itself, before ever calling `_build_grid_blocks`, so the common project case (UMAP's `nested_params: ["metric", "n_components"]`) short-circuits cheaply; (2) `"n_components"` is a *free* parameter (swept within one leaf) with some values other than 2 - each such cell is dropped individually inside `_build_grid_blocks`, while sibling cells at `n_components=2` (in that same block, or in any other block, which stays held at `base_params`' `n_components` throughout) still get plotted. Before 26-08-26 a >2-component cell got a refit-to-2D diagnostic instead of being dropped - removed on request: with `random_state` fixed, that refit was bit-for-bit the same computation as whichever other leaf/cell already swept those same free-parameter values at `n_components=2`, and now that `scripts/plot_tuning_embedding_3d.py` (26-08-26, `docs/dev/plotting.md`) exists as the actual on-demand way to see a >2-component combination's real dimensionality, producing a distorted 2D stand-in for it at all - as either a PNG or, briefly, an interactive HTML - was judged not worth it (same reasoning `src.pipeline.embedding_app` already applies to production: a live Dash app covers this, no static file needed). The n_components-based skip/drop is automatic and unconditional (`test_dim_reduction_fine_tuning_nested_n_components_skips_embeddings_grid_for_non_viz_leaf`, `test_dim_reduction_fine_tuning_free_n_components_drops_non_viz_cells`) - the earlier `write_embeddings_grid` config flag (a coarser manual opt-out disabling the whole grid pass regardless of `n_components`) was removed 26-08-26 (later same day) as redundant with it.

Both modes call `append_run_log_entry` (`run_log.py`, `docs/dev/config.md`) after writing their output, tagged `"production"`/`"tuning"` respectively, into `<output_root>/production/<method>/runs.csv` or `<output_root>/tuning/<method>/runs_tuning.csv`.

### `clustering.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

Same `main()` branch-on-`config.fine_tuning` shape as `dim_reduction.py` above, but `clustering.py` already loops over multiple `clustering_methods` in production mode, so its fine-tuning mode loops too (`_run_fine_tuning` iterates `config.clustering_methods`, calling `_run_one_method_tuning` once per method - same fail-fast "stop on first method's failure" behavior as the production loop's `_run_one_method`, no partial-run tolerance either mode).

- **Production** (`fine_tuning=false`, unchanged): as described above (`load_method_params` → `CLUSTERING_METHODS[method]` → `save_matrix`).
- **Fine-tuning** (`fine_tuning=true`), per method: `load_method_params` + `load_tuning_grid` → `clustering_tuning.run_clustering_tuning_sweep` → `<output_root>/tuning/<method>/<dd-mm>_<session_name>/{tuning_results.csv, tuning_plot.png, config.md}` (same deliberately-separate-branch shape as `dim_reduction.py`'s tuning output, same reasoning: a sweep table is never mistaken for a production artifact, no `manifest.json`). `_write_tuning_output` additionally calls `_write_standalone_diagnostic` when `method in STANDALONE_DIAGNOSTIC_METHODS` (agglomerative/spectral), writing that method's own extra diagnostic plot into the same tuning output directory. When a `"stability"` block is registered for the method (kmeans/gmm - see "Stability analysis" above), `_run_one_method_tuning` additionally calls `_write_stability_output` after the plain sweep, writing `stability_results.csv`/`stability_plot.png` into that same directory. `run_clustering_tuning_sweep` now returns `(results, labels_by_combo)` (26-08-26, mirrors `tuning.py::run_tuning_sweep`'s `(results, embeddings_by_combo)`) - every combination's cluster-label array is already computed to score its 3 generic metrics, so keeping it in memory is free; when `config.save_tuning_clusterings` is `True` (opt-in, off by default), `_write_tuning_clusterings` persists the full grid into `clusterings.npz` (keyed by `_combo_key`, atomic temp-file-then-rename like `dim_reduction.py`'s `embeddings.npz`) plus a self-contained `metadata.csv` next to it - a later reader can inspect any evaluated combination's labels without rerunning the sweep.

Same shared `<output_root>/production/<method>/runs.csv` / `<output_root>/tuning/<method>/runs_tuning.csv` convention as `dim_reduction.py` - `_run_log_dir(config, method, branch)` (`"production"`/`"tuning"`, same literal each caller also passes as `append_run_log_entry`'s own `run_type`) is reused unchanged between `_run_one_method` (production) and `_run_one_method_tuning` (fine-tuning).

**The intended workflow** (confirmed with the user, kept manual by design - no automatic parameter selection, and no plan to add one for any of the 4 fine-tunable methods; cross-validation for a future regression/classification task on top of clustering is a separate, not-yet-designed concern): run with `fine_tuning: true` → open `tuning_results.csv`/`tuning_plot.png` → pick parameters by eye → write them into `params_reduction.json`'s `"params"` for that method → set `fine_tuning: false`, pick a new `session_name`, optionally fill in `run_notes` explaining the change → re-run for the real embedding.
