## `src/analysis/reduction.py` / `clustering.py` — modeling strategies

Plain `dict[str, Callable]` registries (`REDUCTION_METHODS`, `CLUSTERING_METHODS`), not classes/ABCs — same "explicit registry over hardcoded dispatch" precedent as `config/registry/file_patterns.json`. Each entry is a pure `(X, params) -> array` function: `params` is unpacked with `**params` straight into the underlying `sklearn`/`umap` estimator's constructor, no in-code defaults for any hyperparameter (`code_standards.md` §5) — those live only in `config/registry/params_reduction.json`/`params_clustering.json` (`src/analysis/params.py`, see `docs/dev/config.md`). Invalid/unexpected keys in `params` surface as whatever error `sklearn`/`umap` itself raises for a bad constructor argument — not re-validated here, since re-implementing each estimator's accepted-parameter surface would just duplicate their own API.

- `reduction.py`: `umap_embed`, `tsne_embed`, `pca_embed`, `pca_varimax_embed`, `pacmap_embed`.
- `clustering.py`: `kmeans_cluster`, `agglomerative_cluster`, `gmm_cluster`, `hdbscan_cluster`, `spectral_cluster`.

`pca_varimax_embed` is the one exception to the "blind `**params` unpack" rule above: it wraps two distinct estimators (`sklearn.decomposition.PCA`, then `factor_analyzer.Rotator(method="varimax")`, per Thiebaut de Schotten et al. 2020's methodology - `docs/knowledge/dim_reduction.md`), so it reads `n_components`/`rotation_max_iter` from `params` explicitly and raises `ValueError` if either is missing, or if `n_components < 2` (varimax rotates *between* components - nothing to rotate with one). Component scores are computed via `np.linalg.lstsq` (regressing each centered subject row onto the rotated loadings) - the paper's "multiple regression" step, not a re-projection through the rotated loadings directly.

`embedding_for_viz(reduction_method, X, reduction_params, embedding, viz_n_components) -> np.ndarray` (2026-08 session): returns an embedding with exactly `viz_n_components` columns, for plotting only - reuses `embedding` unmodified (`is` identity, zero extra cost) when it already has that many columns, otherwise refits `REDUCTION_METHODS[reduction_method]` from scratch on the same raw `X` with only `n_components` overridden. Exists because `embedding[:, :viz_n_components]` is not a valid substitute for umap/tsne/pacmap: their output dimensions have no importance ordering (unlike PCA's variance-ranked components, where a second fit at fewer components is mathematically equivalent to slicing - the same rule covers every `REDUCTION_METHODS` entry without a per-method branch), so a slice can make real cluster structure look artificially merged or split. The refit shares the original fit's neighbor graph (depends only on `metric`/`n_neighbors`, not `n_components`) since every other param is held identical. Two callers: `dim_reduction.py::_run_production` (own `viz_n_components`, 2 or 3) and `dim_reduction_clustering.py::main()` (`viz_n_components` fixed to 2 there - every cluster-coloring plot function in `docs/dev/plotting.md` is 2D-only).

## `src/analysis/tuning.py` — manual fine-tuning for umap/tsne/pca/pca_varimax/pacmap

No automatic parameter selection anywhere in this module - it only produces a comparison table; a human reads it (or the accompanying plot) and writes the chosen parameters into `params_reduction.json`'s `"params"` by hand. t-SNE's `early_exaggeration`/`learning_rate`/`max_iter` are excluded on purpose (fixed from Thiebaut de Schotten et al. 2020, `docs/knowledge/dim_reduction.md`) - only `perplexity` is swept, added on request since the paper's own supplementary material sweeps it too. Every clustering method is excluded here too - fine-tuning for those lives in `clustering_tuning.py` below, not this module.

`TUNING_METRIC_NAMES = {"umap": "trustworthiness", "tsne": "trustworthiness", "pca": "cumulative_explained_variance", "pca_varimax": "cumulative_explained_variance", "pacmap": "trustworthiness"}` - the quality metric is genuinely different per *family* of method (decided with the user), not per individual method - `pca_varimax` reuses PCA's criterion (varimax is an orthogonal rotation, doesn't change total variance explained) and `tsne`/`pacmap` reuse UMAP's (trustworthiness is a generic neighbor-preservation metric, not UMAP-specific):
- `evaluate_umap(X, params, trustworthiness_n_neighbors)` / `evaluate_tsne(X, params, trustworthiness_n_neighbors)` / `evaluate_pacmap(X, params, trustworthiness_n_neighbors)` embed then score with `sklearn.manifold.trustworthiness` - how well local neighborhoods survive the projection. `evaluate_umap`/`evaluate_tsne` both read `params["metric"]`: for `"jaccard"`/`"dice"` (see `src/analysis/distances.py::binary_pairwise_distance` below), both the embedding *and* the `trustworthiness` call are given the same precomputed distance matrix (`metric="precomputed"` on both) instead of raw `X` - scoring a binary-metric embedding against `trustworthiness`'s own euclidean default would judge it by a notion of "originally close" it was never built to preserve. `evaluate_tsne` additionally forces `init="random"` whenever `metric="precomputed"` - `sklearn.manifold.TSNE`'s own default `init="pca"` can't run on a distance matrix. `evaluate_pacmap` has no such branch - its `tuning_grid` never sweeps `metric`.
- `evaluate_umap`/`evaluate_tsne` also read `params["regress_out_volume"]` (default `False`, umap/tsne only, added session s1.1's 28-07 tuning round) - not a UMAP/TSNE constructor argument, so it's stripped from `params` before the estimator call and applied to the embedding afterwards (`regress_out_covariate(embedding, X.sum(axis=1))`, same call as the production path below), and the `trustworthiness` score is computed on that *residualized* embedding, since that's the artifact a production run with the same flag would actually save. `check_volume_regression_compatible` is called first thing inside each `evaluate_*` function itself, not only by `run_tuning_sweep` - so the check holds regardless of caller (`lessons_learned.md` #2: validation anchored to one call site, not guaranteed by the data itself). When it raises (`regress_out_volume=True` with `metric` in `{"jaccard", "dice"}`), `run_tuning_sweep` catches that specific `VolumeRegressionIncompatibleError` (a `ValueError` subclass, `src/analysis/covariates.py`) around the evaluator call and **excludes that combination from the returned table entirely** (session s1.1's 29-07 round, revised from an earlier NaN-row/`skipped_reason`-column design) - a WARNING is still logged when it happens, so the exclusion isn't silent, but the incompatibility is already a documented fact (this file, `docs/knowledge/dim_reduction.md`), not a per-run finding worth a placeholder row in every `tuning_results.csv`.
- `evaluate_pca(X, params)` / `evaluate_pca_varimax(X, params)` fit `sklearn.decomposition.PCA` directly (not via `pca_embed`/`pca_varimax_embed`, which only return the transformed array) specifically to read `.explained_variance_ratio_.sum()` off the fitted estimator - PCA's own natural criterion, and the exact one the paper uses to choose a component count.

`_EVALUATORS: dict[str, Callable]` dispatches by method name (Strategy registry, same precedent as `REDUCTION_METHODS`/`CLUSTERING_METHODS`) rather than an `if/elif` chain - the original 2-branch `if/elif` (umap/pca) was refactored into this registry specifically when adding `pca_varimax`/`pacmap`, since a 2-branch `if/elif` growing to 4 branches is exactly the pattern `lessons_learned.md` #1 warns about. `METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS = {"umap", "tsne", "pacmap"}` is consulted both here and by `dim_reduction.py` (to decide whether to load `trustworthiness_n_neighbors` from config at all) - a single shared source of truth for "which methods need this extra setting", not duplicated/hardcoded in both places.

`run_tuning_sweep(method, X, base_params, tuning_grid, trustworthiness_n_neighbors) -> tuple[pd.DataFrame, dict[tuple, np.ndarray]]` takes the Cartesian product of `tuning_grid`'s value lists (`itertools.product`), evaluates each combination via `_EVALUATORS[method]` (swept keys override `base_params`; un-swept keys like `random_state` stay fixed). Returns `(results, embeddings_by_combo)`: `results` is unchanged from before 2026-08 (one row per combination, swept values + metric column, still the only thing written to `tuning_results.csv`); `embeddings_by_combo` (added 2026-08, in-memory only, never serialized) keys each combination's actual embedding by its exact `combo` tuple (`tuning_grid.keys()` order) - so a caller that needs to *see* an embedding, not just its score (`dim_reduction.py`'s `embeddings_grid` plot), doesn't have to refit it. A combination excluded by the `VolumeRegressionIncompatibleError` handling below has no entry in either return value. Raises `ValueError` for any method not in `TUNING_METRIC_NAMES` (registry-driven, not an implicit fallback).

## `src/analysis/distances.py` — fast pairwise distances for binary feature data

`binary_pairwise_distance(X, metric) -> np.ndarray` computes a full `(n_samples, n_samples)` Jaccard or Dice distance matrix for a binary `(n_samples, n_features)` array (voxel-wise lesion masks: `metric` must be `"jaccard"` or `"dice"` - `SUPPORTED_BINARY_METRICS` - `ValueError` otherwise, and `ValueError` if any row is all-zero (union/sum would be 0, both metrics undefined for an empty sample).

Exists because `scipy.spatial.distance.pdist`'s boolean metrics compute one pair at a time - measured at ~19 minutes extrapolated for 1150 subjects × 254865 voxel features. Binary overlap between every pair at once is instead a single matrix multiplication (`X @ X.T` counts shared "on" features per pair, via BLAS) - Jaccard/Dice distance follow from that intersection count plus each row's own sum, in seconds instead of minutes. Casts to `float64` before the multiply regardless of `X`'s own dtype (usually `uint8`) - intersection counts can exceed a narrow integer type's range and silently wrap (`lessons_learned.md` #13).

Used by `tuning.py::evaluate_umap`/`evaluate_tsne` (above) whenever the swept `metric` is `"jaccard"`/`"dice"` - not used anywhere in `reduction.py` itself, only in the fine-tuning evaluators (production `dim_reduction.py` calls `REDUCTION_METHODS[method](X, params)` directly, passing `metric` straight through as a string to `umap-learn`/sklearn, which handle jaccard/dice natively on raw `X` without needing this precomputed shortcut - `binary_pairwise_distance` exists purely as the *fine-tuning* sweep's performance fix, not a production dependency). `metric` is an explicit key in both `umap`/`tsne`'s `"params"` in `params_reduction.json` (rather than left absent, silently falling back to the library's own default) specifically so `covariates.py`'s incompatibility check below has something concrete to read - production `umap` runs with `metric="jaccard"` as of session s1.1's 26-07 tuning round, `tsne` still with `metric="euclidean"` (its own tuning round hasn't concluded which value to adopt).

## `src/analysis/covariates.py` — post-reduction volume regression

`regress_out_covariate(embedding, covariate) -> np.ndarray`: removes the linear effect of a covariate from each embedding column via `np.linalg.lstsq` OLS residuals. Deliberately operates on the already-computed 2D embedding, not the raw voxel matrix - regressing a scalar covariate off a binary 0/1 matrix column-by-column would produce non-binary residuals (destroying the structure `distances.py`'s Jaccard/Dice machinery depends on) and is statistically unstable on the many voxel columns with very low lesion prevalence. Raises `ValueError` on an embedding/covariate row-count mismatch, and on a zero-variance covariate (nothing to regress out - not a case that can be silently no-op'd per `code_standards.md` §0).

`check_volume_regression_compatible(regress_out_volume, reduction_params) -> None`: raises `ValueError` if `regress_out_volume=True` together with `reduction_params.get("metric")` in `{"jaccard", "dice"}` - those metrics already normalize distances by each subject's own lesion size (see `docs/knowledge/dim_reduction.md`), so regressing volume out a second time on top would remove real topographic signal, not a confound. A method/params with no `"metric"` key at all (`pca`, `pacmap`, `tsne` today) is unaffected - `regress_out_volume` is free either way. Deliberately **not** a silent override (`regress_out_volume` forced to `False` when the metric is incompatible) - `code_standards.md` §0 treats that as exactly the kind of fallback that hides a real conflict from the caller; this raises instead, at config-boundary time, before either pipeline computes anything.

Both `dim_reduction.py::_run_production` and `dim_reduction_clustering.py::main()` call `check_volume_regression_compatible` right after `load_method_params` resolves `params`/`reduction_params` (that's the only place `metric` is known - it lives in `params_reduction.json`, a file separate from the pipeline's own config, so the check can't run any earlier), then `regress_out_covariate(embedding, X.sum(axis=1))` right after computing the embedding, when `config.regress_out_volume` is `True`. `X.sum(axis=1)` (lesion volume in voxels, not ml) is deliberately not converted to ml first - a scalar rescaling of the covariate doesn't change OLS residuals, so skipping the conversion avoids needing the reference image's voxel size (not otherwise available at this point in either pipeline) for no behavioral difference. Both call sites duplicate this 2-3 line snippet rather than sharing a helper - same per-CLI-duplication convention as `_write_standalone_diagnostic` in `dim_reduction_clustering.py`/`clustering.py` (the two pipelines are deliberately decoupled CLIs, `dim_reduction_clustering.py` does not import from `dim_reduction.py`).

## `src/analysis/clustering_tuning.py` — manual fine-tuning for kmeans/agglomerative/gmm/hdbscan/spectral

Same "no automatic selection" philosophy as `tuning.py`, but clustering has no ground truth to score against - every generic metric is an *internal* validation index computed straight from `(X, cluster_labels)`, meaningful only within one method's own swept grid, never compared across methods.

`compute_clustering_metrics(X, labels) -> dict[str, float]` returns `{"silhouette", "calinski_harabasz", "davies_bouldin", "noise_fraction"}` for every method uniformly - `sklearn.metrics.silhouette_score`/`calinski_harabasz_score`/`davies_bouldin_score` excluding any HDBSCAN-style noise (`label == -1`) first (undefined for a "cluster" that isn't one), with `noise_fraction` always reported so the exclusion is visible rather than silent. A degenerate combination (fewer than 2 non-noise clusters, or every non-noise point its own cluster) can't have the 3 metrics computed at all - caught (the same condition `sklearn` itself would raise on) and recorded as `NaN` with a logged warning rather than aborting the whole sweep, since a bad hyperparameter combination is expected information in a tuning sweep, not a bug (distinct from `lessons_learned.md`'s silent-fallback pattern: this is one documented, intentional strategy for a legitimate domain case, not a caught-and-hidden error).

`compute_silhouette_samples(X, labels) -> tuple[np.ndarray, np.ndarray]` is the per-sample counterpart used for `plotting.plot_silhouette_analysis` (production time, not the sweep above, see `docs/dev/plotting.md`): same noise-exclusion convention as `compute_clustering_metrics`, but returns `(non_noise_labels, sample_silhouette_values)` from `sklearn.metrics.silhouette_samples` instead of one aggregate number - their mean equals `compute_clustering_metrics`'s `"silhouette"` exactly. Unlike `compute_clustering_metrics`'s NaN-and-warn on a degenerate combination (built for an unattended sweep over many combinations), this **raises** `ValueError` - it runs once for the single already-chosen production result, so the caller (`clustering.py`/`dim_reduction_clustering.py`'s `_run_one_method`) decides whether to skip the plot, catching that specific exception and logging a warning rather than failing the whole run.

`run_clustering_tuning_sweep(method, X, base_params, tuning_grid, consensus_config=None) -> pd.DataFrame` mirrors `tuning.py`'s sweep shape (Cartesian product, swept keys override `base_params`), but two methods get an extra scalar column beyond the 3 generic ones, computed by refitting the actual estimator instead of going through `CLUSTERING_METHODS[method]` (which only returns labels): `_kmeans_with_extra_metrics` keeps `KMeans.inertia_` (the elbow criterion), `_gmm_with_extra_metrics` keeps `GaussianMixture.bic(X)`/`.aic(X)` (likelihood-based, unlike the other 3 which are purely geometric) - `_EXTRA_METRICS_EVALUATORS` dispatches by method name, absent for the other 3 (agglomerative/hdbscan/spectral get only the 3 generic columns from their swept grid). `METHOD_METRIC_COLUMNS: dict[str, list[str]]` is the single source of truth `clustering.py` reads to know which columns a given method's sweep will produce (and therefore which to plot) - `noise_fraction` is only listed for `"hdbscan"` even though `compute_clustering_metrics` always returns it, since it's mechanically 0.0 for every other method (never noise-producing) and plotting a flat line adds nothing.

Two methods also get a standalone diagnostic, independent of which value in the swept grid ends up chosen (`STANDALONE_DIAGNOSTIC_METHODS = {"agglomerative", "spectral"}`, computed once from `base_params`, not per swept combination):
- `compute_dendrogram_linkage(X, params) -> np.ndarray` refits `AgglomerativeClustering` with `n_clusters=None, distance_threshold=0, compute_distances=True` (forces the full merge tree down to singleton leaves, ignoring any `n_clusters`/`distance_threshold` already in `params`), then converts `children_`/`distances_` into the scipy linkage-matrix format `plotting.plot_dendrogram` (`docs/dev/plotting.md`) expects (the standard sklearn-docs recipe for bridging the two).
- `compute_eigengap(X, params, max_k=20) -> np.ndarray` builds the same affinity graph `spectral_cluster` would (`"nearest_neighbors"` via `sklearn.neighbors.kneighbors_graph` symmetrized, or `"rbf"` via `sklearn.metrics.pairwise.rbf_kernel` - `ValueError` for any other `affinity`), computes the normalized graph Laplacian (`scipy.sparse.csgraph.laplacian`) and its smallest `max_k` eigenvalues (`scipy.linalg.eigh`, `subset_by_index`) - the eigengap heuristic (`plotting.plot_eigengap`, `docs/dev/plotting.md`) reads a suggested `n_clusters` off the biggest gap between consecutive values, a criterion with actual theoretical grounding for spectral clustering specifically (a Laplacian's near-zero-eigenvalue multiplicity approximates the count of well-separated graph components), unlike the generic geometric indices applied to the other methods.

HDBSCAN (which replaced DBSCAN) gets no standalone diagnostic: DBSCAN had one (`compute_k_distance`, a sorted distance-to-`min_samples`-th-neighbor plot for reading off a reasonable `eps` by eye) because it needs a single global distance threshold; HDBSCAN has no such threshold to read off a plot - `min_cluster_size` is judged directly from the swept `noise_fraction`/silhouette columns instead, so `compute_k_distance`/`plotting.plot_k_distance` were removed rather than kept unused.

`clustering.py`'s `_write_standalone_diagnostic` dispatches to whichever of the 2 applies via an explicit `if/elif` (not a registry - kept as an explicit dispatch for symmetry with when a third branch existed) and raises `ValueError` for any method outside `STANDALONE_DIAGNOSTIC_METHODS` rather than silently no-oping.

`consensus_suggestion_lines(results, method) -> list[str]` reads `rsc_eigengap`/`monti_stability` columns (if present in `results`) and returns the "RSC suggests .../Monti suggests ..." lines described below - empty list when neither column is present. Pure text formatting, shared between `clustering.py`/`dim_reduction_clustering.py`'s `_write_tuning_output`, since it doesn't close over either script's own config type (unlike `_write_standalone_diagnostic`, deliberately duplicated per script). Written to its own `consensus_suggestions.md` (only when the list is non-empty), a sibling of `tuning_results.csv`/`config.md` in the tuning output dir - deliberately **not** appended into `config.md` itself: that file is a static snapshot of how the run was launched (config JSON, swept params, combinations evaluated), and a computed suggestion doesn't belong mixed into a historical launch record.

## `src/analysis/consensus_clustering.py` — consensus/stability clustering (RSC + Monti)

Two literature methods scoring how *stable* a candidate `k` is (as opposed to how *good* it looks on a single run, all silhouette/Calinski-Harabasz/Davies-Bouldin can say) - restricted to `CONSENSUS_ELIGIBLE_METHODS = {"kmeans", "gmm", "spectral"}` (`K_PARAM_NAME` maps each to its own "how many clusters" parameter name: `n_clusters` for kmeans/spectral, `n_components` for gmm), since these are the only 3 with genuine internal stochasticity to exploit without touching the data itself - a repeat of `agglomerative`/`hdbscan` with a different seed reproduces the identical partition (deterministic given the same input), so a "co-occurrence matrix" for them would be degenerate (all 0s/1s, no information).

- `run_rsc_repeats(method, X, params, n_repeats, base_seed=0) -> np.ndarray`: RSC (Tshimanga et al. 2025, cited by Zanola et al. 2026 - `papers/Zanola et al - 2026 - ...`) - `n_repeats` runs of `CLUSTERING_METHODS[method]` on the full, unmodified `X`, only `random_state` varying (`base_seed + i`). Returns the `(n_samples, n_samples)` co-occurrence matrix (fraction of runs where each pair shared a cluster).
- `run_monti_repeats(method, X, params, n_repeats, subsample_fraction, base_seed=0) -> np.ndarray`: Monti et al. 2003 - `n_repeats` runs, each on an `np.random.default_rng`-drawn subsample (without replacement, size `round(subsample_fraction * n_samples)`) of subjects. Returns the `(n_samples, n_samples)` consensus matrix (co-clustered / co-sampled per pair, conditioned on both having been drawn together) - raises `ValueError` if any pair was never jointly sampled across all `n_repeats` draws (too few repeats/too small a fraction for this `n_samples` - an explicit failure, never a silent `NaN`/`0`).
- `compute_rsc_eigengap(cooccurrence_matrix, k) -> float`: gap between the `k`-th and `(k-1)`-th (1-indexed) sorted eigenvalues of the co-occurrence matrix's normalized Laplacian (`scipy.sparse.csgraph.laplacian(..., normed=True)` + `scipy.linalg.eigh`, same machinery as `clustering_tuning.compute_eigengap` but applied to `C` itself as the affinity, and reading the specific position-`k` gap rather than the biggest gap anywhere - matches the paper's own selection criterion, compared across the different `C_k` built per candidate `k`).
- `compute_monti_stability(consensus_matrix, ambiguous_band=(0.1, 0.9)) -> float`: `1 - PAC` (Proportion of Ambiguous Clustering - fraction of the consensus matrix's upper-triangle entries falling inside `ambiguous_band`). Deliberate deviation from Monti et al. 2003's own area-under-CDF statistic, per Șenbabaoğlu et al. 2014's finding that it's biased toward larger `k` - PAC is the standard fix (e.g. `ConsensusClusterPlus`), not an invention here.

Wired into `clustering_tuning.run_clustering_tuning_sweep` via an optional `consensus_config` parameter (`None` by default - zero behavior change to any pre-existing call): `{"rsc": {"n_repeats": int}, "monti": {"n_repeats": int, "subsample_fraction": float}}`, either/both keys, adding `"rsc_eigengap"`/`"monti_stability"` columns per swept row (`k` read straight off that row's own already-built `combo_params[K_PARAM_NAME[method]]`, since it's exactly what `tuning_grid` swept to produce it). `CONSENSUS_METRIC_COLUMNS = ("rsc_eigengap", "monti_stability")` in `clustering_tuning.py` is a fixed constant (not merged into the static `METHOD_METRIC_COLUMNS`, since it's opt-in/conditional) - both pipelines extend their own `metric_cols` with `[c for c in CONSENSUS_METRIC_COLUMNS if c in results.columns]` before plotting, so the subplot grid only ever includes columns that actually got computed. Loaded via `params.py::load_consensus_config(params_file, method) -> dict | None` (`docs/dev/config.md`) (absent `"consensus"` key -> `None`, a legitimate "not requested" case; present for a method outside `CONSENSUS_ELIGIBLE_METHODS`, or malformed, raises `ValueError` - an impossible config must fail loudly, never be silently ignored, per `code_standards.md` §0). Not registered in the checked-in `config/registry/params_clustering.json` by default - fully opt-in, see `docs/guides/clustering.md` for the JSON block to add.

## `src/pipeline/dim_reduction.py` / `dim_reduction_clustering.py` / `clustering.py` — the 3 modeling CLIs

Same shape as `build_lesion_matrix.py` (`docs/dev/lesion_matrix.md`: `main(argv) -> int`, staged `try`/`except`, `reports/<script>/<project>/` + `logs/<script>/<project>/`), reading an existing matrix artifact via `artifacts.load_matrix(input_path)` rather than building one.

**Output tree: `production/` vs `tuning/`** (2026-08 session, all 3 CLIs): the very first segment under `output_root` is always `production` or `tuning` - never mixed, never both writing into the same subtree - so a tuning sweep and a production artifact can never collide on disk and a directory listing immediately says which kind of run produced it. Before this session, `tuning/` sat *inside* each method's own folder (`<output_root>/<method>/tuning/...`); it's now a top-level sibling of `production/`, each with its own method-name segment underneath: `<output_root>/production/<method>/<dd-mm>_<session_name>/` and `<output_root>/tuning/<method>/<dd-mm>_<session_name>/` (`dim_reduction.py`, `clustering.py`), `<output_root>/production/<reduction_method>/<method>/<dd-mm>_<session_name>/` and `<output_root>/tuning/<reduction_method>/<method>/<dd-mm>_<session_name>/` (`dim_reduction_clustering.py`, nested two levels deep under either branch - mirrors `dim_reduction.py`'s own layout one level up, rather than the flat `<reduction>-<method>` folder name used before an earlier reorganization). `comparison/` (both `clustering.py` and `dim_reduction_clustering.py`) and `dim_reduction_clustering.py`'s `color_by` `embedding/` folder are production-only artifacts, so they only ever exist under the `production/` branch. `runs.csv` lives inside the `production/` branch next to the method folders it logs, `runs_tuning.csv` inside `tuning/` - see `src/utils/run_log.py` below for the exact per-CLI paths.

**`clustering.py`/`dim_reduction_clustering.py` run every method in `clustering_methods` in a loop, not just one**: a private `_run_one_method(config, method, ...)` helper does the full per-method flow (params → cluster → `save_matrix` → `cluster_plot.png` → `runs.csv`) and returns the `cluster_labels` it actually saved (or `None` on failure, which stops the whole run - no partial-failure tolerance, consistent with the rest of this pipeline's fail-fast error handling). `main()` collects `{method: cluster_labels}` across the loop and reuses those exact arrays for the comparison plot below - never re-runs a method a second time just to get labels for the plot (would be wasteful, and for a method without a fixed `random_state` could silently produce labels inconsistent with what was actually saved to `matrix.npy`/`metadata.csv`).

**No `summaries/` report for these 3 modeling CLIs** (`dim_reduction.py`/`clustering.py`/`dim_reduction_clustering.py`) - removed on request: it duplicated the same config JSON/summary lines already written to each run's own `config.md` (production: via `save_matrix`'s readme; fine-tuning: `_write_tuning_output`'s `config.md`), just in a second, flat location (`summaries/<pipeline>/<project>/`). `runs.csv` already gives the flat, cross-run chronological view that duplication was half-providing (see `docs/dev/config.md`). `REPORT_FILENAME_PREFIX` survives in each script purely as the log filename prefix (`logs/<pipeline>/<project>/<prefix>__<timestamp>.log`) - unrelated to the removed report. `build_lesion_matrix.py`/`mask_fc.py`/`build_fc_matrix.py`/`compute_sdc.py`/`retrieve_data.py` keep their own `summaries/` reports unchanged - out of scope for this removal.

**Comparison plot**: after the loop (guarded by the same `>= 2` columns check as the per-method `cluster_plot.png`, not by `len(clustering_methods)` - it's written even for a single method, as a degenerate one-subplot grid, so the output shape doesn't depend on how many methods were requested), `plotting.plot_clusters_comparison` (`docs/dev/plotting.md`) writes `cluster_comparison.png` to `<output_root>/production/comparison/<dd-mm>_<session_name>/` (`clustering.py`) or `<output_root>/production/<reduction_method>/comparison/<reduction_method>_<dd-mm>_<session_name>/` (`dim_reduction_clustering.py` - reduction name repeated before the tag here specifically, since the comparison folder is the one place where scanning individual folder names out of context is common) - a grid of subplots (one per method, `ncols = min(3, n)`), same 2D data (raw first-2-features for `clustering.py`, embedding first-2-components for `dim_reduction_clustering.py`), shared x/y axis limits across every subplot so the comparison is visually honest. `plotting.plot_clusters_comparison_interactive` writes a companion `cluster_comparison_interactive.html` alongside it - same dropdown-per-trace-set mechanism as `plot_clusters_interactive`, but one option per clustering method instead of a fixed cluster/dataset pair. A minimal `config.md` lists the methods compared and each one's individual output dir. Same tier as `summaries/`/`logs/` - not atomic, no `manifest.json`, a secondary/derived artifact built from labels the per-method runs already wrote, not a source of truth of its own.

**Where cluster labels live, and what `matrix.npy` means when there's no reduction** (decided during implementation, not fully specified in the handoff note): both clustering-involving scripts append `cluster_label` as a new column on the loaded `metadata.csv` - never a separate `cluster_labels.npy` file - so every artifact this pipeline produces stays loadable through the same `load_matrix(input_dir) -> (X, metadata, extra_arrays)` contract, no special case for "this one has labels in a different place." Consistently, `matrix.npy` always holds *the feature space clustering actually ran on*: the embedding for `dim_reduction_clustering.py`, the unchanged input `X` for `clustering.py` (which re-saves it into the new artifact dir - accepted storage duplication in exchange for one uniform contract instead of a one-off shape for the no-reduction case).

`dim_reduction_clustering.py` clusters the **embedding**, not the raw input matrix (`CLUSTERING_METHODS[method](embedding, params)`) - matches the handoff's stated flow ("reduction dispatch → clustering dispatch on the embedding").

**Same double-embedding split as `dim_reduction.py`'s production mode** (2026-08 session): right after computing `embedding`, `main()` builds `viz_embedding = embedding_for_viz(...)` (`config.viz_n_components`, validated to be exactly `2` here - `main()` rejects `3` outright, since every cluster-coloring plot function this pipeline uses is 2D-only). Clustering itself (`CLUSTERING_METHODS[method](embedding, ...)`) and `compute_silhouette_samples(embedding, ...)` always use the real `embedding`; every plot (`cluster_plot.png`/`cluster_plot_interactive.html`/`silhouette_plot.png`'s scatter panel/both comparison plots) uses `viz_embedding` instead of a `[:, :2]` slice. `regress_out_volume`, when set, is applied to both independently (same `viz_is_clustering_embedding` object-identity check as `dim_reduction.py`'s `_run_production`, to avoid regressing twice or missing one when they're the same object).

**Metadata enrichment happens once, right after the `fine_tuning` branch** (production path only): `metadata = enrich_metadata_with_lesion_info(metadata, X)` reassigns the loaded `metadata` in place (see `docs/dev/plotting.md` for what this function adds and why), so both the optional `color_by` plots below and every `_run_one_method` call downstream (which does `metadata_out = metadata.copy(); metadata_out["cluster_label"] = ...`) see the enriched version - `metadata.csv` in every method's output dir ends up with `lesion_volume_voxels`/`lesion_side`/`nihss` **and** `cluster_label`, not just the latter.

**Optional bonus feature, `config.color_by`** (default `()`, zero behavior change): when non-empty, `main()` calls `embedding_plots.write_embedding_plots(viz_embedding, ...)` once (not per clustering method - the coloring is a property of the embedding/subjects, not of any one method's cluster assignment), writing to a new `<output_root>/<reduction_method>/embedding/<dd-mm>_<session_name>/` folder, reusing the exact same registry/writer `dim_reduction.py`'s production mode uses (`docs/dev/plotting.md`). Low-cost reuse of an already-built function (not a new abstraction built speculatively) - this pipeline's own plots stay cluster-colored only unless a project explicitly opts in.

Both clustering scripts write `cluster_plot.png` via `plotting.plot_clusters_2d` after a successful `save_matrix`, once per method in `clustering_methods` - `dim_reduction_clustering.py` plots `viz_embedding` (see the double-embedding split above - a genuine 2-component projection, not necessarily the first 2 columns of the real, possibly-higher-dimensional `embedding` used for clustering), `clustering.py` plots the raw matrix's first 2 features (explicitly labeled "raw" in the axis titles, since with no reduction those 2 axes are an arbitrary, not-necessarily-meaningful projection - `clustering.py` has no raw feature matrix to refit a proper viz projection from, so it never had an `embedding_for_viz` option to begin with). If fewer than 2 columns are available (e.g. a 1-component reduction, `clustering.py` only - `dim_reduction_clustering.py`'s `viz_embedding` is always exactly 2), the plot step is skipped with a `logging.warning` rather than failing the run - the matrix/labels are still the real output, the plot is a convenience. Right after, both scripts also write `silhouette_plot.png` via `plotting.plot_silhouette_analysis`, fed by `clustering_tuning.compute_silhouette_samples` on the *same* space used to fit the clustering (`dim_reduction_clustering.py`'s real `embedding`, `clustering.py`'s full `X` - never `viz_embedding`, so it stays a reliable diagnostic even when the display scatter isn't the same space the clustering actually ran in). Skipped the same way on a degenerate result (`ValueError` from `compute_silhouette_samples`, caught and logged as a warning).

Both clustering scripts' `_clusters_found_line` helper excludes HDBSCAN/OPTICS-style noise label `-1` from the "Clusters found: N" count and reports it separately ("+ M noise points, label -1") whenever present - counting `-1` as a genuine cluster would silently overstate the result (a real caught case, not a hypothetical: `np.unique(cluster_labels)` alone doesn't know `-1` is special). Generic over any method that happens to produce `-1`, not special-cased on the string `"hdbscan"`.

### `dim_reduction.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

`main()` loads the matrix once, then branches into `_run_production` or `_run_fine_tuning` based on `config.fine_tuning` - two functions, not one function with a large internal `if`, since their output shapes are fundamentally different (a matrix artifact vs. a comparison table) and sharing more than the initial `load_matrix` call would just be forced coupling.

- **Production** (`fine_tuning=false`): `load_method_params` → `REDUCTION_METHODS[method]` → `embedding_for_viz` (builds `viz_embedding`, reused as-is if `params["n_components"] == config.viz_n_components`) → `regress_out_covariate` applied to both the saved embedding and `viz_embedding` when `regress_out_volume` is set → `save_matrix` at `<output_root>/<method>/<dd-mm>_<session_name>/` (the real, possibly-higher-dimensional embedding) → `embedding_plots.write_embedding_plots(viz_embedding, ...)` for the plots (`config.color_by`, `docs/dev/plotting.md`).
- **Fine-tuning** (`fine_tuning=true`): `load_method_params` + `load_tuning_grid` + `load_nested_params` (+ `load_trustworthiness_n_neighbors` iff `method in METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS`, i.e. umap/tsne/pacmap; all from `params.py`, `docs/dev/config.md`) → `tuning.run_tuning_sweep` → written to a **separate branch** of the output tree, `<output_root>/tuning/<method>/<dd-mm>_<session_name>/` (2026-08 session: `tuning/` is a top-level sibling of `production/`, not nested inside `<method>/` as it was before - see "Output tree: `production/` vs `tuning/`" below) - deliberately not `save_matrix`/not the same directory shape as a production run, so a sweep can never be mistaken for, or silently collide with, a real embedding artifact. No `manifest.json` here (unlike every other artifact in this pipeline) - a tuning table isn't meant to be read back via `artifacts.load_matrix`, so there's nothing that needs the completeness marker that function relies on.

  When `config.save_tuning_embeddings` is `True` (opt-in, off by default - a later 2026-08 addition), `_write_tuning_output` also serializes every combination `run_tuning_sweep` actually computed (the full evaluated grid, not just the ones drawn in `embeddings_grid_*.png`) into one `embeddings.npz` at the top of that tuning run's output dir - `np.savez(output_dir / "embeddings.npz", **{key: array for key, array in embeddings_by_combo.items()})`, keyed by a self-describing `"k1=v1,k2=v2,..."` string built from `tuning_grid.keys()`'s own order for that run (`_combo_key`) - the same names/values each row of that same run's `tuning_results.csv` already carries (`str(bool)` is `"True"`/`"False"`, matching pandas' own CSV serialization), so a caller rebuilds the exact key from any row without a separate index file. Exists so a downstream tool (Fase C's PAIR-style interactive replot, `docs/knowledge/dim_reduction_tuning_guide.md`) can read back a saved combination's embedding and just plot it, with no refit.

  Same flag also writes a `metadata.csv` alongside it (one per run, not per leaf - every combination in a sweep shares the same subjects/row order): unlike `embeddings_grid_*.png`'s color modes, which compute `side`/`nihss`/`volume` live from `metadata`/`X` at plot time (`src/analysis/embedding_coloring.py` - `join_lesion_side`/`join_nihss` hit the `participants.tsv` registry on the spot, `volume` is `X.sum(axis=1)`), a saved `embeddings.npz` needs a *self-contained* metadata to be useful later without reloading `X` or re-hitting that registry. `_run_fine_tuning` therefore calls `enrich_metadata_with_lesion_info(metadata, X)` (the same call `_run_production` always makes) right before `_write_tuning_output`, but **only** when `config.save_tuning_embeddings` is `True` - every other tuning run (the default) keeps `metadata` exactly as loaded, unchanged behavior and no registry-lookup cost paid for nothing. Propagates `enrich_metadata_with_lesion_info`'s own `FileNotFoundError`/`ValueError` (an unresolvable dataset/subject) the same way `_run_production` does.

  Without `nested_params` declared: `{tuning_results.csv, tuning_plot.png (1 param only), config.md}` - unchanged since before the 2026-08 session. With `nested_params` declared (umap/tsne): `_write_nested_tuning_leaves` groups `results` by `nested_params` via `results.groupby(nested_params, sort=False)` - grouping the **actual result rows**, not the Cartesian product of every config-declared value, so an excluded combination (e.g. `metric=jaccard` + `regress_out_volume=True`) never produces an empty leaf folder - writing one subfolder per real combination (`<param>=<value>/...`, nested in `nested_params`'s declared order) with its own filtered `tuning_results.csv` always, plus `embeddings_grid_<color>.png` unless `config.write_embeddings_grid` is `False` (`_build_grid_blocks`: for each free/grid parameter, one cell per value it can take, every *other* free parameter held at `base_params`' own value - raises `ValueError` if that exact combination was never computed, i.e. the base value isn't itself in that parameter's `tuning_grid` list; each cell's embedding is reduced to a fixed 2 components via `embedding_for_viz` if the leaf's own dimensionality differs, e.g. a leaf with `n_components=10` in `nested_params` - `embeddings_grid.png` is static-only, always 2D regardless of `config.viz_n_components`).

  **`regress_out_volume` is stripped before that refit, then reapplied to its result** (bug fixed 2026-08, found by actually running a real `n_components`-varying sweep for the first time): `_build_grid_blocks`'s combo dict comes straight from `tuning_grid`'s swept keys, which - unlike `base_params` in production mode - includes `regress_out_volume` whenever it's part of the sweep; passed unstripped into `embedding_for_viz` it used to reach `umap.UMAP(**params)` directly and raise `TypeError` (`regress_out_volume` isn't a constructor argument for any `REDUCTION_METHODS` entry). Masked entirely before that fix in every prior test/run: with `n_components` always equal to `_TUNING_GRID_N_COMPONENTS` (2), `embedding_for_viz` always took its early-return path and never actually called the estimator with the dirty dict. Now: `regress_out_volume` is popped from the combo before the refit, and - since the refit is a brand-new fit that never went through `run_tuning_sweep`'s own post-fit `regress_out_covariate` step - reapplied to the refit result afterward when that combo had it set, so the plotted embedding matches what was actually scored. **Determinism consequence worth knowing**: with `random_state` fixed, that refit call (`metric`/`n_neighbors`/`min_dist`/`n_components=2`/`random_state`, all identical) is bit-for-bit the same computation as whichever other leaf already swept those same free-parameter values at `n_components=2` - not merely similar, genuinely redundant compute. `write_embeddings_grid=False` is the manual opt-out for exactly this case (`test_dim_reduction_fine_tuning_write_embeddings_grid_false_skips_plots_keeps_csv`; the bug itself is covered by `test_dim_reduction_fine_tuning_nested_n_components_and_regress_out_volume_refits_viz`, both `tests/integration/test_dim_reduction_pipeline.py`).

Both modes call `append_run_log_entry` (`run_log.py`, `docs/dev/config.md`) after writing their output, tagged `"production"`/`"tuning"` respectively, into `<output_root>/production/<method>/runs.csv` or `<output_root>/tuning/<method>/runs_tuning.csv`.

### `clustering.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

Same `main()` branch-on-`config.fine_tuning` shape as `dim_reduction.py` above, but `clustering.py` already loops over multiple `clustering_methods` in production mode, so its fine-tuning mode loops too (`_run_fine_tuning` iterates `config.clustering_methods`, calling `_run_one_method_tuning` once per method - same fail-fast "stop on first method's failure" behavior as the production loop's `_run_one_method`, no partial-run tolerance either mode).

- **Production** (`fine_tuning=false`, unchanged): as described above (`load_method_params` → `CLUSTERING_METHODS[method]` → `save_matrix`).
- **Fine-tuning** (`fine_tuning=true`), per method: `load_method_params` + `load_tuning_grid` → `clustering_tuning.run_clustering_tuning_sweep` → `<output_root>/tuning/<method>/<dd-mm>_<session_name>/{tuning_results.csv, tuning_plot.png, config.md}` (same deliberately-separate-branch shape as `dim_reduction.py`'s tuning output, same reasoning: a sweep table is never mistaken for a production artifact, no `manifest.json`; no `embeddings.npz` concept here - clustering has no embedding of its own to save). `_write_tuning_output` additionally calls `_write_standalone_diagnostic` when `method in STANDALONE_DIAGNOSTIC_METHODS` (agglomerative/spectral), writing that method's own extra diagnostic plot into the same tuning output directory.

Same shared `<output_root>/production/<method>/runs.csv` / `<output_root>/tuning/<method>/runs_tuning.csv` convention as `dim_reduction.py` - `_run_log_dir(config, method, branch)` (`"production"`/`"tuning"`, same literal each caller also passes as `append_run_log_entry`'s own `run_type`) is reused unchanged between `_run_one_method` (production) and `_run_one_method_tuning` (fine-tuning).

### `dim_reduction_clustering.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep, clustering only)

Added after `clustering.py`'s own fine-tuning mode, on request - the one-shot alternative to `dim_reduction.py --fine_tuning=false` (save the embedding) then separately `clustering.py --fine_tuning=true` pointed at it: useful when you only want to tune clustering hyperparameters against a specific reduction without needing that embedding written to disk as its own artifact first. The reduction step itself is **never** swept here in either mode - `REDUCTION_METHODS[config.reduction_method](X, reduction_params)` runs exactly once in `main()`, before the `config.fine_tuning` branch, always at `reduction_params_file`'s `"params"` (not `"tuning_grid"`); re-tuning the reduction is `dim_reduction.py`'s job alone, kept a strictly separate concern.

- **Production** (`fine_tuning=false`, unchanged): as described above - clusters the one embedding with every method in `clustering_methods`, writes the comparison plot.
- **Fine-tuning** (`fine_tuning=true`), per method against that same one embedding: `load_method_params` + `load_tuning_grid` (both from `clustering_params_file`) → `clustering_tuning.run_clustering_tuning_sweep` → `<output_root>/tuning/<reduction_method>/<method>/<dd-mm>_<session_name>/{tuning_results.csv, tuning_plot.png, config.md}` + a standalone diagnostic plot for agglomerative/spectral - same shape and same `_write_tuning_output`/`_write_standalone_diagnostic` logic as `clustering.py`'s own fine-tuning mode (duplicated, not shared, per this codebase's established per-CLI convention - see `clustering_tuning.py` above), just nested one level deeper under `reduction_method` and reading `embedding` instead of raw `X`. **No comparison plot** in this mode, even with multiple `clustering_methods` requested - a sweep's rows aren't a single set of cluster labels, there's nothing to compare side by side the way `plot_clusters_comparison` expects. Same shared `<output_root>/tuning/<reduction_method>/runs_tuning.csv` as production's `<output_root>/production/<reduction_method>/runs.csv`, tagged `"tuning"`, same `reduction_method`/`clustering_method` `extra_columns`.

**The intended workflow** (confirmed with the user, kept manual by design - no automatic parameter selection, and no plan to add one for any of the 4 fine-tunable methods; cross-validation for a future regression/classification task on top of clustering is a separate, not-yet-designed concern): run with `fine_tuning: true` → open `tuning_results.csv`/`tuning_plot.png` → pick parameters by eye → write them into `params_reduction.json`'s `"params"` for that method → set `fine_tuning: false`, pick a new `session_name`, optionally fill in `run_notes` explaining the change → re-run for the real embedding.

`DimReductionClusteringConfig` uses two explicitly named fields, `reduction_params_file` and `clustering_params_file`, rather than the two-element positional list (`"params_file": [...]`) shown in the original handoff note — decided during implementation: a positional list makes the mapping from list index to method implicit, the same category of fragility as `lessons_learned.md` #1 (though in practice `params.py`'s own per-method validation would catch a swapped pair too, since a reduction-method key wouldn't be found in a clustering params file). Named fields cost nothing extra and remove the ambiguity outright.
