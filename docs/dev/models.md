## `src/analysis/reduction.py` / `clustering.py` — modeling strategies

Plain `dict[str, Callable]` registries (`REDUCTION_METHODS`, `CLUSTERING_METHODS`), not classes/ABCs — same "explicit registry over hardcoded dispatch" precedent as `config/registry/metadata_sources.json`. Each entry is a pure `(X, params) -> array` function: `params` is unpacked with `**params` straight into the underlying `sklearn`/`umap` estimator's constructor (`pca` is the exception, below), no in-code defaults for any hyperparameter (`code_standards.md` §5) — those live only in `config/registry/params_reduction.json`/`params_clustering.json` (`src/analysis/params.py`, see `docs/dev/config.md`). Invalid/unexpected keys in `params` surface as whatever error `sklearn`/`umap` itself raises for a bad constructor argument — not re-validated here, since re-implementing each estimator's accepted-parameter surface would just duplicate their own API.

- `reduction.py`: `umap_embed`, `tsne_embed`, `pca_embed`, `pacmap_embed`. The theory of each method (objective, library defaults, tuning, evaluation, pitfalls): `knowledge/notes/dim_reduction_clustering/dim_reduction_methods/`.
- `clustering.py`: `kmeans_cluster`, `agglomerative_cluster`, `gmm_cluster`, `hdbscan_cluster`, `hdbscan_soft_fit`/`hdbscan_soft_cluster` (standalone `hdbscan` package, see the section below), `spectral_cluster`.

`pca_embed` is the one exception to the "blind `**params` unpack" rule above: PCA is not one estimator but a family of choices (solver, standardization, dual or covariance computation, rotation, number of components), so it delegates to `pca_method.py::fit_pca`, which owns the `pca` params contract. Every key is validated there: an unknown key, a missing required one (`solver`, `standardize`, `rotation`, and `dual` with the `blocks` solver), a bad value, a `null` (a key is present with a value or absent - a null would travel into the run's recorded params and be read back as a value), both or neither of `n_components`/`variance_share`, or a param the chosen solver would ignore (`dual`/`chunk_columns`/`max_matrix_gib` with `sklearn`, any rotation with `sklearn`) raises `ValueError` naming it. The full list of params and how to choose them: `docs/guides/dim_reduction.md`, section "Il metodo `pca`".

`fit_pca(X, params, model_cache=None) -> PcaFit` returns the embedding, the number of components kept (the answer to `variance_share`), the share of the variance they explain and the whole variance spectrum; `fit_pca_embedding` is its `(embedding, share)` view, which `pca_embed` and `tuning.py::evaluate_pca` use. The `blocks` solver is `covariance_pca.py` (`docs/dev/covariance_pca.md`); the `sklearn` solver fits `sklearn.decomposition.PCA(svd_solver="full")` on an in-memory, centered (and optionally standardized, ddof=1) copy and reads the same quantities off it. The decomposition depends on `solver`/`standardize`/`dual`/the resource knobs but not on `n_components`, `variance_share` or `rotation`, so `model_cache` (a dict the caller owns, only ever shared between calls on the same `X`) lets a sweep over those fit it once.

Rotated scores are the paper's "multiple regression" step (Thiebaut de Schotten et al. 2020, `knowledge/notes/dim_reduction_clustering/employed_dim_reduction_methods.md`, "I punteggi dopo la rotazione"): each subject's centered row regressed onto the rotated loadings, in normal-equation form accumulated block by block. Only the orthogonal rotations of `factor_analyzer` are accepted (the regression assumes uncorrelated rotated components); a rotation needs at least 2 components to rotate (`n_components`, or `rotation_n_components` when given - then `n_components` may be 1: it only keeps some of the rotated ones; it rotates *between* components). The loadings passed to the rotation are `eigenvector * sqrt(eigenvalue)` (factor loadings), never the raw unit-norm eigenvectors: with the latter the rotation would weight every component equally and, since an orthonormal basis rotated orthogonally stays orthonormal, the regression would degenerate into a plain projection. Regression test: `tests/unit/test_reduction.py::test_pca_embed_with_varimax_rotates_scaled_loadings_not_raw_eigenvectors`.

`embed(reduction_method, X, params, distance_cache=None, precompute_distance_metric=True) -> np.ndarray`: the single call site every `REDUCTION_METHODS[reduction_method]` invocation goes through, both in production (`dim_reduction.py`) and in `embedding_for_viz` below - `clustering.py` never calls it. When `params["metric"]` is one of `distances.py::PRECOMPUTABLE_METRICS` (`"jaccard"`/`"dice"`/`"euclidean"`), `X` is replaced by its precomputed `distances.py::precomputed_distance` matrix and `metric` switched to `"precomputed"` - the exact same path `tuning.py`'s `evaluate_umap`/`evaluate_tsne` also use for their fine-tuning sweeps. With `precompute_distance_metric=False` the whole branch is skipped and `metric` reaches the estimator on raw `X` (a "vanilla" call, for comparisons with external UMAP runs: `docs/dev/config.md`); `require_binary_matrix` runs either way, since jaccard/dice on non-binary data is wrong whichever path computes it. Two independent reasons this matters, not just one: (1) *exactness* - umap-learn only computes an *exact* k-NN graph itself for datasets under 4096 samples (`n_index_samples < 4096` in `UMAP.fit()`, sets `self._small_data = True` - `umap/umap_.py` in the umap-learn source) - above that it silently switches to the approximate NNDescent/pynndescent search, an undocumented, version-dependent threshold; routing every call through `embed` removes that dependency entirely, regardless of cohort size (relevant for the real cohort, `25-08_s1.2-vol`, at 5269 subjects - past the threshold). (2) *speed*, for `"euclidean"` specifically - umap-learn/sklearn's own per-fit neighbor search on a high-dimensional raw matrix (264274 voxels) is itself the bottleneck, not the distance computation: measured directly on `25-08_s1.2-vol`, `sklearn.metrics.pairwise.euclidean_distances` computes the *entire* 5269x5269 distance matrix in 88s, while a single uncached umap fit at `metric="euclidean"` took 17-35 *minutes* for one `n_neighbors`/`min_dist` combination alone. For `reduction_method="tsne"` when precomputing, it also sets `init` to `reduction.py::tsne_init_from_distances` (classical MDS of the distance matrix; sklearn's own default `init="pca"` can't run on a distance matrix). `distance_cache`, when passed, lets a caller compute the main embedding and a viz refit at the same metric without recomputing the precomputed matrix twice - `dim_reduction.py` builds one shared cache per run. `pca`/`pacmap` are unaffected by any of this - their `params_reduction.json` entries never carry a `"metric"` key, so `params.get("metric")` is `None` and the whole branch is a no-op for them. Raises `ValueError` listing the known methods for a `reduction_method` not in `REDUCTION_METHODS`; `embedding_for_viz` raises `ValueError` for a `viz_n_components` that isn't an integer >= 1.

`embedding_for_viz(reduction_method, X, reduction_params, embedding, viz_n_components, distance_cache=None, precompute_distance_metric=True) -> np.ndarray`: returns an embedding with exactly `viz_n_components` columns, for plotting only - reuses `embedding` unmodified (`is` identity, zero extra cost) when it already has that many columns, otherwise refits via `embed` above (so a jaccard/dice/euclidean refit gets the same precomputed-distance treatment, sharing `distance_cache` with the main fit rather than recomputing it a second time) from scratch on the same raw `X` with only `n_components` overridden. Exists because `embedding[:, :viz_n_components]` is not a valid substitute for umap/tsne/pacmap: their output dimensions have no importance ordering, so a slice can make real cluster structure look artificially merged or split. The refit shares the original fit's neighbor graph (depends only on `metric`/`n_neighbors`, not `n_components`) since every other param is held identical. One caller: `dim_reduction.py::_run_production` (own `viz_n_components`, 2 or 3). `clustering.py` has no raw `X`/reduction params to refit from by design (it only ever receives an already-built matrix) - its own, unrelated mechanism for the same underlying problem is `_resolve_viz_embedding` below, a companion embedding read from a config-supplied path, never a refit.

Only `umap`/`tsne` actually get this refit (`_REFITTABLE_FOR_VIZ`, deliberately narrow). An **unrotated `pca`** (`reduction_params["rotation"] == "none"`) takes the first `viz_n_components` columns of its own embedding instead (`_leading_components`): unlike any other method's output, its columns are ordered by variance, so the first two are the two directions that separate the subjects most - a slice is a legitimate 2D view of the same fit (`lessons_learned.md` #16 names this as the one exception), and a pca with fewer components than `viz_n_components` raises. The same holds for a **rotated `pca` with `rotation_n_components`** (`_columns_ordered_by_variance`): it keeps the rotated components that explain the most variance, most first (`covariance_pca.py::leading_rotated_scores`, shares from the squared rotated loadings), so its leading columns are its leading components. Every other case raises when the dimensions differ: a **rotated `pca` that kept the components it rotated**, because the rotation is joint across every retained component, so the columns have no order and a refit at a different `K` solves a different optimization problem, not "the same factors, fewer of them" - the whole point of the methodology it reproduces is that each rotated factor has a specific anatomical meaning; and `pacmap`, excluded explicitly rather than inferred, since getting this wrong would silently change a real production method's behavior.

## `src/analysis/tuning.py` — manual fine-tuning for umap/tsne/pca/pacmap

No automatic parameter selection anywhere in this module - it only produces a comparison table; a human reads it (or the accompanying plot) and writes the chosen parameters into `params_reduction.json`'s `"params"` by hand. t-SNE's `early_exaggeration`/`learning_rate`/`max_iter` are excluded on purpose (fixed; `early_exaggeration` and `max_iter` as in Thiebaut de Schotten et al. 2020, `learning_rate` is `"auto"`, see `knowledge/notes/dim_reduction_clustering/dim_reduction_tuning_guide.md`) - only `perplexity` is swept, added on request since the paper's own supplementary material sweeps it too. Every clustering method is excluded here too - fine-tuning for those lives in `clustering_tuning.py` below, not this module.

`TUNING_METRIC_NAMES = {"umap": "trustworthiness", "tsne": "trustworthiness", "pca": "cumulative_explained_variance", "pacmap": "trustworthiness"}` - the quality metric is genuinely different per *family* of method (decided with the user), not per individual method - a rotated `pca` keeps PCA's criterion (the share of variance explained by the kept components); an orthogonal rotation of all the retained components leaves that share as it was, but with `rotation_n_components` the kept components are chosen among the rotated ones and explain less than the leading components of the plain PCA and `tsne`/`pacmap` reuse UMAP's (trustworthiness is a generic neighbor-preservation metric, not UMAP-specific):
- `evaluate_umap(X, params, trustworthiness_n_neighbors)` / `evaluate_tsne(X, params, trustworthiness_n_neighbors)` / `evaluate_pacmap(X, params, trustworthiness_n_neighbors)` embed then score with `sklearn.manifold.trustworthiness` - how well local neighborhoods survive the projection. `evaluate_umap`/`evaluate_tsne` both read `params["metric"]`: for any `distances.py::PRECOMPUTABLE_METRICS` value (`"jaccard"`/`"dice"`/`"euclidean"`), both the embedding *and* the `trustworthiness` call are given the same `distances.py::precomputed_distance` matrix (`metric="precomputed"` on both) instead of raw `X` - scoring a precomputed-metric embedding against `trustworthiness`'s own euclidean-on-raw-`X` default would judge it by a notion of "originally close" it was never built to preserve. For `"euclidean"` specifically this is also a large speed win at this project's scale, not just an exactness/scoring-consistency guarantee - see `embed`'s entry above for the measured numbers, same underlying mechanism. `evaluate_tsne` additionally starts t-SNE from `reduction.py::tsne_init_from_distances` whenever `metric="precomputed"` - `sklearn.manifold.TSNE`'s own default `init="pca"` can't run on a distance matrix, so the start is classical MDS of that matrix (the PCA scores, for euclidean distances), scaled like sklearn's PCA init; `embed` does the same. `evaluate_pacmap` has no such branch - its `tuning_grid` never sweeps `metric`. Caveat: the euclidean speedup magnitude was only independently measured for `evaluate_umap` (see `embed`'s entry above); `evaluate_tsne` uses the same already-validated mechanism, but its speedup has not been timed on a real sweep - don't assume the same 88s-vs-17-35min order of magnitude for t-SNE until it's actually measured on a real sweep.
- `evaluate_pca(X, params, model_cache=None)` returns `pca_method.py::fit_pca_embedding`'s `(embedding, share)`: the share of the total variance the kept components explain - PCA's own natural criterion, and the exact one the paper uses to choose a component count. `run_tuning_sweep` hands it a per-sweep `model_cache` (`METHODS_WITH_MODEL_CACHE = {"pca"}`, the sibling of `METHODS_WITH_DISTANCE_CACHE`), so a grid over `n_components`/`variance_share`/`rotation` fits the decomposition once; a new `standardize`/`dual`/`solver` value fits again.

`_EVALUATORS: dict[str, Callable]` dispatches by method name (Strategy registry, same precedent as `REDUCTION_METHODS`/`CLUSTERING_METHODS`) rather than an `if/elif` chain, which at four methods is exactly the pattern `lessons_learned.md` #1 warns about. `METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS = {"umap", "tsne", "pacmap"}` is consulted both here and by `dim_reduction.py` (to decide whether to load `trustworthiness_n_neighbors` from config at all) - a single shared source of truth for "which methods need this extra setting", not duplicated/hardcoded in both places.

**Evaluation registry** (`src/analysis/tuning_evaluations.py`): the mechanisms a tuning applies are entries of `EVALUATIONS`, an `EvaluationSpec` each (kind, settings validation, optional feasibility check against the grid, run function). Two kinds: `sweep_score` (`trustworthiness`, `cumulative_explained_variance` - the column of `tuning_results.csv`, computed inside `run_tuning_sweep` from `X`, fixed by `reduction_method`) and `embedding_evaluation` (`plot_hdbscan` - reads only the embeddings, so it runs on the in-memory sweep right after `_write_tuning_output` and, identically, on a stored run through `src/pipeline/evaluate_dim_reduction_tuning.py`). A new mechanism is one new entry; config parsing, `dim_reduction.py` and the standalone entry point iterate the registry. `src/analysis/tuning_embeddings.py` holds the on-disk conventions both sides share: `combo_key`/`parse_combo_key` (the `embeddings.npz` key format), `leaf_dir` (the `metric=.../n_components=.../` layout) and `load_tuning_run` (embeddings.npz + the grid snapshot in `config.md`, refusing a directory whose keys are not exactly the declared grid's Cartesian product).

`plot_hdbscan` runs `CLUSTERING_METHODS["hdbscan"]` (`hdbscan_cluster`, the same function `clustering.py` uses) on every combination's embedding in its own space, whatever its number of components, and draws the labels on the combination's 2-component twin: the embedding with the same hyperparameters and `n_components=2`, a separate real fit (`visualization_key`) - never a slice of the first columns of a non-PCA embedding. A sweep whose higher-dimensional combinations have no such twin is refused before it starts. Output per nested leaf: `hdbscan_grid_mcs<N>_ms<M>.png` (`plotting.plot_hdbscan_grid`) and `hdbscan_results_mcs<N>_ms<M>.csv` (`n_clusters_found`, `noise_fraction`).

`run_tuning_sweep(method, X, base_params, tuning_grid, trustworthiness_n_neighbors, model_cache=None) -> tuple[pd.DataFrame, dict[tuple, np.ndarray]]` takes the Cartesian product of `tuning_grid`'s value lists (`itertools.product`), evaluates each combination via `_EVALUATORS[method]` (swept keys override `base_params`; un-swept keys like `random_state` stay fixed). Returns `(results, embeddings_by_combo)`: `results` has one row per combination, swept values + metric column, still the only thing written to `tuning_results.csv`; `embeddings_by_combo` (in-memory only, never serialized) keys each combination's actual embedding by its exact `combo` tuple (`tuning_grid.keys()` order) - so a caller that needs to *see* an embedding, not just its score (`dim_reduction.py`'s `embeddings_grid` plot), doesn't have to refit it. `model_cache` is the dict a method in `METHODS_WITH_MODEL_CACHE` (`pca`) fits its decomposition into; a caller that passes its own reads the fitted models back after the sweep (`pca_method.decomposition_spectra`), omitted the sweep uses a private one, and passing one to any other method raises. Raises `ValueError` for any method not in `TUNING_METRIC_NAMES` (registry-driven, not an implicit fallback). Also raises `ValueError` for a `tuning_grid` axis that is empty or repeats a value.

## `src/analysis/distances.py` — fast precomputed pairwise distances for umap/tsne

`SUPPORTED_BINARY_METRICS = {"jaccard", "dice"}` and `PRECOMPUTABLE_METRICS = SUPPORTED_BINARY_METRICS | {"euclidean"}` - the two sets stay distinct on purpose: `SUPPORTED_BINARY_METRICS` is exactly the metrics with a domain restriction (`require_binary_matrix` below applies only to these), `PRECOMPUTABLE_METRICS` is every metric this module can turn into a cached precomputed distance matrix at all, the set `tuning.py`/`reduction.py` actually check against before taking the precomputed-distance path.

`binary_pairwise_distance(X, metric) -> np.ndarray` computes a full `(n_samples, n_samples)` Jaccard or Dice distance matrix for a binary `(n_samples, n_features)` array (voxel-wise lesion masks): `metric` must be in `SUPPORTED_BINARY_METRICS` - `ValueError` otherwise, and `ValueError` if any row is all-zero (union/sum would be 0, both metrics undefined for an empty sample). Exists because `scipy.spatial.distance.pdist`'s boolean metrics compute one pair at a time - measured at ~19 minutes extrapolated for 1150 subjects × 254865 voxel features. Binary overlap between every pair at once is instead a single matrix multiplication (`X @ X.T` counts shared "on" features per pair, via BLAS) - Jaccard/Dice distance follow from that intersection count plus each row's own sum, in seconds instead of minutes. Casts to `float64` before the multiply regardless of `X`'s own dtype (usually `uint8`) - intersection counts can exceed a narrow integer type's range and silently wrap (`lessons_learned.md` #13).

`euclidean_pairwise_distance(X) -> np.ndarray` wraps `sklearn.metrics.pairwise.euclidean_distances(X.astype(np.float64))` - no binary/domain restriction, any real-valued matrix is valid. Exists for a *different* reason than `binary_pairwise_distance` above: umap-learn/sklearn don't have a slow *distance computation* for euclidean (that part is cheap, the same Gram-matrix/BLAS trick as the binary case) - what's slow is their own per-fit *neighbor search*, repeated from scratch on every call in a sweep with no way to cache it internally. Measured directly on the real `25-08_s1.2-vol` lesion matrix (5269 subjects × 264274 voxels): the entire 5269×5269 distance matrix computes in 88s, while a single uncached umap fit at `metric="euclidean"` took 17-35 *minutes* for one `n_neighbors`/`min_dist` combination. Precomputing once and reusing (`distance_cache` in `tuning.py`/`reduction.py`) turns that per-call cost into a one-time cost, exactly the same shape of fix `binary_pairwise_distance` already was for jaccard/dice, just for a different root cause.

`precomputed_distance(X, metric) -> np.ndarray` dispatches to `binary_pairwise_distance` or `euclidean_pairwise_distance` by metric name - the single entry point `tuning.py`/`reduction.py` call once `metric` is known to be in `PRECOMPUTABLE_METRICS`. Raises `ValueError` for any metric outside that set.

`pairwise_distance(X, metric, n_jobs=-1) -> np.ndarray` accetta `euclidean`/`dice`/`jaccard` su una matrice binaria **o continua `>= 0`**, ed è l'ingresso di `adp.py`. Su una matrice binaria dà esattamente `binary_pairwise_distance`/`euclidean_pairwise_distance` (un test lo verifica), ma lavora a blocchi di colonne (`_GRAM_CHUNK`, 20000) senza mai convertire l'intera matrice in `float64` (una matrice voxelwise grezza è ~5000 x 264274): i prodotti per blocco sono in `float32` (esatti per conteggi interi) e si sommano in `float64`. Su una matrice continua `dice`/`jaccard` sono le versioni pesate, con `sum_min = (sum x + sum y - L1(x, y)) / 2`: `dice = 1 - 2 sum_min / (sum x + sum y)` (Czekanowski), `jaccard = 1 - sum_min / (sum x + sum y - sum_min)` (Ruzicka); le `L1` sono l'unico passo lento: si sommano per blocchi di `_GRAM_CHUNK` colonne (al massimo un blocco `float64` di `X` in memoria, invece dei 13.6 GB di una copia intera di 5845 x 291345) con le righe divise tra `n_jobs` thread (`cdist` rilascia il GIL). Solleva per valori negativi o per una riga a zero con `dice`/`jaccard`.

`require_binary_matrix(X, metric) -> None`: raises `ValueError` if `X` has any value outside `{0, 1}` - jaccard/dice's set-overlap definition (and the `X @ X.T` intersection-count trick above) is meaningless once a "1" can mean "partial membership". Nothing upstream guarantees this: `dim_reduction.py` reads any `matrix.npy` artifact regardless of which pipeline wrote it - `build_lesion_matrix.py` always produces a strictly binary voxel-wise matrix, but `build_fc_matrix.py` (and any future atlas-based/continuous feature source) does not. Called by `binary_pairwise_distance` itself, and directly by `dim_reduction.py`'s production path (before `reduction.py::embed`, so a bad matrix fails fast with a clean error before any output directory is even created) and by `embed` itself (defense-in-depth for any other caller, e.g. a viz refit). Deliberately *not* extended to `euclidean_pairwise_distance` - euclidean has no `{0,1}` domain restriction, any real-valued matrix is a valid input.

Used by `tuning.py::evaluate_umap`/`evaluate_tsne` (above) and by `reduction.py::embed` (also above) - every `REDUCTION_METHODS` call site (production and fine-tuning alike, both umap and tsne) routes any `PRECOMPUTABLE_METRICS` value through this same precomputed-distance path. `metric` is an explicit key in both `umap`/`tsne`'s `"params"` in `params_reduction.json` (rather than left absent, silently falling back to the library's own default) - production `umap` and `tsne` both run with `metric="euclidean"` in the checked-in registry - so the euclidean-specific speed fix is not a hypothetical, it directly speeds up the actual production config.

## `src/analysis/clustering_tuning.py` — manual fine-tuning for kmeans/agglomerative/gmm/hdbscan/spectral

Same "no automatic selection" philosophy as `tuning.py`, but clustering has no ground truth to score against - every generic metric is an *internal* validation index computed straight from `(X, cluster_labels)`, meaningful only within one method's own swept grid, never compared across methods.

`compute_clustering_metrics(X, labels, combo_params=None) -> dict[str, float]` returns `{"silhouette", "calinski_harabasz", "davies_bouldin", "noise_fraction"}` for the methods scored with the geometric indices (the density methods get only `compute_noise_metrics`'s `noise_fraction`, see below) - `sklearn.metrics.silhouette_score`/`calinski_harabasz_score`/`davies_bouldin_score` excluding any HDBSCAN-style noise (`label == -1`) first (undefined for a "cluster" that isn't one), with `noise_fraction` always reported so the exclusion is visible rather than silent. A degenerate combination (fewer than 2 non-noise clusters, or every non-noise point its own cluster) can't have the 3 metrics computed at all - caught (the same condition `sklearn` itself would raise on) and recorded as `NaN` with a logged warning rather than aborting the whole sweep, since a bad hyperparameter combination is expected information in a tuning sweep, not a bug (distinct from `lessons_learned.md`'s silent-fallback pattern: this is one documented, intentional strategy for a legitimate domain case, not a caught-and-hidden error).

`combo_params` (optional, only `run_clustering_tuning_sweep` below always passes it): when given, `require_euclidean_compatible` raises `ValueError` upfront if it names a distance/affinity the 3 geometric indices' Euclidean assumption doesn't hold for - silhouette/Calinski-Harabasz/Davies-Bouldin all default to Euclidean distance internally, correct only as long as the clustering method itself also treated `X` as a plain Euclidean feature space. `_EUCLIDEAN_SAFE_AFFINITY = {None, "nearest_neighbors", "rbf"}` (spectral's `affinity`) and `_EUCLIDEAN_SAFE_METRIC = {None, "euclidean"}` (agglomerative's `metric`) are an explicit allow-list (`lessons_learned.md` #20, over a free-form guess) of every value known to still mean "X is a plain Euclidean feature matrix" - anything else, most importantly `affinity="precomputed"` (X is itself a distance/affinity matrix under an arbitrary metric, e.g. Jaccard/Dice) or a non-Euclidean `metric`, makes X's own coordinates meaningless to a Euclidean index, so the function refuses outright rather than silently scoring the wrong geometry. Dormant today - no production/tuning config sets either value.

`compute_silhouette_samples(X, labels, metric="euclidean") -> tuple[np.ndarray, np.ndarray]` is the per-sample counterpart used for `plotting.plot_silhouette_analysis` (production time, not the sweep above, see `docs/dev/plotting.md`): same noise-exclusion convention as `compute_clustering_metrics`, but returns `(non_noise_labels, sample_silhouette_values)` from `sklearn.metrics.silhouette_samples` instead of one aggregate number - their mean equals `compute_clustering_metrics`'s `"silhouette"` exactly. Unlike `compute_clustering_metrics`'s NaN-and-warn on a degenerate combination (built for an unattended sweep over many combinations), this **raises** `ValueError` - it runs once for the single already-chosen production result, so the caller (`clustering.py`'s `_run_silhouette`) decides what to skip, catching that specific exception and logging a warning rather than failing the whole run. `metric` is the distance the clustering used: `euclidean` and `cosine`/`manhattan` (sklearn scores `X` under that distance, as the sweep does in `compute_clustering_metrics_metric_aware`), or `dice`/`jaccard` (the exact distance matrix); any other raises.

`dunn_index(X, labels) -> float` (`project-clustering-tuning-evaluation-tables` memory): Dunn Index (Dunn 1974) - ratio of the smallest inter-cluster distance to the largest intra-cluster diameter, higher is better (opposite direction from Davies-Bouldin). No sklearn/scipy built-in exists, so it is a from-scratch implementation on `sklearn.metrics.pairwise_distances` (Euclidean by default, same assumption as `compute_clustering_metrics`, not metric-aware). Same noise-exclusion convention as `compute_clustering_metrics`/`compute_silhouette_samples`; raises `ValueError` for fewer than 2 non-noise clusters, or when every non-noise cluster is a singleton (every intra-cluster diameter is `0.0`, which would make the ratio a division by zero). Consumed by `notebooks/post-results_analysis/clustering_evaluation.ipynb` (`docs/guides/evaluation.md`), not wired into `run_clustering_tuning_sweep`'s own per-combination columns (Dunn is not part of the production/tuning sweep itself; the density methods use DBCV instead, see the hdbscan section below).

`run_clustering_tuning_sweep(method, X, base_params, tuning_grid, consensus_config=None) -> (pd.DataFrame, dict[tuple, np.ndarray])` mirrors `tuning.py`'s sweep shape (Cartesian product, swept keys override `base_params`; the returned dict keys each combination's already-computed cluster-label array by its `combo` tuple, same role as `tuning.py`'s `embeddings_by_combo` - see `save_tuning_clusterings` below), but two methods get an extra scalar column beyond the 3 generic ones, computed by refitting the actual estimator instead of going through `CLUSTERING_METHODS[method]` (which only returns labels): `_kmeans_with_extra_metrics` keeps `KMeans.inertia_` (the elbow criterion), `_gmm_with_extra_metrics` keeps `GaussianMixture.bic(X)`/`.aic(X)` (likelihood-based, unlike the other 3 which are purely geometric) - `_hdbscan_with_extra_metrics`/`_hdbscan_soft_with_extra_metrics` add `n_clusters_found` (and, for `hdbscan_soft`, `membership_mean`/`persistence_mean`, below); `_EXTRA_METRICS_EVALUATORS` dispatches by method name and has no entry for agglomerative (own metric-aware branch, below) nor spectral (only the 3 generic columns). `adp` delegates to `adp.run_adp_tuning_sweep`. The sweep raises `ValueError` when it evaluates no combination (an empty axis, or an agglomerative grid whose every combination is `ward` + a non-euclidean metric). `METHOD_METRIC_COLUMNS: dict[str, list[str]]` is the single source of truth `clustering.py` reads to know which columns a given method's sweep will produce (and therefore which to plot) - `noise_fraction` is only listed for `"hdbscan"`/`"hdbscan_soft"` (the only methods scored by `compute_noise_metrics` instead of the 3 geometric indices) even though `compute_clustering_metrics` always returns it, since it's mechanically 0.0 for every other method (never noise-producing) and plotting a flat line adds nothing.

**GMM's `covariance_type` (project-clustering-tuning-redesign memory)**: unlike agglomerative's `linkage`×`metric` (some pairings invalid) or kmeans's `k`×`init` (deliberately never a joint grid), `n_components` × `covariance_type` is a legitimate **joint** sweep with zero code change to `run_clustering_tuning_sweep` - `covariance_type` is just another key in `tuning_grid`, reaching `GaussianMixture(**params)` through the exact same `_gmm_with_extra_metrics` path every other swept key already does. AIC/BIC (already computed, see above) are the statistically correct tool to compare `covariance_type` values (they penalize by the number of free parameters, which is exactly what differs between e.g. `"full"` and `"spherical"`) - this is the standard GMM model-selection technique (Fraley & Raftery 1998/2002; sklearn's own `plot_gmm_selection.html` worked example grids the same two keys), not a compromise. `config/registry/params_clustering.json`'s checked-in `"gmm".tuning_grid` sweeps both.

Two methods also get a standalone diagnostic, independent of which value in the swept grid ends up chosen (`STANDALONE_DIAGNOSTIC_METHODS = {"agglomerative", "spectral"}`). The diagnostics of `agglomerative` and `spectral` are not computed once from `base_params` alone, which would freeze them at one arbitrary value of the swept axis they depend on (`metric` for the dendrogram, `affinity`/its hyperparameter for the eigengap); both group by that axis (one file per value) with a subplot per value of the other. Both mirror `compute_interclass_distance_matrix`'s existing per-metric grouping below:
- `compute_dendrogram_linkage(X, params, distance_cache=None) -> np.ndarray` refits `AgglomerativeClustering` with `n_clusters=None, distance_threshold=0, compute_distances=True` (forces the full merge tree down to singleton leaves, ignoring any `n_clusters`/`distance_threshold` already in `params`), then converts `children_`/`distances_` into the scipy linkage-matrix format `plotting.plot_dendrograms_grid` (`docs/dev/plotting.md`) expects (the standard sklearn-docs recipe for bridging the two). `clustering.py::_write_agglomerative_diagnostics` calls it once per `(metric, linkage)` combination - every swept `metric` value (or `base_params`/default `"euclidean"` alone when `metric` isn't swept) × every swept `linkage` value valid for that metric (`is_invalid_ward_metric_combo` skips `ward`+non-euclidean, same rule the sweep itself applies) - and writes one `dendrogram_metric=<metric>.png` per metric, with one subplot per valid linkage inside (`plot_dendrograms_grid`).

  **Metric-aware**: `compute_dendrogram_linkage` never passes `metric` straight into `AgglomerativeClustering` on raw `X`. On a direct-on-raw-matrix agglomerative tuning run (`data/derived/lesion_matrix/25-08_s1.2-vol`, 5269 subjects x 264274 voxels) that would be far too slow, for two reasons. For `jaccard`/`dice`, sklearn falls back to `scipy.spatial.distance.cdist`'s one-pair-at-a-time computation (the exact slow path `distances.py::binary_pairwise_distance` exists to avoid) - a multi-hour-per-combination cost at this scale, invisible on a small 2-3 column embedding. `euclidean` has the *same* shape of gap: a timing test on a 1000-subject subsample of the same matrix measured `AgglomerativeClustering(metric="euclidean")` fit directly on raw `X` ~6x slower than precomputing the same distances first (48.7s vs. 8.3s at n=1000; fitting on the already-precomputed matrix took 0.0s) - sklearn's internal computation here does **not** use the BLAS-optimized route `distances.py::euclidean_pairwise_distance` does. So every `distances.py::PRECOMPUTABLE_METRICS` value (`jaccard`/`dice`/`euclidean`) goes through `distances.py::precomputed_distance` with `metric="precomputed"`, with one hard exception: `linkage="ward"` never takes it, regardless of `metric` - sklearn only accepts `metric="euclidean"`/`"l2"` for `ward`, never `"precomputed"`, so a `ward`+`euclidean` combination (a valid, common one, not filtered out by `is_invalid_ward_metric_combo` - that only filters ward+*non-euclidean*) always fits directly on raw `X`, with no way to speed it up via this mechanism. `distance_cache` (optional, keyed by metric name) lets `_write_agglomerative_diagnostics` share one precomputed matrix across every `linkage` sweeping the same `metric` (it calls this function once per `(metric, linkage)` pair) instead of recomputing it per linkage - same role and shape as `run_clustering_tuning_sweep`'s own cache below.
- `compute_eigengap(X, params, max_k=20) -> np.ndarray` builds the same affinity graph `spectral_cluster` would (`"nearest_neighbors"` via `sklearn.neighbors.kneighbors_graph` symmetrized, or `"rbf"` via `sklearn.metrics.pairwise.rbf_kernel` - `ValueError` for any other `affinity`), computes the normalized graph Laplacian (`scipy.sparse.csgraph.laplacian`) and its smallest `max_k` eigenvalues (`scipy.linalg.eigh`, `subset_by_index`) - the eigengap heuristic (`plotting.plot_eigengaps_grid`, `docs/dev/plotting.md`) reads a suggested `n_clusters` off the biggest gap between consecutive values, a criterion with actual theoretical grounding for spectral clustering specifically (a Laplacian's near-zero-eigenvalue multiplicity approximates the count of well-separated graph components), unlike the generic geometric indices applied to the other methods. `clustering.py::_write_spectral_diagnostics` calls it once per `(affinity, hyperparameter)` combination - every swept `affinity` value (or `base_params`/default `"rbf"` alone when `affinity` isn't swept) × every swept value of that affinity's own hyperparameter (`SPECTRAL_AFFINITY_HYPERPARAM`: `n_neighbors` for `nearest_neighbors`, `gamma` for `rbf`) - and writes one `eigengap_affinity=<affinity>.png` per affinity, with one subplot per hyperparameter value inside.

HDBSCAN (which replaced DBSCAN) gets no standalone diagnostic: DBSCAN had one (`compute_k_distance`, a sorted distance-to-`min_samples`-th-neighbor plot for reading off a reasonable `eps` by eye) because it needs a single global distance threshold; HDBSCAN has no such threshold to read off a plot - `min_cluster_size` is judged directly from the swept `noise_fraction` column and the DBCV instead, so `compute_k_distance`/`plotting.plot_k_distance` were removed rather than kept unused.

### `hdbscan_soft` — the standalone `hdbscan` package

`hdbscan_soft_fit(X, params)` (`clustering.py`) fits `hdbscan.HDBSCAN(**params, prediction_data=True)` on `X` cast to `float64` and returns the fitted estimator; `hdbscan_soft_cluster` is its labels-only wrapper registered in `CLUSTERING_METHODS`. The import is inside the function: without the package it raises an `ImportError` naming `environment.yml`. It is a separate method from `"hdbscan"` (scikit-learn) because the two implementations do not give the same partition for the same numbers (`min_samples` convention, approximate MST: `knowledge/notes/dim_reduction_clustering/hdbscan_package.md`), so their runs live in separate folders and are not compared.

`soft_membership_matrix(fitted)` returns the (n_subjects, n_clusters) soft clustering (`hdbscan.all_points_membership_vectors`, columns in the package's 0..k-1 cluster order; (n_subjects, 0) when every subject is noise; `ValueError` for a column count that is not the number of clusters) and `own_cluster_membership(membership, labels)` the entry of each subject's own cluster, NaN for noise. `pipeline/clustering.py::_run_one_method` calls them for `method == "hdbscan_soft"` in production: one fit gives the labels and the matrix, `save_matrix` writes the matrix as the extra array `membership` (so `load_matrix` returns it), `metadata.csv` gets `membership_own`, and `cluster_plot.png` sizes the markers by it (noise: smallest marker).

`clustering_tuning._hdbscan_soft_with_extra_metrics` is the sweep evaluator: it fits once and returns the labels plus `n_clusters_found`, `membership_mean` (mean of each non-noise subject's own-cluster entry of `hdbscan.all_points_membership_vectors`) and `persistence_mean` (mean `cluster_persistence_`). There is no threshold on the membership. A combination with no cluster gives NaN for the two; a membership matrix whose column count is not the number of clusters raises `ValueError`. The two columns come from the fit, not from the labels, so no evaluation can recompute them from a stored tuning. The package numbers its clusters 0..k-1, which is what lets the own-cluster entry be read as `membership[i, labels[i]]`.

Three swept parameters (`min_cluster_size`, `min_samples`, `cluster_selection_method`) have no single heatmap: the `tuning_heatmaps` evaluation (`clustering_tuning_evaluations.py`) writes one `tuning_plot_cluster_selection_method=<value>.png` per value, `min_cluster_size` x `min_samples` inside. The sweep itself draws no map for `hdbscan`/`hdbscan_soft` (`DENSITY_SWEEP_METHODS`): the map includes DBCV, which the sweep does not compute. `params_clustering.json`'s `hdbscan_soft` block carries `approx_min_span_tree: false` in `params` (exact MST) and tags production folders with `mcs`/`ms`/`sel_`.

### HDBSCAN — `min_samples` joint sweep + probabilities_-sized production scatter

HDBSCAN's internal index is DBCV (`src/analysis/dbcv.py`, below), not the silhouette-family indices: they are computed on the non-noise subjects only and assume compact clusters. The sweep (`run_clustering_tuning_sweep`) writes for `hdbscan`/`hdbscan_soft` only `noise_fraction` (`compute_noise_metrics`, which refuses a non-euclidean `metric`/`affinity`) and the method's own columns; the `density_metrics` evaluation adds `dbcv`, and it also runs on a stored tuning. `probabilities_` still sizes the production scatter (`hdbscan_labels_and_probabilities`).

`min_samples` was added to `tuning_grid` alongside `min_cluster_size` (`config/registry/params_clustering.json`'s checked-in `"hdbscan"` entry) - deterministic like agglomerative (no `random_state`), so both axes are swept **jointly in one run** (the user's explicit constraint: no repeated/sequential tuning runs), drawn with `plotting.plot_clustering_tuning_heatmaps`, the same 2-swept-param heatmap mechanism built for agglomerative's `n_clusters`×`linkage`, now called by the `tuning_heatmaps` evaluation.

The one genuinely new piece: `hdbscan_labels_and_probabilities(X, params) -> (labels_, probabilities_)` (`clustering_tuning.py`) fits `HDBSCAN` directly and returns both arrays - `CLUSTERING_METHODS["hdbscan"]` (`hdbscan_cluster`) stays labels-only, the uniform contract every generic caller (the sweep, `run_rsc_repeats`, ...) relies on, so `probabilities_` (per-point membership confidence, always `0` for noise) is only reachable this way. `clustering.py::_run_one_method`'s production path calls it specifically for `method == "hdbscan"` (every other method still goes through `CLUSTERING_METHODS[method]`), feeding the result into `plotting.plot_clusters_2d`'s new optional `point_sizes` parameter - `None` (every other method, and every prior call site) is byte-for-byte the original fixed-`_MARKER_SIZE` behavior; when given, each marker's area scales with its own value, floored at `_POINT_SIZE_FLOOR` so a 0-probability noise point stays visible instead of collapsing to nothing. `sns.scatterplot`'s own legend-building breaks on an array-like `s=` (it reuses the array verbatim as a single legend marker size) - the `point_sizes`-given branch builds the categorical legend by hand via `plt.Line2D` instead of `sns.scatterplot`, matplotlib's own `ax.scatter` has no such issue.

`clustering.py`'s `_write_standalone_diagnostic` dispatches to whichever of the 3 applies via an explicit `if/elif` (not a registry) and raises `ValueError` for any method outside `STANDALONE_DIAGNOSTIC_METHODS` rather than silently no-oping.

### Agglomerative's metric-aware sweep — `n_clusters` x `linkage` x `metric`

Per the `project-clustering-tuning-redesign` design record: unlike every other `CLUSTERING_METHODS` entry, agglomerative is deterministic given `(X, linkage, metric)` (no `random_state`) - sweeping `linkage`/`metric` directly alongside `n_clusters` is methodologically fine, no stability pre-check needed. But the grid is deliberately **not a full cube**: sklearn's own `AgglomerativeClustering` `metric` docstring - *"If linkage is 'ward', only 'euclidean' and 'l2' are accepted"* - makes `linkage="ward"` + a non-euclidean `metric` an invalid combination. `is_invalid_ward_metric_combo(combo_params) -> bool` (`clustering_tuning.py` - public, also reused by `clustering.py::_write_agglomerative_diagnostics` to skip the same invalid pairing when building per-metric dendrograms) flags exactly that; `run_clustering_tuning_sweep`'s main loop skips a flagged combination with a logged warning (never lets sklearn's own `ValueError` crash the sweep, never silently drops it either).

For every surviving combination, `run_clustering_tuning_sweep` routes agglomerative through a dedicated branch instead of the generic `compute_clustering_metrics`/`require_euclidean_compatible` guard (which would blanket-abort the whole sweep the moment `metric` isn't euclidean-safe - too coarse for a method whose whole point here is exploring non-euclidean metrics):
- `_agglomerative_fit_metric_aware(X, params, distance_cache=None) -> (labels, metric)` fits `AgglomerativeClustering` with `metric` honored directly for every native sklearn string it doesn't precompute (`cosine`/`manhattan`/...); any metric in `distances.py::PRECOMPUTABLE_METRICS` (`jaccard`/`dice`/`euclidean`; see `compute_dendrogram_linkage`'s entry above for the measured numbers) is precomputed first via `distances.py::precomputed_distance` and fit with `metric="precomputed"` (lesson #29 - reuses the same precompute machinery already built for umap/t-SNE, no new plumbing) - **except** when `linkage="ward"`, which always fits directly on raw `X` regardless of `metric` (sklearn never accepts `metric="precomputed"` for `ward`).

  **Per-metric distance cache**: `distance_cache` (optional, keyed by metric name) - a given metric's precomputed distance matrix depends only on `(X, metric)`, never on the swept `n_clusters`/`linkage`, so recomputing it per combination would be pure waste. Invisible on a 2-3 column embedding (milliseconds either way); on a raw high-dimensional matrix (e.g. `25-08_s1.2-vol`'s raw 264274-voxel matrix) recomputation would be the sweep's actual bottleneck. It covers every `PRECOMPUTABLE_METRICS` value, `euclidean` included (see `_agglomerative_fit_metric_aware`'s own entry above for why). `run_clustering_tuning_sweep` builds one `agglomerative_distance_cache: dict[str, np.ndarray]` per sweep call (method-gated, `None` for every other method) and threads it through, so each metric's matrix is computed once and reused across every `linkage`/`n_clusters` combination sharing it. `ward` linkage never reaches this cache regardless of `metric` (sklearn only accepts `metric="euclidean"`/`"l2"` for `ward`, never `"precomputed"`), so any `ward` combination is unaffected, still fit directly on raw `X` per combination, with no way to cache it via this mechanism.
- `compute_clustering_metrics_metric_aware(X, labels, metric) -> dict[str, float]` always keeps silhouette (`sklearn.metrics.silhouette_score` accepts any metric string or `"precomputed"` - lesson #15, thread the same metric used for clustering into scoring), but Calinski-Harabasz/Davies-Bouldin are mathematically euclidean-only (centroid-based, no `metric` parameter exists for them at all) - `NaN` for any other metric, not aborted. Same degenerate-combination NaN-and-warn convention as `compute_clustering_metrics`; `noise_fraction` is always `0.0` (agglomerative never produces the HDBSCAN-style `-1` label).

**Interclass distance matrix diagnostic** (new, modeled on sklearn's `plot_agglomerative_clustering_metrics.html` "interclass distance matrix" panel): independent of any clustering fit - a metric-selection pre-check, and the substitute diagnostic for combinations where Calinski-Harabasz/Davies-Bouldin were skipped above. `compute_interclass_distance_matrix(X, proxy_labels, metric) -> (groups, matrix)` computes the average pairwise distance within (diagonal) vs. between (off-diagonal) groups of a weak ground-truth `proxy_labels` grouping (`clustering.py::_write_agglomerative_diagnostics` uses each subject's `"dataset"` metadata column as that proxy - vascular territory/lesion side are noted as other candidates in the design record, not yet wired since no such column exists in `metadata` today; skipped with a logged warning, not a sweep failure, when `metadata` has no `"dataset"` column at all). A group with fewer than 2 members has an undefined within-group spread, recorded as `NaN` (not `0.0`, which would misrepresent "no data" as "identical"). `plotting.plot_interclass_distance_matrix(results_by_metric, output_path, title)` (`docs/dev/plotting.md`) lays out one heatmap subplot per metric in `results_by_metric` - computed once per swept `metric` value (or the `base_params`/default `"euclidean"` alone when `metric` isn't swept), written to `interclass_distance_matrix.png` alongside the per-metric dendrogram file(s) above.

`config/registry/params_clustering.json`'s checked-in `"agglomerative".tuning_grid` sweeps all 3 axes (`n_clusters` x `linkage` x `metric`) - with 3 swept keys, `_write_tuning_output`'s generic 1-or-2-param `tuning_plot.png` is skipped (logged warning, existing behavior, unchanged code path) in favor of the two diagnostics above, which are the actually-informative outputs for this method's redesign. The checked-in grid is `n_clusters` 2..30 × `linkage` ∈ {`ward`, `average`, `complete`, `single`} × `metric` ∈ {`euclidean`, `cosine`, `manhattan`}, with `ward` skipped for a non-euclidean `metric` (above). The registry is mutable state that holds the last launched configuration, not canonical defaults: compare it with the `params` column of `runs_tuning.csv` before relaunching an older tuning (`lessons_learned.md` #36). On a raw feature matrix (264274 voxel columns) `ward` stays expensive whatever the cache does: `sklearn`'s `ward_tree`, used whenever `metric` isn't `"precomputed"`, works in the original feature space rather than off a distance matrix, so precomputation does not help it (a single `euclidean`+`ward` combination on `25-08_s1.2-vol` ran over 20 minutes without finishing). A sweep of `ward` on a raw matrix has to budget for that cost explicitly.

`consensus_suggestion_lines(results, method) -> list[str]` reads `rsc_eigengap`/`monti_stability` columns (if present in `results`) and returns the "RSC suggests .../Monti suggests ..." lines described below - empty list when neither column is present. Pure text formatting, called from `clustering.py`'s `_write_tuning_output`. Written to its own `consensus_suggestions.md` (only when the list is non-empty), a sibling of `tuning_results.csv`/`config.md` in the tuning output dir - deliberately **not** appended into `config.md` itself: that file is a static snapshot of how the run was launched (config JSON, swept params, combinations evaluated), and a computed suggestion doesn't belong mixed into a historical launch record.

### Stability analysis (kmeans/gmm) — init/n_init validation before trusting the sweep

Per the `project-clustering-tuning-redesign` design record: `k`/`n_components` is the real target hyperparameter for kmeans/gmm, but both methods converge to a local optimum of their own objective (inertia for k-means, log-likelihood for GMM's EM) depending on random init - a plain sweep over `k`/`n_components` alone never validates that its own `init`/`n_init` choice is actually stable. `k` and `init` are deliberately **not** swept as a joint 2D grid (a heatmap was explicitly rejected) - instead, `init`/`n_init` is validated once, separately, at a handful of representative target values, *before* trusting the plain sweep's per-target scores.

`STABILITY_ELIGIBLE_METHODS = {"kmeans", "gmm"}` (`clustering_tuning.py`) - the only 2 `CLUSTERING_METHODS` with this genuine random-init instability; agglomerative/hdbscan are deterministic given the data, spectral's own k-means-inherited instability is instead removed at the source (`assign_labels="cluster_qr"`, see the spectral section below), so none of the 3 need this diagnostic. `STABILITY_TARGET_PARAM`/`STABILITY_NUISANCE_PARAM`/`STABILITY_METRIC_NAME` map each eligible method to its own hyperparameter names/scored metric (kmeans: `n_clusters`/`init`/`inertia`; gmm: `n_components`/`init_params`/`bic`) - one generic sweep function serves both, only these 3 lookups differ per method.

`representative_values(values: list[int]) -> list[int]`: min/median/max of a swept list, deduplicated and sorted (e.g. `[2,3,4,5,6,8,10] -> [2,6,10]`) - instability generally grows with the target value, so validating at a single point of `tuning_grid` doesn't generalize across its whole range. Raises `ValueError` on an empty list.

`compute_stability_sweep(method, X, target_values, nuisance_values, n_init_range, n_repeats) -> pd.DataFrame`: for each `(target, nuisance, n_init)` combination, repeats a fit `n_repeats` times varying only `random_state`, recording the method's own metric - long-form, one row per `(target, nuisance, n_init, repeat)`, aggregated (mean ± std per `n_init`) only at plot time. `target_values` is typically `representative_values(tuning_grid[STABILITY_TARGET_PARAM[method]])`, not the full swept range - the caller (`clustering.py::_write_stability_output`) decides that; this function only runs the grid it's given. Raises `ValueError` for a method outside `STABILITY_ELIGIBLE_METHODS`.

`plotting.plot_stability_analysis(df, target_param, nuisance_param, metric_col, output_path, title)` (`docs/dev/plotting.md`): one panel per unique `target_param` value, errorbar mean ± std(`metric_col`) vs `n_init`, one line per `nuisance_param` value - modeled on sklearn's `plot_kmeans_stability_low_dim_dense.html`, faceted across the representative target values instead of a single one.

Config: `params.py::load_stability_config(params_file, method) -> dict | None` loads the optional `"stability"` block (`{"nuisance_values": [...], "n_init_range": [...], "n_repeats": int}` - `docs/dev/config.md`) - absent means "not requested" (`None`), present for a method outside `STABILITY_ELIGIBLE_METHODS` or malformed raises `ValueError`. The representative target values are deliberately **not** part of this block - they're always derived from the method's own `tuning_grid`, never declared separately (a second source of truth for the same values would drift). Wired into `clustering.py::_run_one_method_tuning`: when a `"stability"` block is present, `_write_stability_output` runs after the plain sweep completes, writing `stability_results.csv`/`stability_plot.png` into the same tuning output directory - a failure here (bad `tuning_grid`/sklearn `ValueError`) fails the whole method's tuning run, same fail-fast philosophy as every other tuning step.

### Spectral — `assign_labels="cluster_qr"` + `affinity`×(`n_neighbors`/`gamma`) sweep

Per the `project-clustering-tuning-redesign` design record: `compute_eigengap` (above) was judged "already covered" at design time - same shape as kmeans's inertia elbow/GMM's AIC-BIC. Its *plotting*, `plotting.plot_eigengaps_grid` (above), groups by `affinity` with a subplot per hyperparameter value, the same as the dendrogram.

**Hidden instability found and removed at the source**: `SpectralClustering`'s `assign_labels` parameter (the final label-assignment step on the Laplacian eigenvectors) defaults to `"kmeans"` in sklearn - our config never overrode it, so `spectral` silently inherited k-means's own seed-sensitivity (sklearn's own `random_state` docstring: *"used for [...] the K-Means initialization"* when `assign_labels='kmeans'`). Resolved **without** a stability analysis on the label step (unlike kmeans/gmm, which needed one because `init`/`n_init` are their only options): sklearn's own `assign_labels` docstring recommends an alternative - *"The cluster_qr method directly extract[s] clusters from eigenvectors in spectral clustering. In contrast to k-means and discretization, cluster_qr has no tuning parameters and runs no iterations, yet may outperform k-means and discretization in terms of both quality and speed."* `config/registry/params_clustering.json`'s checked-in `"spectral"` entry fixes `"assign_labels": "cluster_qr"` explicitly in `"params"`: the label step has no iterations and no seed. The whole result is deterministic **only when the affinity graph is connected**: `random_state` still sets the starting vector of the ARPACK eigensolver, and when the graph has several connected components the eigenvalue 0 has multiplicity greater than 1, so the eigenvectors it selects are an arbitrary basis of that subspace and the labels change with the seed (a `nearest_neighbors` graph with `n_neighbors=10` on a 2D UMAP embedding can have several components). sklearn warns "graph is not fully connected" in that case; derivation and reading in `knowledge/notes/dim_reduction_clustering/clustering_methods/spectral.md`.

**`affinity`×its own hyperparameter** - same asymmetric-grid shape as agglomerative's `linkage`×`metric`, but the risk here is wasted compute, not an invalid sklearn combination (sklearn silently ignores whichever of `n_neighbors`/`gamma` doesn't apply to the chosen `affinity`, it doesn't raise): `run_spectral_affinity_aware_sweep(X, base_params, tuning_grid, consensus_config=None) -> (pd.DataFrame, dict[tuple, np.ndarray])` (`clustering_tuning.py`) requires `"affinity"` to be a `tuning_grid` key, and runs `run_clustering_tuning_sweep` once per swept `affinity` value (`SPECTRAL_AFFINITY_HYPERPARAM = {"nearest_neighbors": "n_neighbors", "rbf": "gamma"}` picks each sub-sweep's own extra hyperparameter), concatenating the results with an explicit `"affinity"` column - `"n_neighbors"`/`"gamma"` end up `NaN` on the rows of the affinity they don't apply to (an artifact of `pd.concat`, not a degenerate combination). `clustering.py::_run_one_method_tuning` dispatches to it only when `"affinity"` is actually a swept key; the plain `n_clusters`-only sweep (no `"affinity"` swept, e.g. any pre-existing config) is entirely unaffected, still goes through `run_clustering_tuning_sweep` directly.

`plotting.plot_spectral_tuning(df, param_col, metric_cols, output_path, title)` renders the result: one subplot per metric, one line per `(affinity, hyperparameter)` combination (label built from whichever of `n_neighbors`/`gamma` is actually set for that row) - `clustering.py::_write_tuning_output` calls it instead of the generic 1-or-2-swept-param dispatch specifically when `method == "spectral" and "affinity" in tuning_grid`, writing to the same `tuning_plot.png` filename every other method uses (`param_col` is whichever other `tuning_grid` key isn't `affinity`/`n_neighbors`/`gamma` - typically `n_clusters`; a shape with more than 1 such key logs a warning and skips the plot, same fallback spirit as the generic dispatch's `>2`-param case).

**Known limitation, by design, not a gap**: `config.save_tuning_clusterings` is rejected upfront (clear `ValueError`-shaped `logging.error` + `return False`, not a silent misalignment) when combined with a swept `"affinity"` - `run_spectral_affinity_aware_sweep`'s `labels_by_combo` keys are `(affinity, *sub_combo)`, where `sub_combo`'s own key order varies per affinity sub-sweep (each restricted to only its own hyperparameter), so it never lines up with the full `tuning_grid.keys()` order `_write_tuning_clusterings`/`_combo_key` assume for every other method's sweep.

**Considered and rejected as out of scope**: `SpectralBiclustering` (clusters rows AND columns of a matrix simultaneously, meant for checkerboard-structured data like genomics/images) is a genuinely different algorithm, not a tuning variant of `SpectralClustering` - would be a 7th `CLUSTERING_METHODS` entry if ever pursued, not part of this redesign.

## `src/analysis/consensus_clustering.py` — consensus/stability clustering (RSC + Monti)

Two literature methods scoring how *stable* a candidate `k` is (as opposed to how *good* it looks on a single run, all silhouette/Calinski-Harabasz/Davies-Bouldin can say) - restricted to `CONSENSUS_ELIGIBLE_METHODS = {"kmeans", "gmm", "spectral"}` (`K_PARAM_NAME` maps each to its own "how many clusters" parameter name: `n_clusters` for kmeans/spectral, `n_components` for gmm), since these are the only 3 with genuine internal stochasticity to exploit without touching the data itself (for `spectral` only on a disconnected affinity graph: on a connected one `cluster_qr` repeats identically across seeds and the co-occurrence matrix is degenerate) - a repeat of `agglomerative`/`hdbscan` with a different seed reproduces the identical partition (deterministic given the same input), so a "co-occurrence matrix" for them would be degenerate (all 0s/1s, no information).

- `run_rsc_repeats(method, X, params, n_repeats, base_seed=0) -> np.ndarray`: RSC (Tshimanga et al. 2025, cited by Zanola et al. 2026 - `knowledge/papers/stroke_core/Zanola et al - 2026 - ...`) - `n_repeats` runs of `CLUSTERING_METHODS[method]` on the full, unmodified `X`, only `random_state` varying (`base_seed + i`). Returns the `(n_samples, n_samples)` co-occurrence matrix (fraction of runs where each pair shared a cluster).
- `run_monti_repeats(method, X, params, n_repeats, subsample_fraction, base_seed=0) -> np.ndarray`: Monti et al. 2003 - `n_repeats` runs, each on an `np.random.default_rng`-drawn subsample (without replacement, size `round(subsample_fraction * n_samples)`) of subjects. Returns the `(n_samples, n_samples)` consensus matrix (co-clustered / co-sampled per pair, conditioned on both having been drawn together) - raises `ValueError` if any pair was never jointly sampled across all `n_repeats` draws (too few repeats/too small a fraction for this `n_samples` - an explicit failure, never a silent `NaN`/`0`).
- `compute_rsc_eigengap(cooccurrence_matrix, k) -> float`: gap between the `(k+1)`-th and `k`-th (1-indexed) sorted eigenvalues of the co-occurrence matrix's normalized Laplacian (`scipy.sparse.csgraph.laplacian(..., normed=True)` + `scipy.linalg.eigh`, same machinery as `clustering_tuning.compute_eigengap` but applied to `C` itself as the affinity, and reading the specific position-`k` gap rather than the biggest gap anywhere - matches the paper's own selection criterion, compared across the different `C_k` built per candidate `k`).
- `compute_monti_stability(consensus_matrix, ambiguous_band=(0.1, 0.9)) -> float`: `1 - PAC` (Proportion of Ambiguous Clustering - fraction of the consensus matrix's upper-triangle entries falling inside `ambiguous_band`). Deliberate deviation from Monti et al. 2003's own area-under-CDF statistic, per Șenbabaoğlu et al. 2014's finding that it's biased toward larger `k` - PAC is the standard fix (e.g. `ConsensusClusterPlus`), not an invention here.

`subsampling_stability_index(method, X, params, subsample_fraction, base_seed=0) -> float` (`project-clustering-tuning-evaluation-tables` memory): a lighter sibling of `run_monti_repeats` above - a single full-vs-one-subsample comparison (Adjusted Rand Index between a fit on all of `X` and the same `method`/`params` refit on one random `subsample_fraction` subsample, without replacement), not an `n_repeats` co-occurrence ensemble. Deliberately **not** restricted to `CONSENSUS_ELIGIBLE_METHODS`: unlike `run_rsc_repeats`/`run_monti_repeats` (meaningless for a deterministic method - repeating it gives an identical result every time), a single full-vs-subsample comparison is meaningful for any `CLUSTERING_METHODS` entry, deterministic or not (e.g. `agglomerative`). Raises `ValueError` for an unregistered `method`, an out-of-range `subsample_fraction`, or a subsample smaller than 2 points. Reuses only `CLUSTERING_METHODS` and the same `rng.choice` draw-without-replacement shape as `run_monti_repeats` - not its co-occurrence-matrix machinery, a different output shape for a different question. Not called by any pipeline, notebook or config: only the tests exercise it.

Wired into `clustering_tuning.run_clustering_tuning_sweep` via an optional `consensus_config` parameter (`None` by default - zero behavior change to any pre-existing call): `{"rsc": {"n_repeats": int}, "monti": {"n_repeats": int, "subsample_fraction": float}}`, either/both keys, adding `"rsc_eigengap"`/`"monti_stability"` columns per swept row (`k` read straight off that row's own already-built `combo_params[K_PARAM_NAME[method]]`, since it's exactly what `tuning_grid` swept to produce it). `CONSENSUS_METRIC_COLUMNS = ("rsc_eigengap", "monti_stability")` in `clustering_tuning.py` is a fixed constant (not merged into the static `METHOD_METRIC_COLUMNS`, since it's opt-in/conditional) - `clustering.py` extends its `metric_cols` with `[c for c in CONSENSUS_METRIC_COLUMNS if c in results.columns]` before plotting, so the subplot grid only ever includes columns that actually got computed. Loaded via `params.py::load_consensus_config(params_file, method) -> dict | None` (`docs/dev/config.md`) (absent `"consensus"` key -> `None`, a legitimate "not requested" case; present for a method outside `CONSENSUS_ELIGIBLE_METHODS`, or malformed, raises `ValueError` - an impossible config must fail loudly, never be silently ignored, per `code_standards.md` §0). Not registered in the checked-in `config/registry/params_clustering.json` by default - fully opt-in, see `docs/guides/clustering.md` for the JSON block to add.

## `src/analysis/dbcv.py` — the internal index of the density methods

`dbcv(X, labels) -> (score, per_cluster)`: DBCV (Moulavi et al. 2014) of a clustering with the `hdbscan` package's `validity_index` (euclidean, per-cluster scores). `run_dbcv(X, labels, combo_params) -> RunDbcv(score, clusters, note)` is the one call for the tuning (`clustering_tuning_analysis.density_metrics` writes it in `density_metrics.csv`), the production run (`pipeline/clustering.py`: `config.md` line, `dbcv_per_cluster.csv`, `dbcv_plot.png` via `plotting.plot_dbcv_per_cluster`) and the Embedding Explorer (`clustering_evaluation.density_summary`, `cluster_quality.build_dbcv_figure`), so they give the same number, and the same answer when it is not defined, for the same labels. A run clustered under a non-Euclidean metric/affinity, or with fewer than 2 clusters, gets `score` NaN, no cluster rows and the reason in `note` (never an error, never a number); a cluster of one subject, non-finite values or a length mismatch raise.

- Fewer than 2 clusters (all noise, or one): `score` is NaN and `per_cluster` empty. The package returns the integer `0` for all noise, indistinguishable from a real score, and `nan` with a warning for one cluster: the call is never made for these inputs.
- A cluster of one subject, non-finite values in `X` or a length mismatch raise `ValueError`.
- Labels are renumbered to 0..k-1 before the call; `per_cluster` is keyed by the original labels.
- Cost: quadratic in the size of the largest cluster (about 1.5 s per combination on 5845 subjects x 12-30 components, up to about 15 s with a very large cluster).

## `src/analysis/clustering_evaluation.py` — single-run evaluation

Backs `notebooks/post-results_analysis/clustering_evaluation.ipynb`. `EVALUATIONS` maps each evaluation to the `CLUSTERING_METHODS` it is defined for, `require_applicable` refuses the others, `model_fit_metrics` reads inertia / BIC-AIC / noise of a run. `geometric_metrics` applies to every method except adp and the density methods; `dbcv` applies to `hdbscan` and `hdbscan_soft` only.

`geometric_summary(X, labels, combo_params) -> GeometricSummary` bundles sections 2 and 2.1 of the notebook: silhouette (mean over subjects and mean of the per-cluster means), the weakest cluster's silhouette and the per-cluster table (`per_cluster_silhouette`, kept in `GeometricSummary.clusters`; the silhouette of every subject, noise left out, in `GeometricSummary.subject_labels`/`subject_values`, which `cluster_quality.build_silhouette_figure` draws as one panel per cluster), Calinski-Harabasz, Davies-Bouldin (`compute_clustering_metrics`), Dunn (`dunn_index`), number of clusters, share of the largest cluster and of the noise. The silhouette is measured in the run's own `metric` (`run_metric`: its `metric` param, euclidean when it has none; `GeometricSummary.metric` says which); Calinski-Harabasz, Davies-Bouldin and Dunn are Euclidean-only, as in the tuning sweep, so for a run clustered under another metric they are NaN (the panel shows a dash). An affinity that is not Euclidean (`require_euclidean_affinity`) or a `metric` `compute_silhouette_samples` does not support is refused; raises `ValueError` for fewer than 2 clusters once noise is left out or an undefined index. The Dash app's "Clustering evaluation" panel (`embedding_app.cluster_quality_content_for`) calls it through `run_geometric_summary`, which also refuses `adp` (`require_applicable`) and a matrix wider than `MAX_QUALITY_COLUMNS`, and caches the result per run for the life of the app. The per-cluster silhouette bars are drawn by `src/analysis/cluster_quality.py::build_silhouette_figure` (bar color = the cluster's color in the scatter, label carries the cluster size). The notebook computes the same numbers inline from the same functions. Section 3 (`model_fit_metrics`: inertia for kmeans, BIC/AIC for gmm, cophenetic correlation and dendrogram jump at the run's own k for agglomerative (refit like kmeans/gmm: the partition must reproduce the stored labels; the tree is `compute_dendrogram_linkage`, the jump is `clustering_tuning_analysis.dendrogram_jump`), noise and number of clusters for hdbscan/hdbscan_soft) is `embedding_app.run_model_fit`, which refuses a method without the statistic (`require_applicable`) and a matrix wider than `MAX_QUALITY_COLUMNS`; `cluster_quality_content_for` renders it as its own block, so a failing geometric part never hides it, and the reverse. Sections 3.1 and 3.2 are `embedding_app.run_membership_confidence` (`membership_confidence`: sklearn's HDBSCAN refitted, accepted only if it reproduces the labels; hdbscan only) and `run_soft_membership` (`soft_membership_summary` + `weakest_soft_members` on the saved `membership.npy`, mmap for the matrix; hdbscan_soft only). `weakest_soft_members(labels, membership, n_lowest)` lists the lowest own-cluster probabilities with the best other cluster, indexed by row position; the heatmap of the mean membership vectors is `cluster_quality.build_mean_membership_figure`. `LOW_PROBABILITY`, `LOW_MEMBERSHIP` (0.5) and `N_WEAKEST_MEMBERS` (10) are examples with no literature reference, as in the notebook. Each block renders its own cause when not computable.

`adp_summary(distances, non_empty, labels, k) -> AdpSummary` is section 2.2: `knn_purity`, `distance_matrix_silhouette` and `saturated_pair_share` on the clustered subjects of an adp run (noise and the all-zero-row subjects, whose dice is undefined and which adp labels -1, are left out; an all-zero-row subject with another label raises). The distance matrix comes from `src/analysis/raw_distances.py::RawDistanceStore`: `request(matrix_path, subject_ids, metric)` returns `RawDistances` or None while a single worker thread (`src/analysis/background_cache.py::BackgroundDiskCache`, shared with `component_maps.py`) computes it (`pairwise_distance`, about 4 min for the lesions, up to 25 for the voxelwise disconnection); the result is written atomically (temporary directory renamed into place) under `<--cache-dir>/raw_distances`, in a directory named after a hash of the matrix content (shape, dtype, 64 sampled rows, subject ids, metric), so a rebuilt matrix gets a new entry (the hash samples 64 rows: a change confined to the other rows is not seen). A failed computation is raised once and retried at the next request. The panel (`embedding_app.adp_quality_content_for`) polls every 5 s through a `dcc.Interval` that is enabled only while the result is pending.

- `per_cluster_silhouette(X, labels, combo_params) -> SilhouetteBreakdown`: the silhouette, in the run's own `metric` (`run_metric`), split by cluster (`n`, `silhouette_mean`, `share_negative`) plus `micro` (mean over subjects, what sklearn returns, dominated by the large clusters), `macro` (mean of the per-cluster means), `minimum` and the silhouette of every subject (`subject_labels`, `subject_values`: noise left out, same order). `combo_params` is required so the silhouette is never measured in another geometry than the run's (lessons_learned #15): `clustering_tuning.require_euclidean_affinity` refuses a non-Euclidean affinity, `compute_silhouette_samples` a `metric` it cannot score.
- `distance_matrix_silhouette(distances, labels) -> SilhouetteBreakdown`: the same per-cluster silhouette as `per_cluster_silhouette` (`micro`, `macro`, `minimum`, per-cluster `n`/`silhouette_mean`/`share_negative`), but on a precomputed distance matrix of the clustered subjects (noise raises): the geometry adp clusters in (dice on the raw matrix). `saturated_pair_share(distances) -> float` is the share of pairs of distinct subjects at distance 1 (within `1e-9`); it says when that silhouette is readable: 84% on the lesion matrix (the silhouette sits near 0 whatever the neighbourhoods look like), 0.0015% on the voxelwise disconnection matrix (it reads like any silhouette). Used for `adp`, next to `knn_purity` (section 2.2).
- `knn_purity(distances, labels, k) -> KnnPurity`: for each subject, the share of its k nearest neighbours (itself excluded) with its own label, from a precomputed distance matrix (the clustered subjects only: noise raises). Only the order of the distances matters, so it is not flattened by a saturated distance: between binary lesion masks with no voxel in common dice is exactly 1, which is true for 84% of the pairs of the lesion matrix and puts the silhouette of an adp run near 0 whatever its neighbourhoods look like. Ties at the k-th distance are resolved by expectation under a uniform choice among the tied candidates (never by position); `tied_share` is the share of subjects that needed it. `chance` is `(n_c - 1) / (n - 1)` per subject. A cluster with k or fewer members cannot reach 1 (`max_possible < 1`): it is listed with `evaluable=False` and left out of the summary. Used for `adp` (section 2.2).

- `soft_membership_summary(labels, membership) -> SoftMembership` (hdbscan_soft only): per cluster `n`, `own_mean`, `top_other` and `top_other_mean` (the other cluster its subjects belong to most on average), plus `mean_vectors` (mean membership vector of each cluster's subjects over all clusters, a -1 row for noise). Reads the matrix a production run saved; the rows do not sum to 1 and are not renormalised. Raises `ValueError` for an all-noise run, labels that are not 0..k-1, or a matrix that is not (n_subjects, k). Registered as `soft_membership`.
- `membership_confidence(method, X, params, labels) -> MembershipConfidence` (hdbscan only): how close the subjects sit to the core of their cluster, from `probabilities_`, a lambda value normalised to [0, 1] inside each cluster (0 for noise). It is not the probability of belonging to this cluster rather than another, and not comparable across clusters. `probabilities_` exists only on the fitted estimator, so the run is refit with its own params through `clustering_tuning.hdbscan_labels_and_probabilities` and accepted only if it reproduces the stored labels exactly (otherwise `ValueError`, as in `model_fit_metrics`). `clusters` has `n` and `probability_mean` per cluster and `n_noise` is the total; there is no threshold, since no literature gives a reference value for a probability. It describes the density of the space that was clustered, not a validity index: on an embedding with `min_dist=0` it measures how packed UMAP made the cluster. Noise is left out of every number; a run where every subject is noise raises.

- `density_summary(X, labels, combo_params) -> DensitySummary` (hdbscan and hdbscan_soft, registered as `dbcv`): the DBCV of the run (`dbcv.run_dbcv`), number of clusters, share of the largest one and of the noise, and a per-cluster table (`n`, `dbcv`). Euclidean only: for a non-Euclidean run or one with fewer than 2 clusters `dbcv` is NaN, the table empty and `note` says why; the shares are still there. There is no noise warning and no threshold on the noise.

## `src/analysis/partition_shape.py` — how many clusters, how much noise

`partition_shape(labels) -> PartitionShape` (`n_subjects`, `n_clusters`, `n_noise`, `noise_fraction`, `largest_cluster_share`, `cluster_sizes`) and `NOISE_LABEL`: label -1 is noise, never a cluster, and both shares are over all the subjects, noise included. `largest_cluster_share` is NaN with no cluster; empty or non-1D `labels` raise. The tuning (`clustering_tuning.py`, `clustering_tuning_analysis.py`, `tuning_evaluations.py`), the production run and `clustering_evaluation.py` count through it, so they cannot disagree. `adp` keeps its own count.

## `src/analysis/tuning_match.py` — which tuning reproduces an agglomerative production run

A production run is one fit, a tuning sweeps many combinations, and their dates differ. `find_compatible_tunings(production_dir, tuning_root, base_dir)` returns the agglomerative tuning runs under `tuning_root` (`results/<modality>/clustering/tuning/agglomerative`) that clustered the same matrix, each as a `TuningMatch` (`run_dir`, `reason_rejected`, `compatible`).

- **Same matrix = same `input_path`.** Both config.md record it (the `dim_reduction` production run for a reduced run, the feature matrix for a raw one), and it already carries the reduction method, `n_components`, metric and date of the embedding, so none of those is parsed from a run name. Paths are compared absolute (`base_dir` is the working directory they are relative to). `docs/experiments/pipelines.md` is a drawing of the same relation, not read by the code.
- **Compatible = also reproduces the labels.** A candidate is compatible only if its `clusterings.npz` has the production combination (`n_clusters`, `linkage`, `metric`, from the run's `Params used:`), its `metadata.csv` has the same subjects in the same order, and its labels for that combination are the production partition (`adjusted_rand_score == 1.0`; label names are free). Same `input_path` alone is not enough: a tuning directory reused by a later run keeps the key and changes the labels (lessons learned #18).
- **Errors.** A candidate that cannot be read (no `clusterings.npz`, truncated archive) is returned rejected with the reason, not dropped. A tuning whose config.md cannot be parsed is logged and skipped. A production run that is not agglomerative, or whose params lack `n_clusters`/`linkage`/`metric`, raises `ValueError`: the `metric` is not assumed to be the library default.
- **Today.** Of the 95 agglomerative production runs, 82 have a compatible tuning. 7 have none (raw `s2.3-stream`, never tuned) and 6 raise (lesion `01-09`/`03-09` `k4-k6`, whose params do not record `metric`).

## `src/analysis/dendrogram_splits.py` — an agglomerative tree followed k by k

Pure logic and two figures, no Dash: the Embedding Explorer's "Dendrogram Explorer" section (`embedding_app.py`: `build_run_split_tree`, `dendrogram_steps_content_for`, `dendrogram_step_content_for`) calls it, and `notebooks/post-results_analysis/dendrogram_embedding_explorer.ipynb` carries its own copy of the same tree logic.

- `build_split_tree(X, linkage, metric, saved)` recomputes the linkage matrix of the matrix the run clustered (`compute_dendrogram_linkage`), truncates it to `min(MAX_LEAVES, highest saved k)` leaves and returns a `SplitTree` (linkage matrix, leaves, labels of every k from 1, `saved_ks`: the k the tuning swept, the only ones the app offers). A k the tuning did not sweep (a sweep over 2..6, 8, 10 has holes) gets the cut of the tree into k clusters (`labels_by_k_from`, `scipy.cluster.hierarchy.cut_tree`): the walk down the tree needs every k, and the tree is what the saved labels are verified against. `saved_labels_for(tuning, linkage, metric)` takes those labels from a `ClusteringTuningRun`.
- `check_tree_reproduces_labels` is what makes the recomputation safe: for every saved k the cut of the tree must have adjusted Rand index exactly 1.0 against the saved labels, and for every k no leaf may be cut in two, or it raises. The tuning does not store the tree, so a tuning rewritten later, or a matrix that is not the one clustered, fails here instead of drawing splits that never happened.
- `split_at(Z, k, ...)` is merge `Z[-(k-1)]` undone: the cluster of k-1 and its two children, each with its label in the cut at k. `replay_splits` replays every split from k=2 and returns, per k, the leaf colours and the split (`colors_at` is its last item), because the colour of a cluster depends on the history: the bigger piece of a split keeps the colour of its parent, the smaller takes a new one (`recolor_after_split`). Clusters are named by the leaves they hold (`L5–L6`, `leaf_name`), the only name stable from one k to the next.
- `build_tree_figure` and `build_step_embedding_figure` draw the tree and the embedding as two separate figures (two subplots of one figure shared margins and their axis titles overlapped) with the same colours. The embedding figure has no legend (it grows with k): each cluster's name sits on a white label at its median, bigger and bold for the clusters that divide. Points are `Scatter`, not `Scattergl`: a page of many `Scattergl` figures runs out of browser WebGL contexts and the plots come out blank (lessons learned #45). The embedding figure refuses an embedding that is not 2-component (`ValueError`), never slicing a larger one (lessons learned #16). At most `MAX_LEAVES` (30, the highest n_clusters the tunings sweep) leaves, one palette colour each. `split_at`'s parent carries its `members`, which the app uses to find the parent's label in the cut at k-1.

In the app the section is one screen per k (`dendrogram_step_content_for`, described by a `DendrogramStep`; the k clusters of a cut all together are the "all" option of the Clustering Explorer, not part of this section): the first screen is the smallest k of the tuning with only the map of the cluster that splits next, every later one is the split k-1 → k with the maps of the parent ("Era") and of its two children and, below the drawing, a table (`group_stats` of `cluster_description.py`, rendered by `_stats_table`, the renderer the cross-cluster table uses too; at most 900 px wide, smaller type and wrapping column names via `.dendrogram-step-table`, not zoomed; its margin rule needs the double class `.stats-table-wrap.dendrogram-step-table` because `.stats-table-wrap`'s own margin is declared later). The left column (tree and embedding) is 560 px, 60 px from the maps. Maps come from `_build_cluster_overlap_view` / `_build_cluster_disconnection_view` on a copy of the run's metadata whose `cluster_label` is the tree's cut at k-1 (parent) or k (children), because the run's own column is the cut at its single k; both take a `width_view`, since the overview, the steps and a cluster's own panel draw the same cluster at different sizes. The view cache is keyed by the cluster's name (the leaves it holds) and the width, not by k: a cluster that survives several splits is built once per width. Callbacks of the section also fire with the tuning value left over from the previously chosen run: `_chosen_tuning_dir` ignores any value that is not one of the current run's compatible tunings.

## `src/analysis/cluster_overview.py` — every cluster at once

## `src/analysis/adp.py` — ADP (DADApy) as `CLUSTERING_METHODS["adp"]`

*Advanced Density Peaks* (d'Errico et al. 2021) come metodo di clustering a sé, `adp_cluster(X, params) -> labels`, registrato come gli altri. Scelte di disegno:

- **Gira sulla matrice grezza, con la sua distanza.** DADApy riceve le tabelle dei `maxk` vicini (`distances=(dist, ind)`) calcolate da `distances.py::pairwise_distance`, non coordinate. È l'unico metodo con `dice`/`jaccard` come metrica di clustering vera; gli altri la usano al massimo per una distanza precalcolata (agglomerative) o non la usano.

- **Il numero di cluster non è un parametro.** `params = {"metric", "Z", "maxk"}`, validati da `validate_adp_params`: un'altra chiave, o un valore fuori dominio, solleva. `halo=False` e gli stimatori (2NN per la dimensione intrinseca, PAk per la densità) sono fissi.

- **Una sessione per matrice (`_AdpSession`).** Piano delle righe e distanze (per `metric`) si calcolano una volta; densità e dimensione intrinseca una volta per `(metric, maxk)`, perché non dipendono da `Z`. Un tuning su `Z` ripete solo `compute_clustering_ADP`. Per questo `clustering_tuning.run_clustering_tuning_sweep` delega ad `adp.run_adp_tuning_sweep` invece di chiamare `CLUSTERING_METHODS["adp"]` a ogni combinazione, che ricalcolerebbe le distanze N x N ogni volta (stessa ragione della cache delle distanze di agglomerative, `lessons_learned.md` #29).

- **Righe a zero e duplicati sono gestiti, non nascosti** (`_plan_rows`). `dice`/`jaccard` non esistono per una riga a zero, e DADApy divide per la distanza dal primo vicino, che è 0 tra duplicati esatti. Le righe a zero prendono `NOISE_LABEL = -1` per ogni metrica (stesso insieme di soggetti per tutte, convenzione del rumore di HDBSCAN: escluse dagli indici, contate da `noise_fraction`); i duplicati si clusterizzano una volta e il gemello eredita l'etichetta. Entrambi i casi sono loggati a `WARNING` con gli indici di riga. Due righe *diverse* a distanza numericamente 0 sollevano `ValueError`, non si perturbano.

- **Silhouette con la distanza giusta.** `silhouette_score` sulla matrice precalcolata della metrica usata (lezione #15); `calinski_harabasz`/`davies_bouldin` solo per `euclidean` (centroidi), `NaN` altrimenti, come per agglomerative; calcolati dalla matrice delle distanze euclidee al quadrato (`_euclidean_dispersion_scores`, formule esatte, uguali a quelle di sklearn: un test lo verifica), senza `X`: le versioni di sklearn convertono `X` in `float64`, 10-14 GB a ogni `Z` su queste matrici. `compute_silhouette_samples(X, labels, metric)` (grafico di produzione) accetta `metric` per lo stesso motivo; agglomerative con `metric` non euclidea passa dalla silhouette euclidea del grafico di produzione (`clustering.py::SILHOUETTE_OWN_METRIC_METHODS` contiene solo `adp`).

- **Import lazy di `dadapy`** (`_import_dadapy`): `src/analysis/clustering.py` importa `adp.py` per il registro, e deve caricarsi anche nell'ambiente `nemesis`, che non ha `dadapy` (dipende da `jax`). Il fit senza `dadapy` solleva `ImportError` con il messaggio che indica l'ambiente separato; `clustering.py` lo cattura (produzione e tuning) e ritorna 1 senza traceback.

- **Determinismo.** La "perturbazione" che DADApy applica ai vicini a distanza identica (frequenti con `dice` su dati binari) è un offset fisso di precisione macchina, non un rumore casuale: due run danno le stesse etichette (test).

Colonne di `tuning_results.csv`, plateau e uso: `docs/guides/clustering.md`, sezione "ADP".

## `src/pipeline/dim_reduction.py` / `clustering.py` — the 2 modeling CLIs

Same shape as `build_lesion_matrix.py` (`docs/dev/lesion_matrix.md`: `main(argv) -> int`, staged `try`/`except`, `reports/<script>/<project>/` + `logs/<script>/<project>/`), reading an existing matrix artifact via `artifacts.load_matrix(input_path)` rather than building one.

**Output tree: `production/` vs `tuning/`** (both CLIs): the very first segment under `output_root` is always `production` or `tuning` - never mixed, never both writing into the same subtree - so a tuning sweep and a production artifact can never collide on disk and a directory listing immediately says which kind of run produced it. `tuning/` is a top-level sibling of `production/` (not nested inside each method's own folder), each with its own method-name segment underneath: `<output_root>/production/<method>/<dd-mm>_<session_name>/` and `<output_root>/tuning/<method>/<dd-mm>_<session_name>/`. `runs.csv` lives inside the `production/` branch next to the method folders it logs, `runs_tuning.csv` inside `tuning/` - see `src/utils/run_log.py` below for the exact per-CLI paths.

**`clustering.py` gets one more segment** (`ClusteringConfig.reduction_method`, `docs/dev/config.md`): `<output_root>/production/<method>/<reduction_method>/<dd-mm>_<session_name>/` and `<output_root>/tuning/<method>/<reduction_method>/<dd-mm>_<session_name>/` - `dim_reduction.py` has no equivalent (its own `method` segment already *is* the reduction method, there's no separate "which embedding" axis to key). `runs.csv`/`runs_tuning.csv` are unaffected - `_run_log_dir` still returns `<output_root>/<branch>/<method>/`, one history file per clustering method spanning every `reduction_method` it's ever been run against, not one per `reduction_method`. `src/analysis/embedding_app.py::discover_production_runs` glob depth is pipeline-conditional because of this (3 segments after `production/` for `clustering`, 2 for `dim_reduction`).

### File inventory per run, and how to roll one back

Everything either CLI ever writes to disk, for one single invocation - the reference to answer "delete everything this run produced" or "undo this run" precisely, without missing a file or deleting something shared with other runs.

**Exclusively owned by one run** (safe to `rm -rf` the whole directory, nothing else reads it):

```
logs/dim_reduction/<project>/dim_reduction__<dd-mm-yy>__<HH-MM-SS>.log
logs/clustering/<project>/clustering__<dd-mm-yy>__<HH-MM-SS>.log

results/<project>/dim_reduction/production/<method>/<dd-mm>_<session_name>/
├── matrix.npy, metadata.csv, config.md, manifest.json
└── *.png                                  (embedding + silhouette plots)

results/<project>/dim_reduction/tuning/<method>/<dd-mm>_<session_name>/
└── tuning_results.csv, tuning_plot.png, config.md
    (+ embeddings.npz, metadata.csv iff save_tuning_embeddings=true;
      <param>=<value>/ nested leaves iff nested_params declared)

results/<project>/clustering/production/<method>/<reduction_method>/<dd-mm>_<session_name>/
├── matrix.npy, metadata.csv, config.md, manifest.json
└── *.png                                  (cluster_plot.png, silhouette_plot.png)

results/<project>/clustering/tuning/<method>/<reduction_method>/<dd-mm>_<session_name>/
└── tuning_results.csv, tuning_plot.png, config.md
    (+ stability_results.csv, stability_plot.png iff method in kmeans/gmm;
      + <diagnostic>.png iff method in STANDALONE_DIAGNOSTIC_METHODS;
      + clusterings.npz, metadata.csv iff save_tuning_clusterings=true;
      + the files of the evaluations listed in tuning_evaluations (cophenetic_correlation.csv, density_metrics.csv, k_curves_*.png, ...)
        and report.md iff write_report - the same ones src/pipeline/evaluate_clustering_tuning.py writes later on a stored run;
      hdbscan/hdbscan_soft: tuning_plot*.png only from the tuning_heatmaps evaluation, not from the sweep)
```

Note the `<method>`/`<reduction_method>` segments must be resolved to their actual values (e.g. `umap`, `agglomerative`) - `<method>` alone is never a real path.

**Shared, append-only** - a run adds exactly one row here; deleting the run means removing that one row, never the file itself (other runs' history lives in the same file):

```
results/<project>/dim_reduction/production/<method>/runs.csv
results/<project>/dim_reduction/tuning/<method>/runs_tuning.csv
results/<project>/clustering/production/<method>/<reduction_method>/runs.csv
results/<project>/clustering/tuning/<method>/<reduction_method>/runs_tuning.csv
```

Each row is identified by its `run_id`/`session`+`timestamp` columns (`docs/dev/config.md`) - match on those, not on position.

**No cross-method `comparison/` artifact** - `clustering.py` writes nothing at `results/<project>/clustering/production/comparison/<reduction_method>/<dd-mm>_<session_name>/` (not even when `len(clustering_methods) > 1`). A directory of that shape from earlier runs may still sit on disk (`src/analysis/embedding_app.py::discover_production_runs` excludes it, see below), but nothing writes new ones.

**`clustering.py` runs every method in `clustering_methods` in a loop, not just one**: a private `_run_one_method(config, method, ...)` helper does the full per-method flow (params → cluster → `save_matrix` → `cluster_plot.png` → `runs.csv`) and returns the `cluster_labels` it actually saved (or `None` on failure, which stops the whole run - no partial-failure tolerance, consistent with the rest of this pipeline's fail-fast error handling).

**No `summaries/` report for these 2 modeling CLIs** (`dim_reduction.py`/`clustering.py`) - it would duplicate the same config JSON/summary lines already written to each run's own `config.md` (production: via `save_matrix`'s readme; fine-tuning: `_write_tuning_output`'s `config.md`), just in a second, flat location (`summaries/<pipeline>/<project>/`). `runs.csv` already gives the flat, cross-run chronological view that duplication would half-provide (see `docs/dev/config.md`). Each script keeps a `LOG_FILENAME_PREFIX` (`"dim_reduction"`/`"clustering"`) purely as the log filename prefix (`logs/<pipeline>/<project>/<prefix>__<timestamp>.log`) - unrelated to any report. `build_lesion_matrix.py`/`mask_fc.py`/`build_fc_matrix.py` keep their own `summaries/` reports.

**Where cluster labels live, and what `matrix.npy` means**: `clustering.py` appends `cluster_label` as a new column on the loaded `metadata.csv` - never a separate `cluster_labels.npy` file - so every artifact this pipeline produces stays loadable through the same `load_matrix(input_dir) -> (X, metadata, extra_arrays)` contract, no special case for "this one has labels in a different place." `matrix.npy` always holds *the feature space clustering actually ran on* - whatever `input_path` pointed at (an already-computed embedding or a raw matrix, see `reduced_data` below), re-saved unchanged into the new artifact dir (accepted storage duplication in exchange for one uniform contract).

**`reduced_data` + `viz_embedding_path` - how `clustering.py` decides what it can plot**: `clustering.py` never calls `embed()`/`embedding_for_viz()` itself - `config.reduced_data` (required bool) states whether `input_path` is an already-computed embedding or a raw feature matrix; loading (`load_matrix`) is identical either way, but `reduced_data` is no longer purely declarative (see below). What branches on `X`'s actual shape is `_resolve_viz_embedding(X, metadata, viz_embedding_path, input_path, reduced_data)`, called once in `main()` before the per-method loop: reuses `X` unmodified when it already has 2 or 3 columns; otherwise reads a companion 2D/3D embedding from `config.viz_embedding_path` (optional - a separate artifact, e.g. produced via `dim_reduction.py` with the same `random_state`/`n_neighbors`/`metric` and only `n_components` different), validated to cover the exact same subjects in the exact same order (`ValueError` otherwise); returns `None` (never a slice of `X`, `lessons_learned.md` #16) when neither applies. `None` propagates through the whole run: every scatter plot (`cluster_plot.png`/`silhouette_plot.png`) is skipped with a warning, while the matrix/cluster-label artifact itself is still written normally - a missing viz is a display limitation, not a pipeline failure.

**Companion-embedding cross-check** (the two structural checks above - shape, subject order - don't guarantee `viz_embedding_path` is actually a *twin* of `X`'s own embedding, only that it's plottable and covers the right subjects; a companion built with a different reduction method or different hyperparameters passes both checks while producing a geometrically unrelated layout - real cluster labels plotted onto a misleading picture, with no error to notice it by). When `reduced_data` is `True` (`input_path` is itself a `dim_reduction.py` production run, so it has something comparable to check), `_resolve_viz_embedding` additionally calls `_require_matching_reduction_run(input_path, viz_embedding_path)`, which raises `ValueError` unless: (1) both runs' reduction method matches (`src.utils.artifacts.read_dim_reduction_method`, read from each run's own `config.md` title line - not derived from either path's directory structure, since neither is guaranteed to sit under a `<production>/<method>/` convention the way `embedding_app.py`'s `discover_production_runs` can rely on); (2) every resolved param except `n_components` is identical between the two runs (`src.utils.artifacts.read_run_params`, each run's own `"Params used: {...}"` line - generic dict comparison, symmetric, no per-method special-casing). Skipped entirely when `reduced_data` is `False` - `input_path` is then a raw feature matrix from a different pipeline (e.g. `build_lesion_matrix.py`), whose `config.md` has no reduction method/params to compare against in the first place. `read_run_params` is also the extraction target for `embedding_app.py`'s own `run_params` (thin wrapper, `src/utils/artifacts.py` is the single source of truth for both).

Right after a successful `save_matrix`, `clustering.py` writes `cluster_plot.png` via `plotting.plot_clusters_2d` on the resolved viz embedding (once per method in `clustering_methods`), then `silhouette_plot.png` via `plotting.plot_silhouette_analysis` - fed by the run's `RunSilhouette` (metric, non-noise labels, per-subject values), computed on the *real* `X` (never the viz embedding), so the silhouette diagnostic stays reliable even when the display scatter isn't the same space the clustering actually ran in. `_run_silhouette` scores under `params["metric"]` (default `euclidean`, the model's own) for `agglomerative` and `adp` (`SILHOUETTE_OWN_METRIC_METHODS`) and under euclidean for every other method; on a degenerate result (`ValueError` from `compute_silhouette_samples`: fewer than 2 non-noise clusters) it logs a warning and returns `None`, and the plot, the table and the config line below are all skipped. It runs before `save_matrix`: for `agglomerative` (always, with or without a viz embedding) its mean goes into `config.md`'s `## Summary` (`Average silhouette coefficient: <mean> (<metric>)`) and, right after `save_matrix`, `silhouette_per_cluster.csv` is written from `clustering_evaluation.silhouette_breakdown` (an `OSError` there fails the run, like the other writes of the run folder); for every other method it runs only when there is a viz embedding.

For agglomerative, `clustering.py::_run_agglomerative_geometry` scores the run once with `geometric_summary` (silhouette in the run's `metric`, Calinski-Harabasz, Davies-Bouldin and Dunn only if Euclidean, largest-cluster share) and `model_fit_metrics` (cophenetic correlation and dendrogram jump at the run's k; it refits the tree and must reproduce the labels), the same functions as the Embedding Explorer and the notebook; `_geometry_lines` writes them in `config.md` and the silhouette per subject comes from the same call (`RunGeometry.silhouette`), so it is not computed twice. A result with fewer than 2 clusters logs a warning and writes none of these lines; a refit that does not reproduce the labels logs an error and writes none. The other methods keep `_run_silhouette`.

`clustering.py`'s `_clusters_found_line` helper excludes HDBSCAN/OPTICS-style noise label `-1` from the "Clusters found: N" count and reports it separately ("+ M noise points, label -1") whenever present - counting `-1` as a genuine cluster would silently overstate the result (a real caught case, not a hypothetical: `np.unique(cluster_labels)` alone doesn't know `-1` is special). Generic over any method that happens to produce `-1`, not special-cased on the string `"hdbscan"`.

### `dim_reduction.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

`main()` loads the matrix once, then branches into `_run_production` or `_run_fine_tuning` based on `config.fine_tuning` - two functions, not one function with a large internal `if`, since their output shapes are fundamentally different (a matrix artifact vs. a comparison table) and sharing more than the initial `load_matrix` call would just be forced coupling.

- **Production** (`fine_tuning=false`): `load_method_params` → `reduction.py::embed` (routes jaccard/dice through the precomputed-distance path, see the `embed`/`distances.py` sections above; `pca` goes through `pca_method.fit_pca` instead, via `_embed_production`: the params recorded for the run carry the `n_components` actually kept, and the whole variance spectrum is saved beside the embedding as `eigenvalues.npy`) → `embedding_for_viz` (builds `viz_embedding`, reused as-is if `params["n_components"] == config.viz_n_components`) → `save_matrix` at `<output_root>/<method>/<dd-mm>_<session_name>/` (the real, possibly-higher-dimensional embedding) → `embedding_plots.write_embedding_plots(viz_embedding, ...)` for the plots (`config.color_by`, `docs/dev/plotting.md`).
- **Fine-tuning** (`fine_tuning=true`): `load_method_params` + `load_tuning_grid` + `load_nested_params` (+ `load_trustworthiness_n_neighbors` iff `method in METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS`, i.e. umap/tsne/pacmap; all from `params.py`, `docs/dev/config.md`) → `tuning.run_tuning_sweep` → written to a **separate branch** of the output tree, `<output_root>/tuning/<method>/<dd-mm>_<session_name>/` (`tuning/` is a top-level sibling of `production/` - see "Output tree: `production/` vs `tuning/`" below) - deliberately not `save_matrix`/not the same directory shape as a production run, so a sweep can never be mistaken for, or silently collide with, a real embedding artifact. No `manifest.json` here (unlike every other artifact in this pipeline) - a tuning table isn't meant to be read back via `artifacts.load_matrix`, so there's nothing that needs the completeness marker that function relies on.

  For `pca`, `_run_fine_tuning` passes the sweep a `model_cache` and, once `_write_tuning_output` has written the sweep, `_write_pca_spectra` writes `eigenvalues.npz` (`pca_method.decomposition_spectra(model_cache)`: one array per decomposition the grid fitted, keyed by `solver=...,standardize=...,dual=...`; two decompositions differing only in `chunk_columns`/`max_matrix_gib` would share a key and raise). Unlike `embeddings.npz` this is not opt-in: it is 47 KB and the spectrum is what a `n_components`/`variance_share` choice is read from. It is a separate step after the sweep's own files, so a failure there logs an error and returns 1 without removing them.

  When `config.save_tuning_embeddings` is `True` (opt-in, off by default), `_write_tuning_output` also serializes every combination `run_tuning_sweep` actually computed (the full evaluated grid, not just the ones drawn in `embeddings_grid_*.png`) into one `embeddings.npz` at the top of that tuning run's output dir - written atomically (temporary file renamed into place, `_savez_atomic`), keyed by a self-describing `"k1=v1,k2=v2,..."` string built from `tuning_grid.keys()`'s own order for that run (`tuning_embeddings.combo_key`) - the same names/values each row of that same run's `tuning_results.csv` already carries (`str(bool)` is `"True"`/`"False"`, matching pandas' own CSV serialization), so a caller rebuilds the exact key from any row without a separate index file. Exists so a downstream tool (Fase C's PAIR-style interactive replot, `knowledge/notes/dim_reduction_clustering/dim_reduction_tuning_guide.md`) can read back a saved combination's embedding and just plot it, with no refit.

  Same flag also writes a `metadata.csv` alongside it (one per run, not per leaf - every combination in a sweep shares the same subjects/row order): the `metadata` is written exactly as loaded from `input_path`. It does not need to be self-contained beyond that: `side`/`nihss` resolve from the subject registry (`assets/metadata/participants.csv`) at plot time via `src/analysis/embedding_coloring.py::color_values`, so a saved `embeddings.npz` stays colourable later without reloading `X`.

  Without `nested_params` declared: `{tuning_results.csv, tuning_plot.png (1 param only), config.md}`. With `nested_params` declared (umap/tsne): `_write_nested_tuning_leaves` groups `results` by `nested_params` via `results.groupby(nested_params, sort=False)` - grouping the **actual result rows**, not the Cartesian product of every config-declared value, writing one subfolder per real combination (`<param>=<value>/...`, nested in `nested_params`'s declared order) with its own filtered `tuning_results.csv` always, plus `embeddings_grid_<color>.png` unless every cell this leaf could show turns out to need `n_components != _TUNING_GRID_N_COMPONENTS` (2).

  **No cell is ever refit** - `_build_grid_blocks` (for each free/grid parameter, one cell per value it can take, every *other* free parameter held at `base_params`' own value - raises `ValueError` if that exact combination was never computed) looks up each cell's already-computed embedding from `embeddings_by_combo` and, if its own `n_components` isn't exactly `_TUNING_GRID_N_COMPONENTS`, **drops that cell** (logged, never rendered) instead of calling `embedding_for_viz` to refit it to 2D - a block left with zero surviving cells is omitted from the returned blocks list entirely, and a leaf whose every block ends up empty gets no `embeddings_grid` output written at all. Two ways a cell/leaf can end up dropped: (1) `"n_components"` is itself one of `nested_params` (fixed for the whole leaf) and isn't 2 - checked upfront in `_write_nested_tuning_leaves` itself, before ever calling `_build_grid_blocks`, so the common project case (UMAP's `nested_params: ["metric", "n_components"]`) short-circuits cheaply; (2) `"n_components"` is a *free* parameter (swept within one leaf) with some values other than 2 - each such cell is dropped individually inside `_build_grid_blocks`, while sibling cells at `n_components=2` (in that same block, or in any other block, which stays held at `base_params`' `n_components` throughout) still get plotted. A >2-component cell gets no refit-to-2D diagnostic: with `random_state` fixed, such a refit would be bit-for-bit the same computation as whichever other leaf/cell already swept those same free-parameter values at `n_components=2`, and `src/pipeline/plot_tuning_embedding_3d.py` (`docs/dev/plotting.md`) is the on-demand way to see a >2-component combination's real dimensionality, so a distorted 2D stand-in (PNG or interactive HTML) is not produced (same reasoning `src.pipeline.embedding_app` already applies to production: a live Dash app covers this, no static file needed). The n_components-based skip/drop is automatic and unconditional (`test_dim_reduction_fine_tuning_nested_n_components_skips_embeddings_grid_for_non_viz_leaf`, `test_dim_reduction_fine_tuning_free_n_components_drops_non_viz_cells`) - there is no `write_embeddings_grid` config flag (a coarser manual opt-out disabling the whole grid pass regardless of `n_components`): it would be redundant with it.

Both modes call `append_run_log_entry` (`run_log.py`, `docs/dev/config.md`) after writing their output, tagged `"production"`/`"tuning"` respectively, into `<output_root>/production/<method>/runs.csv` or `<output_root>/tuning/<method>/runs_tuning.csv`.

### `clustering.py`'s two modes: `fine_tuning: false` (production) vs. `true` (manual sweep)

Same `main()` branch-on-`config.fine_tuning` shape as `dim_reduction.py` above, but `clustering.py` already loops over multiple `clustering_methods` in production mode, so its fine-tuning mode loops too (`_run_fine_tuning` iterates `config.clustering_methods`, calling `_run_one_method_tuning` once per method - same fail-fast "stop on first method's failure" behavior as the production loop's `_run_one_method`, no partial-run tolerance either mode).

- **Production** (`fine_tuning=false`, unchanged): as described above (`load_method_params` → `CLUSTERING_METHODS[method]` → `save_matrix`).
- **Fine-tuning** (`fine_tuning=true`), per method: `load_method_params` + `load_tuning_grid` → `clustering_tuning.run_clustering_tuning_sweep` → `<output_root>/tuning/<method>/<reduction_method>/<dd-mm>_<session_name>/{tuning_results.csv, tuning_plot.png, config.md}` (same deliberately-separate-branch shape as `dim_reduction.py`'s tuning output, same reasoning: a sweep table is never mistaken for a production artifact, no `manifest.json`; the extra `<reduction_method>` segment is explained in "Output tree" above). after the sweep's own files `_run_one_method_tuning` runs the evaluations the `tuning_evaluations` block lists for the method (`clustering_tuning_evaluations.run_evaluations` on the in-memory matrix and the saved `clusterings.npz`, so `save_tuning_clusterings: true` is required whenever the block lists an evaluation: the config refuses it otherwise) and, with `write_report`, `clustering_tuning_report.write_report`; the same functions run on a stored tuning through `src/pipeline/evaluate_clustering_tuning.py` (`docs/guides/evaluate_clustering_tuning.md`). `_write_tuning_output` additionally calls `_write_standalone_diagnostic` when `method in STANDALONE_DIAGNOSTIC_METHODS` (agglomerative/spectral), writing that method's own extra diagnostic plot into the same tuning output directory. When a `"stability"` block is registered for the method (kmeans/gmm - see "Stability analysis" above), `_run_one_method_tuning` additionally calls `_write_stability_output` after the plain sweep, writing `stability_results.csv`/`stability_plot.png` into that same directory. `run_clustering_tuning_sweep` returns `(results, labels_by_combo)` (mirrors `tuning.py::run_tuning_sweep`'s `(results, embeddings_by_combo)`) - every combination's cluster-label array is already computed to score its 3 generic metrics, so keeping it in memory is free; when `config.save_tuning_clusterings` is `True` (opt-in, off by default), `_write_tuning_clusterings` persists the full grid into `clusterings.npz` (keyed by `_combo_key`, atomic temp-file-then-rename like `dim_reduction.py`'s `embeddings.npz`) plus a self-contained `metadata.csv` next to it - a later reader can inspect any evaluated combination's labels without rerunning the sweep.

Same shared `<output_root>/production/<method>/runs.csv` / `<output_root>/tuning/<method>/runs_tuning.csv` convention as `dim_reduction.py` - `_run_log_dir(config, method, branch)` (`"production"`/`"tuning"`, same literal each caller also passes as `append_run_log_entry`'s own `run_type`) is reused unchanged between `_run_one_method` (production) and `_run_one_method_tuning` (fine-tuning).

**The intended workflow** (confirmed with the user, kept manual by design - no automatic parameter selection, and no plan to add one for any of the 4 fine-tunable methods; cross-validation for a future regression/classification task on top of clustering is a separate, not-yet-designed concern): run with `fine_tuning: true` → open `tuning_results.csv`/`tuning_plot.png` → pick parameters by eye → write them into `params_reduction.json`'s `"params"` for that method → set `fine_tuning: false`, pick a new `session_name`, optionally fill in `run_notes` explaining the change → re-run for the real embedding.
