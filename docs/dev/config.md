# Modeling config & run bookkeeping — technical reference

Audience: developers/agents working on `src/analysis/params.py`, `model_config.py`, `src/utils/run_log.py`, and `src/utils/logging_setup.py`.

This file covers how the 3 modeling CLIs (`dim_reduction.py`/`clustering.py`/`dim_reduction_clustering.py`, see `docs/dev/models.md`) parse their JSON config and record what they ran. For the actual algorithms these configs parameterize, see `docs/dev/models.md`. For visualization config (`color_by`, `viz_n_components` are parsed here but *consumed* by the plotting layer), see `docs/dev/plotting.md`. For the named design patterns used throughout (boundary validation, immutable value objects, ...), see `docs/dev/design_patterns.md`.

**Note on build order**: `model_config.py` was deliberately built *after* `reduction.py`/`clustering.py` (reversing the handoff's original listing order) - it validates `reduction_method`/`clustering_methods` against `REDUCTION_METHODS`/`CLUSTERING_METHODS` upfront (same "fail fast at the config boundary" principle as `build_config.py`), which requires those registries to exist first.

## `src/analysis/params.py` — per-method hyperparameters

`load_method_params(params_file, method) -> dict` reads `config/registry/params_reduction.json`/`params_clustering.json`'s `{method: {"params": {...}}}` shape and returns the raw `params` dict for one method. Validates the file exists, its top-level shape is a JSON object (`lessons_learned.md` #7), `method` has an entry, and that entry's `"params"` value is itself a JSON object — raises `ValueError` naming what's wrong and, for an unknown method, the list of methods actually registered in the file. Does **not** validate individual hyperparameter keys/values — that's `sklearn`/`umap`'s own job when `reduction.py`/`clustering.py` (`docs/dev/models.md`) unpacks the returned dict into an estimator constructor.

Two more loaders, sharing the same private `_load_method_entry` helper (refactored out of `load_method_params` when these were added): `load_tuning_grid(params_file, method) -> dict[str, list]` reads an optional `"tuning_grid"` key (`{hyperparam: [values to sweep]}`) — raises `ValueError` if the method has none registered (fine-tuning not configured for it, e.g. any clustering method in `params_reduction.json`'s sense - see `docs/dev/models.md`'s `clustering_tuning.py` section for those), or if any swept value list is empty. `load_trustworthiness_n_neighbors(params_file, method) -> int` reads an optional `"trustworthiness_n_neighbors"` key (umap/tsne/pacmap - see `tuning.py`'s `METHODS_REQUIRING_TRUSTWORTHINESS_N_NEIGHBORS`, `docs/dev/models.md`) — the `n_neighbors` passed to `sklearn.manifold.trustworthiness` when scoring a fine-tuning sweep, a *different* setting from the `n_neighbors` hyperparameter being swept in `tuning_grid`, kept as its own named field specifically so the two aren't confused.

`load_nested_params(params_file, method, tuning_grid) -> list[str]` (2026-08 session, `dim_reduction.py` only): reads an optional `"nested_params"` key - an **ordered** subset of `tuning_grid`'s keys, fixed one-at-a-time in nested output subfolders (outermost first), as opposed to the "free"/grid parameters left over (`tuning_grid` minus `nested_params`) that get swept jointly and actually plotted (see `dim_reduction.py`'s `_write_nested_tuning_leaves`/`_build_grid_blocks`, `docs/dev/models.md`). Absent → `[]` (no nesting, every `tuning_grid` key is free - the pre-2026-08 behavior, still exactly what `pca`/`pacmap` use today, 1-2 total swept params). Raises `ValueError` if any declared name isn't actually a `tuning_grid` key (typo), or if the free parameters left over aren't exactly 1 or 2 (0 = nothing to visualize in a leaf, >2 = not representable by the 2-block embeddings-grid layout).

`load_consensus_config(params_file, method) -> dict | None` — absent `"consensus"` key → `None` (a legitimate "not requested" case); present for a method outside `CONSENSUS_ELIGIBLE_METHODS`, or malformed, raises `ValueError` (`docs/dev/models.md`'s `consensus_clustering.py` section for what it feeds).

## `src/analysis/model_config.py` — modeling config parsing

3 loaders, one per modeling pipeline script: `load_dim_reduction_config`, `load_clustering_config`, `load_dim_reduction_clustering_config` → `DimReductionConfig`/`ClusteringConfig`/`DimReductionClusteringConfig` (all `frozen=True`). 5 fields are identical across all three (`project`, `input_path`, `output_root`, `session_name`, `overwrite`) and are parsed once by a shared `_load_shared_fields` helper — the method-specific fields (`reduction_method`/`clustering_methods`, and their `params_file`(s)) are parsed per-loader.

`reduction_method` (single string) is validated against `REDUCTION_METHODS` via `_validate_method`, same fail-fast-at-the-config-boundary principle as `build_config.py`'s `resample_interpolation` check (`docs/dev/lesion_matrix.md`), and the reason this module was built *after* `reduction.py`/`clustering.py` rather than in the handoff's original listing order. `clustering_methods` on `ClusteringConfig`/`DimReductionClusteringConfig` is **always a list** (`tuple[str, ...]` once parsed), never a bare string, even for one method - `_require_str_list` validates it's a non-empty list of non-empty strings with no duplicate entries (`lessons_learned.md` #5 - an undetected duplicate would silently re-run the same method twice in the loop below), then `_require_method_list` validates each element against `CLUSTERING_METHODS` the same way `_validate_method` does for a single value. `reduction_method` deliberately stayed single-valued when this was added - a run reduces the input once, then clusters that one embedding with however many clustering methods are requested.

**`run_notes: str | None`** (optional, `_optional_str`) is on all 3 configs here (and on `BuildMatrixConfig` in `build_config.py`, `docs/dev/lesion_matrix.md`) — a free-text note the human writes explaining *why* a run's config differs methodologically from a previous one, propagated into that method's `runs.csv` entry (see `run_log.py` below). **`fine_tuning: bool`** (required, `_require_bool`) is on all 3 configs - but on `DimReductionClusteringConfig` it only ever governs the *clustering* half: the reduction step there always runs once at its already-chosen production params (`reduction_params_file`'s `"params"`, never `"tuning_grid"`) - re-sweeping the reduction itself is `dim_reduction.py`'s job alone. See `docs/dev/models.md`'s `dim_reduction_clustering.py` section for what its `fine_tuning=true` actually does.

**`regress_out_volume: bool`** (required, `_require_bool`) is on `DimReductionConfig`/`DimReductionClusteringConfig` only (not `ClusteringConfig` - clustering never computes an embedding itself, nothing to regress there) - production-mode-only, ignored when `fine_tuning=true` (a tuning sweep is diagnostic, never saved as a production artifact). See `src/analysis/covariates.py` (`docs/dev/models.md`) for what it does and why it can't be a silent default.

**`color_by: tuple[str, ...]`** (required, `_require_str_list_allow_empty` - unlike `_require_str_list`, an *empty* list is valid here, only the field's absence is an error) and **`viz_n_components: int`** (required, `_require_viz_n_components`, must be `2` or `3`) are on both `DimReductionConfig` and `DimReductionClusteringConfig` (2026-08 session) - not validated against `embedding_coloring.COLOR_MODES` here (an unknown name in `color_by` is only caught at plot time, by `resolve_color_mode`, `docs/dev/plotting.md`), keeping this module free of a dependency on that registry. `dim_reduction_clustering.py`'s own `main()` additionally rejects `viz_n_components=3` at runtime (not here, since the constraint is that pipeline's own - every one of its cluster-coloring plot functions is 2D-only, `model_config.py` doesn't know that).

**`write_embeddings_grid: bool`** (required, `_require_bool`, `DimReductionConfig` only - not on `DimReductionClusteringConfig`, which has no `nested_params`/embeddings-grid mechanism of its own): a manual opt-out for `_write_nested_tuning_leaves`' `embeddings_grid_*.png` output (2026-08 session, `docs/dev/models.md`) - `tuning_results.csv` is written per leaf regardless of this flag.

**`save_tuning_embeddings: bool`** (required, `_require_bool`, `DimReductionConfig` only - a later 2026-08 addition, separate flag from `write_embeddings_grid` on purpose: one controls a *plot*, this one controls whether the sweep's actual embedding arrays are persisted at all): when `True`, `_write_tuning_output` serializes every combination `run_tuning_sweep` computed (the full evaluated grid, not just the ones shown in `embeddings_grid_*.png`) into a single `embeddings.npz` at the top of that run's tuning output dir, plus a self-contained `metadata.csv` alongside it (same `enrich_metadata_with_lesion_info` enrichment `_run_production` always applies) - opt-in and off by default, since no tuning run before this flag existed ever wrote either file (`docs/dev/models.md` for the exact key format and why the enrichment is needed here).

## `src/utils/run_log.py` — per-method `runs.csv`/`runs_tuning.csv`, and hand-written `SESSIONS.md`

Two separate concerns, deliberately not one file:

- **`runs.csv`/`runs_tuning.csv`** (machine-written, `run_log.py`): "every run that ever wrote into this method folder, and how did it differ." `append_run_log_entry(log_dir, run_id, now, run_type, params_summary, output_dir, run_notes, extra_columns=None)` appends one row (`session, id, timestamp, params, output, notes`, plus any `extra_columns` prepended as leading columns) - **never overwritten**, unlike a run's own `config.md`/report which describe only that one run. `params`/`notes` are free text (JSON-dumped params, the human's `run_notes`); a real CSV rather than markdown so it's queryable with pandas once a project accumulates many runs. `run_type` (`"production"`/`"tuning"`) picks **which file** the row goes to - `runs.csv` for production, `runs_tuning.csv` for tuning - not a column distinguishing rows within one shared file (a run's own `session`/`id` split comes from splitting `run_id` on its first `_`). Not atomic (a log, not a primary artifact - same tier as `summaries/`/`logs/`, see `docs/dev/design_patterns.md`). `run_log.py` has no notion of session *meaning* - it never reads or writes session descriptions, only appends rows keyed by `run_id`. `extra_columns` exists solely for `dim_reduction_clustering.py` (every other caller passes none, keeping their files' schema exactly `FIELDNAMES`) - every call writing to the same file must pass the same `extra_columns` keys, since the header is fixed on the first write.

  Called once per clustering method actually run (`clustering.py`/`dim_reduction_clustering.py`, `docs/dev/models.md`, call it once per iteration of their `clustering_methods` loop, not once per whole CLI invocation) after writing that method's report - `runs_csv_path` sits one directory above the dated `session_name` subfolders, **and** since the 2026-08 production/tuning results-layout split (`docs/dev/models.md`) it's also a *different `log_dir` per call site*, not just a different filename: `<output_root>/production/<method>/runs.csv` (production call) vs. `<output_root>/tuning/<method>/runs_tuning.csv` (tuning call) for `dim_reduction.py`/`clustering.py`, or directly `<output_root>/runs.csv` for `build_lesion_matrix.py`/`compute_sdc.py` (no method axis, no production/tuning branch there either). `dim_reduction_clustering.py` is the one exception: it has *two* axes (reduction, clustering) but only nests output folders two levels deep (`<output_root>/{production,tuning}/<reduction_method>/<clustering_method>/<session>/`) and shares one `<output_root>/production/<reduction_method>/runs.csv` (or `.../tuning/<reduction_method>/runs_tuning.csv`) across every clustering method run against that reduction, distinguishing rows via the `reduction_method`/`clustering_method` `extra_columns` rather than splitting into one file per `(reduction, clustering)` combination - a single reduction's methods are naturally compared together, so one shared, queryable history serves that better than N near-duplicate files.

- **`SESSIONS.md`** (hand-written, never touched by code): what a `session_name`'s session number (e.g. `s1.1`) actually *means* - datasets, modality, what changed - one entry per session, written by a human, not generated. Canonical copy lives at `data/SESSIONS.md` (a session spans the whole data→results chain, not just matrix building, so it isn't nested under any one pipeline's output folder); `results/SESSIONS.md` is a symlink to it, so it's visible from either side without duplication. `data/SESSIONS.md` is the one path under `data/` explicitly un-ignored in `.gitignore` (`!data/SESSIONS.md`) - everything else under `data/` stays local-only (raw/derived neuroimaging data), but this file is small, hand-curated project knowledge and is meant to be versioned/shared like any other doc.

## `src/utils/logging_setup.py` — shared log-file-handler helper

`attach_file_handler(log_path)` - the same "console + file, remove any stale FileHandler from a previous `main()` call in-process" logic every pipeline script needs. Extracted once `build_lesion_matrix.py` (`docs/dev/lesion_matrix.md`) plus the 3 modeling scripts (`docs/dev/models.md`) would otherwise have carried 4 near-identical copies (past the "revisit at the 4th consumer" threshold already applied to `_require_*`). **Deliberately not** used by `retrieve_data.py`, which keeps its own pre-existing copy - that script is stable/in production and wasn't touched.
