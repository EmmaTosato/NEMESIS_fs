# Lessons Learned — NEMESIS

Cumulative, concise index of recurring error patterns and best practices found while debugging or reviewing code in this repo. **One entry per pattern** — if the same pattern resurfaces in a different context in a later session, it is NOT duplicated here, only appended to that entry's "Seen in" list. This file only grows when a genuinely new pattern is found; it stays short by design.

Read this before starting a debugging session or writing new code in `src/`. For the full narrative behind an entry (the concrete bug, the exact fix, the test added), follow its "Seen in" reference into `docs/debugging/`.

## Patterns

### 1. Implicit fallback in `if/else` with no explicit handling of the unknown case
**Rule**: a two-branch `if/else` (or ternary) is only safe if the domain truly has exactly 2 values. If it can have more, use `if/elif/else: raise`, or better, make the invalid value unconstructable at the type level (e.g. validate in a constructor).
**Seen in**: `debug_09_07_26.md` (§1), `debug_11_08_26.md` (§15 - `src/utils/run_log.py`'s `run_type` picked its target file via `"runs.csv" if run_type == "production" else "runs_tuning.csv"`, latent since every call site today only ever passes the two known literals; fixed with an explicit `_FILE_NAME_BY_RUN_TYPE` lookup + `Literal["production", "tuning"]`, raising for anything else)

### 2. Validation anchored to one call site, not guaranteed by the data itself
**Rule**: if a value/object can be constructed from more than one place (tests routinely bypass loaders), validation belongs in the constructor/type when the rule is static, or in exactly one always-run cross-validation step when the rule depends on external/runtime data — never left to a single "well-behaved" caller to remember.
**Seen in**: `debug_09_07_26.md` (§2), `debug_11_08_26.md` (§3, §6 - `scripts/verify_retrieval.py`/`scripts/data_summary.py` both imported `retrieve_data.py`'s subject-selection helper but never its upfront validation; a typo'd `subjects`/`group_filter` silently selected zero subjects and both scripts reported success. Note: `data_summary.py`'s consumer, `matrix.select_all_subjects`, has a genuinely *broader* scope than `retrieve_data._validate_upfront` - reusing that validator directly would have checked the wrong subject set, so a new `matrix.validate_subject_filters` was written scoped to the same broader picture, not a blind reuse)

### 3. Ambiguous multi-match resolved arbitrarily (glob/wildcard/first-hit)
**Rule**: never `next(glob(...), None)`, `results[0]`, or similar without checking whether a second match exists. Register known naming variants explicitly with a declared priority order; if more than one still matches for the same real input, use the first by priority but surface the ambiguity (log + report) — never resolve it invisibly.
**Seen in**: `debug_09_07_26.md` (§3), `debug_11_08_26.md` (§1 - `src/features/subject_discovery.py::discover_files_by_subject` collapsed >1 file matching the same glob for one subject_id into whichever sorted last, via a plain dict comprehension - fixed to raise `ValueError` listing every conflicting subject/path, same schema already correct in `src/sdc/manifest.py` for the identical problem)

### 4. Same bad input, different behavior depending on which code path reaches it
**Rule**: if a validation/normalization step only runs on some branches (e.g. only when an optional filter is active), the same bad input can crash one path and be silently accepted as valid on another. Move the check to the shared source of the data, not to individual consumers. Watch specifically for the *default/most common* branch being the unvalidated one (e.g. "no filter set" is usually the common case, not the edge case) - it's easy to validate every *optional* branch and forget the plain one has no validation trigger at all.
**Seen in**: `debug_09_07_26.md` (§4), `debug_13_07_26.md` (§2 - subject discovery/template validation skipped entirely when `group_filter` was unset, the most common config)

### 5. Undetected duplicates in an input list corrupt aggregate counts/reports
**Rule**: reject duplicate entries in user/config-provided lists explicitly (clear error) rather than silently deduplicating, whenever that list feeds counts or report lines — a repeated entry processed twice produces misleading numbers (e.g. looks like overlap with a previous run that never happened). Also applies when the list feeds a `dict` keyed by its entries (e.g. dataset names) — a duplicate there doesn't corrupt a count, but collapses invisibly into one, silently ignoring what's very likely a copy-paste mistake. Re-check this pattern after fixing it once elsewhere in the same session — easy to reintroduce in a sibling list handled by different code.
**Seen in**: `debug_09_07_26.md` (§5, two instances in the same session), `debug_13_07_26.md` (§4 - duplicate dataset names silently collapsed via dict-keyed construction), `debug_11_08_26.md` (§8, §12 - two more sibling lists found in the same repo-wide review missing the uniqueness check their neighbors already had: `src/sdc/config.py::stage2_presets` (duplicate inflates `check_stage2_outputs`' expected atlas count, misattributing the failure to Stage 2 instead of the config typo) and `src/retrieval/config.py::subjects` (harmless today only because of a downstream dedupe, but inconsistent with `datasets` two fields away) - both fixed with a shared `_optional_unique_str_list` helper)

### 6. Aggregate ("collection has it") vs per-item ("this item has it") availability
**Rule**: an upfront/aggregate availability check that's deliberately permissive (avoids false negatives on otherwise-valid requests) is fine — but only if per-item gaps are tracked and reported separately, and the aggregate check is documented as "possible", not "guaranteed for every item".
**Seen in**: `debug_09_07_26.md` (§6)

### 7. External data shape not validated before its content
**Rule**: validate that parsed external data (JSON/config) has the expected top-level shape (e.g. is actually a dict) before indexing into it — otherwise a malformed file produces a raw `TypeError`/`AttributeError` instead of a clear domain error, and may not even be caught by surrounding error handling written for the domain exception type.
**Seen in**: `debug_09_07_26.md` (§7)

### 8. External JSON leaf values not type-checked before use as a hash key
**Rule**: a field parsed from external JSON and later used as a `dict` key or `set` element (directly, or packed into a tuple that is) must have its *value type* checked at parse time, not just that the key is present — JSON allows a list/object anywhere a string is expected, and using one as a hash key raises `TypeError: unhashable type`, not a domain `ValueError`. That error looks nothing like a config-validation failure and is confusing to debug from the message alone. Distinct from pattern #7 (top-level container shape) — this is about validating each individual leaf value before it reaches code that assumes it's hashable.
**Seen in**: `debug_13_07_26.md` (§3)

### 9. A CLI entry point's later-added phases aren't automatically inside the error boundary
**Rule**: when a CLI `main()` accumulates phases over time (validate → copy → verify → write report → write log), each filesystem-touching phase needs its *own* explicit try/except around the exception types it can legitimately raise (typically `OSError` for mkdir/write failures) — being adjacent to, or downstream of, an already-protected phase does not extend that protection. Re-audit every phase after adding a new one: "if this specific line raises, is it inside a try/except that produces a clean STOP, or does it propagate as a raw traceback?"
**Seen in**: `debug_13_07_26.md` (§1, §5 — two separate instances in the same session: `_copy_one`'s `mkdir()` sitting just outside its neighboring try/except, and `main()`'s log/report setup having no try/except at all), `debug_11_08_26.md` (§2 - `run_clustering_tuning_sweep(...)` sat between two try/except blocks in `_run_one_method_tuning`, itself unprotected, identically duplicated in `clustering.py`/`dim_reduction_clustering.py`; §14 - `src/sdc/runner.py::run_stage1`/`run_stage2` caught only `subprocess.CalledProcessError`, not the `OSError`/`FileNotFoundError` raised when the binary itself isn't on `PATH` - propagated as a raw traceback instead of the pipeline's usual clean `logging.error`+`return 1`)

### 10. Widening a shared function's scope to fix one consumer's visibility gap can silently break another consumer's already-documented scope
**Rule**: a shared helper used by several consumers (a report, a validation, a selection) sometimes gets *broadened* to fix a real problem for one of them ("subject X invisible when only Y is requested") - but if another consumer already declares a narrower contract elsewhere (a docstring, a doc section, a test), the broadening silently contradicts it instead of raising anything. Before widening a shared function's scope, `grep -rn` every call site and read each consumer's own stated scope (docstring/doc/test) - not just confirm the original problem is fixed.
**Seen in**: `debug_16_07_26.md` (§1 - `_known_object_spaces` broadened in a prior session to fix a real invisibility gap, but this made `copy_summary` report subjects outside the exact `(object, space, modality)` combinations in `retrieve`, contradicting that report's own already-documented scope in `_missing_message`'s docstring and `docs/dev/retrieval.md`)

### 11. Bilateral (left/right) atlas indices extrapolated from a partial offset pattern instead of read from the authoritative source
**Rule**: never infer a third-party atlas's right-hemisphere label index by applying an offset observed on a subset of left-hemisphere structures to the rest — a single non-bilateral structure interleaved in the label list (e.g. `Brain-Stem`, one slot, no right counterpart) breaks the offset's uniformity past that point. Always read indices from the atlas's own authoritative LUT/XML, and cross-check against the data itself (cluster size/centroid, since e.g. hippocampus is consistently larger than amygdala) before using an index in code.
**Seen in**: `debug_21_07_26.md` (§1 - proposed `R_Hippocampus`/`R_Amygdala` indices for `HarvardOxford-sub-maxprob-thr25-2mm.nii.gz` off by one, extrapolated from the +11 offset that only holds for Thalamus/Caudate/Putamen/Pallidum; caught before entering `src/` by reading `HarvardOxford-Subcortical.xml` and confirming cluster sizes on the real data)

### 12. A rename/refactor fixed at the most obvious call site, not grepped across every consumer repo-wide
**Rule**: after renaming a variable, a filename constant, or a function's return shape - or splitting one config file into several - `grep -rn` the OLD name/shape across the **entire** repo, not just the module being edited: sibling modules with copy-pasted logic (not just the one you're looking at), the whole test suite (not just the test file for the module touched), `jobs/*.sh` (hardcoded paths, never covered by `pytest`), `scripts/`, `docs/`, and `README.md`. A rename that "works" locally (the one file you tested) can still leave a sibling module writing the old filename, a test asserting the old shape, or a real `sbatch` job pointing at a config file that no longer exists - none of which `pytest tests/` on the touched file alone would catch. Re-run the *full* suite (`code_standards.md` §4) before considering a rename done, not just the tests for the module changed.
**Seen in**: `debug_21_07_26.md` (§2 - `base_params` left undefined after a local variable rename inside `_run_fine_tuning`, a `NameError` not caught because the surrounding `except OSError` didn't match it; §3 - `README.md`→`config.md` rename applied to the primary module and one of two sibling comparison-writers, missed in the other sibling and in 5 test assertions; §4 - `retrieval.json`/`file_patterns.json` split into `_local`/`_server` variants applied to the config files themselves but not to 3 real `sbatch` job scripts, which would have failed immediately in production, nor to README/docs/script docstrings), `debug_28_07_26.md` (§1 - `append_run_log_entry`'s contract changed from "caller passes the exact CSV path" to "caller passes a log directory, function picks the filename" (production `runs.csv` vs. tuning `runs_tuning.csv`); only the 2 call sites in the same refactor session (`dim_reduction.py`/`dim_reduction_clustering.py`) were updated, leaving 5 more call sites (`build_lesion_matrix.py`, `compute_sdc.py`, `mask_fc.py`, `build_fc_matrix.py`, `clustering.py::_runs_csv_path`) passing a path that already ended in `"runs.csv"` - silently created a *directory* named `runs.csv` instead of the log file, plus `tests/unit/test_run_log.py` and 6 assertions across 4 integration test files still asserting the pre-refactor column names (`run_id`/`run_type`) and single-file behavior), `debug_26_08_26.md` (§2 - `run_log.py`'s `input_path` field, added 14-08-26 with a hard-fail header check added 25-08-26 (commit `9fb13fb`), migrated by hand only in the `runs.csv` files touched by that same session's own runs (`lesion_matrix/runs.csv`) - `data/derived/clinical_metadata/runs.csv`, untouched since 17-08-26, sat one schema version behind until the next `enrich_lesion_metadata` run hit the new hard-fail check; recovered the missing `input_path` value for the one preexisting row from that run's own `config.md`, not guessed), `.claude/stato_progetto.md` Sessione 2026-08-03 (`config/pipelines/dim_reduction_clustering.json`'s `clustering_methods` still listed `"dbscan"`, never updated after `CLUSTERING_METHODS` dropped it in favor of `"hdbscan"` during session 2026-07-29 - caught only because it blocked this session's own end-to-end verification, not by any test, since `dim_reduction_clustering.json` itself isn't loaded by the test suite), `debug_11_08_26.md` (§10 - `embedding_coloring.COLOR_MODES` grew a 4th entry (`"nihss"`) but `scripts/replot_dim_reduction.py`, a pre-existing sibling consumer never wired to the registry at all, kept its own hardcoded 3-mode loop - the new mode was silently never replotted, no error/log, and no test existed for the script to catch it; §13 - the exact same minute-granularity report/log timestamp format (`%d-%m-%y__%H-%M`, collision risk for two runs started in the same minute) was found copy-pasted identically across 8 pipeline files, only 1 of which (`compute_sdc.py`) had already been fixed to include seconds - the other 7 were only found by grepping the exact old format string across `src/pipeline/` *after* fixing the first one, not from the original finding itself).

### 16. A multi-dimensional embedding sliced down to its first N columns for plotting, assuming it's ordered by importance like PCA
**Rule**: only PCA-family methods (and anything built as a linear/orthogonal decomposition) guarantee that column 1 matters more than column 2, etc. - a neighbor-graph-based embedding (UMAP, t-SNE, PaCMAP) optimizes all of its output dimensions jointly for one objective; its columns have no importance ordering, so `embedding[:, :2]` on a >2-component fit is an arbitrary cut, not a summary - it can make real cluster structure look artificially merged or split, with no error to notice it by. The only valid way to get a lower-dimensional view is a **separate fit** at the target dimensionality with every other hyperparameter held identical (same `metric`/`n_neighbors`/`random_state` - shares the same neighbor graph, since that depends only on those, not on `n_components`) - never a slice, never a second reduction stacked on top of the first (doubles distortion). A tool that can't refit (e.g. a "replot from saved artifact" script with no access to the original raw matrix) must reject a saved embedding whose dimensionality it can't honestly display, not silently slice it.
**Seen in**: `.claude/stato_progetto.md` Sessione 2026-08-03 - `dim_reduction.py`/`dim_reduction_clustering.py`'s cluster/embedding plots all sliced `embedding[:, :2]` directly; fixed with `src/analysis/reduction.py::embedding_for_viz` (refit when the saved embedding's dimensionality differs from the visualization target, reuse when it already matches). `scripts/replot_dim_reduction.py` hit the same slice but can't refit (no raw feature matrix by design) - fixed by raising `ValueError` instead of producing a silently-wrong plot.

### 13. Third-party imaging library calls that silently drop or corrupt data instead of raising
**Rule**: when delegating a computation to an external library (`nilearn`, `nibabel`, ...) instead of writing it by hand, still verify its output against a ground truth on real data before trusting it - library calls can fail silently in ways that look like a valid result. Two concrete failure modes found together in the same call (`nilearn.maskers.NiftiLabelsMasker`): (1) a too-narrow integer dtype (`uint8`) on a "counting" image summed via `strategy="sum"` overflows silently (wraps modulo 256, no error/warning) - always use a wide dtype (`int32`+) for any voxel count computed via a library's own reduction, never assume it upcasts; (2) a masked region with zero surviving voxels is *removed* from the output (`labels_` shorter than expected) rather than returned as 0 - never combine two related masker outputs by array position, always index both by their own `labels_`/label ids and treat an absent label as an explicit domain value (here, 0 coverage), never let it become a silent shape mismatch or misalignment.
**Seen in**: `debug_23_07_26.md` (§1, §2 - both found while validating `nilearn.maskers.NiftiLabelsMasker`-based parcel coverage on real WashU subjects, before any code entered `src/`)

### 14. A project-wide subject-naming rule (ST vs HC vs ...) re-derived independently by every layer that discovers subjects by globbing, instead of reused from the one place that already implements it
**Rule**: when one module (here `src/retrieval/dataset.py`) already parses/validates a project-wide subject-naming convention (which group a subject belongs to, from its ID), every other module that discovers subjects directly from the filesystem - even if it deliberately doesn't reuse that module's *registry* machinery for good architectural reasons (e.g. a template-per-atlas-combo model doesn't fit a "process one combo at a time" pipeline) - must still reuse the *naming-parsing* function itself, not silently assume the input population is uniform. A dataset mixing groups under the exact same directory tree that a downstream feature-building pipeline globs (e.g. WashU's `features/` holding both stroke patients and healthy controls) will otherwise be processed identically for every group, with no error, no warning - the bug only "doesn't happen" for as long as some incidental data property (e.g. healthy controls happening to lack a lesion mask) accidentally filters them out through an unrelated code path.
**Seen in**: `debug_27_07_26.md` (§1 - `src/features/functional.py`/`src/features/lesion.py` globbed `data/clinical_connectome/derivatives/` directly, independently of `src/retrieval/dataset.py`'s already-correct `group_of()`/`group_filter`, until WashU's healthy-control subjects actually landed under the same `features/` tree as the stroke patients)

### 15. A generic scoring/evaluation function's own default distance metric silently outlives a non-default metric chosen upstream
**Rule**: a generic quality-scoring function that takes its own optional `metric` parameter (e.g. `sklearn.manifold.trustworthiness`, or similarly any function that independently recomputes "how close were these points originally") defaults to its own notion of distance (typically Euclidean) regardless of what metric was actually used to build the thing being scored. If a pipeline lets a non-default metric be swept/configured for the upstream step (e.g. an embedding built with Jaccard/Dice for binary data) but never threads that same metric into the scoring call, every score is silently computed against a mismatched yardstick - not an error, just a quietly unfair comparison that looks like a normal number. Whenever a metric/distance choice becomes configurable anywhere in a pipeline, grep forward for every later step that also takes a `metric` parameter (scoring, cross-validation, nearest-neighbor lookups) and confirm it's fed the same choice, not left at its own default.
**Seen in**: `.claude/stato_progetto.md` Sessione 2026-07-27 (4) - `evaluate_umap` (`src/analysis/tuning.py`, found while extending `params_reduction.json`'s `umap.tuning_grid` to sweep `metric` alongside `n_neighbors`) - `trustworthiness(X, embedding)` was scoring every combination against `X`'s default-Euclidean neighborhoods even when the embedding itself was built with `metric="jaccard"`/`"dice"`; fixed by also passing that same metric (via a precomputed distance matrix, `src/analysis/distances.py::binary_pairwise_distance`) into the `trustworthiness` call itself. No dedicated `docs/debugging/` report - found/fixed during feature work, not a debugging session.

### 17. An early-return/reuse branch in a shared function stays untested by construction as long as every existing caller and every test happens to satisfy the early-return condition
**Rule**: a "cheap reuse if already in the right shape, otherwise do the expensive thing" branch (e.g. `if embedding.shape[1] == viz_n_components: return embedding`) is only as safe as its *expensive* branch - if every caller built so far always keeps the condition true, that branch has never actually executed on real input, for any test or any production run, no matter how long the function has existed. A caller-specific field that was never meant to reach it (a pipeline-level flag, not a valid constructor argument for whatever the branch calls) can sit unstripped in the data passed toward it indefinitely, with zero signal - not even a slow-burning symptom, just silence, because the branch itself was silent. The first real input that finally makes the condition false is the first real test the branch has ever had. When adding a new caller/config that can vary a previously-constant condition, explicitly trace what that specific branch receives and does with it - "the fast-path callers all still work" says nothing about the slow path's correctness.
**Seen in**: `.claude/stato_progetto.md` Sessione 2026-08-04 - `embedding_for_viz`'s refit branch (`src/analysis/reduction.py`, called from `_build_grid_blocks` in `src/pipeline/dim_reduction.py`) received an un-stripped `regress_out_volume` key - a pipeline-level flag, never a `REDUCTION_METHODS` constructor argument - inside the same dict built from `tuning_grid`'s swept keys. Every `nested_params` sweep and every test up to that point kept each leaf's own `n_components` equal to the grid's fixed 2, so `embedding_for_viz` always took the "already right shape, reuse as-is" path and never actually called `umap.UMAP(**params)` with the dirty dict - the first real sweep varying `n_components` (5, 10) crashed immediately with `TypeError: UMAP.__init__() got an unexpected keyword argument 'regress_out_volume'`. Fixed by stripping the flag before the refit and reapplying `regress_out_covariate` to its result afterward (the refit never went through the sweep's own post-fit regression step). Regression test added specifically to exercise the refit branch with that flag present (`test_dim_reduction_fine_tuning_nested_n_components_and_regress_out_volume_refits_viz`).

### 18. A non-atomic output directory reused/extended across separate runs leaves its own top-level `config.md` silently describing a structure that no longer exists on disk
**Rule**: unlike `save_matrix`'s production artifacts (temp-dir-then-rename, see `docs/dev/design_patterns.md` "Atomic write"), `dim_reduction.py`'s tuning output (`_write_tuning_output`) writes directly into `output_dir` via `output_dir.mkdir(parents=True, exist_ok=True)` - if that same `output_dir` (same date-stamped `session_name`) is reused by a second run with a *different* `nested_params`/`tuning_grid` (or manually reorganized, e.g. moving existing leaves under a new nesting level to make room for more), the newest run's `config.md` (written last, so internally correct for *that* run) ends up sitting beside leaf folders it never produced and never describes. `config.md` alone is not proof of what's actually in a tuning output directory - cross-check leaf folder names and each leaf's own `tuning_results.csv` (ground truth of what was actually evaluated) before trusting a top-level `config.md` you didn't just write yourself, especially in a directory known to be touched by more than one run/session.
**Seen in**: `.claude/stato_progetto.md` Sessione 2026-08-04 (2) - `results/lesion/dim_reduction/umap/tuning/03-08_s1.1/config.md` declared 2 `nested_params`/60 combinations (matching its own Aug-3 mtime and the original run), but the directory had grown a third `n_components={2,5,10}` nesting level (180 combinations total, confirmed via each leaf's own `tuning_results.csv` row count) from a separate, later run into the same `output_dir` - config.md manually reconstructed from the verified on-disk structure, not from any preserved original config. **Fixed in `debug_11_08_26.md` (§5)**: `dim_reduction.py::_write_tuning_output` now `shutil.rmtree(output_dir)`s before recreating it whenever `overwrite=True` and the directory already exists - same all-or-nothing semantics as `save_matrix`. Same missing-cleanup pattern found and fixed in the same session in its two siblings, `clustering.py`/`dim_reduction_clustering.py::_write_tuning_output` (there the risk is a stale `tuning_plot.png`, not stale nested leaves, since that writer has no `nested_params` concept).

### 19. An existence check used as a proxy for a correctness check on an idempotent write
**Rule**: `if destination.exists(): return` (skip re-doing the work) is only safe if "exists" and "is already correct" are guaranteed to mean the same thing. For a symlink/pointer meant to always reflect the *current* source of truth (e.g. re-linking a subject to whichever task most recently produced valid output for them), a stale target that still happens to exist on disk makes `.exists()` true without the link being right - the check needs to compare *what it points to*, not just *whether it points to something*. Watch for this specifically in any "aggregate/merge" step re-run more than once over the same output (retries, reprocessing) - the second run is exactly when staleness first has a chance to matter, and the first run's tests never exercise it.
**Seen in**: `debug_11_08_26.md` (§4 - `src/pipeline/compute_sdc.py::_link_subject`, called from `--mode aggregate`: a subject reprocessed in a later, retried task (newer `task_id`) never got re-linked by a subsequent aggregate run, because the old symlink's target - an earlier task's directory - still existed on disk. Fixed by comparing `destination.resolve()` against `source.resolve()`, unlinking and relinking only when they differ.)

### 20. A naming/ID ambiguity resolved by regex backtracking instead of validated against an authoritative, closed registry
**Rule**: generalizes #11 beyond atlas indices - any time a parser splits an identifier into semantic parts using a *greedy or lazy* regex quantifier (`[A-Z]+?`, `.*`, etc.) where more than one split is grammatically valid, the regex always resolves the ambiguity the same mechanical way regardless of whether that's the *correct* way for a given real value - it is not "usually right", it is "always resolves to whichever split the quantifier prefers by construction". If the identifier space is closed (a known, finite list of valid values for the ambiguous part - site codes, dataset names, method names), build the pattern from an alternation over that explicit list instead of a free-form character class, and let an unregistered value raise instead of being guessed.
**Seen in**: `debug_11_08_26.md` (§7 - `src/retrieval/dataset.py::_SUBJECT_RE` used `(?P<site>[A-Z]+?)` (lazy) followed by an optional `(?P<hc>HC)?` group - always preferring to split a trailing "HC" into the healthy-control marker whenever the tail allowed it, regardless of whether "HC" was actually part of the site code. A hypothetical unregistered site ending in "HC" (e.g. "MONTREALHC") would silently misclassify every one of its stroke patients as healthy controls. Fixed with an explicit `KNOWN_SITES` tuple (confirmed against real subject IDs across all 4 in-scope datasets) and a regex built from an alternation over it - an unregistered site now raises `ValueError` instead of being guessed.)

### 21. A per-item aggregation must isolate one item's write/read failure from the rest, symmetrically on both sides
**Rule**: the well-known "write atomically" fix (temp-file-then-rename, see `docs/dev/design_patterns.md` "Atomic write") only prevents *new* corruption - it does nothing for a reader that later iterates many such files and aborts entirely on the first one that fails to parse (e.g. a leftover from before the atomic-write fix existed, or corruption from an unrelated cause). Any function that reads back N independently-written files to build an aggregate view needs its own per-file try/except, returning both the successfully-parsed items and a `{item_id: reason}` map of the ones that failed - mirroring whatever per-item isolation convention the write side (or a sibling processing step) already established, not just fixing the write side and assuming that's sufficient.
**Seen in**: `debug_11_08_26.md` (§9 - `src/sdc/status.py::write_status` wrote status JSON non-atomically (a task killed mid-write left a truncated file); `read_all_statuses` had no try/except at all around `json.load`, so the first corrupt file aborted `--mode aggregate` for every other already-completed subject in the run - unlike `resample_nonconforming_rows`/`check_stage1_outputs` elsewhere in the same pipeline, which already isolate a per-subject failure from the rest. Fixed on both sides: `write_status` now temp-file-then-renames; `read_all_statuses` now returns `(statuses, failed)`.)

### 22. A template placeholder repeated more than once must bind to the same value everywhere it appears, not be treated as independent wildcards
**Rule**: when a path template contains the same named placeholder in more than one segment (e.g. `{subject_id}` in both a directory and the filename), replacing every occurrence with an independent `*` for a glob-based existence/availability check silently accepts a match where the occurrences disagree (a file whose folder claims one subject and whose filename claims another - a realistic mis-copy, not a hypothetical). If the check only needs to know "does *some* file matching this shape exist" rather than "does this *specific* subject's file exist" (that's a separate, already-correct code path via `resolve()`), build a regex with a backreference (first occurrence a named group, every later one `(?P=name)`) instead of a plain wildcard substitution, so only internally-consistent matches count.
**Seen in**: `debug_11_08_26.md` (§11 - `src/retrieval/dataset.py::Dataset.available()`'s `template.replace("{subject_id}", "*")` made `sub-A/anat/sub-B_label-lesion_mask.nii.gz` register as "available" even though no real subject would ever produce that path via `resolve()`. Fixed with a new `_subject_id_pattern()` helper building a backreferenced regex from the template.)

### 23. A concurrency-sensitive filename's timestamp granularity must match how close together two real invocations can plausibly start
**Rule**: a report/log filename timestamped for uniqueness (not just for humans to read) needs granularity fine enough that two genuinely-plausible near-simultaneous invocations of the same script can't collide - "two runs in the same minute" is not a corner case on a shared cluster (a quick manual resubmit after a transient mount blip, a retry script) the way "two runs in the same second" usually is. When you find and fix this in one entry point, grep the *exact* format string across every sibling entry point before considering it done - a timestamp format is exactly the kind of thing that gets copy-pasted verbatim into every new pipeline script as it's created, so one instance found almost guarantees siblings share it (see pattern #12).
**Seen in**: `debug_11_08_26.md` (§13 - `%d-%m-%y__%H-%M` (minute only) used for `copy_summary__*`/`build_summary__*` report and log filenames in `retrieve_data.py` and, found only by grepping the exact string afterward, 7 more pipeline files that had copy-pasted the identical format. Fixed by switching all 8 to `%d-%m-%y__%H-%M-%S` (`compute_sdc.py` already had seconds, the only one of the 9 that did).)

### 24. A recorded `output`/path column in a log is trusted as still valid without checking it against disk
**Rule**: a gitignored results/logs directory can be reorganized, renamed, or pruned over time with no corresponding update to already-written log rows that recorded a path into it (e.g. `runs.csv`'s own `output` column). Any script/index that reads such a log and treats a row's recorded path as ground truth must verify it (`Path(...).is_dir()`) before counting that row as "existing" - otherwise a stale/deleted/renamed entry silently inflates or mischaracterizes what the index reports as real. If the stale path matches a known, specific historical rename shape, a narrow, disk-verified swap (try the known renamed form, use it only if confirmed present) is a legitimate recovery; guessing an arbitrary "close enough" alternative is not.
**Seen in**: `.claude/stato_progetto.md` sessione 2026-08-16/17 - `scripts/build_dim_reduction_strategies_csv.py` initially counted every `runs.csv`/`runs_tuning.csv` row as an existing strategy regardless of whether its `output` directory still existed on disk; fixed with `_output_dir_exists`. A specific, disk-verified subset of the resulting stale rows (a mid-project `<method>/tuning/` → `tuning/<method>/` directory-layout reorg had left old rows pointing at the pre-reorg path) was recovered, not discarded, via a new one-off `scripts/backfill_stale_tuning_output_paths.py` - one targeted, verified segment-swap per row, nothing guessed.

### 25. A sweep row's "base/starting" config field is read to characterize the whole sweep, silently dropping every value actually swept on that same field
**Rule**: when a log row records both a fixed "base" config and a swept grid for the same run, any consumer wanting "what values did this row actually evaluate for field X" must check whether X is itself a key in the swept grid - if so, the grid's own value list is the authoritative answer (every value in it was genuinely run), and reading only the base config's value for X silently reports one arbitrary starting point instead of the true set. Easy to miss because the base value is always present and type-correct, so nothing fails loudly - it just quietly under-represents reality, worse the more of a field's real diversity lives *only* in the swept branch (e.g. every production run for a given method having been deleted/moved away, leaving a tuning sweep as the only surviving evidence at all).
**Seen in**: `.claude/stato_progetto.md` sessione 2026-08-17 - `scripts/build_dim_reduction_strategies_csv.py::_strategy_variants` (formerly `_extract_metric_and_n_components`) read only `base_params.metric`/`base_params.n_components` for a tuning row, dropping 2 of 3 metrics a real t-SNE tuning sweep had genuinely explored (each with its own on-disk `metric=<name>/` results subfolder) - found by the user comparing the generated CSV against `results/lesion/dim_reduction/` directly, not by any test. Fixed by reading from `tuning_grid[key]` whenever present, falling back to the base config's value only when that key wasn't swept at all.

### 26. `sacct`/SLURM job exit code is not a reliable source of truth for "did this task's actual work succeed"
**Rule**: on at least this cluster, `sacct` can report a SLURM array task as `FAILED` (nonzero/unusual exit code, e.g. `120:0`) even when the wrapped script ran to completion, logged its own success message, and produced fully valid output - conversely, a task can crash before writing any log at all (see #27) and still show up as `FAILED` for an unrelated, legitimate reason. Never decide what to resubmit/retry purely from `sacct` state. Always cross-check against the pipeline's own per-item ground truth (here, `_status/<subject_id>.json`, written by the pipeline itself once real work is verified) before resubmitting anything - a "failed" task may already hold valid, reusable output, and re-running it wastes compute at best and risks clobbering good output at worst.
**Seen in**: `.claude/stato_progetto_archive.md` Sessione 2026-08-07 - single-task verification runs against `compute_sdc`'s `334358` array repeatedly picked tasks already marked `ok` in `_status/*.json` despite `sacct` reporting them `FAILED` (task 237 outright already done; task 247-249 done with a full stage trace despite exit code `120:0`); of 328 `sacct`-`FAILED` tasks only 325 were genuine, non-executed failures.

### 27. A job script that derives a chunking parameter from `${SLURM_ARRAY_TASK_COUNT}` breaks the moment `--array` is resubmitted as a subset
**Rule**: when a pipeline's stride-slice chunking (`rows[task_id::task_count]`) requires `task_count` to always equal the *total* number of chunks the input was originally divided into, a job script must never derive that value from `${SLURM_ARRAY_TASK_COUNT}` - that SLURM variable reflects how many elements are in *this specific* `sbatch --array=...` submission, which is correct only the first time (a full `0-N%c` array) and silently wrong the moment a partial resubmission (`sbatch --array=250-574%3 ...`, e.g. to retry a failed subrange) is issued: every task then reprocesses the wrong subset of rows (different chunk boundaries), with no error, just a scrambled/incomplete result silently written under still-plausible-looking task IDs. Hardcode (or otherwise pin) the chunking parameter to the manifest's true total chunk count in the job script itself, independent of the array's submission size. Same root shape as pattern #12 (a rename/contract change not propagated everywhere it's read) but here the "old contract" (`task_count == total chunks`) breaks implicitly via environment-variable semantics rather than a code edit, making it easy to miss in review.
**Seen in**: `.claude/stato_progetto_archive.md` Sessione 2026-08-07 - `jobs/run_compute_sdc.sh` passed `--task-count "${SLURM_ARRAY_TASK_COUNT}"`; resubmitting only the failed range (`--array=250-574`, task-count 325 instead of the true 575) made 75 tasks each grab 3 unrelated subjects instead of the intended 2, none of which were the subjects actually missing for that `task_id` under the correct stride. Recovered without data loss only because subject output is located at aggregate time via each subject's own recorded `task_id` (not by re-deriving it from the chunking scheme), so the wrongly-placed output could be relocated and re-pointed-to instead of lost. Fixed by pinning `TASK_COUNT=575` as a fixed variable in the script instead of reading it from SLURM.

### 28. Tightening a shared, low-level validation to close a silent-acceptance gap has a blast radius invisible from the diff alone - only running the full suite reveals it
**Rule**: when a validation gap is fixed by making a shared, low-level function (here `group_of()`, the ST/HC/PD/GM naming check) run *unconditionally* instead of only on one branch (pattern #4's fix), every caller several layers removed - including test fixtures in modules that never touch the function/file being edited - can be silently relying on the old, permissive behavior via synthetic input that was never valid in the first place (e.g. `sub-01`/`sub-00` test subject IDs that never matched the real ST/HC/... naming convention, only "worked" because the validation they'd now trip was skipped). The true blast radius of tightening a validation is not visible from reading the diff or the module changed - it only shows up by actually running the full test suite (`code_standards.md` §4) after the change, before considering the fix done. When the blast radius is real, fix it at the shared fixture-helper level (the function that generates the synthetic ID), not by patching each failing test's assertion individually - one helper fix often resolves many failing tests at once, and keeps the fixture honestly representative of real data going forward (test data that doesn't obey a validated project-wide invariant was already a latent gap before this specific fix surfaced it).
**Seen in**: AUDIT_FINDINGS.md #26/#46 (session 21-08-26) - `src/features/subject_discovery.py::discover_files_by_subject` and `src/features/lesion.py::_discover_lesion_files` both called `group_of()` only inside `if group_filter is not None:` (pattern #4's exact shape); making it unconditional broke 44 tests across 5 files (`test_clustering_pipeline.py`, `test_dim_reduction_pipeline.py`, `test_build_lesion_matrix_pipeline.py`, `test_mask_fc_pipeline.py`, `test_features_functional.py`) that had never used real site-prefixed subject IDs in their synthetic fixtures - fixed by renaming the *fixture-generating helper* in each file (e.g. `f"sub-{i:02d}"` -> `f"sub-STUNIPD{i:04d}"`), not by touching 44 individual assertions.

### 29. A precompute-and-cache optimization applied to only a subset of a parameter's valid values leaves the rest exposed to the exact same O(n²) cost it was built to avoid
**Rule**: when a "compute once per sweep, reuse across combinations" cache is keyed by a value (here `metric`) that has more than 2-3 valid options, restricting the optimization to only the options it was originally built for (`SUPPORTED_BINARY_METRICS = {"jaccard", "dice"}`, both needing a hand-written distance function) can silently leave a "native"/default-seeming option (`euclidean`) on the slow, uncached path indefinitely - especially when that option's slowness has a *different root cause* than the one that motivated the original cache (here: not the distance computation itself, ~88s for a full 5269x5269 matrix measured directly, but the umap-learn/sklearn library's own per-fit approximate-neighbor-search machinery, repeated on every combination with no cache to short-circuit it). Diagnosing this needs runtime profiling of the actual bottleneck (`sample`/`py-spy` on the live process, not just "N times slower, must be the same O(n²) cost as before") before assuming a fix generalizes correctly - the fix here (widen the metric set the cache applies to) only works because the measured bottleneck turned out to be the same *shape* of waste (a per-combination redundant computation independent of the swept hyperparameters), not a coincidence.
**Seen in**: `debug_25_08_26.md` (§1) - `src/analysis/tuning.py::evaluate_umap`'s `metric="euclidean"` branch recomputed umap-learn's own approximate neighbor graph from scratch per combination (17-35 min each on a 5269x264274 matrix, vs. 88s to precompute the full distance matrix once) - fixed by widening `SUPPORTED_BINARY_METRICS` to a new `PRECOMPUTABLE_METRICS` set in `src/analysis/distances.py` and adding `euclidean_pairwise_distance`. Also applied to `reduction.py::embed()` (production's single fit *and* its optional visualization refit, `embedding_for_viz` - the refit specifically was the same redundant-cost shape as the tuning sweep: same metric/n_neighbors as the main fit, just a different `n_components`, so without the cache it repeated the expensive part for no reason). Initially gated to `reduction_method == "umap"` only (t-SNE deliberately deferred, to keep the first fix verifiable in one shot) - extended to `evaluate_tsne`/`embed()` for tsne too later the same session, on explicit request, *without* first independently measuring whether t-SNE has the same magnitude of redundant-cost problem UMAP did (only UMAP's 88s-vs-17-35min number is directly measured) - the fix itself is safe to widen this way regardless (same precomputed-distance mechanism already validated for jaccard/dice), but don't assume the t-SNE number is the same order of magnitude until it's actually measured on a real tuning run. **Follow-up measured in `debug_26_08_26.md`'s session**: the real t-SNE tuning sweep on s1.2 (14 combinations, dice+euclidean) completed in 7m09s total with no crash/no RAM pressure - confirms the extension was sound, though still not an isolated per-combination measurement like UMAP's 88s-vs-17-35min.

### 30. A newly onboarded external data file assumed to follow an established structural convention, never checked against it until a downstream hard-failure happens to hit it
**Rule**: when every existing file of a given type (here, one `participants.tsv` per dataset in `assets/metadata/`) follows the same undeclared structural convention (a specific column holds the project's canonical subject ID, a *different* named column holds any legacy/site-specific ID) purely by precedent - not by any schema, header check, or onboarding script that verifies it - a newly added file for a newly onboarded dataset can violate that convention with zero signal at the point it's added. The violation is only caught later, indirectly, by whatever downstream consumer happens to have its own strict validation (here, `check_participant_variable_coverage`'s hard-fail on unresolvable subjects, itself a `code_standards.md` §0 discipline win) - and even then, the error message describes the *symptom* ("N subjects unresolvable") not the *cause* (two columns swapped relative to every sibling file). Diagnose by comparing the new file's header against 2-3 known-good siblings of the same type side by side, not by reading the new file in isolation. If this class of file recurs often enough, consider a lightweight structural check at onboarding time (e.g. in the retrieval/build pipeline that first touches a new dataset) rather than relying indefinitely on an unrelated downstream check to catch it.
**Seen in**: `debug_26_08_26.md` (§1 - `assets/metadata/UCL-UK_UCLStrokeData_participants_lesions.tsv`'s `participant_id` held the legacy site ID (`ST_UCL-UK_0001`) and the canonical `sub-STUCLUKxxxx` ID sat in a plain `subject` column instead - inverted relative to every other dataset's tsv (UKLFR/PASPORT/PSP/WashU), where `participant_id` already *is* the canonical ID and the legacy one - if kept at all - lives in a secondary `participant_id_dmp`/`original_id` column. All 4119 UCL-UK subjects showed up as "unresolvable" in `enrich_lesion_metadata`'s coverage report; fixed by renaming the two header cells in place (`participant_id`→`original_id`, `subject`→`participant_id`), confirmed with the user first since it's a data asset, not code.)

### 31. A "standalone" diagnostic plot computed once from a sweep's `base_params`, never re-varied along the very axis it's meant to diagnose
**Rule**: in a fine-tuning sweep that grids several hyperparameters, an auxiliary/standalone diagnostic (a dendrogram, an eigengap plot, or any other derived artifact meant to explain "why" a swept axis' values look the way they do) must be recomputed per value of the axis it structurally depends on. Building it once from `base_params` - i.e. whichever value that axis happens to hold in the base/default config - silently freezes the diagnostic at one arbitrary value while the grid varies that same axis across many others: the plot is correct for exactly one combination and silently misleading for the rest, with no error, no crash, nothing that looks wrong. Any standalone diagnostic added alongside a tuning sweep needs to be grouped/faceted by every axis it depends on, not just built once from the sweep's base config - and should fall back to a single-subplot file only when that axis genuinely isn't swept.
**Seen in**: commit `b71ff7c` (28-08-26) - `clustering.py`'s `STANDALONE_DIAGNOSTIC_METHODS` (agglomerative's dendrogram, spectral's eigengap) were both built once from `base_params` alone: the dendrogram was always drawn at `base_params`'s metric (euclidean by default) even when `metric` was the swept axis (cosine/manhattan/dice) - already flagged as a known limitation in `clustering_tuning_guide.md` before being fixed here; the eigengap plot was found to have the identical bug (same for `affinity`'s own hyperparameter) immediately after, while auditing the other standalone diagnostic for the same shape of issue. Fixed via `plot_dendrogram`→`plot_dendrograms_grid` (one file per metric, one subplot per valid linkage) and `plot_eigengap`→`plot_eigengaps_grid` (one file per affinity, one subplot per hyperparameter value). No dedicated `docs/debugging/` report - found/fixed during feature work, not a debugging session.

### 32. A shared helper's own error contract widens over time (a new exception type added to what it can raise), but an existing caller's `except` clause was written for the old, narrower contract
**Rule**: distinct from #9 (a phase with *no* error boundary at all) - here the boundary exists, but was written against the callee's error contract *at the time the caller was written*, and never revisited when the callee later grew a new failure mode (e.g. a validation added to a shared function, raising a new exception type on top of what it already raised). The caller's `except` clause silently stops catching that new case, so it propagates as a raw, unhandled traceback instead of the caller's own clean logged-error-and-return-1. When a shared function (especially one with many call sites, like `run_log.py::append_run_log_entry`) gains a new `raise` on a new exception type, grep every call site's `except` clause - not just the ones being actively touched - and widen each to match the callee's current, full contract.
**Seen in**: `31-08-26` session (runs.csv `id`-column audit) - `mask_fc.py`/`build_fc_matrix.py` both wrapped `append_run_log_entry` in `except OSError` only, written before that function's header-consistency guard (which raises `ValueError` on a schema mismatch) existed; the guard was added later without revisiting these 2 call sites (only `dim_reduction.py`/`clustering.py` were updated at the time). Their own `runs.csv`/`.../fc_matrix/runs.csv` had drifted to a schema predating any current `FIELDNAMES` shape entirely (`atlas_combo,run_id,timestamp,run_type,...` vs. today's `session,...`) - the next real run of either pipeline would have crashed with a raw traceback instead of a clean `return 1`. Fixed by widening both to `except (OSError, ValueError)`.

### 34. A join function that assumes "input columns" and "requested columns" are always disjoint breaks silently the first time a real refresh makes them coincide
**Rule**: a function like `_join_variables(metadata, variables)` that adds columns to an already-existing DataFrame, building the final selection as `list(metadata.columns) + requested_variables`, is only safe as long as no name appears in both lists - true by construction for as long as every historical caller requests a variable subset complementary to what's already present (never the same name twice), false for a genuine "re-enrich with the same variables" (a refresh after fixing an upstream source). A repeated name in the selection list produces duplicate columns in the output, silently (`rc==0`, no warning) - every name about to be re-added must be excluded from `metadata.columns` first (`preserved = [c for c in metadata.columns if c not in ordered_variable_columns]`). An even sneakier variant: when a single variable has a different input name than its output name (here `NIHSS`->`nihss`, a case-only rename), the rename itself can collide with an already-present column under the output name even though the intermediate DataFrame never literally had two columns with the same name at any point - the column being refreshed must be dropped from the join's own starting point *before* the join/rename, not just excluded from the final selection.
**Seen in**: `debug_02_09_26.md` (§1) - `src/pipeline/enrich_lesion_metadata.py::_join_variables`, never exercised on an overlapping variable set by any historical run in this repo (each one always requested variables complementary to what was already present) until the first genuine refresh (`lesion_matrix/21-07_s1.1`, re-requesting the same 6 variables after fixing the `assets/metadata` drift, same debug session, upstream cause). The real file had already been written once with the bug (17 columns instead of 9) - recovered by restarting from the 3 columns known to be intact (verified by recomputing `lesion_volume_voxels` from `matrix.npy`), not by a manual dedup of the corrupted file.

### 33. Two independently-evolved schemas merged into one CSV row/config can share a hyperparameter name by coincidence, silently colliding
**Rule**: when a row/record needs to describe two related-but-distinct things that each have their own hyperparameter set (e.g. a clustering run's own hyperparameters, and the upstream embedding it was computed on), don't assume their key names are disjoint just because they come from different config registries - a name as generic as `n_components` is exactly the kind of key two unrelated `params_*.json` registries reuse independently (a GMM's own mixture-component count vs. a UMAP embedding's own output dimensionality). Writing both into the same row/columns under their bare names lets one silently overwrite or be conflated with the other. Prefix the newly-added, structurally-different concept (here, "the upstream thing this row's subject was built from") rather than assuming today's key set is exhaustive - cheaper to prefix defensively than to discover the collision only when a specific method combination (here, gmm) happens to share a name.
**Seen in**: `31-08-26` session - `clustering.py`'s new `reduction_n_components`/`reduction_metric` runs.csv columns (the *embedding's* own resolved hyperparameters) were prefixed `reduction_` specifically because `gmm`'s own `tag_param` is literally `n_components` (`params_clustering.json`, its mixture component count) - an unprefixed `n_components` column would have silently collided with gmm's own same-named column in every gmm row. Caught before writing any data, by inventorying every clustering method's own `tag_param` set against the two new column names before picking them; regression test added (`test_clustering_gmm_reduction_n_components_does_not_collide_with_gmm_own_n_components`).
